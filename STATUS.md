# Аудит достаточности источников (миссия appsec-audit)

Вопрос миссии: хватает ли собранных источников, чтобы написать тему по
каноническому скелету — механика, как выглядит в коде, как чинится, как
проверить фикс. Состояние аудита живёт в `audit.yaml`, по одной записи на
тему, с оценкой каждого из четырёх блоков.

## Этап 0 — закрыт. 11 тем из 11

Все одиннадцать тем получили вердикт `closed`. Каждый из семнадцати уже
заведённых источников этапа открыт заново лично и оценён по содержимому
страницы, а не по полю `notes`: примечание писал тот же агент, который
источник и выбирал, и в пяти случаях оно расходилось со страницей.

```
$ python tools/validate.py
Реестр: 254 записи, из них ok: 253
  этап 0:  11/ 11 ... этап 8: 5/5     188 тем из 188
ПРЕДУПРЕЖДЕНИЕ [ГЛУБИНА] тема t-0-0-10: 4 собственных источников
ПРЕДУПРЕЖДЕНИЕ [ГЛУБИНА] тема t-8-0-01: 4 собственных источников

ВАЛИДАТОР: ЗЕЛЁНЫЙ — 0 ошибок, 2 предупреждений
```

Оба предупреждения [ГЛУБИНА] — норма, разрешённая досье: тема 0.10 составная
(SPA, API, рендеринг, reverse proxy, CDN), тема 8.1 перечисляет четыре
фаззера.

## Что нашлось на этапе 0

Три дыры такого рода, что тема писалась бы с выдуманным содержанием.

- **Тема 0.04 «серверные сессии vs stateless-токены» была покрыта наполовину.**
  В OWASP Session Management Cheat Sheet нет ни слова `JWT`, ни `stateless`,
  ни `self-contained` — проверено по тексту страницы и по списку заголовков
  разделов. Примечание в реестре при этом обещало «серверное хранение против
  самодостаточных токенов». Привязан `rfc7519-jwt`.
- **RFC 9846 не описывает проверку цепочки сертификатов.** §4.5.1.3 говорит
  дословно: «detailed certificate validation procedures are out of scope for
  TLS (see [RFC5280])». Треть названия темы 0.09 писать было не по чему.
  Заведён `rfc5280-x509`.
- **Страница MDN про прокси ничего не говорит о подделке `X-Forwarded-*`.**
  Она перечисляет заголовки и на этом останавливается, а недоверие к ним —
  это и есть содержание темы для AppSec. Заведён `rfc7239-forwarded` с его
  Security Considerations. Та же запись стоит вторым источником у темы 1.1.07
  про обход контроля доступа через заголовки — там пробел тот же, снимется
  при аудите этапа 1.

Дальше — пробелы поменьше, все закрыты: тема 0.01 держалась на одном RFC 9110,
который даёт семантику, но не даёт ни ревью, ни фикса, ни проверки; тема 0.02
осталась бы без расхождений парсеров и Unicode; тема 0.10 не описывала CDN
ничем; тема 0.11 не имела стороны защиты для REST.

## Ловушки, добавленные к списку из HANDOFF

- **UTR #36 «Unicode Security Considerations» стабилизирован и не
  поддерживается с 2014 года.** Напрашивающийся источник по нормализации;
  страница открывается нормально и сообщает об этом сама, отсылая к UTS #39.
  Обратная ошибка того же рода — считать живой документ отозванным: так
  прошлая миссия поступила с NIST SP 800-162, см. ниже.
- **`developer.mozilla.org/en-US/observatory/` — JS-приложение.** Таблица
  тестов и баллов не отдаётся ни curl'ом, ни штатным фетчером; в `mdn/content`
  на GitHub этих страниц нет. Источник не заводился, и не понадобился.
- **RFC 5280 не обсолетен, но обновлён девятью RFC** (6818, 8398, 8399, 9549,
  9598, 9608, 9618, 9925, 10007). Список `Updated by` на странице `info/`
  сверять при написании темы.

## Решения, принятые по ходу

1. **Скелет для тем-моделей читается так:** «как чинится» — это канонически
   правильная конфигурация, «как проверить фикс» — как убедиться, что она
   применена. Планка не меняется; этап 0 по части 4 PLAYBOOK и есть модели
   исполнения, которые идут до первого разбора уязвимости.
2. **Тема оценивается в границах своего места в плане.** Эксплуатация
   мисконфигураций CORS — тема 1.1.09, атаки на JWT — 1.7.02, обходы CSP —
   1.4.06. Тянуть их источники в этап 0 значит писать тему дважды.
3. **Блок оставлен `partial`, а не закрыт слабым источником.** Так вышло с
   блоками 5 и 7 темы 0.05 (SOP) и блоком 7 темы 0.10. Третий источник ради
   зелёной строчки в `audit.yaml` не заводится — в `notes` записано, чем блок
   пишется на практике.
4. **Пять примечаний в реестре исправлены по факту страницы.** Расхождение
   примечания со страницей — это и есть то, что ищет аудит, поэтому оно не
   просто отмечено в `audit.yaml`, а исправлено в `sources.yaml`:
   `owasp-cs-session-management`, `owasp-cs-http-headers`,
   `mdn-same-origin-policy`, `rfc9846-tls13`, `mdn-proxy-tunneling`.
5. **UTS #39 заведён с `type: spec`, а не `standard`.** Это спецификация,
   изданная самим Unicode Consortium, — та же форма, что у W3C и WHATWG.
   Инструмент не правился, предупреждение [УРОВЕНЬ] снялось само.

## Что устроено в репозитории

| Файл | Роль |
|---|---|
| `sources.yaml` | реестр источников — **источник истины**, правится руками |
| `topics.yaml` | карта «этап → подраздел → тема → sources»; структура генерируется, руками правятся только списки `sources` |

статусом `ok`, дубль источника в теме там, где он уже наследуется от этапа или
подраздела. Предупреждения: источник-сирота, больше трёх собственных источников
на тему, тема, держащаяся только на источниках уровня этапа, несовпадение

## Провалы: три сняты, два подтверждены

**Снято — источник нашёлся.**

- *Этап 0, «модель современного приложения».* Одной опорной ссылки нет, но
  двух хватает: web.dev «Rendering on the Web» (SSR, статическая генерация,
  гидратация, клиентский рендеринг) и MDN «Proxy servers and tunneling»
  (прямой и обратный прокси, CONNECT, `X-Forwarded-*`).
- *Этап 1, бизнес-логика.* Стандарта нет, но темы 1.9 закрываются: PortSwigger
  по логике и гонкам (TOCTOU, limit overrun, single-packet attack), CWE-682 и
  документация Python по плавающей точке, CWE-190, черновик IETF
  Idempotency-Key — последний помечен как черновик без назначенного статуса RFC.
- *Этап 5, attack trees и abuse cases — прежняя оценка была ошибочной.* По
  abuse cases в серии OWASP есть Abuse Case Cheat Sheet, его просто не нашли.
  По attack trees: эссе Шнайера отвергли как «журнальную публицистику», но
  уровень 5 в самом `SOURCES.md` определён как «оригинальная публикация
  признанного автора, вводящая технику, которой нет больше нигде» — работа
  Шнайера (Dr. Dobb's Journal, декабрь 1999) подходит буквально. Третьим взят
  разбор Carnegie Mellon SEI «Threat Modeling: 12 Available Methods», он же
  закрывает «PASTA обзорно»: сама PASTA описана в платной книге, а разборы на
  сайтах консультантов — маркетинг.

**Подтверждено — источника действительно нет.**

- *Этап 3, матрица «что на pre-commit / что на MR / что на релизе» и таксономия
  блокирующих против информационных гейтов.* Проверены OWASP DevSecOps
  Guideline, GitLab Application security testing и документация GitHub.
  Guideline даёт упорядоченный набор проверок, но без привязки к стадиям;
  ближайшее к таксономии — required status checks в «About protected
  branches», то есть механизм, а не критерий. Матрицу придётся построить
  самостоятельно.
- *Этап 7, FastAPI и Pydantic.* Обе страницы открыты заново. Pydantic даёт
  механику валидаторов, но безопасность не разбирает; Security-раздел FastAPI
  покрывает только OAuth2. Связку «валидация как граница доверия» придётся
  выстроить самостоятельно.

## Что вскрылось при личном открытии

Каждый из этих случаев был бы ошибкой в гайде, если бы источники перенесли по
старым записям.

- ~~**NIST SP 800-162 (Guide to ABAC) отозван 2 августа 2019.**~~ **Этот вывод
  оказался ошибкой и снят аудитом 2026-08-20.** На странице CSRC написано
  «Date Published: January 2014 (includes updates as of 08-02-2019)» — это
  дата обновления, а не отзыва; пометки withdrawn нет ни там, ни в PDF.
  Документ живой и заведён как `nist-sp-800-162-abac`. NISTIR 7316 при этом
  остаётся: он разбирает ACL, DAC, MAC и RBAC, которых у 800-162 нет.
- **Даты Living Standard уехали:** Fetch Standard и URL Standard обновлены
  20 и 18 августа 2026 против 2 и 6 июля в старом реестре.
- **RFC 9846 (TLS 1.3, июль 2026) обсолетит RFC 8446** — ссылка на 8446 была
  бы устаревшей на момент написания.
- **rfc6265bis доехал до draft-22**, intended status Proposed Standard.
- **Двух cheat sheet'ов не существует:** «NoSQL Injection Prevention» и
  «JSON Web Token for Java» дают 404.
- **NIST SP 800-131A** по адресу без номера ревизии — 404; актуален Rev. 2.
- **go-fuzz из плана фактически заменён** встроенным фаззингом Go 1.18.

## Решения, принятые по ходу

1. **Оснастка на Python + PyYAML в `.venv-tools/`.** Обратимо.
2. **`topics.yaml` генерируется из плана, а не пишется руками.** Расхождение с
   планом — блокирующая ошибка. Привязки `sources` переносятся между
   перегенерациями по заголовку темы, поэтому правка плана не сбрасывает
   собранное. План — документ автора, агент его не трогал.
3. **`id` темы — `t-<этап>-<подраздел>-<NN>`,** без транслитерации русских
   заголовков.
4. **Правило «1–3 источника на тему» относится к собственным источникам темы.**
   Наследуемое от этапа и подраздела в лимит не входит: это каркас, который по
   решению автора заводится один раз на своём уровне.
5. **Добавлена проверка `КАРКАС`** — тема, у которой нет ни своего источника,
   ни источника подраздела, помечается предупреждением. Без неё три записи на
   уровне этапа 1 разом «покрыли» бы все 83 темы и валидатор позеленел бы
   вхолостую. Проверка молчит по всем этапам.
6. **CVSS отнесён к теме 2.5.01 «Оценка severity», а не к 2.2.07** — иначе в
   одной теме оказалось бы пять реестров сразу.
7. **Вендорские страницы российских продуктов** (Solar appScreener,
   CodeScoring, AppSec Solutions) взяты с оговоркой в `notes`: годятся, чтобы
   знать назначение, и не годятся как источник утверждений о качестве. План
   требует по ним ровно уровня «знать по назначению».
8. **Экспериментальный API помечен как экспериментальный.**
   `experimental_taintObjectReference` React живёт только в канале Canary — это
   записано в источнике и должно попасть в текст темы.
9. **Архивные снимки не делались** по решению автора; `archived_url` пуст.
