# Лаба jwt-basics: подпись — не шифрование

Кабинет магазина держит сессию на самодостаточном токене: при входе выдаётся
JWT, на каждом запросе из него читаются роль и внутренние поля. Токен подписан
HS256, и подпись проверяется честно — подделать роль нельзя (опыт 3 это
показывает). Дефект в другом: в полезную нагрузку положено то, что не должно
быть видно предъявителю, — адрес почты и внутренний скидочный код. Содержимое
токена читается без ключа.

## Файлы

| файл | что это |
|---|---|
| `code.py` | уязвимый модуль: конфиденциальные поля в нагрузке |
| `solution.py` | образец починки: в нагрузке только несекретные утверждения |
| `hack.py` | эксплойт: читает нагрузку без ключа; возврат 0 — почат, 1 — уязвимо |
| `tests.py` | функциональность кабинета: должна остаться зелёной |
| `labtarget.py` | загрузка проверяемого модуля (`LAB_TARGET=solution.py`) |
| `hint.md` | одна подсказка |

## Как запускать

```text
cd pilot/lab/jwt-basics
../../../.venv-tools/bin/python hack.py      # против code.py: 2 из 2 опытов
../../../.venv-tools/bin/python tests.py     # функциональность: 0 упало
LAB_TARGET=solution.py ../../../.venv-tools/bin/python hack.py    # 0 опытов
LAB_TARGET=solution.py ../../../.venv-tools/bin/python tests.py   # 0 упало
```

## Цель одной фразой

Добиться, чтобы `hack.py` вышел с кодом 0 (в нагрузке нет конфиденциальных
полей), а `tests.py` продолжил выходить с кодом 0 (роль, скидка и почта
доступны через сервер).

## Задача «почини»

Уберите из нагрузки токена `email` и `discount_code`; оставьте `sub`, `role`,
`iat`, `exp`. Скидку и почту доставайте по проверенному `sub` из серверного
профиля. Подпись не трогайте — она и так проверяется.

## Правило SAST

`pilot/semgrep/jwt-confidential-claim.yaml` ловит конфиденциальное имя поля в
нагрузке `jwt.encode`: на `code.py` одна находка, на `solution.py` — ноль.
Сверка: `.venv-tools/bin/python pilot/semgrep/check.py jwt-confidential`.

Всё исполняется локально, к сети не обращается и применимо только к этой лабе.
