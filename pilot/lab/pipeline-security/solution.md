# Решение

Эталоны — `.github/workflows/pr-greeter.yml.example` и
`.gitlab-ci.yml.example`. Шесть правок, из них две про инъекцию и четыре про
всё остальное.

## Инъекция: две системы — две разные правки

**GitHub Actions.** Выражение `${{ … }}` подставляется в **текст скрипта** до
оболочки. Заголовок `Опечатка"; id; echo "` превращается в три команды. Правка:
вынести значение в переменную окружения шага, а в скрипте обращаться к
переменной.

```text
      - name: greet
        env:
          TITLE: ${{ github.event.pull_request.title }}
        run: |
          echo "Спасибо за запрос: $TITLE"
```

Значение теперь едет в окружение процесса, а не в текст программы. Оболочка
подставляет его после разбора синтаксиса, и `$(…)` внутри значения остаётся
знаками.

**GitLab CI.** Предопределённые переменные раннер кладёт в окружение сразу, и
`echo "$CI_MERGE_REQUEST_TITLE"` инъекции не даёт. Дефект в лабе другой:
строку разбирают второй раз через `eval`. Правка — убрать второй разбор:

```text
    - printf 'Здравствуйте, %s\n' "$CI_MERGE_REQUEST_TITLE"
```

**Почему это одна тема, а не две.** Класс дефекта общий: значение из чужого
запроса доходит до разбора оболочкой. Различается только место, где разбор
случается: у одной системы — при подстановке в текст, у другой — при повторном
разборе строки. Отсюда общий признак в ревью: найдите, где чужое значение
встречается с разбором.

## Остальные четыре

**`permissions: write-all` → `contents: read`.** Права нужны шагу выкладки, а не
всему workflow. Ставится минимум на весь файл, повышается точечно на job.

**`pull_request_target` → `pull_request`.** Событие `pull_request_target` идёт с
секретами и правами основной ветки; вместе с checkout по `head.sha` оно
собирает чужой код с этими правами. Приветствию такие права не нужны вовсе.
Если бы понадобились — разносят на два workflow: один собирает чужой код без
секретов, второй берёт готовый артефакт.

**`some-vendor/publish-action@main` → сумма коммита.** Ветка и тег переписываются
владельцем действия в любой момент; сумма коммита — нет.

**Секрет из описания конвейера — в хранилище форжа.** Значение в файле читает
каждый, у кого есть доступ к репозиторию, и оно остаётся в истории после
удаления строки.

## Чего лаба не показывает

Серверную половину: что именно делает форж, получив событие
`pull_request_target`, какие права у токена сборки по умолчанию и что видно в
журнале после маскирования. Живого форжа тут нет; эти вещи разбираются по
документации вендора, и на странице темы так и сказано.

Ещё одно, замеченное при сборке лабы. Первая версия правила CI-1 искала
`${{ github.event.* }}` по всему файлу и срабатывала на **починенном**
описании: в блоке `env:` то же самое выражение стоит законно. Правило пришлось
ограничить телом скрипта. Это тот самый случай, ради которого правило проверяют
на исправленном коде, а не только на дефектном.
