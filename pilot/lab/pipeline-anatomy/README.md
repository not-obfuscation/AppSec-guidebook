# Лаба pipeline-anatomy: зелёный конвейер, который ничего не проверил

Конвейер из трёх стадий, исполняемый локально. Ни сети, ни контейнеров, ни
форжа: `runner.py` запускает каждый job подпроцессом во временном каталоге и
воспроизводит четыре свойства настоящего конвейера — чистый рабочий каталог у
каждого job, артефакт как единственный объявленный канал между job, кэш без
гарантии, вердикт по коду возврата.

## Файлы

| файл | что это |
|---|---|
| `pipeline.yml` | описание конвейера: три стадии, три job |
| `runner.py` | исполнитель конвейера |
| `src/app.py` | приложение, которое собирается в `out/app.txt` |
| `src/test_app.py` | тест собранного артефакта |
| `solution-pipeline.yml` | эталон описания конвейера |
| `check.py` | проверялка задачи: два прогона, исправная сборка и испорченная |
| `hint.md` | одна подсказка |
| `solution.md` | разбор решения |

## Как запускать

```text
cd pilot/lab/pipeline-anatomy
python3 runner.py pipeline.yml    # посмотреть конвейер
python3 check.py                  # проверить свою правку
```

## Задача

Прогон конвейера в исходном состоянии печатает `вердикт конвейера: зелёный` и
одну строку, ради которой лаба и заведена:

```text
test     test       0  — -> —
           тест: артефакта нет — проверять нечего
```

Три job отработали, ни один не покраснел, и при этом собранный артефакт никто
не проверил. Почините конвейер так, чтобы стадия `test` действительно
проверяла то, что собрала стадия `build`.

Критерий наблюдаемый: `check.py` печатает «зачтено». Внутри он делает два
прогона — на исправной сборке ждёт зелёного и слова «артефакт проверен», на
испорченной ждёт красного.

## Сброс

Чтобы вернуть исходный `pipeline.yml`, восстановите его из репозитория
гайдбука.

## Удаление

```bash
rm -rf pilot/lab/pipeline-anatomy
```

Вне этого каталога лаба ничего не создаёт и не меняет: рабочие каталоги
job исполнитель создаёт во временном каталоге системы.
