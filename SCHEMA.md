# Контентная модель: часть 9 `PLAYBOOK.md`, разложенная на проверки

Часть 9 свода говорит, что гайдбук на 250 тем — база данных с текстом, и что
модель фиксируется до первой содержательной страницы. Двенадцать страниц уже
написаны, схема — нет. Этот документ её записывает по факту, и три вещи делает
явно:

1. называет каждое поле frontmatter, его тип, обязательность и то, чем оно
   отличается от соседнего;
2. закрепляет состав блоков по уровням L1/L2/L3 и разбирает одно расхождение
   внутри свода, из-за которого «состав по уровню» иначе читается двумя
   способами (§ 4);
3. присваивает каждой проверке идентификатор семейства `C-*` и цену: что
   правило ловит, чего не ловит и почему уровень у него такой (§ 8).

Если формулировка здесь расходится с частью 9 `PLAYBOOK.md`, права часть 9, а
расхождение — дефект обвязки. Единственное место, где этот документ решает сам,
— § 4, и там сказано почему.

Проверки живут в `tools/validate_content.py`, словари — в `taxonomy.yaml`.
Правила языка и типографики — не здесь, а в `STYLE.md`: границы между
инструментами описаны в `STYLE.md` § 1.3.

## 1. Что где лежит

Модель разложена по файлам так, чтобы у каждого факта был ровно один хозяин.

| Файл | Что держит | Кто правит |
|---|---|---|
| `content/**/*.md` | сами темы: frontmatter + текст | автор |
| `taxonomy.yaml` | словари: этапы, уровни, статусы, режимы, теги, блоки скелета | автор |
| `topics.yaml` | план как данные: этапы, подразделы, темы с номерами | генератор `tools/gen_topics.py` |
| `sources.yaml` | коллекция `reference`: первоисточники с реквизитами | автор |
| `labs.yaml` | коллекция `lab`: лабы и задачи с критерием | автор |
| `glossary.yaml` | коллекция `term` | автор |

Два правила про этот стол:

- **`topics.yaml` не правится руками.** Он выводится из плана
  (`plan.md.md`) и переписывается генератором целиком; правка в нём живёт до
  первого прогона `tools/gen_topics.py`. Источник истины по номерам и составу
  плана — сам план.
- **Значение из словаря не удаляется, пока на него ссылается тема.** Тег,
  этап, статус и режим — контролируемые словари (9.2), и значение вне словаря
  ломает сборку. Обратное тоже верно: убрать значение из словаря, оставив
  ссылку, — тот же слом, только с другой стороны.

## 3. Frontmatter темы

Двадцать шесть полей, из них двадцать два обязательны. Порядок в таблице —
**канонический порядок в файле**: он один и тот же во всех двенадцати темах, и
проверка `C-FM-SEQ` его закрепляет. Причина не в аккуратности: diff двух тем
должен показывать разницу смысла, а не разницу раскладки.

| Поле | Тип | Обяз. | Норма | Правило |
|---|---|---|---|---|
| `id` | строка | да | kebab-case, совпадает с именем файла, уникален, неизменяем | `C-FM-ID` |
| `plan_id` | строка | да | `t-<этап>-<подраздел>-<номер>`, разрешается в `topics.yaml` | `C-FM-PLAN` |
| `title` | строка | да | ≤60 символов, совпадает с h1 | `C-FM-TITLE`, `C-FM-TITLE-LEN` |
| `summary` | строка | да | 1–2 предложения; идёт в поиск и карточки | `C-FM-SUMMARY` |
| `stage` | строка | да | ровно один слаг из `taxonomy.yaml`; каталог файла — каталог этапа | `C-FM-VOCAB`, `C-FM-STAGE-DIR` |
| `order` | целое | да | кратен 10, уникален внутри этапа | `C-FM-ORDER` |
| `status` | строка | да | `stub` \| `draft` \| `published` | `C-FM-VOCAB` |
| `depth` | строка | да | `L1` \| `L2` \| `L3` — главный управляющий рычаг | `C-FM-VOCAB` |
| `mode` | строка | да | один из шести режимов 9.2 | `C-FM-VOCAB` |
| `skeleton` | строка | нет | скелет темы: `уязвимость` \| `инструмент`; поля нет — `default_skeleton` словаря (§ 4.3) | `C-FM-VOCAB` |
| `time_min` | целое | да | > 0, совпадает со временем в шапке | `C-FM-TYPE`, `C-HEAD-TIME` |
| `teaches` | список | да | 2–5 целей, каждая с большой буквы, активным глаголом | `C-FM-TEACHES`, `C-BODY-GOALS` |
| `prerequisites` | список | да | только прямые, ≤4, разрешаются в `id`, без циклов | `C-FM-PREREQ`, `C-REF-TOPIC`, `C-REF-CYCLE` |
| `related` | список | да | ≤5, разрешаются в `id`, без ссылки на себя | `C-FM-RELATED`, `C-REF-TOPIC` |
| `fixes_in` | список | у темы-инструмента | темы, где чинится найденное; разрешаются в `id`; пуст — только при пустом `cwe`; у темы-уязвимости поля быть не должно | `C-FM-SKELETON`, `C-REF-TOPIC`, `C-BODY-FIX` |
| `tags` | список | да | ≥1, все из словаря, без повторов | `C-FM-VOCAB` |
| `cwe` | список | да | `CWE-<число>` | `C-FM-IDENT` |
| `asvs` | список | да | `v<major>.<minor>-<раздел>` | `C-FM-IDENT` |
| `wstg` | список | да | `WSTG-v<версия>-<КОД>-<номер>` | `C-FM-IDENT` |
| `owasp` | список | да | `A<NN>:<год>` — всегда с годом (9.6 п. 25) | `C-FM-IDENT` |
| `labs` | список | да | id из `labs.yaml`, и лаба указывает на эту же тему | `C-REF-LAB` |
| `sources` | список | да | ≥2 id из `sources.yaml` | `C-FM-SOURCES`, `C-REF-SOURCE`, `C-BODY-SOURCES` |
| `derived_from` | список | нет | id из `sources.yaml`; ставится при адаптации лицензированного материала (9.3) | `C-REF-SOURCE` |
| `updated` | дата | нет | любая правка (9.6 п. 19) | `C-FM-TYPE` |
| `reviewed` | дата | да | осознанная проверка актуальности, не в будущем; на странице темы не печатается (свод 4.1) | `C-FM-DATE` |
| `review_interval` | целое | да | 6, 12 или 24 месяца (9.6 п. 20) | `C-FM-VOCAB`, `C-FM-REVIEW` |

### 3.1 Три решения, которые схема принимает

**`plan_id` — поле, которого в 9.3 нет.** Свод даёт `id` и `stage`, но не даёт
способа сказать, какому номеру плана тема соответствует. Без этого номера
нельзя ни проверить, что все темы этапа на месте (11.1 стадия 0), ни разрешить
ссылку в прозе на ненаписанную тему («тема 1.6.04»). Поле добавлено, его форма
жёсткая, и оно сверяется с `topics.yaml` в трёх точках: тема существует, номер
не занят другой темой, этап в номере совпадает с полем `stage`.

**Поля `next` в схеме нет и не будет.** DoD 21 требует, чтобы у темы были
проставлены предпосылки и «дальше» и чтобы тема стояла в навигации. Первое —
поле `prerequisites`. Второе — блок 13 «Дальше»: 9.5 п. 8 говорит о **двух
текстовых блоках** на странице, а не о поле в данных, и ≤5 ссылок в каждом.
Третье выводится: страница попадает в навигацию из `stage` и `order`, вручную
списки тем не ведутся (9.1 п. 7). Отдельное поле `next` продублировало бы блок
13 и немедленно с ним разошлось.

**`asvs` и `wstg` — отдельные поля, а не подмножество `cwe`.** В 9.3 показаны
только `cwe` и `owasp`, но 9.6 п. 25 требует печатать все внешние
идентификаторы с версией, а маппинг в шапке темы в готовых темах перечисляет
четыре системы. Держать ASVS и WSTG внутри одного поля означало бы разбирать
их формы регулярным выражением при каждом чтении; разные поля разбираются
разными выражениями один раз (`C-FM-IDENT`).

### 3.2 Норма объёма: что считается, а что нет

Норму задаёт `depth` — поле шапки, поэтому правило объёма живёт здесь, а не в
разделе о блоках, и адресуется строкой этого поля. Свод 3.1 после решения
оператора от 2026-08-23 требует считать норму **по тексту без служебного
аппарата**; тот же раздел свода перечисляет, что из подсчёта выпадает. Здесь
это перечисление сведено к машинным признакам.

| Что выпадает | Признак в файле |
|---|---|
| `frontmatter` | от `---` в первой строке до закрывающего `---` |
| заголовок и шапка | h1, за ним абзац от «Уровень **L2**» до пустой строки |
| абзац предпосылок | абзац от «Что прочитать сначала:» до пустой строки |
| расшифровка схемы | абзац от `**Описание схемы.**` до пустой строки |
| блок 14 и всё за ним | от `## 14.` до конца файла — там же каркас этапа, скоропортящийся слой, маркеры уверенности |
| листинги | ограждённые блоки от ``` до ``` |
| ответы самопроверки | от `<details>` до `</details>` |
| «**Зачем это в работе AppSec-инженера.**» | абзац от маркера до пустой строки |
| «Откуда это взялось» | абзац, в котором стоит эта строка, — вместе с врезкой-обёрткой |

Последние две строки внесены решением оператора от 2026-08-23 (свод 3.1 п. 8,
находка Н-04 оглавления этапа 1): два абзаца обязательны на всех трёх уровнях,
а в норму не заложены, и на L3 съедали от четверти до двух пятых бюджета.
Признак у них разный не по прихоти. Маркер «Зачем это в работе» всегда
открывает свой абзац, поэтому ловится якорем начала строки. «Откуда это
взялось» законно и абзацем основного потока, и внутри врезки «Глубже»
(`validate_content.py`, оговорка 2026-08-23), поэтому выпадает абзац, в котором
эта строка стоит. Следствие, которое надо знать: фраза, вписанная в середину
длинного абзаца, унесёт из подсчёта весь абзац. Ставить её отдельным абзацем —
не только вопрос вёрстки.

Считается всё остальное. Три метрики печатаются рядом, решает первая: `текст`
(вердиктная), `проза` (тело без листингов, ответов и блока 14) и `тело` (всё
после frontmatter). Справочные оставлены потому, что по `проза` считаны находки
Ф-09 и Ф-42 двух приёмок: без этой колонки старые числа не с чем сверить.

Инструмент — `tools/wordcount.py`; в `make check` он стоит дважды, линтером
`volume` (вердикт) и отчётом `wordcount` (таблица целиком). Норма хранится в
одном месте — словарь `NORM` в этом скрипте; расхождение словаря с таблицей 3.1
свода — дефект обвязки, а не второе мнение о норме.

## 4. Состав блоков по уровням

Скелетов два (свод 4.2), и какой применяется — сведение о теме, а не догадка:
его задаёт поле `skeleton`, поля нет — `default_skeleton` словаря, то есть
`уязвимость`. Словарь — `taxonomy.yaml`, ключ `skeletons:`; у каждого скелета
свой список блоков, и каждый блок несёт `num` (номер на странице), `key`
(машинное имя, по которому блок ищут проверки), `title`, `required` (на каких
уровнях обязателен), `allowed` (где законен, но не обязателен) и `alt`
(альтернативное название и уровни, на которых оно допустимо).

**Номера у двух скелетов разные, `key` — общий.** В скелете уязвимости
пятнадцать блоков с номерами 0–14, в скелете инструмента — четырнадцать с
номерами 0–13, и расходятся они начиная с четвёртого. Поэтому проверки
наполнения (`C-BODY-*`) ищут блок по `key`, а не по номеру: правило, знающее
номер, молча проверяло бы не тот блок другого скелета. Почему нумерация не
выровнена — § 4.3.

### 4.1 Расхождение внутри свода и как оно разрешено

Состав по уровням в своде задан дважды, и два места расходились в **пяти**
точках, а не в трёх, как говорил этот параграф до 2026-08-23. Три точки —
блоки 4, 11 и 3 — схема разрешила сама, и разбор ниже не менялся. Ещё две —
блоки 5 и 12 на уровне L3 — схема разрешила молча, в пользу `taxonomy.yaml`, и
нигде этого не записала; находка Н-01 оглавления этапа 1. Их закрыло решение
оператора, и оно последним пунктом ниже.

Таблица 3.1 перечисляет для L2 блоки 0, 1, 3, 5, 6, 9, 10, 12 — без блока 4 и
без блока 11. Часть 4 помечает блок 4 как `[L1 L2]`, а блок 11 — как `[L1]`.
Дальше — то, что схема решает сама, и почему.

**Блок 4 «Эксплуатация»: обязателен на L1, разрешён на L2.** Таблица 3.1
задаёт минимум уровня, часть 4 — где блок в принципе законен. Прочтение
«таблица задаёт минимум» сохраняет оба текста, а прочтение «часть 4 задаёт
обязательность» делает L2-колонку 3.1 неполной. Все десять L2-тем корпуса
блок 4 удаляют, и это законно.

**Блок 11 на L2 существует под названием «Задача».** Часть 4 помечает блок как
`[L1]`, но колонка L2 в таблице 3.1 требует «задачу с критерием», а другого
места для задачи в скелете нет. Поэтому на L2 блок 11 разрешён и называется
«Задача», на L1 обязателен и называется «Лаба». Ровно так он и написан во всех
десяти L2-темах, и декларация состава в них говорит «блок 11 сведён к задаче
без лабы».

**Блок 3 «Механика» обязателен и на L3.** Часть 4 такого не говорит, но
колонка L3 в таблице 3.1 требует «своё короткое объяснение механизма с одним
примером», и единственный блок скелета, куда это объяснение встаёт, — третий.
`security-headers` (единственная L3-тема) так и сделана: блоки 0, 3, 13, 14, и
декларация состава прямо говорит, что объяснение поставлено на позицию блока 3.

**Блоки 5 и 12 на L3: расхождение закрыто правкой свода.** Таблица 3.1 до
2026-08-23 требовала от L3 блок 5 «Как выглядит в коде» и блок 12 «Проверь
себя», `taxonomy.yaml` их на L3 не разрешал, а `C-BLOCK-EXTRA` — ошибка, не
предупреждение. То есть тема L3, написанная точно по таблице, не собиралась бы;
не всплывало это потому, что на этапе 0 не осталось ни одной темы L3. Здесь
схема не решает ничего сама: решением оператора от 2026-08-23 **свод правится
под обвязку** — блоки 5 и 12 убраны из состава L3 в таблице 3.1 и в тегах части
4. Обоснование по существу стоит в своде рядом с таблицей. Таблица § 4 выше уже
показывала итоговое состояние («—» в колонке L3 у блоков 5 и 12) — теперь оно
не расходится с текстом свода и перестало быть незаписанным решением.

### 4.2 Декларация состава снята

До 2026-08-24 каждая тема после шапки несла абзац «Состав блоков — …»: какой
уровень взят и что из скелета удалено. Абзац сверялся с фактом правилами
`C-DECL` и `C-DECL-SET`. Решением оператора от 2026-08-24 (свод 4.1) абзац со
страницы убран целиком вместе с обоими правилами: это отчёт автора о работе, а
не сведение о предмете темы, и ссылался он на `PLAYBOOK.md` — файл, которого у
читателя нет.

Довод, на котором абзац держался, — «без него удалённый блок не отличить от
забытого» — закрыт машинно и без участия страницы: состав, положенный уровню,
задан таблицей § 4 и `taxonomy.yaml`, а `C-BLOCK-REQ` и `C-BLOCK-EXTRA` роняют
сборку и на пропущенном обязательном блоке, и на лишнем. Декларация проверяла
не состав, а собственную правдивость — то есть сама себя.

### 4.3 Второй скелет: что схема решает и почему

Решение оператора от 2026-08-24 (свод 4.2) вводит второй скелет и называет
четыре его блока. Всё остальное — состав по уровням, нумерация, форма связи
вместо блока «Как чинится» — схема решает сама, и вот эти решения.

**Поле, а не вывод из этапа или режима.** Скелет мог бы выводиться:
«этап 2 — значит инструмент». Так нельзя. На этапе 2 есть темы про класс
дефекта (`supply-chain-threats` — модель угроз, а не инструмент), а тема про
инструмент появится на этапах 3 и 4. Режим тоже не годится: `рецепт` бывает и
у темы-уязвимости. Скелет — сведение о предмете темы, и объявляет его тема.

**Поле условное, а не обязательное.** Обязательным его не сделать, не
переписав шапки 94 готовых тем, а правка, задевающая уже написанное, сделана
неправильно. Умолчание стоит в словаре (`default_skeleton`), а не в коде: там
его видно, и там его меняют, если когда-нибудь скелетов станет три.

**Нумерация сплошная, а не выровненная.** Можно было оставить блоку
«Источники» номер 14 в обоих скелетах и держать в скелете инструмента дыру на
месте восьмого блока. Отвергнуто: номер стоит на странице, и пропущенный номер
читатель прочтёт как пропущенный блок — то есть как отчёт о производстве,
который со страницы убран решением 4.2 свода. Цена решения — номера двух
скелетов расходятся, и правило, знающее номер, стало бы проверять не тот блок.
Поэтому у каждого блока есть `key`, и правила ищут по нему. Три места, где
номер блока был вписан в код (`wordcount.py` — блок 14, `lint_style.py` — блок
13, `linkcheck.py` — оба), переведены на заголовок блока: результат на 94
темах тот же до байта, а на скелете инструмента — верный.

**Связь `fixes_in`, а не пункт в `related`.** Смежная тема и тема, где чинится
найденное, — разные отношения: `related` говорит «об этом же», `fixes_in` —
«отсюда идут с находкой». Сложить их в одно поле значило бы потерять различие
ровно там, где оно нужно. Поле держит три правила:

| Условие | Правило | Почему |
|---|---|---|
| у темы-инструмента поле есть | `C-FM-SKELETON` | иначе связь просто забывают, и блок «Как чинится» пропадает без замены |
| поле пусто только при пустом `cwe` | `C-FM-SKELETON` | тема назвала класс дефекта и умолчала, куда с ним идти, — это и есть пропажа блока |
| у темы-уязвимости поля нет | `C-FM-SKELETON` | про починку там пишет блок, и вторая запись о том же разойдётся с ним при первой правке |
| каждый `id` назван в тексте | `C-BODY-FIX` | frontmatter читателю не виден; связь, которой нет на странице, для него не существует |

**Механика рецепта проверяется адресом, а не объёмом.** Свод (9.2) требует от
рецепта писать механику в объёме, нужном, чтобы понять вывод. Померить объём
блока схема могла бы — и не меряет: граница была бы выдумана, а «столько-то
слов на механику» ловило бы длину, а не подмену жанра. `C-BODY-MECH` проверяет
другое: назван ли адрес, по которому лежит разбор. Правило спрашивается только
с темы-инструмента в режиме `рецепт` — с концепта объяснение механизма
спрашивать нечего, это его работа.

**Словарь скелетов сверяется с проверками, которые его читают.** Проверки
наполнения ищут блок по `key`, и скелет, где такого ключа нет, правило не
роняет, а **выключает**: `C-BODY-SOURCES` промолчит на теме без единой сноски.
Линтер, который молчит, снаружи неотличим от сломанного, поэтому
`C-TAX-SKELETON` требует от каждого скелета полного набора ключей
(`goals`, `mechanics`, `checklist`, `selfcheck`, `next`, `sources`),
неповторяющихся ключей, сплошной нумерации от нуля и умолчания, указывающего
на существующий скелет. Это цена второго скелета: пока состав был один, такой
сверки не требовалось.

**Чего схема не проверяет.** «Два разных объекта проверки» и «разбор вывода с
ложным срабатыванием и пропуском» из определения L1 (свод 3.1) остаются
глазами — они в § 9 вместе с остальным, что требует чтения текста, а не его
формы.

## 5. Шапка темы

Шапка — та часть frontmatter, которая нужна читателю до первого абзаца: уровень
и время. Дублирование данных остаётся, и вся группа `C-HEAD-*` существует
против расхождения после правки одного из двух экземпляров.

Форма задана частью 4 свода и выглядит так (перенос строк свободный):

```text
Уровень **L2** · время 30 мин (теория 15 / задача 10 / самопроверка 5, оценка)

Что прочитать сначала: `id`, `id`.
```

Абзаца предпосылок нет вовсе, когда `prerequisites` пуст: строка «пререквизитов
нет» была служебной отметкой, читателю она ничего не сообщала.

| Что сверяется | С чем | Правило |
|---|---|---|
| уровень | поле `depth` | `C-HEAD-DEPTH` |
| общее время | поле `time_min` | `C-HEAD-TIME` |
| слагаемые времени | их сумма равна общему времени | `C-HEAD-TIME` |
| предпосылки | поле `prerequisites`, тот же состав и порядок; при пустом поле абзаца нет | `C-HEAD-PREREQ` |
| следы процесса | их нет во всей вводной части — от h1 до первого `## ` | `C-HEAD-CLEAN` |

**Разбивка времени обязательна, кроме L3.** На L1 и L2 время делится на теорию,
лабу или задачу и самопроверку — из этой разбивки читатель понимает, во что
вкладывается. У L3 («узнать») нет ни задачи, ни самопроверки, делить нечего, и
единственная L3-тема корпуса разбивки не несёт.

**`C-HEAD-CLEAN` — правило против возврата.** Оно ищет во вводной части темы
шесть признаков: код темы `**AG-…**`, `reviewed:`, «проверено на:», «маппинг:»,
слово «пререквизиты» и «Состав блоков». Всё это решением оператора от
2026-08-24 со страницы убрано (свод 4.1), а данные остались во frontmatter,
`topics.yaml` и `audit.yaml`. Правило смотрит не первый абзац, а всё до первого
`## `: след, вернувшийся в соседний абзац, — тот же след.

**Снятые правила.** `C-HEAD-CODE`, `C-HEAD-REVIEWED`, `C-HEAD-VERSIONS` и
`C-HEAD-MAP` сверяли шапку с полями, которых на странице больше нет, и сняты
той же правкой. Сверка идентификаторов с каталогами при этом не ослабла: её
делают `C-FM-*` по frontmatter и маппинг-индекс сборки, а `C-BODY-IDENT`
по-прежнему ловит номер, напечатанный в тексте и не объявленный в полях.

## 6. Наполнение блоков

Проверяется не качество текста, а те признаки состава, которые часть 4 задаёт
числом или залогом. Всё, что задано смыслом, остаётся глазами (§ 9).

| Что | Норма | Правило | Уровень |
|---|---|---|---|
| «Зачем это в работе AppSec-инженера» | ровно один абзац на тему | `C-BODY-WHY` | error |
| «Маркеры уверенности» | ровно один абзац на тему | `C-BODY-TRUST` | error |
| «Откуда это взялось» | не меньше одного места на тему | `C-BODY-ORIGIN` | error |
| блок 1 «Цели» | столько пунктов, сколько в `teaches` | `C-BODY-GOALS` | error |
| блок 10 «Чеклист ревью» | 5–8 пунктов, каждый в залоге «Verify that…» | `C-BODY-CHECKLIST` | error |
| блок 10 на уровне L2 | 5–7 пунктов | `C-BODY-CHECKLIST` | warning |
| блок 12 «Проверь себя» | 4–6 вопросов на воспроизведение | `C-BODY-SELFCHECK` | error |
| блок 12: возврат к прошлым темам | 1–2 вопроса, если у темы есть предпосылки | `C-BODY-SELFCHECK` | error |
| блок 12: ответы | под `<details>`, число ответов равно числу вопросов | `C-BODY-SELFCHECK` | error |
| блок 13 «Дальше» | 1–5 пунктов, каждый называет `id` темы или номер плана | `C-BODY-NEXT` | error |
| блок 14 «Источники» | ≥2 сносок; названные в сносках id совпадают с `sources` | `C-BODY-SOURCES` | error |
| внешний идентификатор в тексте | объявлен во frontmatter | `C-BODY-IDENT` | error |
| идентификатор во frontmatter | напечатан где-нибудь на странице | `C-BODY-IDENT` | warning |

Пять решений внутри этой таблицы стоят объяснения.

**Формулировка цели не сверяется дословно.** `teaches` — короткая форма для
карточек и поиска, блок 1 — фраза для читателя, и в двадцати одном случае из
пятидесяти пяти они законно расходятся пересказом. Свод (11.1, стадия 2) требует
от автоматики только «наличия блока целей». Поэтому правило сверяет число
пунктов, а формулировки — лишь на грубое несовпадение: если строки расходятся
больше чем наполовину, это уже не пересказ, а цель из другой темы. Порог
выставлен по корпусу с запасом: минимальное совпадение на живых темах — 0.73,
правило срабатывает ниже 0.55.

**Идентификаторы сверяются в обе стороны, но разными уровнями.** Frontmatter —
указатель: по нему тему находят, спрашивая «где про 7.4.2». Требование, названное
в тексте и не попавшее в указатель, из поиска выпадает, и это ошибка. Обратный
случай — объявлено, но нигде не напечатано — предупреждение: связь темы с
требованием бывает законно неявной, и решать, разбор это или лишняя запись,
должен человек. Обе стороны считаются по странице целиком, вместе с шапкой и
листингами: «напечатано» здесь значит «читатель это видит». Правило добавлено
2026-08-23 по находке Ф-31 и нашло расхождения в трёх темах корпуса из
двенадцати: два требования ASVS разобраны в тексте `sessions-vs-tokens` и не
объявлены, тест WSTG назван в ответе `cookies` при пустом поле `wstg`, два
требования объявлены в `password-storage` и в теме не разбираются.

**«Возврат к теме» не требуется у темы без предпосылок.** Часть 4 просит 1–2
вопроса на возврат к темам N−2 и N−5. У первой темы этапа возвращаться некуда,
и `http-basics` — единственная тема корпуса с пустыми `prerequisites` — таких
вопросов не несёт. Правило смотрит на `prerequisites`, а не на порядок.

**Чеклист: 5–8 ошибкой, 5–7 предупреждением.** Часть 4 говорит 5–8, DoD 8 для
L2 говорит 5–7. Расхождение внутри свода, и решать его схема не вправе: за
границы 5–8 — ошибка, восьмой пункт на L2 — предупреждение с указанием на DoD 8.
Три темы корпуса (`cookies`, `http-basics`, `rest-and-graphql`) это
предупреждение получают, и снимать его правкой текста не задача обвязки.

**Идентификаторы источников берутся только из сносок.** Абзац после сносок
законно называет источники, унаследованные всем этапом («Каркас этапа:
`owasp-asvs-5-document`»), и в `sources` каждой темы они не дублируются. Правило
читает нумерованные сноски и игнорирует прозу вокруг них: иначе оно давало бы
двенадцать ложных срабатываний из двенадцати возможных.

## 6.1. Словари против плана обучения

`code_categories` в `taxonomy.yaml` — единственное место, где категории
подразделов записаны машиночитаемо. Со страницы код темы `AG-<CAT>-<NN>` убран
решением оператора от 2026-08-24 (свод 4.1), и с этого момента ни одна тема на
словарь не ссылалась: `validate_content.py` его загружал и не использовал. Две
миссии подряд дописывали туда значения, которых никто не читал, и обе завели об
этом находку (Н-S2 миссии SSRF, Н-I3 миссии Injection).

Проверять словарь через тему больше нечем, поэтому `C-TAX-CATEGORY` сверяет его
прямо с планом. Три условия:

| Условие | Почему |
|---|---|
| у категории есть `sub` и `means` | без номера подраздела запись не с чем сверять |
| `sub` — подраздел из `topics.yaml` | категория на выдуманный подраздел ничего не описывает |
| на подраздел не больше одной категории | соответствие подраздел — категория одно к одному |
| у написанного подраздела категория есть | иначе подраздел выпадает из машиночитаемой карты молча |

Подразделы, по которым тем ещё нет, в словаре не перечисляются. Категория,
придуманная заранее, — догадка о ненаписанном тексте, и проверить её нечем;
заводится она вместе с первой темой своего подраздела, как и тег (9.2).

## 7. Связи между записями

Ссылка между записями — только по `id` (9.1 п. 2), и неизвестный `id` в любой
ссылке ломает сборку (9.4). Отсюда группа `C-REF-*`.

| Ссылка | Куда разрешается | Правило |
|---|---|---|
| `prerequisites`, `related` | `id` темы в `content/**` | `C-REF-TOPIC` |
| `fixes_in` | `id` темы в `content/**`; ребро входящее, как `related` | `C-REF-TOPIC` |
| граф `prerequisites` | без циклов | `C-REF-CYCLE` |
| `sources`, `derived_from` | `id` в `sources.yaml` | `C-REF-SOURCE` |
| `labs` | `id` в `labs.yaml`, и `topic` лабы указывает на эту тему | `C-REF-LAB` |
| «тема X.Y.ZZ» в прозе | `t-X-Y-ZZ` в `topics.yaml` | `C-REF-PLAN` |
| «подраздел X.Y» в прозе | подраздел в `topics.yaml` | `C-REF-PLAN` |
| входящие ссылки на тему | хотя бы одна из другой темы | `C-REF-ORPHAN` (warning) |

**Почему ссылки в прозе на номер плана вообще законны.** Правило «только по
`id`» работает, когда цель написана. Пока темы 1.4.х не существует, ссылаться на
неё по `id` нельзя: `id` появится вместе с файлом. Корпус в таких местах пишет
номер плана — «CSRF разбирается в подразделе 1.5» — и `C-REF-PLAN` проверяет,
что номер настоящий. Это не обход правила 9.1 п. 2, а его дополнение для
ненаписанного: как только тема появится, ссылка станет ссылкой по `id`, а не
мёртвым номером.

**Сирота — предупреждение, а не ошибка.** 9.4 относит «тему без входящих ссылок»
к предупреждающим, и корпус показывает, почему: `password-storage` — первая и
единственная тема этапа 1, ссылаться на неё пока некому. Ошибкой это станет,
когда рядом появятся соседи.

Входящие ссылки собираются из трёх мест: `prerequisites` и `related` других тем
и `id` в обратных кавычках внутри блока 13. Блок 13 учитывается потому, что
навигация вперёд — тоже ребро графа, и тема, на которую ведёт только он, сиротой
не является.

## 9. Что осталось глазами

Часть 9 и часть 4 требуют больше, чем поддаётся проверке. Список ниже закрыт:
пункт, которого в нём нет, либо проверяется машиной, либо не требуется сводом.

| Требование | Пункт | Почему не машине |
|---|---|---|
| Режим не смешан: одна страница — один режим | 9.2, DoD 5 | «Почему» на странице-рецепте отличается от «почему» на концепте смыслом абзаца, а не признаком формы |
| Цели активными глаголами и по уровню | 9.3, 11.1 стадия 2 | список активных глаголов открыт; проверять его словарём — либо шум, либо решето |
| Каждая цель достигается текстом | DoD 4 | требует понимания текста |
| Страница самодостаточна для пришедшего из поиска | 9.5 п. 13 | самодостаточность не признак, а суждение |
| Задача блока «Лаба» стоит в реалистичном контексте, критерий проверяем | DoD, 5.6 | проверяемость критерия видна только человеку; наличие блока — `C-BLOCK-REQ` |
| Два разных объекта проверки у темы-инструмента L1 | 3.1 | «два проекта» и «два формата отчёта» — суждение о содержании прогона, а не признак формы |
| Разбор вывода несёт ложное срабатывание и пропуск | 3.1 | требует понимания того, что напечатал инструмент |
| Механика рецепта не переросла в объяснение предмета | 9.2 | машина проверяет наличие адреса (`C-BODY-MECH`), а не то, что по этому адресу вынесено |
| Долгоживущее ядро отделено от скоропортящегося слоя | 9.6 п. 21 | абзац «Скоропортящийся слой» есть в десяти темах из двенадцати, и в двух его законно нет: делить нечего. Правило на его наличие давало бы два ложных срабатывания из двенадцати |
| Каждое утверждение сведено к лично открытому источнику | DoD 10 | смысловая сверка с текстом источника |
| Числа, версии, флаги проверены вручную | DoD 13 | то же |
| Соседние темы не повторяют вводные абзацы | DoD 20 | измеримо (общие четырёхграммы прозы), но порог на двенадцати темах не выставить: у корпуса их ноль, и первое же срабатывание будет первым наблюдением |

Три требования части 6.6 — аналогия с «где ломается», помеченное упрощение,
раскрытие у аналогии — проверяются как наличие блока в скелете и разобраны в
`STYLE.md` § 8. Ссылки — не здесь: внутренние и внешние проверяет
`tools/linkcheck.py`, правила `S-LINK-*` и `S-EXT-IN-BODY` описаны в
`STYLE.md` § 6.
