## 0. Коротко

Same-Origin Policy закрывает чтение чужого ответа. CORS — набор полей
заголовка, которыми сервер объявляет, что конкретному origin читать всё-таки
можно. Решение принимает браузер, и принимает он его по ответу сервера, а не
по запросу. Мисконфигурация выглядит не как открытая дверь, а как одно
подставленное значение: сервер возвращает в разрешении тот самый origin,
который пришёл в запросе, и разрешение перестаёт что-либо ограничивать.

**Зачем это в работе AppSec-инженера.** Настройка CORS правится в каждом
втором сервисе с отдельным фронтендом, а её ошибки приходят в работу под
видом «у нас не работает фронт» — и чинятся расширением разрешений до тех
пор, пока не заработает.

## 1. Цели

После этого раздела вы сможете:

1. Отличить простой кросс-доменный запрос от требующего предварительного.
2. Прочитать пару транскриптов preflight и назвать, что именно разрешил
   сервер.
3. Найти в конфигурации отражение заголовка `Origin` без списка разрешённых.
4. Назвать сочетания значений, которые браузер отвергает как незаконные.
5. Объяснить, почему CORS не ограничивает исполнение запроса на сервере.

## 3. Механика

### Что считается запросом CORS

Fetch Standard определяет **CORS request** как запрос HTTP, содержащий поле
`Origin`, и сразу оговаривает: надёжно опознать участие в протоколе по этому
признаку нельзя, потому что `Origin` добавляется ко всем запросам, метод
которых не `GET` и не `HEAD`.

**CORS-preflight request** — отдельный запрос, проверяющий, понимает ли
ресурс протокол. Он использует метод `OPTIONS` и несёт поле
`Access-Control-Request-Method`; при необходимости добавляется
`Access-Control-Request-Headers`.

Предварительный запрос отправляется тогда, когда обычной формой HTML такой
запрос не выразить. Границу задаёт понятие **CORS-safelisted request-header**:
значение поля не длиннее 128 байт, а само поле — одно из `accept`,
`accept-language`, `content-language`, `content-type` или `range`. У
`content-type` дополнительное условие: тип должен быть
`application/x-www-form-urlencoded`, `multipart/form-data` или `text/plain`.

### Что отвечает сервер

| Поле ответа | Что объявляет |
|---|---|
| `Access-Control-Allow-Origin` | можно ли поделиться ответом: буквальное значение `Origin` (в том числе `null`) либо `*` |
| `Access-Control-Allow-Credentials` | можно ли поделиться при режиме учётных данных `include` |
| `Access-Control-Allow-Methods` | какие методы поддержаны для целей протокола |
| `Access-Control-Allow-Headers` | какие поля запроса поддержаны |
| `Access-Control-Max-Age` | на сколько секунд кешируются два предыдущих ответа; по умолчанию 5 |
| `Access-Control-Expose-Headers` | какие поля ответа открыть скрипту |

Успешный ответ на обычный запрос CORS может иметь любой статус. Успешный
ответ на предварительный запрос ограничен статусом класса «ok» — например
`200` или `204`. Поле `Allow`, которое обязательно в ответе `405`, к
протоколу CORS отношения не имеет, и спецификация говорит это прямо.

### Сочетания, которые браузер отвергает

Предварительный запрос **никогда** не несёт учётных данных: его режим всегда
`same-origin`. Поэтому поддержку учётных данных сервер объявляет заранее, в
ответе на предварительный запрос. Fetch Standard приводит таблицу законных и
незаконных сочетаний; для ревью существенны три строки:

- режим `include` и `Access-Control-Allow-Origin: *` — не разделяется;
- значение `Access-Control-Allow-Credentials` сравнивается побайтово, поэтому
  `True` с прописной буквы не работает;
- у сериализованного origin нет завершающей косой черты, и
  `https://rabbit.invalid/` не совпадёт с `https://rabbit.invalid`.

При режиме `include` символ `*` недопустим и в `Access-Control-Expose-Headers`,
`Access-Control-Allow-Methods`, `Access-Control-Allow-Headers`.

> **Примечание.** MDN добавляет к этому правило кеширования: если сервер
> возвращает не `*`, а конкретный origin, вычисленный по запросу, ответ обязан
> нести `Vary: Origin`. Без него общий кеш отдаст чужому origin разрешение,
> выданное вашему.

## 5. Как выглядит в коде

Настройка CORS почти всегда лежит в одном месте — промежуточном слое
приложения или конфигурации обратного прокси. Ревьюер читает четыре строки.

```text
# Псевдокод, не исполняется. УЯЗВИМО — демонстрация, не для продакшена.
on_response(req, resp):
    resp["Access-Control-Allow-Origin"] = req["Origin"]      # (1)
    resp["Access-Control-Allow-Credentials"] = "true"        # (2)
    resp["Access-Control-Allow-Headers"] = "*"               # (3)
    # Vary не выставляется                                   # (4)
```

1. Значение из запроса возвращается в разрешение без сверки со списком.
   Разрешение получает любой origin, включая `null`, который приходит от
   документа в песочнице `iframe` и от страницы со схемой `data:`.
2. Вместе с первой строкой это открывает чтение ответа, полученного по cookie
   пользователя. По отдельности каждая строка выглядит безобидно.
3. Подстановка `*` при режиме `include` незаконна, поэтому браузер отвергнет
   ответ — и разработчик заменит `*` списком, оставив первые две строки.
4. Ответ различается по значению `Origin`, но кеш об этом не предупреждён.

**Что искать глазами.** Признак — не имя заголовка, а источник его значения.
Строка вида `Allow-Origin = <что-то из запроса>` есть отражение; строка
`Allow-Origin = "https://app.example.com"` отражением не служит. Между ними
попадается третий вариант — сверка по вхождению подстроки, и он опаснее
первых двух, потому что выглядит как проверка.

> **Примечание.** `Access-Control-Allow-Origin: *` сам по себе находкой не
> считается. У ответа без учётных данных и без чувствительного содержимого
> это штатная настройка публичного API. ASVS v5.0-3.4.2 требует в этом случае
> убедиться, что ответ не несёт чувствительных сведений.

## 6. Как чинится

```text
# Псевдокод, не исполняется. Исправленный вариант.
ALLOWED = {"https://app.example.com", "https://admin.example.com"}

on_response(req, resp):
    origin = req["Origin"]
    if origin in ALLOWED:                                    # (1)
        resp["Access-Control-Allow-Origin"] = origin
        resp["Access-Control-Allow-Credentials"] = "true"
    resp["Vary"] = "Origin"                                  # (2)
```

Закройте разбор и назовите, почему `Vary` выставляется за пределами условия.

<details>
<summary>Разбор выносок</summary>

1. Сравнение идёт с множеством целиком, а не по вхождению подстроки. Значение
   `null` в множество не входит, поэтому документы в песочнице разрешения не
   получают.
2. Ответ зависит от `Origin` в обоих случаях — и когда разрешение выдано, и
   когда нет. Выставленный только внутри условия `Vary` оставляет кеш без
   предупреждения ровно в той ветке, где ответ ничего не разрешает, и
   отравленный кеш отдаст его тому, кому разрешение полагалось.

</details>

**Что остаётся незакрытым.** Список разрешённых origin не ограничивает то, что
сервер уже сделал с запросом: изменение состояния произойдёт независимо от
того, прочитает ли скрипт ответ. ASVS v5.0-3.5.2 требует отдельно
удостовериться, что чувствительную функциональность нельзя вызвать запросом,
который предварительного не порождает.

**Во что обходится.** Каждый новый поддомен фронтенда требует правки списка, а
ошибка в нём проявляется у пользователя как молчаливый отказ: тело ответа
скрипту недоступно, и подробностей JavaScript не получит — MDN отмечает, что
по соображениям безопасности причина видна только в консоли браузера.

## 9. Ловушка

Формулировка, которая звучит на каждом втором ревью: CORS закрывает API от
обращений с чужих сайтов.

**Она неточна.** CORS управляет тем, кто прочитает ответ, а не тем, кто
отправит запрос.

Разбор. Браузер отправляет простой запрос сразу и предъявляет ответ скрипту
только после проверки заголовков. Сервер к этому моменту запрос уже исполнил.
Предварительный запрос действительно уходит раньше основного — но только для
тех запросов, которые не выражаются формой HTML.

Контрпример. Запрос `POST` с телом и заголовком
`Content-Type: text/plain` предварительного не порождает: этот тип входит в
список безопасных. Сервер, разбирающий тело как JSON независимо от
объявленного типа, исполнит его целиком. Fetch Standard приводит родственный
случай прямо в тексте: два поля `Content-Type` в одном запросе — `application/
json` и `text/plain` — прошли бы проверку, если бы браузер разбирал тип
снисходительным алгоритмом, и наивный разбор на сервере принял бы тело за
JSON.

## 10. Чеклист ревью

1. Verify that значение `Access-Control-Allow-Origin` либо задано
   приложением неизменным, либо сверяется со списком доверенных origin
   (ASVS v5.0-3.4.2).
2. Verify that сверка origin выполняется по полному значению, а не по
   вхождению подстроки, и что значение `null` в список не входит.
3. Verify that ответ с `Access-Control-Allow-Origin: *` не несёт
   чувствительных сведений.
4. Verify that ответ, зависящий от поля `Origin`, содержит `Vary: Origin`.
5. Verify that чувствительная функциональность недостижима запросом, который
   не порождает предварительного (ASVS v5.0-3.5.2).
6. Verify that `Access-Control-Max-Age` не превышает срока, на который вы
   готовы оставить разрешение действующим без повторной проверки.

## 11. Задача

Возьмите любой эндпоинт своего стенда и добейтесь от браузера предварительного
запроса, а затем такого же обращения без него.

Подсказка ровно одна: границу задаёт список безопасных полей запроса, и
проще всего её перейти собственным полем заголовка.

**Критерий выполнения.** Сохранены четыре транскрипта: предварительный запрос
и ответ на него, затем основной запрос и ответ. В каждом ответе подчёркнуты
поля семейства `Access-Control-*`. Отдельной строкой записано, какое из полей
запроса вызвало предварительный запрос и что произошло, когда вы его убрали.

## 12. Проверь себя

1. Какой метод и какое обязательное поле несёт предварительный запрос?
2. Почему поддержку учётных данных сервер обязан объявить уже в ответе на
   предварительный запрос?
3. Три сочетания, при которых браузер откажется поделиться ответом, — назовите
   их.
4. Чему равно значение `Access-Control-Max-Age` по умолчанию?
5. Возврат к теме `same-origin-policy`: какую из трёх категорий межоригинного
   доступа изменяет CORS и какие две оставляет как были?
6. Возврат к теме `http-basics`: чем поле `Allow` в ответе `405` отличается по
   назначению от `Access-Control-Allow-Methods`?

<details>
<summary>Ответы</summary>

1. Метод `OPTIONS` и поле `Access-Control-Request-Method`. Поле
   `Access-Control-Request-Headers` добавляется при необходимости.
2. Потому что сам предварительный запрос учётных данных никогда не несёт: его
   режим всегда `same-origin`. Проверить поддержку на нём невозможно, её
   объявляют заранее.
3. Режим `include` вместе с `Access-Control-Allow-Origin: *`; значение
   `Access-Control-Allow-Credentials`, записанное иначе, чем `true` побайтово;
   несовпадение сериализации origin, например из-за завершающей косой черты.
4. Пять секунд.
5. CORS меняет чтение: сервер разрешает конкретному origin прочитать ответ.
   Запись и встраивание остаются как были — политика их и так, как правило,
   разрешает.
6. `Allow` перечисляет методы, поддержанные ресурсом, и обязателен в ответе
   `405`. `Access-Control-Allow-Methods` перечисляет методы для целей
   протокола CORS; Fetch Standard прямо отмечает, что `Allow` к этому
   протоколу не относится.

</details>
