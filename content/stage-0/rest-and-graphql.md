# Устройство REST и GraphQL API: где точки входа

## 0. Коротко

Ревью API начинается с перечня точек входа, и у двух распространённых стилей
этот перечень собирается по-разному. В REST точка входа — пара «метод и путь»,
и её видно в маршрутах и в описании OpenAPI. В GraphQL адрес один, обычно
`/graphql`, а точками входа служат поля схемы: их сотни, и каждое исполняется
своей функцией-резолвером. Отсюда и разная работа ревьюера: в первом случае вы
перечисляете маршруты, во втором — обходите схему.

**Зачем это в работе AppSec-инженера.** Пропущенная точка входа не находится
никогда: ни сканером, который её не увидел, ни ревью, которое до неё не
дошло. Перечень точек входа — первый артефакт любого ревью API и единственный
способ отличить «проверено» от «посмотрели, что дали».

## 1. Цели

После этого раздела вы сможете:

5. Перечислить меры контроля спроса, которые нужны GraphQL и не нужны REST.

## 3. Механика

### REST: перечень виден в описании

OpenAPI Specification v3.2.0 описывает устройство API машиночитаемо: пути,
операции на каждом пути, параметры, тела запросов и схемы безопасности. Для
ревьюера это готовый перечень точек входа — при условии, что описание
соответствует коду.

Параметр операции берётся из одного из **пяти** мест, которые задаёт поле
`in`: `path` (часть адреса операции, например `itemId` в `/items/{itemId}`),
`query` (добавляется к адресу), `querystring` (вся строка запроса целиком как
одно значение), `header` (собственные поля заголовка) и `cookie`.

> **Примечание.** Место `querystring` появилось в версии 3.2.0 и не может
> встречаться в одной операции вместе с `query`. Описания, написанные под
> версию 3.1, этого места не знают — при сверке описания с кодом это первое,
> что расходится.

### GraphQL: перечень виден в схеме

Курс GraphQL формулирует различие прямо: HTTP принято связывать с REST, где
основное понятие — ресурс, а понятийная модель GraphQL — граф сущностей,
поэтому сущности не адресуются URL. Сервер работает на **одном** адресе,
обычно `/graphql`, и все запросы направляются туда.

Сервер обязан обрабатывать `POST` для запросов и мутаций и может принимать
`GET` — только для операций чтения. Тело запроса `POST` несёт объект JSON с
обязательным полем `query` и необязательными `operationName`, `variables`,
`extensions`; ответ возвращается объектом с полями `data`, `errors` и
`extensions`.

Отдельно курс называет место GraphQL в конвейере: он ставится **после** всего
промежуточного слоя аутентификации, а после аутентификации сервер не должен
принимать решений об авторизации до начала исполнения — авторизация на уровне
поля выполняется бизнес-логикой, вызываемой из резолверов, чтобы получился
частичный ответ с ошибками там, где доступа нет.

Схему можно спросить о ней самой: поле `__schema` доступно на корневом типе
операции чтения всегда, а мета-поле `__typename` спецификация обязывает
предоставлять клиентам для любого поля объектного, интерфейсного или
объединяющего типа.

### Контроль спроса

У REST стоимость запроса задана эндпоинтом. В GraphQL её задаёт клиент, и
курс перечисляет меры, которых у REST нет: доверенные документы как список
разрешённых операций, пагинация списочных полей, ограничение глубины
вложенности, ограничение ширины и числа операций в пакете, ограничение
частоты в слое бизнес-логики и анализ сложности запроса по весам типов и
полей.

## 5. Как выглядит в коде

Один класс дефекта — точка входа без своей проверки — выглядит в двух стилях
по-разному.

**REST: маршрут без ограничений приёма.**

```text
# Псевдокод, не исполняется. УЯЗВИМО — демонстрация, не для продакшена.
route "/api/v1/checkout/confirm":            # (1)
    order = parse_body(request.body)         # (2)
    finalize(order)                          # (3)
```

1. Метод не ограничен, тип содержимого не проверен, размер тела не ограничен.
2. Тело разбирается независимо от объявленного типа.
3. Шаг оформления исполняется без проверки того, что предыдущие шаги пройдены.
   Cheat Sheet называет это исполнением вне очереди: атакующий обращается к
   `POST /checkout/confirm`, не выполнив `POST /checkout/pay`.

**GraphQL: проверка на верхнем поле вместо поля с данными.**

```graphql
# УЯЗВИМО — демонстрация, не для продакшена. Фрагмент схемы.
type Query {
  me: User                    # (4) проверка стоит здесь
}
type User {
  email: String
  invoices: [Invoice!]!       # (5) а данные отдаются здесь
}
```

4. Резолвер `me` проверяет, что запрос аутентифицирован, и возвращает объект.
5. Поле `invoices` — самостоятельная точка входа со своим резолвером. Оно
   отдаёт список без ограничения размера и без собственной проверки: список
   выдаётся всякому, кто дошёл до объекта.

**Что искать глазами.** В REST признак — объявление маршрута: есть ли список
методов, есть ли `@consumes`-подобное ограничение типа, есть ли предел
размера. В GraphQL признак — уровень, на котором стоит проверка: если она
стоит в резолвере корневого поля, все вложенные поля не защищены ничем.

> **Примечание.** Включённая интроспекция сама по себе находкой не служит.
> Курс называет её выключение «security through obscurity» и говорит, что
> одного этого недостаточно: даже при выключенной интроспекции форма схемы
> выводится перебором имён полей по подсказкам в сообщениях об ошибках.

## 6. Как чинится

```text
# Псевдокод, не исполняется. Исправленный вариант, сторона REST.
route "/api/v1/checkout/confirm",
      methods = ["POST"],                    # (1)
      consumes = "application/json",         # (2)
      max_body = 64 * 1024:                  # (3)
    require_state(order_id, "paid")          # (4)
    finalize(order)
```

Ответ на это стоит сформулировать до раскрытия: какая из четырёх строк
осталась бы нужной, даже если бы все остальные три были на месте?

<details>
<summary>Разбор выносок</summary>

1. Список методов задан явно; всё, что вне списка, получает `405`.
2. Тип содержимого проверяется: Cheat Sheet предписывает отвергать запросы с
   неожиданным или отсутствующим типом ответом `406` либо `415`.
3. Предел размера тела задан, превышение отвергается ответом `413`.
4. Четвёртая — та самая. Ограничения приёма не знают ничего о порядке шагов:
   состояние рабочего процесса проверяется на сервере при каждом запросе, и
   это единственное, что закрывает исполнение вне очереди.

</details>

Со стороны GraphQL то же требование выглядит как перенос проверки: она
уходит из резолвера корневого поля в бизнес-логику, вызываемую резолвером
`invoices`, а само поле получает пагинацию.

**Оставшийся зазор.** Перечень точек входа верен ровно настолько, насколько
описание соответствует коду. Описание OpenAPI пишут руками, схему GraphQL
часто порождают из моделей — и во втором случае новое поле модели становится
новой точкой входа само собой, без единой строки кода и без ревью.

**Накладные расходы.** Проверка на уровне поля повторяется в каждом резолвере
и стоит обращений к хранилищу; отсюда требование курса выносить её в
бизнес-логику, а не писать в каждом резолвере заново.

## 9. Ловушка

Общее место: у GraphQL один эндпоинт, значит и защищать надо один эндпоинт.

**Факты против.** Один адрес — свойство транспорта, а не модели доступа.

Почему так. За `/graphql` стоит схема, и каждое её поле исполняется своим
резолвером. Правило на прокси, разрешающее `POST /graphql`, разрешает всё, что
можно выразить схемой. Ограничение частоты по числу запросов тоже не работает:
курс отмечает, что сервер заранее не знает, насколько дорого обойдётся
конкретный набор полей, и советует применять ограничения в слое бизнес-логики.

Пример. Один запрос с сотней псевдонимов одного и того же поля
(`friends1: friends(limit: 1)` … `friends100: friends(limit: 100)`) остаётся
одним запросом `POST` и проходит любой ограничитель, считающий запросы. Курс
приводит ровно этот случай, называя меру: ограничивать число полей верхнего
уровня и псевдонимов в одной операции.

## 10. Чеклист ревью

1. Verify that перечень точек входа получен из описания API или схемы и
   сверен с маршрутами в коде.
2. Verify that каждый маршрут REST объявляет список допустимых методов и
   отвергает остальные ответом `405`.
3. Verify that тип содержимого запроса проверяется, а неожиданный или
   отсутствующий отвергается ответом `406` либо `415`.
4. Verify that задан предел размера тела запроса, а превышение отвергается
   ответом `413`.
5. Verify that шаги многошагового процесса проверяют состояние на сервере, а
   не полагаются на порядок вызовов с клиента.
6. Verify that в GraphQL проверка доступа стоит на том поле, которое отдаёт
   данные, а не только на корневом.
7. Verify that для GraphQL заданы пределы глубины, ширины и размера пакета
   операций, а списочные поля пагинированы.
8. Verify that чувствительные операции вызываются небезопасными методами, а
   не `GET` (ASVS v5.0-3.5.3).

## 11. Задача

Возьмите один API и соберите перечень его точек входа двумя независимыми
способами: из описания или схемы и из кода.

Подсказка одна: расхождение почти всегда одностороннее — в коде находится то,
чего нет в описании, а не наоборот.

**Критерий выполнения.** Готов список операций. Для REST в каждой строке:
метод, путь, места параметров, требуется ли аутентификация. Для GraphQL: имя
поля, тип, возвращает ли список, где стоит проверка доступа. Отдельным
абзацем — перечень расхождений между двумя способами сбора и вывод, какой из
двух источников оказался неполным.

## 12. Проверь себя

1. Пять мест, откуда операция REST берёт параметр, — назовите их.
2. Какие методы обязан и какие может поддерживать сервер GraphQL, и для каких
   операций?
3. Почему авторизация на уровне поля выполняется во время исполнения, а не
   раньше?
4. Чем ограничение числа запросов бесполезно для GraphQL?
5. Возврат к теме `app-architecture`: почему перечень точек входа, собранный
   на обратном прокси, будет неполным?
6. Возврат к теме `sessions-vs-tokens`: какие утверждения токена REST Cheat
   Sheet предписывает проверять принимающей стороне?

<details>
<summary>Ответы</summary>

1. `path`, `query`, `querystring`, `header`, `cookie`.
2. Обязан обрабатывать `POST` для запросов и мутаций; может принимать `GET`,
   но только для операций чтения.
3. Потому что решение зависит от конкретного поля и конкретного объекта, а
   они становятся известны только в резолвере. Курс добавляет вторую причину:
   так получается частичный ответ с ошибками там, где доступа нет.
4. Потому что стоимость запроса задаёт клиент набором полей, и сервер заранее
   её не знает: один запрос может стоить дороже тысячи.
5. Прокси видит адреса, а не схему: за одним адресом `/graphql` скрыты все
   поля, и в перечне они не появятся. Для REST перечень с прокси тоже неполон,
   если часть маршрутов доступна только изнутри.
6. `iss` — доверенный ли издатель; `aud` — входит ли принимающая сторона в
   аудиторию; `exp` — не истёк ли срок; `nbf` — начался ли он.

</details>
