# GitHub Actions: workflow, job, секреты, права токена

Уровень **L2** · время 45 мин (теория 25 / задача 15 / самопроверка 5,
оценка)

Что прочитать сначала: `pipeline-anatomy`.

## 0. Коротко

Описание конвейера лежит в репозитории по пути `.github/workflows/`. Читается
оно сверху вниз четырьмя вопросами: что запускает (`on`), с какими правами
(`permissions`), из каких работ состоит (`jobs`), что каждая работа делает
(`steps`).

Шаг бывает двух видов. Либо `run` — команда оболочки. Либо `uses` — чужой
готовый шаг, подключаемый по адресу репозитория и ссылке на версию. Второе и
есть то, чем эта система отличается от прочих: половина типового конвейера
собрана из чужих шагов.

Три вещи в этом описании относятся к безопасности напрямую, и все три задаются
в самом файле. Это набор событий в `on`, набор прав в `permissions` и способ
сослаться на чужой шаг в `uses`.

**Зачем это в работе AppSec-инженера.** Систему называют в вакансиях по имени, и
чтение чужого описания конвейера — ежедневная работа, а не разовая настройка.
Три четверти замечаний по конвейеру пишутся по одному файлу, без доступа к
серверу. Права шире нужного, чужой шаг по подвижной ссылке, значение из запроса
в команде шага.

## 1. Цели

После этого раздела вы сможете:

1. Описать конвейер из нескольких job с передачей артефакта.
2. Урезать права токена сборки до нужных областей.
3. Отличить переменную шага от секрета репозитория по месту объявления.
4. Проверить описание конвейера линтером без сервера.

## 3. Механика

Механизм здесь не свой: событие, граф работ, артефакт, кэш и вердикт разобраны в
`pipeline-anatomy`, а модель прав токена сборки как класс дефекта — в
`pipeline-security`. Ниже — только то, чем эта система записывает уже
разобранное.

**Откуда это взялось.** Ранние конвейеры описывались настройками в интерфейсе
сервера сборки: галочки, поля, порядок шагов мышью. Проверить такую настройку в
ревью было нечем, а восстановить после потери сервера — только по памяти.
Переезд описания в репозиторий решил обе задачи разом и создал третью. Файл,
который выполняется с правами сборки, стал править любой, кто может прислать
запрос на слияние.

**Событие и права идут вместе.** `on` перечисляет события. Для каждого из них
токен сборки получает набор прав, а секреты репозитория — доступность. Значение
по умолчанию задаётся настройкой организации, и полагаться на него не стоит:
`permissions` в самом файле перекрывает умолчание и делает решение видимым в
ревью. Область, не названная в блоке `permissions`, получает `none`; запись
`permissions: {}` отключает всё [^2].

**Секрет объявляется не там, где переменная.** Переменная шага — блок `env`
рядом с шагом или с job. Секрет живёт в настройках репозитория или организации и
попадает в описание выражением `secrets.ИМЯ`. Разница видна в файле: значение
переменной в нём написано, значение секрета — нет.

**Чужой шаг подключается ссылкой, и ссылка бывает подвижной.** Запись
`uses: владелец/шаг@v4` называет тег, а тег переписывается владельцем шага в
любой момент. Запись с полной суммой коммита — не переписывается.

## 4. Что умеет и чего не умеет

**Что умеет.** Описать конвейер целиком одним файлом, который проходит ревью
вместе с кодом. Дать готовые шаги на всё типовое — получение кода, установку
среды, выгрузку и загрузку артефактов. Задать права токена сборки построчно, в
том числе по-разному для разных job.

**Чего не умеет.** Проверить чужой шаг. Подключая шаг, вы подключаете
репозиторий целиком с правами своей сборки, и содержимое его вам никто не
показывает.

Не умеет система и развести доверенный код и недоверенный автоматически. Событие
запроса на слияние из чужой копии репозитория бывает двух видов, и они
различаются правами; выбор между ними делает автор файла, а не сервер.

## 5. Как запустить

**Шаг 1. Написать описание.** Минимальный полезный конвейер — сборка, проверка,
передача артефакта между ними, урезанные права:

```yaml
name: ci
on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  build:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683
      - run: mkdir -p out && python -c "print('собрано')" > out/app.txt
      - uses: >-                                      # v4.6.2
          actions/upload-artifact@ea165f8d65b6e75b540449e92b4886f43607fa02
        with:
          name: app
          path: out/app.txt
```

Свёрнутый скаляр `>-` в шаге выгрузки — только ради ширины страницы: он даёт
ту же строку, что и запись в одну строку. Две оставшиеся работы:

```yaml
  scan:
    needs: [build]
    runs-on: ubuntu-24.04
    steps:
      - uses: >-                                      # v4.3.0
          actions/download-artifact@d3f86a106a0bac45b974a628896c90dbdf5c8093
        with:
          name: app
          path: out
      - run: echo "сканирую $(wc -c < out/app.txt) байт"

  release:
    needs: [build, scan]
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-24.04
    permissions:
      contents: write
    steps:
      - run: echo "выпуск"
```

Три вещи в этом файле стоит прочитать отдельно. `permissions: contents: read` на
уровне файла — умолчание для всех job. Блок `permissions` внутри `release` —
повышение для одного job, которому запись нужна. Суммы коммитов после `@` —
неподвижные ссылки; номер версии стоит рядом комментарием, для чтения.

**Шаг 2. Положить секрет.** Настройки репозитория, раздел секретов и переменных
для конвейера. Значение вводится один раз и обратно не читается. В описании оно
доступно как `${{ secrets.ИМЯ }}` и передаётся шагу через `env`, а не
подставляется в текст команды — почему именно так, разбирается в
`pipeline-security`.

**Шаг 3. Проверить описание до отправки.** Линтер описаний работает локально и
сети не требует:

```text
docker run --rm -v "$PWD":/repo -w /repo rhysd/actionlint:1.7.12 -no-color
```

Каталог должен быть репозиторием: линтер ищет `.github/workflows` от корня и без
`.git` отказывается работать.

## 6. Как читать вывод

Линтер печатает по строке на замечание: путь, строка, столбец, текст, правило в
квадратных скобках. Прогон на файле с пятью подставленными дефектами:

```text
vuln.yml:16:58: "github.event.pull_request.title" is potentially untrusted.
  avoid using it directly in inline scripts. [expression]
vuln.yml:24:35: "github.event.pull_request.body" is potentially untrusted.
  avoid using it directly in inline scripts. [expression]
rc=1
```

**Две находки из пяти — и это важнее самих находок.** В файле, кроме двух
подстановок, стояли `permissions: write-all`, событие запроса на слияние с
получением чужого кода и чужой шаг по подвижной ссылке. Линтер о них не сказал
ничего: он проверяет синтаксис, типы выражений и известный список недоверенных
источников, а не политику.

Отдельно поучителен пропуск. Выражение с именем учётной записи автора запроса в
том же файле не помечено. В списке недоверенных источников линтера его нет:
набор знаков в имени ограничен. Ограничен — не значит безопасен в
любом контексте, и решение о том, чем ограничение считать, линтер оставляет
человеку.

Вывод для работы: **линтер описаний закрывает синтаксис и часть инъекций, а
права, события и ссылки на чужие шаги остаются своим правилам.** Как они
пишутся, разбирается в `pipeline-security`.

## 7. Границы метода

**Граница первая: конвейер этой системы без её сервера не проверить.** Локально
проверяются синтаксис описания и часть выражений. Права токена сборки, поведение
событий, хранилище секретов и маскирование в журнале — серверные, и
эмулятора у них нет по устройству, а не по бедности. Всё, что о них сказано в
этой теме, взято из документации вендора и прогоном не подтверждалось; это
названо в маркерах уверенности отдельно.

**Граница вторая: тег версии чужого шага — не версия.** Ссылка вида `@v4`
указывает на подвижный тег, который владелец шага перемещает при каждом выпуске.
Единственная неподвижная ссылка — полная сумма коммита.

**Граница третья: описание версионно.** Имена ключей, состав областей прав и
набор событий меняются от выпуска к выпуску. Устройство — событие, граф,
артефакт, вердикт — не меняется, и лежит оно в `pipeline-anatomy`.

**Цена.** Написать первый рабочий конвейер — час. Прочитать чужой и выписать из
него события, права и список чужих шагов — двадцать минут. Поставить локальный
линтер — минуты, и это лучшее вложение из трёх.

## 8. Ловушка

Распространённое мнение: если в описании конвейера не написано `permissions`,
права у токена сборки минимальные.

**Умолчание задаётся не файлом, а настройкой организации или репозитория, и
исторически оно было широким.** Файл без блока `permissions` наследует то, что
выставлено снаружи, и в ревью этого не видно: страница выглядит одинаково при
любом умолчании. Отсюда правило: блок `permissions` в описании стоит писать
всегда, даже когда он повторяет умолчание, — он превращает невидимую настройку в
строку, которую читает ревьюер [^3].

Контрпример к обратному выводу — «значит, надо ставить `permissions: {}` везде».
Не везде: job, которому нужно опубликовать артефакт или поставить отметку о
проверке, с пустыми правами не отработает. Правило не «минимум всегда», а
«минимум по умолчанию и повышение точечно, на уровне job».

## 9. Чеклист ревью

1. Verify that в описании конвейера есть блок `permissions`, а не унаследованное
   умолчание.
2. Verify that права повышаются на уровне job, которому они нужны, а не на
   уровне всего файла.
3. Verify that чужие шаги подключены по полной сумме коммита, а не по тегу или
   ветке.
4. Verify that значения секретов передаются шагу через `env`, а не
   подставляются в текст команды.
5. Verify that события в `on` перечислены явно и для события из чужой копии
   репозитория набор job отличается от основного.
6. Verify that описание конвейера проходит локальный линтер до отправки на
   сервер.

## 10. Задача

Взять любой открытый репозиторий с конвейером на этой системе и составить по
его описанию три списка. События с правами, которые они дают. Чужие шаги с
пометкой, подвижная ссылка или сумма коммита. Шаги, в командах которых стоит
значение из события.

Работа делается по одному файлу, доступа к репозиторию не требует. После этого
прогнать по нему локальный линтер и сравнить свои три списка с его выводом.

**Наблюдаемый признак выполнения:** у вас есть три списка и ответ на вопрос,
какие пункты линтер нашёл сам, а какие пришлось выписывать глазами. Второй
список обычно длиннее первого.

## 11. Проверь себя

1. Чем шаг `run` отличается от шага `uses` по тому, что попадает в вашу сборку?
2. Где объявляется переменная шага и где — секрет, и как эта разница видна в
   самом файле?
3. Что получает область прав, не названная в блоке `permissions`?
4. Почему ссылка на чужой шаг по тегу `@v4` не считается закреплённой версией?
5. Что локальный линтер описаний находит и чего не находит по устройству?
6. Возврат к теме `pipeline-anatomy`: почему job, объявленный через `needs`, всё
   равно нуждается в шаге загрузки артефакта?

<details>
<summary>Ответы</summary>

1. `run` — своя команда, её текст виден в файле. `uses` — чужой репозиторий,
   который выполнится с правами вашей сборки; его содержимое в файле не видно.
2. Переменная — блок `env` рядом с шагом или job, значение написано в файле.
   Секрет — настройки репозитория, в файле стоит только имя. Значение секрета в
   описании не встречается.
3. `none`. Права выдаются перечислением, а не вычитанием, и запись
   `permissions: {}` отключает все области сразу.
4. Тег перемещается владельцем шага в любой момент, и следующая сборка возьмёт
   другой код по той же ссылке. Неподвижна только полная сумма коммита.
5. Находит синтаксис, ошибки типов в выражениях и подстановку известных
   недоверенных полей события в команды шага. Не находит широких прав, опасного
   выбора события и подвижных ссылок на чужие шаги — это политика, а не синтаксис.
6. `needs` задаёт порядок, а не доставку. Рабочий каталог у job чистый, и
   артефакт попадает в него только отдельным объявлением на стороне получателя.

</details>
