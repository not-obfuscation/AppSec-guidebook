# Секреты в коде и конфигурации

Уровень **L2** · время 35 мин (теория 21 / задача 9 / самопроверка 5,
оценка)

Что прочитать сначала: `information-disclosure`, `source-config-exposure`.

Предмет темы — секрет в коде: рабочий ключ или пароль, попавший в
исходники. Такие находки приходят от сканера секретов постоянно, и
удаление строки из файла находку не закрывает.

Пример. Стенд `e10-secrets.py`: строку с ключом удалили из файла и
закоммитили. Вот что показывают два запроса — поиск по файлам и поиск
по истории:

```text
grep по файлам: не найден
git log -S по ключу: коммитов 2
объект 3d219c8e: AKIAIOSFODNN7EXAMPLE
```

Рабочее дерево чисто, история — нет: ключ лежит в объектах репозитория и в
каждой копии у каждого, кто успел склонировать.

Секрет, попавший в код, сохраняется при копировании: репозиторий, слои
образа, артефакт сборки, журналы сборки, резервные копии. У каждого из этих
мест свои правила доступа, и правка рабочего файла не трогает ни одно из них.
Поэтому порядок устранения находки обратный привычному: сначала ключ отзывают
и меняют, и только потом убирают следы.

Дальше — полный перечень мест, где секрет оседает, почему переменная
окружения не решает задачи хранения и как отличить рабочий ключ от тестового
значения.

Что развёртывание оставляет доступным снаружи, разбирает тема
`source-config-exposure`. Здесь другой конец той же задачи: секрет, попавший
внутрь артефакта, и порядок действий, когда его нашли.

## 0. Коротко

Секрет в исходниках — не одна ошибка, а свойство, которое сохраняется при
копировании. Строка ключа попадает в репозиторий, оттуда в каждую копию у
каждого разработчика, в слой образа, в артефакт сборки, в журнал сборки и в
резервную копию. Каждое из этих мест живёт по своим правилам доступа, и
удаление строки из рабочего файла не трогает ни одно из них.

Отсюда порядок действий, обратный привычному. Сначала отзыв и смена: скомпро
метированный ключ перестаёт работать. И только потом уборка следов, которая
уже ничего не решает, а лишь мешает следующему нашедшему. Наоборот — сначала
почистили историю, потом собирались менять — оставляет рабочий ключ в чужих
клонах на всё время между двумя действиями.

Разряды секретов различаются по тому, что они открывают. Учётные данные к
внешней системе. Ключ подписи токенов. Ключ шифрования хранимых полей.
Закрытый ключ сертификата. Начальное значение для одноразовых кодов. Каталог
уязвимостей разводит их по двум записям — зашитый ключ и зашитые учётные
данные, — и OWASP относит эти записи к разным категориям.

**Зачем это в работе AppSec-инженера.** Находка почти всегда бесспорна, и весь
разговор идёт про то, что делать дальше: где хранить, чем заменить, кто
меняет ключ и что при этом сломается. Тема даёт готовую последовательность и
перечень мест, по которым надо пройти, — без него уборка сводится к правке
одного файла, а секрет остаётся доступным.

## 3. Механика

**Откуда это взялось.** Настройки приложения писались в файл рядом с кодом, и
адрес базы вместе с паролем к ней лежал там же — иначе приложение не
запускалось. Пока код жил на одной машине, места лучше не было. Система
контроля версий изменила цену: у файла появилась история, у истории — копии, у
копий — своя жизнь. Правило «настройки отдельно от кода» появилось как ответ,
но перенесло проблему в файл настроек, а не убрало. Настоящий ответ пришёл
позже — хранилище с собственным доступом, выдающее секрет во время работы.

Стенд заводит репозиторий, кладёт в него ключ, потом «убирает» его правкой
файла и смотрит, что осталось.

```text
$ python e10-secrets.py
(1) В рабочем дереве секрета больше нет
  grep по файлам: не найден
(2) В истории он остался
  git log -S по ключу: коммитов 2
  git show HEAD~1:settings.py -> ключ виден: True
  объектов в базе репозитория: 6
(3) Поиск по всем объектам, а не по рабочему дереву
  объект 3d219c8e: AKIAIOSFODNN7EXAMPLE
  всего вхождений: 1
```

Первая строка — то, что видит разработчик, доложивший об исправлении. Вторая и
третья — то, что видит любой, у кого есть клон. Отсюда и способ искать: по
объектам репозитория, а не по рабочему дереву.

### Где ещё оседает

- **Слои образа.** Файл, добавленный в одном слое и удалённый в следующем,
  остаётся в первом. Образ раздаётся целиком.
- **Артефакт сборки.** Ключ, попавший в клиентский пакет, уезжает в браузер
  каждого посетителя.
- **Журналы сборки.** Значение, напечатанное в отладочной строке, живёт
  столько, сколько хранится журнал.
- **Переменные окружения процесса.** Читаются из файла окружения процесса и
  печатаются функциями вроде вывода конфигурации интерпретатора.
- **Резервные копии и дампы.** Копия базы или файловой системы уносит с собой
  и настройки.

## 5. Как выглядит в коде

Признак первый — строковая константа рядом с именем, обещающим секрет.

```python
# УЯЗВИМО — демонстрация, не для продакшена.
AWS_SECRET_ACCESS_KEY = "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEX"  # (1)
JWT_SIGNING_KEY = "change-me-in-production"                 # (2)
DB_DSN = os.getenv("DB_DSN", "postgres://app:hunter2@db/app")  # (3)
```

1. Ключ доступа целиком в исходнике.
2. Значение-заглушка, дожившее до рабочего контура: подходит любому, кто читал
   репозиторий.
3. Значение по умолчанию у переменной окружения — тот же секрет, спрятанный за
   безопасным на вид вызовом.

Признак второй — закрытый ключ файлом в репозитории: заголовок
`-----BEGIN PRIVATE KEY-----`, расширения `.pem`, `.p12`, `.jks`, файл
`.npmrc` или `.pypirc` с токеном.

```javascript
// УЯЗВИМО — демонстрация, не для продакшена.
const client = new Analytics({
  writeKey: 'sk_live_51H8kQ2eZvKYlo2C0X9wRzT'   // (4)
});
```

4. Ключ в клиентском коде: сборка отдаёт его каждому посетителю. Ключ с
   приставкой `sk_live` предназначен для сервера.

Ложное срабатывание того же вида — тестовые и заведомо публичные значения:
ключ из примера документации, значение в фикстуре теста, открытый ключ рядом с
закрытым. Руководство по секретам предлагает завести на организацию единый
набор тестовых секретов: тогда список исключений короток и не растёт.

## 6. Как чинится

- **Сначала отзыв и смена.** Ключ отзывается, новый выпускается и
  раскатывается. Всё остальное делается после и на скорость реакции не влияет.
- **Потом уборка.** Удаление из истории переписывает её и ломает ссылки на
  коммиты; руководство прямо просит взвесить это, а не делать по умолчанию.
- **Хранилище с собственным доступом.** Ключевое хранилище или система
  управления секретами, а не файл и не переменная сборки (`v5.0-13.3.1`).
  Секретов не должно быть ни в исходниках, ни в артефактах сборки.
- **Право на секрет — по минимуму.** Доступ к каждому секрету у тех, кому он
  нужен для работы, и не шире (`v5.0-13.3.2`).
- **Срок жизни и смена по расписанию.** Динамический секрет, выдаваемый на
  время работы, снимает вопрос смены целиком.
- **Поиск до коммита и в сборке.** Проверка на стороне разработчика ловит
  раньше, проверка в сборке — надёжнее; обе нужны.
- **Служебные каталоги не уезжают в развёртывание.** Каталог системы контроля
  версий в контуре развёртывания недоступен ни снаружи, ни приложению
  (`v5.0-13.4.1`).

## 9. Ловушка

Ходовое правило гласит: настройки берутся из окружения, а не из файлов, и
секрет в переменной окружения — уже правильно сделанная работа.

**Переменная окружения — способ доставки, а не хранилище.** Она решает одну
задачу — вынуть значение из образа — и не решает остальных. Значение виднó
через файл окружения процесса и печатается функциями вывода конфигурации. Оно
попадает в отчёт об аварии вместе со снимком окружения и наследуется каждым
дочерним процессом, включая посторонние. Руководство по хранению прямо
советует избегать переменных окружения для ключей и называет оба канала утечки
поимённо. Годная связка выглядит иначе: хранилище с собственным доступом
выдаёт значение работающему процессу, а переменная окружения несёт разве что
адрес этого хранилища.

Соседняя ошибка того же порядка — считать уборку истории мерой защиты.
Переписывание истории не отменяет ключа: копии уже разошлись по клонам,
зеркалам и кэшам платформы. Пока ключ не отозван, он работает.

## 10. Чеклист ревью

1. Verify that секретов нет ни в исходниках, ни в артефактах сборки, а
   хранятся они в системе управления секретами (`v5.0-13.3.1`).
2. Verify that поиск ведётся по всей истории репозитория и по слоям образа, а
   не по рабочему дереву.
3. Verify that при находке ключ отозван и заменён прежде, чем начата уборка
   следов.
4. Verify that доступ к каждому секрету ограничен теми, кому он нужен для
   работы (`v5.0-13.3.2`).
5. Verify that значения по умолчанию у переменных окружения не содержат
   рабочих учётных данных.
6. Verify that ключи, предназначенные серверу, не попадают в клиентскую
   сборку.
7. Verify that каталоги системы контроля версий недоступны в контуре
   развёртывания (`v5.0-13.4.1`).

## 11. Задача

Возьмите один репозиторий. Пройдите поиском по истории, а не по рабочему
дереву: по строкам `BEGIN PRIVATE KEY`, `password`, `secret`, `token`,
`api_key` и по формату ключей вашего облака. Отдельно посмотрите на значения
по умолчанию в вызовах чтения переменных окружения.

**Критерий:** составлен список находок с пометкой у каждой — рабочий секрет,
тестовое значение или заглушка. Для рабочих названо, кто и как их меняет, и
записано, отозван ли уже найденный. Отдельно записано, чем находки по истории
отличались от находок по рабочему дереву.

## 12. Проверь себя

1. Почему удаление строки с ключом и новый коммит не устраняют находку?
2. В каком порядке идут отзыв, смена и уборка следов и что ломается при
   обратном порядке?
3. Чем переменная окружения отличается от хранилища секретов по набору
   закрываемых задач?
4. Какие два канала делают переменную окружения видимой посторонним?
5. Как отличить рабочий секрет от тестового значения и что предлагают делать,
   чтобы отличать их дёшево?
6. Возврат к теме `source-config-exposure`: чем находка секрета в истории
   репозитория отличается от находки доступного снаружи файла настроек?

<details markdown="1">
<summary>Ответы</summary>

1. Потому что значение остаётся в объектах репозитория и во всех его копиях.
   Стенд показал: рабочее дерево чисто, а `git show` по предыдущему коммиту и
   поиск по объектам находят ключ.
2. Сначала отзыв, затем выпуск и раскатка нового значения, затем уборка. При
   обратном порядке между уборкой и сменой остаётся окно, в котором рабочий
   ключ уже разошёлся по клонам, а сменить его ещё не успели.
3. Переменная окружения доставляет значение процессу и на этом её работа
   кончается. Хранилище добавляет собственный доступ, разграничение прав,
   запись обращений, срок жизни и смену — то есть всё, ради чего секрет и
   выносили.
4. Файл окружения процесса, доступный на чтение, и функции вывода
   конфигурации интерпретатора. Плюс наследование окружения дочерними
   процессами и снимок окружения в отчёте об аварии.
5. По тому, что ключ открывает: рабочий контур или ничего. Дёшево это делается
   единым набором тестовых секретов на организацию — тогда список исключений
   короток и не растёт с каждым новым проектом.
6. Доступный снаружи файл настроек читает любой прохожий, и закрывается он
   настройкой веб-сервера. Секрет в истории виден тем, у кого есть доступ к
   репозиторию, и настройкой не закрывается: значение уже скопировано, и
   помогает только его смена.

</details>
