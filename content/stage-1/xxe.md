# XXE: чтение файлов и SSRF через парсер XML

Уровень **L2** · время 30 мин (теория 17 / задача 8 / самопроверка 5,
оценка)

Что прочитать сначала: `ssrf-basics`, `http-basics`.

Механизм SSRF — сервер ходит по адресу из данных — разобран в `ssrf-basics`.
XXE даёт тот же ход через парсер XML, а сверх него — чтение файлов.

## 0. Коротко

XXE (XML external entity) — дефект обработки XML, при котором присланный
документ объявляет внешнюю сущность, а парсер её разворачивает. Через сущность
`SYSTEM "file:///etc/passwd"` парсер читает файл и вставляет его в документ;
через `SYSTEM "http://внутренний-адрес/"` — ходит по адресу, то есть даёт SSRF.
Когда ответ не виден, данные уносят внеполосно, как в `blind-ssrf`.

Причина — парсер настроен разворачивать внешние сущности. Парсеры закрыты по умолчанию:
проверено на стандартной библиотеке Python 3.14.7, где внешняя сущность не
разворачивается вовсе. Поэтому дефект чаще не в том, что защиту забыли включить,
а в том, что обработку сущностей включили обратно. Каталог MITRE держит номер
CWE-611, а OWASP относит его к A02:2025 Security Misconfiguration.

**Зачем это в работе AppSec-инженера.** XXE называют в вакансиях, а исход у него
тяжёлый: чтение файлов сервера и SSRF во внутреннюю сеть. Ревьюеру важно
проверить не наличие «фильтра», а настройку парсера XML: разворачивает ли он
внешние сущности и DTD. Вопрос задаётся каждому месту, где приложение принимает
XML: загрузка документов, SOAP, форматы вроде SVG и DOCX, разбор конфигураций.

## 1. Цели

После этого раздела вы сможете:

1. Объяснить, как внешняя сущность XML читает файл или ходит по адресу.
2. Назвать три исхода XXE: чтение файла, SSRF, слепой внеполосный.
3. Проверить настройку парсера XML на обработку внешних сущностей.
4. Отличить безопасный по умолчанию парсер от включённого обратно.

## 3. Механика

**Откуда это взялось.** XML задумывали расширяемым: документ может объявлять
сущности — сокращения, которые парсер подставляет при разборе. Внешняя сущность
берёт значение из внешнего ресурса: файла или адреса. Возможность полезная для
документов, но опасная для присланного: тот, кто прислал XML, объявляет, что
парсеру прочитать. Историю это и объясняет — раньше парсеры разворачивали
сущности по умолчанию, и присланный документ управлял чтением. Ущерб оказался
велик, и парсеры закрыли обработку внешних сущностей по умолчанию.

### Как устроена сущность

Документ объявляет сущность в DTD и подставляет её в тело:

```xml
<?xml version="1.0"?>
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]>
<stockCheck><productId>&xxe;</productId></stockCheck>
```

Ключевое слово `SYSTEM` указывает парсеру внешний ресурс. При разборе `&xxe;`
парсер читает файл и вставляет его содержимое туда, где стоит сущность. Если это
значение попадает в ответ, атакующий читает файл.

### Три исхода

**Чтение файла.** Сущность указывает на путь `file://`, и содержимое файла
попадает в ответ. Так читают файлы конфигурации, ключи, любые доступные парсеру.

**SSRF.** Сущность указывает на адрес `http://`, и парсер ходит по нему —
`ssrf-basics` в чистом виде, но инициатор запроса здесь парсер XML. Целью берут
внутренние службы и служебные интерфейсы облака.

**Слепой XXE.** Когда значение сущности в ответ не попадает, данные уносят
внеполосно: через параметрические сущности и обращение к серверу атакующего,
как в `blind-ssrf`. Или через сообщение об ошибке парсера, если оно возвращается
и содержит часть прочитанного.

## 5. Как выглядит в коде

Ревьюер смотрит не на данные, а на настройку парсера.

```python
# УЯЗВИМО — демонстрация, не для продакшена.
parser = etree.XMLParser(resolve_entities=True)   # (1)
tree = etree.fromstring(user_xml, parser)         # (2)
```

1. Обработка сущностей включена явно. Внешняя сущность из присланного
   развернётся.
2. Присланный документ разбирается этим парсером. Источник — тело запроса XML,
   сток — разбор с включёнными сущностями.

Проверено на стандартной библиотеке Python: `xml.etree.ElementTree` не
разворачивает внешнюю сущность и на документе выше падает с «undefined entity»,
а `minidom` не подставляет её значение. Значит, признак дефекта — не отсутствие
проверки ввода, а включённая обработка сущностей или устаревший парсер,
делающий это по умолчанию.

## 6. Как чинится

Первоисточник называет главную меру прямо: отключить обработку внешних сущностей
и DTD в парсере — это проще и надёжнее всего.

```python
# Исправлено (lxml).
parser = etree.XMLParser(
    resolve_entities=False,   # (1)
    no_network=True,          # (2)
    load_dtd=False)
tree = etree.fromstring(user_xml, parser)
```

1. Внешние сущности не разворачиваются.
2. Парсеру запрещён выход в сеть — закрывает SSRF-исход даже при ошибке в
   настройке сущностей.

**Границы применимости.** Набор флагов зависит от библиотеки и языка: у каждого
парсера свои имена настроек, и cheat sheet ведёт их список по стекам. Общее
правило одно: отключить внешние сущности, DTD и XInclude. Где обработка DTD
нужна по делу, оставляют локальные сущности и запрещают внешние. Проверять
настройку надо там, где парсер создаётся, потому что значение по умолчанию
зависит от версии библиотеки и могло быть переопределено.

## 9. Ловушка

Распространённое представление: приложение проверяет присланный XML на
корректность и опасные строки, значит XXE закрыт.

**XXE закрывается настройкой парсера, а не проверкой содержимого.** Проверять
данные бесполезно: сущность объявлена по правилам XML, документ корректен, а
чтение файла делает сам парсер при разборе. Фильтр строк не поможет — опасен не
символ, а включённая возможность парсера.

Контрпример. Приложение отклоняет XML с подозрительными словами, но парсер
создан с обработкой сущностей. Документ с `<!ENTITY xxe SYSTEM
"http://169.254.169.254/">` подозрительных слов не содержит, проходит проверку и
заставляет парсер сходить на служебный интерфейс облака. Проверка данных не
сработала, потому что дефект в настройке, а не в данных.

## 10. Чеклист ревью

1. Verify that парсер XML создан с отключёнными внешними сущностями, DTD и
   XInclude (WSTG-v42-INPV-07).
2. Verify that значение по умолчанию не принято на веру: настройка задана явно
   там, где парсер создаётся.
3. Verify that парсеру запрещён выход в сеть, чтобы закрыть SSRF-исход при
   ошибке в настройке сущностей.
4. Verify that защита не сведена к проверке содержимого XML: она против XXE не
   действует.
5. Verify that учтены неявные точки разбора XML: SOAP, SVG, форматы офисных
   документов, импорт конфигураций.

меняется? Что произойдёт с документом из блока 3 — ошибка, пустое значение или

**Критерий выполнения** наблюдаемый: три письменных ответа со ссылкой на
конкретные имена настроек вашего парсера и с результатом разбора документа
(ошибка, пусто или чтение).

## 12. Проверь себя

1. Как внешняя сущность заставляет парсер прочитать файл или сходить по адресу?
2. Три исхода XXE — какие и чем различаются?
3. Почему XXE чинят настройкой парсера, а не проверкой содержимого XML?
4. Почему у парсера, закрытого по умолчанию, дефект чаще появляется, чем
   остаётся с самого начала?
5. Возврат к теме `ssrf-basics`: чем SSRF через XXE отличается от обычного SSRF
   по инициатору запроса?

<details>
<summary>Ответы</summary>

1. Документ объявляет сущность с ключевым словом `SYSTEM` и внешним ресурсом.
   При разборе парсер читает файл или ходит по адресу и вставляет результат туда,
   где стоит сущность.
2. Чтение файла (`file://`, содержимое в ответе), SSRF (`http://`, парсер ходит
   по адресу) и слепой внеполосный, когда значение в ответ не попадает и
   уносится через параметрические сущности или ошибку.
3. Сущность объявлена по правилам XML, документ корректен, а чтение делает сам
   парсер. Опасен не символ, а включённая возможность парсера — её и отключают.
4. Парсеры закрыты по умолчанию, поэтому дефект появляется, когда обработку
   сущностей включили обратно явно или взяли устаревшую библиотеку.
5. Инициатор запроса — парсер XML, а не код приложения напрямую. Механизм и цели
   те же, но точка входа — разбор присланного документа.

</details>
