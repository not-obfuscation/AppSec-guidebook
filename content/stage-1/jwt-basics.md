# JWT: структура, подпись, алгоритмы

Уровень **L1** · время 90 мин (теория 45 / лаба 30 / самопроверка 15,
оценка)

Что прочитать сначала: `sessions-vs-tokens`, `hmac-vs-signature`.

Эта тема несёт весь подраздел. JSON Web Token (JWT) — самый частый формат
самодостаточного токена, и почти каждая следующая тема опирается на то, как он
устроен. Разбор атак на него, сроки и отзыв, а также место токена в OAuth идут
отдельными темами; здесь — устройство и одна мысль, из которой растёт половина
ошибок в проде: подпись защищает от изменения, но не прячет содержимое. Эту
мысль тема доводит до кода, до прогона и до правила ревью, потому что на словах
её принимают, а на практике всё равно кладут секрет в нагрузку.

## 0. Коротко

JSON Web Token (JWT) — формат самодостаточного токена: три части, разделённые
точками, каждая закодирована в base64url. Первая часть — заголовок, вторая —
набор утверждений о пользователе (claims), третья — подпись первых двух.
Заголовок и нагрузка декодируются кем угодно без ключа: base64url — это
кодирование, а не шифрование.

Подпись отвечает на один вопрос: менял ли кто-то заголовок или нагрузку после
выдачи. На вопрос «кто это прочитает» она не отвечает вовсе. Отсюда два
следствия. Класть в нагрузку секрет или персональные данные нельзя — их прочтёт
любой предъявитель. Доверять содержимому можно только после проверки подписи
ожидаемым алгоритмом и ключом.

**Зачем это в работе AppSec-инженера.** MITRE держит для утечки такого рода
номер CWE-522, а издание OWASP 2025 года относит слабую защиту данных к
категории `A02:2025` Cryptographic Failures. На ревью тема даёт два быстрых
вопроса к любому механизму на JWT: что лежит в нагрузке выданного токена и чем
именно проверяется подпись на входе. Оба вопроса закрываются чтением двух-трёх
строк кода.

## 1. Цели

После этого раздела вы сможете:

1. Разобрать JWT на три части и прочитать заголовок и нагрузку без ключа.
2. Назвать, что защищает подпись токена и чего она не защищает.
3. Отличить подписанный токен от зашифрованного и понять роль поля `alg`.
4. Проверить токен так, чтобы сверялись срок, получатель и издатель.
5. Найти в коде конфиденциальное поле, положенное в нагрузку токена.

## 2. Предвопросы

Попробуйте ответить до чтения — даже неверный ответ дальше будет с чем сравнить.

1. Сервер выдал вошедшему пользователю подписанный JWT с полем `role`. Может ли
   пользователь прочитать своё поле `role`, не зная ключа подписи?
2. В нагрузку токена положили внутренний идентификатор договора. Скрывает ли его
   подпись от предъявителя?
3. Проверка подписи прошла успешно. Достаточно ли этого, чтобы принять токен?

## 3. Механика

**Откуда это взялось.** Сессию долго держали ссылочным значением: клиент носил
бессмысленный идентификатор, а всё о пользователе лежало на сервере. Это
требовало общего хранилища сессий между серверами. Когда приложения
разъехались на много узлов, понадобился токен, который сервер проверяет, ничего
не храня. Так появился самодостаточный токен: он несёт утверждения о
пользователе прямо в себе, а подпись защищает их от подмены. Удобство обошлось
ценой, о которой часто забывают: раз данные едут в самом токене, они и читаются
из самого токена.

### Три части

JWT — это последовательность из трёх частей, разделённых точками. Каждая часть
закодирована в base64url. RFC 7519 показывает разбор на примере; повторим его на
своём стенде.

```text
$ python e01-anatomy.py
частей в токене   3
длина токена      195 символов
часть 1, заголовок (base64url -> JSON, ключ не нужен):
  {"alg":"HS256","typ":"JWT"}
часть 2, нагрузка (base64url -> JSON, ключ не нужен):
  {"iss":"shop.example","sub":"wiener","role":"user",...}
часть 3, подпись  32 байт двоичных данных
```

Первая часть — заголовок JOSE (JSON Object Signing and Encryption). Он несёт
метаданные о самом токене. Обязательное поле здесь одно — `alg`, алгоритм
подписи. Второе частое поле — `typ`, тип; для обычного JWT его значение — `JWT`.

Вторая часть — набор утверждений, claims. Это обычный объект JSON с полями о
пользователе и о самом токене. RFC 7519 регистрирует несколько
зарегистрированных имён: `iss` (издатель), `sub` (субъект), `aud` (получатель),
`exp` (истекает), `nbf` (не раньше), `iat` (выдан), `jti` (идентификатор
токена). Все они по стандарту необязательны, но приложение вправе требовать
любые из них.

| claim | смысл | что проверяет приложение |
|---|---|---|
| `iss` | издатель токена | что токен выдан доверенной стороной |
| `sub` | субъект: о ком токен | по нему находят пользователя на сервере |
| `aud` | получатель токена | что токен предъявлен именно этой стороне |
| `exp` | время истечения | что срок ещё не прошёл |
| `nbf` | не действует раньше | что время начала уже наступило |
| `iat` | время выдачи | возраст токена, отсчёт для политик |
| `jti` | идентификатор токена | однократность, вход в список отзыва |

Cheat sheet OWASP добавляет к этому предупреждение об ещё одном классе полей.
`iss`, `aud` и `sub` участвуют в решении о доверии, и их нельзя принимать на
веру от непроверенного токена: сначала подпись, потом смысл claims.

Третья часть — подпись. Её считают по строке «заголовок.нагрузка», то есть по
первым двум частям в их закодированном виде. Тот же стенд это подтверждает:
HMAC-SHA256 от строки «заголовок.нагрузка» совпадает с третьей частью байт в
байт.

### Подпись — не шифрование

Ключевая мысль темы читается прямо из разбора. Заголовок и нагрузка
раскодированы без всякого ключа: base64url переводит двоичные данные в печатные
символы и обратно, ключа для этого не нужно. Значит, содержимое токена открыто
любому предъявителю.

Подпись меняет ровно одно: изменить заголовок или нагрузку и остаться
незамеченным нельзя. Стенд меняет в нагрузке роль на `admin`, подпись оставляет
прежней и предъявляет токен проверке:

```text
роль в нагрузке подменена на admin, подпись не тронута
  проверка подписи: отклонён (InvalidSignatureError)
  нагрузка подделки читается без ключа: admin
```

Две строки вместе и есть тема. Подмену видно — целостность защищена. Но
подделанная нагрузка всё равно читается без ключа — конфиденциальности нет.
RFC 7519 в разделе о доверии говорит о том же с другой стороны. Содержимому
токена нельзя доверять в решении, пока оно не проверено криптографически и не
привязано к нужному контексту.

### JWS и JWE: подпись или шифрование

Стандарт JWT сам по себе описывает только формат утверждений. Как именно их
защитить, задают два соседних стандарта. JSON Web Signature (JWS) описывает
подписанный токен: содержимое открыто, подпись подтверждает целостность. JSON
Web Encryption (JWE) описывает зашифрованный: содержимое закрыто.

На практике словом «JWT» почти всегда называют именно JWS — подписанный, а не
зашифрованный токен. Всё, о чём идёт речь в этой теме и в атаках на JWT, — про
JWS. Если содержимое действительно нужно скрыть от предъявителя, применяют JWE
или, чаще, не кладут секрет в токен вовсе.

Стандарт допускает и третий случай — токен без подписи вовсе. RFC 7519 называет
его незащищённым (unsecured) JWT: поле `alg` равно `none`, а третья часть —
пустая строка. Такой токен применим лишь там, где содержимое защищено чем-то
другим, например подписью на внешней структуре. Стоит запомнить сам факт: токен
имеет право заявить о себе «я не подписан». Что делает с этим заявлением
неаккуратный проверяющий — разбирает тема атак на JWT.

### Алгоритмы подписи

Поле `alg` называет, чем подписан токен, и делит алгоритмы на два семейства.

Первое — код аутентификации сообщения, Message Authentication Code (MAC): общий
секрет. Одним и тем же секретом издатель подписывает, а получатель проверяет.
Семейство `HS256`, `HS384`, `HS512` — это HMAC поверх SHA-2, и cheat sheet
OWASP относит его к рекомендованным. Секрет тут — как пароль: его нельзя ни
угадать, ни подобрать. Стандарт требует энтропии не ниже длины выхода: не меньше
256 бит для `HS256`.

Второе — цифровая подпись на паре ключей. Издатель подписывает закрытым ключом,
получатель проверяет открытым. Открытый ключ не секрет: его можно публиковать.
Сюда входят `RS256`, `ES256`, `PS256`, `EdDSA`. Cheat sheet рекомендует `EdDSA`,
`ES256` и `PS256`, а `RS256` (RSASSA-PKCS1-v1_5) помечает как не
рекомендованный.

Разница семейств — не деталь. На ней держится целая атака: если проверяющий сам
выбирает алгоритм по заголовку токена, открытый ключ можно подсунуть на место
секрета MAC. Это тема атак на JWT; здесь важно запомнить, что `alg` управляет
проверкой, а значение его приходит из токена, то есть от предъявителя.

### Что проверяется, кроме подписи

Проверенная подпись означает «этот токен выдали мы и его не меняли». Она не
означает «токен ещё годен» и «токен выдан для нас». За это отвечают отдельные
проверки claims, и часть из них по умолчанию молчит. Стенд перебирает варианты
на верной подписи:

```text
А. срок жизни, ожидаемое не объявлено:
  exp час назад                          откл. (ExpiredSignatureError)
  claims exp нет вовсе                          ПРИНЯТ
Б. получатель (aud):
  aud='other', audience='api.shop'       откл. (InvalidAudienceError)
  aud нет, audience не объявлен                 ПРИНЯТ
В. издатель (iss):
  iss='evil.test', issuer='auth.shop'          отклонён (InvalidIssuerError)
  iss='evil.test', issuer не объявлен           ПРИНЯТ
```

Читается это так. Срок `exp` библиотека проверяет сама, но только если поле в
токене есть: токена без `exp` она пропустит, пока приложение явно не потребует
это поле. Получателя `aud` и издателя `iss` она сверяет лишь тогда, когда
приложение назвало ожидаемое значение. Не назвало — сверять не с чем, и чужой
получатель проходит. Отсюда правило: проверка токена — это подпись, ожидаемый
алгоритм, срок и — для многосторонних систем — получатель и издатель.

RFC 7519 задаёт порядок проверки списком из десяти шагов и требует одного:
если любой шаг не прошёл, токен отклоняется целиком. Библиотеки исполняют эти
шаги за приложение, но решают за него не всё. Какие claims обязательны и с
какими значениями их сверять — задаёт протокол приложения, а не библиотека, и
именно этот выбор чаще всего оставляют на умолчании.

## 4. Эксплуатация

Стенд — лаба этой темы (`pilot/lab/jwt-basics`). Кабинет магазина держит
сессию на JWT: при входе выдаёт токен, на каждом запросе читает из него роль и
внутренние поля. Подпись HS256 проверяется честно — подделать роль нельзя. Но в
нагрузку положено то, чему там не место: адрес почты и внутренний скидочный код.

```text
$ python hack.py
  опыт 1 — discount_code из нагрузки без ключа: ПОЛУЧЕН PROMO-8842-INTERNAL
  опыт 2 — email из нагрузки без ключа: ПОЛУЧЕН wiener@shop.example
  опыт 3 — контроль, подмена role=admin с той же подписью: отвергнута
  опыт 4 — контроль, честный вход wiener: роль user
```

Опыт 1 берёт свой законный токен, отрезает вторую часть и раскодирует её из
base64url. Ключа для этого не нужно. В нагрузке лежит внутренний скидочный код —
он утёк предъявителю, хотя тот его в глаза не должен был видеть.

Опыт 2 тем же приёмом достаёт адрес почты. Персональные данные в нагрузке —
такая же утечка, как секрет.

Опыт 3 — контроль на целостность. Атакующий меняет роль на `admin`, кодирует
новую нагрузку обратно и оставляет старую подпись. Проверка подписи это
отвергает: подмену видно. Целостность работает, конфиденциальности нет — и это
не одно и то же.

Опыт 4 — контроль на живучесть. Честный вход обязан работать и после починки.

Тяжесть утечки решает не факт чтения, а что именно прочитано. Внутренний
скидочный код — это доступ к чужой цене; адрес и телефон — персональные данные,
попавшие к любому, кто держал токен. Токен часто оседает в журналах прокси, в
истории браузера, в отчётах об ошибках: всё это места, где нагрузку прочтут уже
без всякого участия пользователя. Один и тот же токен утекает не однажды и не в
одни руки.

## 5. Как выглядит в коде

Ревьюер смотрит на два места: что кладётся в нагрузку при выдаче и чем
проверяется токен на входе. Первое — здесь.

```python
# УЯЗВИМО — демонстрация, не для продакшена.
return jwt.encode({
    "sub": username,
    "role": profile["role"],
    "email": profile["email"],               # конфиденциально: PII
    "discount_code": profile["discount_code"],  # внутреннее
    "iat": issued,
    "exp": issued + 3600,
}, _SECRET, algorithm="HS256")
```

Признак дефекта — поле в нагрузке, значение которого предъявитель не должен
видеть: адрес, телефон, внутренний код, секрет, номер карты. Подпись здесь ни
при чём: она защитит эти поля от подмены, но не от чтения.

**Тот же дефект на другом стеке.** В Node он выглядит так же — меняется только
имя вызова:

```javascript
// УЯЗВИМО — демонстрация, не для продакшена.
const token = jwt.sign(
  { sub: username, role: profile.role, ssn: profile.ssn },
  SECRET, { algorithm: "HS256", expiresIn: "1h" }
);
```

Инвариант здесь — «конфиденциальное поле в нагрузке подписанного токена».
Декорация — язык и имя функции: `encode` на одном стеке, `sign` на другом.

**Второе место — проверка на входе.** Дефект тут — доверие содержимому без
проверки подписи или с ослабленной проверкой:

```python
# УЯЗВИМО: подпись не проверяется вовсе.
claims = jwt.decode(token, options={"verify_signature": False})
if claims["role"] == "admin":
    ...
```

Отключение проверки подписи снимает и сверку срока заодно: стенд показывает, что
просроченный токен при `verify_signature=False` проходит. Такой вызов законен
ровно в одном случае — прочитать заведомо ненадёжный токен, чтобы показать
сообщение, а не принять решение о правах.

Найти оба места помогает один приём. Выпишите каждый вызов, который выдаёт
токен, и каждый, который его принимает. У первых смотрите состав нагрузки, у
вторых — набор проверок. Двух списков обычно хватает: механизм на JWT в
приложении один, и оба вызова стоят рядом с ним.

**Где ревьюер ошибается.** Чтение нагрузки без ключа — не всегда дефект.
Публичные, неконфиденциальные поля (`sub`, `role`, `exp`) в нагрузке — норма:
именно для них токен и нужен. Дефект начинается там, где значение поля закрытое.
И обратная ошибка: наличие подписи ещё не значит, что её проверяют, — проверку
надо увидеть на входе, а не предположить по формату токена.

## 6. Как чинится

Правило выдачи: в нагрузку идёт только то, что предъявителю и так известно и что
нужно для проверки. Конфиденциальное держат на сервере и достают по проверенному
`sub`.

```python
# Исправлено: в нагрузке только несекретные утверждения.
return jwt.encode({
    "sub": username,
    "role": profile["role"],
    "iat": issued,
    "exp": issued + 3600,
}, _SECRET, algorithm="HS256")
```

Почта и скидочный код теперь берутся из серверного профиля по `sub`, а сам `sub`
читается из токена только после проверки подписи. ASVS формулирует запрет прямо:
требование v5.0-3.1.1 говорит, что чувствительные данные в токене сессии не
передаются в форме, доступной клиенту.

Правило проверки: назвать ожидаемый алгоритм и ожидаемые claims.

```python
# Исправлено: алгоритм закрыт списком, срок и получатель сверяются.
claims = jwt.decode(
    token, _SECRET,
    algorithms=["HS256"],          # список закрыт: не из заголовка токена
    audience="api.shop.example",   # иначе чужой получатель пройдёт
    options={"require": ["exp"]},  # иначе токен без срока живёт вечно
)
```

**Где это не работает.** Если содержимое действительно нужно скрыть от
предъявителя, одной подписи мало по определению: нужен зашифрованный токен (JWE)
или отказ от передачи данных в токене вовсе. Список claims для проверки задаёт
не библиотека, а протокол приложения: для однопользовательской системы `aud` и
`iss` могут быть избыточны, для федерации — обязательны.

**Что добавляется поверх.** Секрет подписи HS256 обязан быть случайным и
длинным: cheat sheet требует не меньше 256 бит энтропии для `HS256`, и пароль
секретом быть не может. Устройство отзыва и сроков — тема `token-lifetime-revocation`. Отдельный вопрос
— где хранить сам токен на клиенте: место хранения решает, кто до него дотянется,
и разбирается в теме про сессии и токены.

## 7. Как проверить фикс

Ретест повторяет опыты эксплойта и добавляет то, что обязано работать.

```text
$ LAB_TARGET=solution.py python hack.py
  опыт 1 — discount_code из нагрузки без ключа: нет в токене
  опыт 2 — email из нагрузки без ключа: нет в токене
  опыт 3 — контроль, подмена role=admin с той же подписью: отвергнута
  опыт 4 — контроль, честный вход wiener: роль user
```

Два поля исчезли из нагрузки, целостность как проверялась, так и проверяется,
вход работает. Функциональность закрывается тестами: в лабе их пять — вход
пользователя и администратора, отказ на мусоре, доступность скидки и почты через
сервер. Все пять зелёные и на уязвимом коде, и на решении: тема правит не
поведение кабинета, а состав нагрузки.

## 8. Как ловится автоматикой

Правило написано на выдачу: конфиденциальное имя поля в нагрузке `jwt.encode`.

```yaml
patterns:
  - pattern-either:
      - pattern: 'jwt.encode({..., "email": $V, ...}, ...)'
      - pattern: 'jwt.encode({..., "ssn": $V, ...}, ...)'
      - pattern: 'jwt.encode({..., "api_key": $V, ...}, ...)'
```

Правило целиком — в `pilot/semgrep/jwt-confidential-claim.yaml`, сверено
прогоном: на уязвимом файле лабы одна находка, на решении — ноль, на трёх
размеченных тест-кейсах расхождений нет.

**Чего это правило не ищет.** Оно судит о конфиденциальности по имени поля. Поле
`internal_tier` или `contract_ref` оно пропустит: имя ему ничего не говорит.
Обратная сторона — ложные срабатывания: поле с именем `address`, хранящее
почтовый индекс города доставки, а не домашний адрес, оно пометит зря.

**Что правило пропустит.** Нагрузку, собранную по частям в переменную и потом
переданную в `encode`: правило смотрит на литерал в самом вызове. И вторую
половину темы — доверие токену без проверки подписи — оно не ловит: `decode` с
отключённой проверкой выглядит как обычный вызов.

**Что здесь сильнее автоматики.** Список полей нагрузки достаётся из одного места
выдачи токена и читается глазами за минуту; решение, какое поле закрытое, — тоже
человеческое. Правило годится как сеть на известные имена, а не как ответ.

## 9. Ловушка

Часто слышно: раз токен подписан, данные в нём защищены, и класть туда можно что
угодно. Подпись же криптографическая.

**Подпись подтверждает целостность, а не скрывает содержимое.** Это разные
операции, и путать их дорого. Нагрузка подписанного токена — открытый текст в
base64url: её читает любой предъявитель без ключа. Стенд достаёт из неё
скидочный код и почту, не зная секрета. Подпись при этом честная — подменить
поле нельзя, но прочитать можно всё.

Заблуждение держится на виде токена. Строка base64url выглядит как
шифртекст — набор букв без смысла, — и глаз принимает непонятное за закрытое. Но
непонятное человеку не значит закрытое для машины: одна операция декодирования
возвращает исходный JSON. Проверить это стоит руками хоть раз, чтобы вид токена
перестал обманывать.

Контрпример из прогона — опыт 3 против опытов 1 и 2. В опыте 3 подмена роли
отвергнута: целостность работает. В опытах 1 и 2 те же данные утекают: скрытности
нет. Один токен, одна подпись — и оба исхода сразу.

## 10. Чеклист ревью

1. Verify that в нагрузке выданного токена нет секретов, персональных данных и
   внутренних кодов (ASVS v5.0-3.1.1).
2. Verify that подпись каждого входящего токена проверяется, а не только
   декодируется.
3. Verify that ожидаемый алгоритм задан списком на стороне проверки, а не берётся
   из заголовка токена.
4. Verify that срок `exp` присутствует и требуется при проверке, иначе токен
   живёт бессрочно.
5. Verify that получатель `aud` и издатель `iss` сверяются, когда токен ходит
   между несколькими сторонами.
6. Verify that секрет HS256 случаен, не короче размера выхода алгоритма и не
   задан паролем.
7. Verify that отключение проверки подписи применяется только для чтения заведомо
   ненадёжного токена, а не для решения о правах.

## 12. Проверь себя

1. Из каких трёх частей состоит JWT и какие из них читаются без ключа?
2. Что защищает подпись токена и что она не защищает?
3. Чем подписанный токен (JWS) отличается от зашифрованного (JWE)?
4. Почему успешной проверки подписи мало, чтобы принять токен?
5. Возврат к теме `sessions-vs-tokens`: чем самодостаточный токен отличается от
   ссылочного и какой ценой даётся отказ от серверного хранилища?
6. Тема `hmac-vs-signature` разбирает разницу подписи и шифрования. Почему
   секрет HS256
   нельзя задавать паролем?

<details>
<summary>Ответы</summary>

1. Заголовок, нагрузка и подпись. Первые две — base64url поверх JSON, читаются
   без ключа; третья — двоичная подпись первых двух.
2. Защищает целостность: подмену заголовка или нагрузки видно по несошедшейся
   подписи. Не защищает конфиденциальность: содержимое читается без ключа.
3. JWS подписан — содержимое открыто, подпись подтверждает целостность. JWE
   зашифрован — содержимое закрыто от предъявителя.
4. Подпись говорит «выдали мы и не меняли», но не «токен ещё годен» и «выдан для
   нас». Срок, получателя и издателя проверяют отдельно, и часть по умолчанию
   молчит, пока приложение не назвало ожидаемое.
5. Самодостаточный токен несёт утверждения в себе, и сервер о сессии ничего не
   хранит. Цена — отзыв: до истечения срока нужен список завершённых токенов,
   отказ от старых или ротация ключа.
6. Секрет HS256 — вход HMAC; пароль слаб по энтропии и подбирается офлайн по
   перехваченному токену. Нужен случайный секрет не короче размера выхода.

</details>

1. RFC 7519, «JSON Web Token (JWT)»; реестр `rfc7519-jwt`. Разделы: 3 JWT
   Overview, 4.1 Registered Claim Names, 5 JOSE Header, 6 Unsecured JWTs, 7.2
   Validating a JWT, 11.1 Trust Decisions.
   <https://www.rfc-editor.org/rfc/rfc7519.html>
2. OWASP JSON Web Token Cheat Sheet; реестр `owasp-cs-jwt`. Разделы: Token
   Structure, Considerations about using JWTs, Public-key Signatures vs. MAC,
   Header fields, Claims.
   <https://cheatsheetseries.owasp.org/cheatsheets/JSON_Web_Token_Cheat_Sheet.html>
3. RFC 8725, «JSON Web Token Best Current Practices»; реестр `rfc8725-jwt-bcp`.
   Разделы: 3.1 Perform Algorithm Verification, 3.2 Use Appropriate Algorithms,
   3.5 Ensure Cryptographic Keys Have Sufficient Entropy.
   <https://www.rfc-editor.org/rfc/rfc8725.html>

Каркас этапа: `owasp-asvs-5-document` (ASVS v5.0.0), `owasp-wstg-42`,
`owasp-top10-2025`. Наследуются всеми темами и отдельной строкой не
повторяются.

**Скоропортящийся слой.** Список рекомендованных и не рекомендованных алгоритмов
из cheat sheet меняется вместе с криптографической практикой: `RS256` уже помечен
как не рекомендованный, семейство постквантовых подписей добавлено черновиком.
Поведение конкретной библиотеки по умолчанию тоже привязано к её версии.

**Маркеры уверенности.** Разбор токена, чтение нагрузки без ключа, поведение
проверки claims по умолчанию и утечка полей из лабы — **проверено лично**
2026-08-24 на PyJWT 2.13.0 и Python 3.14.7 (стенды `e01-anatomy.py`,
`e04-claims.py` и `hack.py` лабы): нагрузка декодируется без ключа; подмена роли
при неизменной подписи отклоняется; токен без `exp` проходит, пока поле не
затребовано; чужой `aud` и `iss` проходят, пока ожидаемое не объявлено; правило
SAST даёт одну находку на уязвимом файле и ноль на решении; пять тестов
функциональности зелёные в обоих случаях. Состав частей, зарегистрированные
claims, шаги проверки и требование о доверии — **по документации** (RFC 7519,
открыт лично 2026-08-24). Разница JWS и JWE, семейства алгоритмов и требование к
энтропии секрета — **по документации** (JSON Web Token Cheat Sheet и RFC 8725,
открыты лично 2026-08-24). Поведение Node-стека **не воспроизводилось**: листинг
показывает форму дефекта, а не прогон.
