# SQL-инъекции: классические и UNION-based

Уровень **L1** · время 90 мин (теория 40 / лаба 35 / самопроверка 15,
оценка)

Что прочитать сначала: `http-basics`, `app-architecture`.

Слепой случай, обход фильтров и защита разобраны отдельными темами
подраздела. Здесь — механизм в чистом виде и четыре приёма, которыми им
пользуются, когда ответ виден в выдаче.

## 0. Коротко

SQL-инъекция — дефект, при котором присланные данные меняют не результат
запроса, а сам запрос. Приложение собирает текст команды SQL склейкой строк, и
кавычка внутри данных закрывает строковый литерал раньше времени. Дальше
атакующий дописывает своё: срезает условие, добавляет всегда истинную проверку,
подклеивает через `UNION` чтение чужой таблицы. Опасно это тем, что база
исполняет присланное как код: результат — вход без пароля, выдача скрытых
записей, чтение всей базы. Чинится тем, что текст запроса едет постоянной
строкой, а данные — отдельными связанными параметрами.

**Зачем это в работе AppSec-инженера.** Инъекция стоит пятым пунктом в
OWASP Top 10:2025, а SQL держит больше 14 тысяч записей CVE — это самый
проверяемый класс дефектов. В ревью SQL-инъекция ищется одним вопросом к
каждому запросу: собран ли его текст из данных. Вопрос задаётся поиску по
каталогу, форме входа, фильтру отчётов, сортировке и любому месту, где значение
из запроса попадает в строку запроса SQL.

## 2. Предвопросы

Попробуйте ответить до чтения — даже если ответ окажется неверным, дальше он
будет с чем сравнить.

1. Форма входа проверяет имя и пароль одним запросом к таблице пользователей.
   Что произойдёт, если в поле имени прислать кавычку?
2. Поиск по каталогу возвращает только выпущенные товары. Откуда база знает,

3. Запрос возвращает две колонки. Почему это важно тому, кто хочет прочитать
   через него чужую таблицу?

## 3. Механика

**Откуда это взялось.** Реляционная база принимает не структуры данных, а
текст на языке SQL: строка разбирается в дерево команды и исполняется. Пока
запросы писали руками, один язык покрывал и выборку, и изменение схемы. Затем
запросы стали собираться в приложении, и в них потребовалось подставлять данные
пользователя: имя для входа, категорию для поиска. Короткий способ подстановки —
склеить строку. С этого момента данные и код поехали в базу одной строкой, и
граница между ними осталась только в голове автора. Драйверы получили отдельный
механизм подстановки — связанные параметры, — но склейка никуда не делась,
потому что работает и выглядит короче.

Определение короткое. Инъекция, по описанию OWASP, — это когда недоверенные
данные попадают в интерпретатор и тот исполняет их часть как команды.
Интерпретатор здесь — база, команды — SQL.

### Разбор по общей рамке

Разбор дефекта в гайдбуке идёт по одному набору подцелей, и SQL-инъекция
раскладывается по нему без остатка.

**Источник** — значение в запросе: параметр строки запроса, поле формы, поле
JSON, значение заголовка. **Путь** — код, который вставляет это значение в
текст запроса SQL. **Sink** — вызов, отправляющий текст в базу:
`cursor.execute`, `Statement.executeQuery`, `db.query`. **Отсутствующий
контроль** — разделение кода и данных: текст запроса должен быть постоянным, а
данные — приезжать связанными параметрами. Когда контроля нет, кавычка в данных
меняет структуру команды.

### Что видит база

Возьмём поиск товаров по категории. Приложение строит запрос склейкой:

```sql
SELECT name, price FROM products
WHERE category = '<CATEGORY>' AND released = 1
```

Слово `<CATEGORY>` — место, куда подставляется присланное. При честном значении
`Gifts` запрос ищет выпущенные подарки. При значении `Gifts'--` строка
превращается в другую команду:

```sql
SELECT name, price FROM products
WHERE category = 'Gifts'-- ' AND released = 1
```

Кавычка закрыла литерал категории, а `--` открыл комментарий: всё до конца
строки база пропускает. Условие `released = 1` исчезло из запроса, и в выдачу
попали товары, снятые с витрины. Присланное не изменило результат — оно
изменило команду.

### Один класс, разные интерпретаторы

SQL-инъекция — частный случай общего дефекта. OWASP держит инъекцию одной
категорией, потому что механизм у всех её форм один: недоверенные данные
попадают в интерпретатор, и тот исполняет их часть как команды. Меняется только
интерпретатор.

- База читает SQL — это SQL-инъекция.
- Оболочка операционной системы читает командную строку — это инъекция команд
  ОС, тема `os-command-injection`.
- Браузер читает HTML и JavaScript — это XSS, подраздел 1.4.
- Документная база читает оператор запроса — это NoSQL-инъекция, тема
  `nosql-injection`.

Отсюда общий вывод, который переносится на все формы: чинит инъекцию не
чистка данных, а разделение кода и данных на входе в интерпретатор. У SQL это
связанные параметры, у оболочки — вызов без строки команды, у браузера —
контекстное экранирование. Разные средства, одно правило: интерпретатор не
должен получать код и данные одной строкой.

**Не путать с утечкой прав.** Инъекция даёт исполнение чужой команды, а не
доступ к своему объекту по чужому идентификатору. Второе — тема `idor`: там
запрос корректен, а неверна проверка прав. При инъекции неверен сам запрос.

### Три круга приёмов

Классических приёмов с видимой выдачей три, и они идут по нарастанию.

**Срез условия.** Комментарий `--` (или `#` в MySQL) отсекает хвост запроса.
Так снимается вторая половина условия: проверка выпуска в поиске, проверка
пароля во входе. Имя `administrator'--` в форме входа закрывает литерал имени и
срезает проверку пароля — база возвращает администратора без пароля.

**Тавтология.** Вместо среза дописывается условие, истинное всегда:
`' OR '1'='1`. Запрос `WHERE category = 'no-such' OR '1'='1'` возвращает все
строки таблицы, потому что второе условие выполнено для каждой. Тем же приёмом
обходят фильтры выборки: доступ к чужим строкам открывается там, где условие
ограничивало выдачу владельцем.

**UNION.** Оператор `UNION` подклеивает к выдаче результат второго запроса
`SELECT`. Так из запроса о товарах читается таблица пользователей — при двух
условиях, разобранных ниже. Это переход от «сломать своё условие» к «прочитать
чужие данные».

### UNION: два условия

`UNION` объединяет две выборки в одну, и Web Security Academy называет два
требования к этому.

1. Оба запроса возвращают одинаковое число колонок.
2. Типы колонок попарно совместимы.

Число колонок узнают до чтения. Первый способ — `ORDER BY` с растущим номером:
`' ORDER BY 1--`, `' ORDER BY 2--` и так, пока база не ответит ошибкой о
номере вне диапазона. Последний принятый номер — число колонок. Второй способ —
подстановка `NULL`: `' UNION SELECT NULL--`, затем `NULL,NULL` и дальше, пока
число не совпадёт и ошибка не исчезнет. `NULL` подходит к любому типу, поэтому
проверяет только число.

Дальше в подходящую по типу колонку ставят нужные данные:

```sql
' UNION SELECT username, password FROM users--
```

Выдача о товарах теперь несёт имена и пароли. На Oracle у каждого `SELECT`
обязан быть источник, поэтому туда добавляют встроенную таблицу: `FROM dual`.

### Где в запросе встречается вставка

Место входа не сводится к условию `WHERE`, хотя оно самое частое. Web Security
Academy перечисляет пять мест, и у каждого своя механика.

- `WHERE` в `SELECT` — выбор строк, разобранный выше.
- Значения в `UPDATE` и условие `WHERE` в нём — правка чужих строк.
- Значения в `INSERT` — вставка своих данных в команду вставки.
- Имя таблицы или колонки в `SELECT` — их нельзя параметризовать, и это
  опасное место по построению.
- Выражение в `ORDER BY` — сортировка, тоже не параметризуемая.

Последние два важны для починки. Заполнитель `?` подставляет значение, но не
имя объекта и не порядок сортировки. Значит, там, где в запрос попадает имя
колонки или направление сортировки, параметр не спасает и нужна сверка со
списком разрешённого. Тема `parameterized-queries` разбирает эти случаи
отдельно, потому что типовая ошибка — считать, что параметры закрывают весь
запрос.

### Что ещё достаёт атакующий

Видимая выдача открывает не только чужие таблицы. Через `UNION` читают
устройство самой базы: список таблиц и колонок лежит в `information_schema`, а
версию СУБД отдаёт свой запрос на каждом движке — на Oracle это
`SELECT * FROM v$version`. Зная версию и схему, атакующий переходит от догадок
к точным запросам.

Отдельно стоит инъекция второго порядка. Присланное сохраняется без вреда — имя
пользователя с кавычкой легло в таблицу без вреда. Позже другой код достаёт его
значение и вставляет в запрос склейкой, и тогда оно срабатывает. Опасен не тот
запрос, что принял данные, а тот, что позже собрал из них команду. Поэтому в
ревью проверяются оба конца: и место, где данные входят, и место, где они потом
идут в запрос.

## 4. Эксплуатация

Стенд — лаба этой темы (`pilot/lab/sqli-basics`). Витрина каталога ищет товары
и пускает в кабинет. База — SQLite в памяти, оба запроса собраны склейкой,
сокет и HTTP не поднимаются.

Шаг первый — найти место вставки. Признак — ответ меняется от кавычки: запрос
либо ломается ошибкой, либо возвращает не то. Пустая одиночная кавычка `'` —
первая проба: она либо даёт ошибку синтаксиса, либо меняет выдачу.

Шаг второй — снять условие и прочитать чужое.

```text
$ python3 hack.py
  опыт 1 — вход как administrator'-- : РОЛЬ ADMIN БЕЗ ПАРОЛЯ
  опыт 2 — Gifts'-- показывает невыпущенное: ДА, 3 строк
  опыт 3 — OR '1'='1 отдаёт весь каталог: ДА, 3 строк
  опыт 4 — UNION вытягивает пароль admin: ДА, пароль s3cr3t-9f2a
  опыт 5 — контроль, поиск Gifts: работает
  опыт 6 — контроль, вход wiener: работает
```

Опыт 1 — срез условия во входе. Комментарий убрал проверку пароля, и база
вернула первую строку с именем `administrator`.

Опыт 2 — срез условия в поиске. Пропал `released = 1`, и снятый с витрины товар
попал в выдачу.

Опыт 3 — тавтология. `OR '1'='1` сделал условие категории истинным для каждой
строки.

Опыт 4 — UNION. Второй `SELECT` прочитал таблицу `users`, и пароль
администратора приехал в списке товаров.

Опыты 5 и 6 — контроль: обычный поиск и честный вход обязаны работать и после
починки. Без них исправление сведётся к запрету кавычек, и это выяснится на
приёмке.

Шаг третий — оценить добычу. Вход администратором — повышение прав. Выдача
скрытых товаров — утечка. Чтение таблицы паролей через UNION — компрометация
всех учётных записей. Отсюда пятое место инъекции в Top 10:2025: одним дефектом
берётся вся база.

## 5. Как выглядит в коде

Ревьюер ищет пару: текст запроса SQL, собранный из строк, и данные запроса в
этой сборке.

```python
# УЯЗВИМО — демонстрация, не для продакшена.
def search_products(category):
    query = (
        "SELECT name, price FROM products "
        "WHERE category = '" + category + "' AND released = 1"  # (1)
    )
    cur.execute(query)                                          # (2)
    return cur.fetchall()
```

1. Значение `category` склеено в текст запроса между кавычек. Кавычка внутри
   значения закроет литерал и начнёт команду.
2. Сток: готовая строка уходит в базу одним аргументом. Разделить код и данные
   здесь уже нельзя — они одна строка.

Признаки, по которым это находится глазами: оператор `+`, f-строка, `%` или
`.format()` вокруг текста запроса; имя переменной с данными запроса внутри этой
сборки; вызов `execute` с одним аргументом-строкой.

**Ложное срабатывание.** Склейка постоянных строк без данных — перенос длинного
запроса на несколько литералов подряд. `"SELECT ... " "WHERE ... "` — это один
литерал, данных в нём нет, дефекта тоже.

## 6. Как чинится

Правило одно: текст запроса — постоянная строка, данные — связанные параметры.
База разбирает структуру команды до того, как увидит данные, и данные структуру
уже не меняют.

```python
# Исправлено.
def search_products(category):
    cur.execute(
        "SELECT name, price FROM products "
        "WHERE category = ? AND released = 1",   # (1)
        (category,))                             # (2)
    return cur.fetchall()
```

1. В тексте запроса на месте данных стоит заполнитель `?`. Текст постоянный.
2. Значение едет вторым аргументом. Кавычка в нём — часть данных, а не команды.

Тот же приём на другом стеке. Java-код с `PreparedStatement`:

```java
// Исправлено.
PreparedStatement ps = conn.prepareStatement(
    "SELECT name, price FROM products WHERE category = ? AND released = 1");
ps.setString(1, category);   // (1)
ResultSet rs = ps.executeQuery();
```

1. Текст запроса задан один раз с заполнителем, значение связывается отдельно.
   Инвариант тот же, что в Python: постоянный текст плюс связанный параметр.
   Меняется синтаксис, не механизм.

**Границы применимости.** Параметризуются данные, но не структура запроса. Имя
таблицы, имя колонки и направление сортировки `ASC`/`DESC` заполнителем не
подставляются — они часть команды, а не значение. Cheat sheet называет это
прямо: там, где параметр невозможен, нужна проверка по списку разрешённого или
переделка запроса. Разбор этих случаев — тема `parameterized-queries`.

Побочная выгода параметров важнее, чем кажется: запрос на параметрах правильно
обрабатывает данные с кавычкой. Имя `O'Brien` ломает склейку и работает через
параметр, потому что кавычка едет как данные. Починка от инъекции чинит заодно
и обычную ошибку с апострофом.

**Почему параметр надёжен.** База получает текст запроса и данные раздельно.
Сначала она разбирает текст в дерево команды и планирует выполнение — на этом
шаге данных ещё нет. Затем на места заполнителей подставляются значения уже
готового дерева. Значение не может стать новым узлом дерева: структуру
определил постоянный текст. Кавычка, `--` или `UNION` внутри значения остаются
данными, потому что решение о структуре принято до того, как их прочитали.
Экранирование пытается сделать то же на уровне символов и потому хрупко;
параметр делает это на уровне разбора и потому надёжен.

**Что добавляется поверх.** Параметры закрывают дефект, остальное ограничивает
цену промаха. Cheat sheet называет две дополнительные меры. Первая — наименьшие
права: учётная запись базы, от которой идёт запрос, не должна иметь
административного доступа, тогда даже сработавшая инъекция достанет меньше.
Вторая — проверка по списку разрешённого как второй рубеж перед запросом, для
случаев, где параметр невозможен. Отдельно: текст ошибки базы не уходит в ответ
пользователю, иначе он подсказывает атакующему структуру запроса и ускоряет
подбор.

## 7. Как проверить фикс

Ретест повторяет четыре приёма и добавляет то, что обязано работать.

```text
$ LAB_TARGET=solution.py python3 hack.py
  опыт 1 — вход как administrator'-- : отвергнут
  опыт 2 — Gifts'-- показывает невыпущенное: нет
  опыт 3 — OR '1'='1 отдаёт весь каталог: нет
  опыт 4 — UNION вытягивает пароль admin: нет
  опыт 5 — контроль, поиск Gifts: работает
  опыт 6 — контроль, вход wiener: работает
```

Четыре отказа и два рабочих контроля. Отказ на пятом или шестом опыте означал
бы, что витрина сломалась, и приёмку такая починка не проходит.

Регресс закрывается тестами функциональности. В лабе их девять, и проверяют они
сохранность работы: обе категории, неизвестную категорию, оба входа, неверный
пароль. Отдельно стоит проверить два негативных случая. Первый: неизвестная
категория и снятое условие дают разную выдачу, иначе тавтология останется
незамеченной. Второй: честное значение с кавычкой (`O'Brien`) проходит, а не
роняет запрос.

Отдельный тест на регресс — тот, что ловит возврат склейки. Он пишется не
тестом, а правилом из блока 8 и потому работает на каждом коммите.

## 8. Как ловится автоматикой

У дефекта есть источник (данные), сток (`execute`) и очищающий приём
(параметризация), поэтому он ложится на анализ помеченных данных. Правило
написано в режиме `taint` и отвечает на один вопрос: доходит ли до `execute`
строка, собранная склейкой, f-строкой, `%` или `.format()`.

```yaml
mode: taint
pattern-sources:
  - pattern: f"...{$X}..."
  - pattern: $A + $B
  - pattern: $S % $X
  - pattern: $S.format(...)
pattern-sinks:
  - patterns:
      - pattern: $CUR.execute($Q, ...)
      - focus-metavariable: $Q
```

Правило целиком лежит в `pilot/semgrep/sql-query-string-built.yaml` и сверено
прогоном: на уязвимом файле лабы две находки, на решении — ноль, на восьми
размеченных тест-кейсах расхождений нет.

**Что правило пропустит.** Запрос, собранный процентным форматированием в
логгере и оттуда попавший в базу иным путём. Текст запроса, пришедший из другой
функции или из константы модуля, если склейка была вне анализируемого тела.
Запрос через ORM, где инъекция прячется в «сыром» фрагменте, — это отдельный
разбор в теме `parameterized-queries`.

**Какой шум даст.** Всякую склейку строк, уходящую в функцию с именем `execute`,
даже когда это не база: правило видит форму вызова, а не смысл. На корпусе с
собственной обёрткой над базой список стоков дополняется её именем — это правка
одной строки.

Отдельно стоит сказать, чего от статического анализа ждать не стоит. Он не
скажет, опасны ли данные на самом деле: пришли они от пользователя или из
доверенной константы. Он отвечает на форму, а не на происхождение, и поэтому
даёт и пропуски, и шум. Надёжнее сама конструкция: запрос на параметрах нечему
находить.

## 9. Ловушка

Распространённое представление: инъекция закрывается экранированием кавычек.
Достаточно заменить каждую `'` на `''` или отбросить опасные символы, и склейку
можно оставить.

**Экранирование чинит один символ, а инъекция живёт не только в нём.**
Cheat sheet называет экранирование ненадёжной крайней мерой: оно зависит от
СУБД и ломается на мелочи. Числовой параметр без кавычек экранировать нечего —
`OR 1=1` вставляется прямо. Многобайтные кодировки дают последовательности, где
экранирующий обратный слэш склеивается с соседним байтом. Обход фильтров —
предмет отдельной темы, и он показывает, что чёрный список проигрывает всегда.

Контрпример. Фильтр удаляет одиночные кавычки из всех полей. Поиск по числовому
идентификатору `id=1 OR 1=1` кавычки не содержит вовсе и проходит фильтр
целиком: условие становится истинным для всех строк. Экранирование кавычек не
сработало, потому что кавычек тут и не было. Тот же разрыв виден и с текстовым
полем: многобайтная кодировка склеивает экранирующий слэш с чужим байтом, и
кавычка проходит фильтр целой.

## 10. Чеклист ревью

1. Verify that текст запроса SQL — постоянная строка, а данные передаются
   связанными параметрами (ASVS v5.0-1.2.4).
2. Verify that вокруг текста запроса нет склейки, f-строки, `%` или `.format()`
   с данными из запроса.
3. Verify that имена таблиц и колонок и направление сортировки не берутся из
   присланных данных, а сверяются со списком разрешённого.
4. Verify that запрос через ORM не содержит «сырого» фрагмента, собранного из
   данных.
5. Verify that данные проверяются на сервере, а не только в браузере
   (WSTG-v42-INPV-05).
6. Verify that учётная запись базы, от которой идёт запрос, имеет только нужные
   права, а не административные.
7. Verify that сообщение об ошибке базы не уходит в ответ пользователю.

## 12. Проверь себя

1. Почему кавычка в присланном значении меняет не результат запроса, а сам
   запрос?
2. Что делает `--` в конце присланного значения и зачем это атакующему?
3. Чем тавтология `OR '1'='1` отличается по действию от среза условия
   комментарием?
4. Какие два условия должен выполнить запрос, чтобы через `UNION` прочитать
   другую таблицу?
5. Почему экранирование кавычек не закрывает инъекцию в числовом параметре?
6. Возврат к теме `app-architecture`: на каком узле исполняется запрос SQL и
   почему компрометация базы задевает всех пользователей сразу?

<details>
<summary>Ответы</summary>

1. Данные и текст запроса склеены в одну строку. Кавычка закрывает строковый
   литерал, и то, что стоит дальше, база читает как продолжение команды.
2. `--` открывает комментарий: остаток запроса база пропускает. Так срезается
   вторая половина условия — проверка пароля или проверка выпуска.
3. Срез убирает часть запроса, тавтология добавляет истинное условие. Первое
   снимает ограничение, второе делает выборку полной независимо от исходного
   условия.
4. Одинаковое число колонок в обоих запросах и совместимые типы в
   соответствующих колонках. Число узнают через `ORDER BY` или подстановку
   `NULL`.
5. В числовом параметре кавычек нет: `OR 1=1` вставляется без них. Экранирование
   правит один символ, а условие можно дописать и без него.
6. Запрос исполняется на сервере базы, общем для всех пользователей приложения.
   Чтение таблицы пользователей через один запрос отдаёт учётные данные всех
   сразу.

</details>
