# Загрязнение прототипа

Уровень **L2** · время 30 мин (теория 18 / задача 7 / самопроверка 5,
оценка)

Что прочитать сначала: `xss-dom`.

Рамка «источник — сток» разобрана в `xss-dom`. Здесь между ними появляется
третья часть, без которой цепочка не складывается, — гаджет.

## 0. Коротко

Загрязнение прототипа — запись присланного значения в прототип встроенного
объекта JavaScript. Объект, у которого своего такого свойства нет, наследует
записанное, и потому одна запись действует сразу во всём коде страницы.

Ключ, которым это делается, — `__proto__`: язык понимает его как обращение к
прототипу, а разборщики строки запроса и JSON видят в нём обычную строку.
Слияние двух объектов, идущее вглубь и не проверяющее ключи, переносит
присланное в прототип.

Сама запись почти всегда безвредна. Опасной её делает **гаджет** — место, где
код читает свойство и делает из него что-то опасное. Академия PortSwigger
разбирает цепочку тремя частями: источник, гаджет, сток. На клиенте исход
обычно XSS в DOM, на сервере — выполнение кода; серверная половина разбирается
на этапе 7.

Отдельно стоит сказать про номер каталога. Загрязнение прототипа — это
CWE-1321, и в издании OWASP 2025 года эта слабость не сопоставлена ни одной из
десяти категорий: её нет ни в одном списке. Поле категории у темы поэтому
пустое, а не заполнено по догадке.

**Зачем это в работе AppSec-инженера.** Дефект живёт на стыке двух ревью:
источник обычно в приложении, а гаджет — в чужой библиотеке, и порознь оба
места читаются как безопасные. Ревьюеру нужен признак, который виден в своём
коде: рекурсивное слияние объектов без проверки ключей и объектные словари там,
где нужен словарь. ASVS формулирует это требованием v5.0-15.3.6 — писать код
так, чтобы загрязнение прототипа было невозможным.

## 1. Цели

После этого раздела вы сможете:

1. Объяснить, как ключ `__proto__` при слиянии попадает в прототип.
2. Назвать три части цепочки: источник, гаджет, сток.
3. Узнать в коде рекурсивное слияние без проверки ключей.
4. Выбрать структуру данных, у которой этой связи нет.

## 3. Механика

**Откуда это взялось.** Наследование в JavaScript устроено ссылкой: у объекта
есть прототип, и свойство, которого нет у самого объекта, ищется в нём. Ссылка
эта долго была доступна под именем `__proto__` — как расширение, потом как
часть стандарта ради совместимости. Одновременно объект стал типовым способом
передавать настройки, а слияние настроек с умолчаниями — типовой операцией. Две
эти привычки встретились, и получилось, что имя, которое язык понимает
особым образом, приезжает в слияние обычной строкой из запроса.

### Как ключ доезжает до прототипа

Академия описывает механизм точно. Слияние, идущее вглубь, рано или поздно
выполняет присваивание вида `цель.__proto__.свойство = значение`. В этот момент
язык понимает `__proto__` не как имя свойства, а как обращение к прототипу — и
значение ложится в прототип, а не в объект.

Разница между двумя способами получить такой ключ проверена прогоном. В записи
объекта литералом ключ `__proto__` собственным свойством не становится. В
объекте, полученном разбором строки JSON, — становится: проверка
`hasOwnProperty('__proto__')` даёт истину. Разборщик JSON видит обычную строку,
и потому строка JSON — рабочий источник.

Проверено прогоном и следствие. Присланная строка JSON несёт ключ `__proto__`
с двумя свойствами внутри. После слияния оба читаются у нового пустого
объекта, и то же значение видно у пустого массива. Запись одна, действует везде.

### Три части цепочки

**Источник** — вход, позволяющий добавить свойство в прототип. Академия
называет три: строка запроса или фрагмент адреса, вход в виде JSON, сообщение
между окнами.

**Гаджет** — свойство, которое приложение или его библиотека читает и передаёт
дальше без проверки. Ключевое условие: у объекта не должно быть своего такого
свойства, иначе своё побеждает наследованное.

**Sink** — место, дающее исполнение: те же стоки, что в `xss-dom`.

Типовой гаджет — значение по умолчанию. Академия показывает его одной строкой:
`config.transport_url || defaults.transport_url`. Пока свойства нет ни у
объекта настроек, ни в прототипе, берётся умолчание. После загрязнения берётся
подставленное. Дальше это значение попадает в адрес загружаемого скрипта — и
цепочка замкнулась.

Проверено прогоном: после загрязнения выражение `opts.polluted || 'default'`
на пустом объекте `opts` возвращает подставленное значение вместо умолчания.
Гаджет сработал.

### Почему это трудно заметить

Три части лежат в трёх разных местах. Источник — в своём коде, в функции
слияния настроек. Гаджет — чаще всего в чужой библиотеке, где он написан как
обычное умолчание. Сток — там же или в браузерном интерфейсе.

Ни одно из трёх мест по отдельности дефектом не выглядит. Слияние объектов —
обычная операция. Умолчание через `||` — обычная идиома. Присваивание адреса
скрипту — обычная работа загрузчика. Академия отмечает и мотив: разработчик,
не знающий про этот класс, считает такие свойства неуправляемыми снаружи и
потому не проверяет их вовсе.

## 5. Как выглядит в коде

Ревьюер ищет слияние, идущее вглубь и не проверяющее ключи.

```javascript
// УЯЗВИМО — демонстрация, не для продакшена.
function merge(dst, src) {
  for (const key in src) {                                    // (1)
    if (typeof src[key] === 'object' && src[key] !== null) {
      dst[key] = dst[key] || {};
      merge(dst[key], src[key]);                              // (2)
    } else {
      dst[key] = src[key];
    }
  }
  return dst;
}

const settings = merge({}, JSON.parse(await res.text()));     // (3)
```

1. Ключи берутся из присланного объекта как есть. Проверки на `__proto__` и
   `constructor` нет.
2. Рекурсия: на глубине и происходит присваивание в прототип.
3. Источник: объект получен разбором строки JSON, и ключ `__proto__` в нём —
   собственное свойство.

Признаки в коде: цикл `for ... in` по присланному объекту; рекурсивный вызов
слияния; функция с именем `merge`, `extend`, `deepAssign`, `setValue`. Второй
признак — объект-словарь, ключи которого приходят снаружи: `counts[name] += 1`
на обычном объекте.

## 6. Как чинится

Правило одно: структура, у которой нет связи с прототипом, либо проверка
ключей на входе.

```javascript
// Исправлено.
const counts = new Map();                       // (1)
counts.set(name, (counts.get(name) ?? 0) + 1);

const settings = Object.create(null);           // (2)
merge(settings, safeKeys(JSON.parse(body)));

const BANNED = new Set(['__proto__', 'constructor', 'prototype']);
function safeKeys(obj) {                        // (3)
  for (const key of Object.keys(obj)) if (BANNED.has(key)) delete obj[key];
  return obj;
}
```

1. Словарь по ключам от пользователя — `Map`, а не объект. Cheat sheet ставит
   это первой мерой. Проверено прогоном: после загрязнения прототипа проверка
   `new Map().has('polluted')` даёт ложь.
2. Объект без прототипа: `Object.create(null)`. Проверено прогоном: у такого
   объекта загрязнённое свойство не читается.
3. Отсев ключей — как второй рубеж, а не как основная мера: он перечисляет
   запрещённое, и потому его слабое место то же, что у любого чёрного списка.

**Границы применимости.** Cheat sheet называет и тяжёлую меру — заморозку
прототипа через `Object.freeze`. Тут же оговаривается её цена: приложение
ломается, если какая-нибудь из его библиотек правит встроенные прототипы. Там
же сказано, что удаление `__proto__` (в Node.js это флаг запуска) закрывает не
всё: тот же результат достигается через цепочку `constructor.prototype`.

**Чего починка одного места не даёт.** Убрать источник в своём коде полезно, но
источников три, и один из них — сообщение между окнами. Разбор в теме
`postmessage-vulns`. Убрать гаджет в чужой библиотеке нельзя вовсе — можно
только обновить её или заменить.

## 9. Ловушка

Распространённое представление: загрязнение прототипа — дефект библиотеки
слияния объектов, и починка сводится к обновлению этой библиотеки.

**Дефект складывается из трёх частей, и они в разных местах.** Обновление
библиотеки убирает источник, если он был там. Гаджет от этого никуда не
девается: он живёт в другом коде и сработает от любого другого источника. И
наоборот — приложение с безопасным слиянием остаётся уязвимым, если ключи
попадают в прототип через объектный словарь.

Контрпример из прогонов. Загрязнение сделано один раз строкой JSON. После него
свойство читается у нового пустого объекта, у пустого массива и у объекта
настроек, к которому эта строка отношения не имела. Ни одна из этих трёх точек
чтения не связана с местом записи ни вызовом, ни ссылкой.

## 10. Чеклист ревью

1. Verify that словари, ключи которых приходят снаружи, построены на `Map` или
   на объекте без прототипа, а не на объектном литерале (ASVS v5.0-15.3.6).
2. Verify that рекурсивное слияние объектов отсеивает ключи `__proto__`,
   `constructor` и `prototype`.
3. Verify that объект, полученный разбором строки JSON, не сливается с
   настройками без проверки ключей.
4. Verify that сообщения между окнами и значения из адреса не попадают в
   слияние настроек напрямую.
5. Verify that в коде нет чтения настроек через `||` и `??` там, где значение
   идёт дальше в опасный сток.
6. Verify that библиотеки, принимающие объект настроек, обновляются по
   расписанию: гаджет чаще всего находится в них.

## 11. Задача

Возьмите консоль браузера и проведите три опыта, не трогая чужие системы.
Первый: сравните `({}).hasOwnProperty('__proto__')` и
`JSON.parse('{"__proto__":{}}').hasOwnProperty('__proto__')`. Второй:
присвойте `Object.prototype.mark = 'x'` и прочитайте `mark` у нового пустого
объекта и у пустого массива. Третий: повторите чтение у `Object.create(null)`
и через `new Map()`.

**Критерий выполнения** наблюдаемый: три пары результатов и одно предложение о
том, почему второй опыт объясняет, зачем в третьем нужна другая структура.
Прототип после опытов вернуть: `delete Object.prototype.mark`.

## 12. Проверь себя

1. Почему присваивание вглубь по ключу `__proto__` меняет прототип, а не
   свойство объекта?
2. Чем объект из `JSON.parse` отличается от объекта-литерала по этому ключу?
3. Что такое гаджет и почему без него запись в прототип чаще всего безвредна?
4. Почему `Map` закрывает эту связь, а объектный литерал нет?
5. Возврат к теме `xss-dom`: чем стоки этой темы отличаются от стоков XSS в
   DOM?

<details>
<summary>Ответы</summary>

1. Язык понимает `__proto__` как обращение к прототипу объекта, а не как имя
   свойства. Присваивание по этому пути кладёт значение в прототип.
2. У литерала `__proto__` собственным свойством не становится, у объекта из
   `JSON.parse` — становится: разборщик видит обычную строку.
3. Гаджет — место, где код читает свойство и передаёт его дальше без проверки.
   Без него подставленное свойство никто не читает, и запись ничего не меняет.
4. У `Map` ключи не свойства объекта, и наследование в поиске ключа не
   участвует. У объектного литерала поиск свойства уходит в прототип.
5. Ничем: стоки те же. Разница в пути к ним — значение приходит не из
   источника напрямую, а через свойство, подставленное в прототип.

</details>
