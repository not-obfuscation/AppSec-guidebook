# NoSQL-инъекции: операторы MongoDB

Уровень **L2** · время 30 мин (теория 17 / задача 8 / самопроверка 5,
оценка)

Что прочитать сначала: `sqli-basics`, `rest-and-graphql`.

Вот тело запроса на вход, присланное обычным POST:

```json
{"username": {"$ne": null}, "password": {"$ne": null}}
```

Кавычек в нём нет, склейки нет — запрос к этой базе вообще не строка. И
тем не менее вход проходит без пароля. Приложение ждало от поля строку,
а получило объект, и оператор `$ne` («не равно») стал частью фильтра.
Условие «пароль равен присланному» превратилось в «пароль не равен
null», истинное для каждой записи, — и база вернула первого пользователя.

Это NoSQL-инъекция: данные снова стали командой, только командой здесь
служит структура, а данные дотягиваются до её оператора. Дальше тема
разводит операторную и синтаксическую формы, показывает, как дефект
узнать в коде обработчика, и закрывает его приведением к типу и списком
разрешённых ключей.

Механизм инъекции — источник, путь, сток, отсутствующий контроль — разобран в
`sqli-basics`. Тема показывает ту же причину в документной базе, где команда —
не строка, а объект.

## 0. Коротко

NoSQL-инъекция — тот же дефект, что SQL-инъекция, в базе, которая принимает
запрос не строкой, а структурой. У MongoDB запрос — это объект: поле, значение
и, при желании, оператор вроде `$ne` («не равно») или `$gt` («больше»).
Приложение ждёт от поля строку, а получает объект с оператором — и запрос
меняет смысл. Классический пример: в поле пароля вместо строки приходит
`{"$ne": null}`, условие «пароль равен присланному» превращается в «пароль не
равен null», и вход проходит без пароля. Синтаксическая инъекция тоже
существует, но операторная встречается чаще, потому что не требует ломать
кавычки. Чинится приведением поля к ожидаемому типу и списком разрешённых
ключей.

**Зачем это в работе AppSec-инженера.** MongoDB и подобные базы называют в
требованиях вакансий, а операторная инъекция — типовой дефект API, принимающего
JSON. Ревьюеру важно узнать её в коде: место, где значение из тела запроса
уходит в фильтр напрямую, без проверки, что это строка. Механизм источник-сток
уже знаком по `sqli-basics`; здесь меняется форма команды.

4. Закрыть дефект приведением к ожидаемому типу и списком ключей.

## 3. Механика

**Откуда это взялось.** SQL-инъекция живёт в том, что команда — текст, и данные
склеивают в этот текст. Документные базы ушли от текста: запрос к MongoDB —
структура данных, объект с полями и операторами. Казалось, это закрывает
инъекцию — склеивать нечего. Но API стали принимать от клиента готовые
структуры, JSON, и подставлять их в запрос напрямую. Тогда данные снова
получили доступ к тому, что раньше решал только код: к выбору оператора. Форма
инъекции сменилась, причина осталась.

### Две формы

Web Security Academy делит NoSQL-инъекцию на две.

**Синтаксическая** — как в SQL: сломать разбор запроса. Там, где MongoDB
исполняет выражение (например, оператор `$where` с кодом на JavaScript),
присланное `'||'1'=='1` превращает условие в истинное для всех записей. Это
редкий случай: он требует, чтобы приложение отдавало базе выражение.

**Операторная** — своя для документных баз и потому основная. Кавычки ломать не
нужно: достаточно вместо строки прислать объект с оператором. Приложение
подставляет его в фильтр, и оператор начинает работать как часть запроса.

### Обход входа оператором

Запрос входа сравнивает присланные имя и пароль с записью:

```text
фильтр = { "username": <имя>, "password": <пароль> }
```

Когда `<имя>` и `<пароль>` — строки, фильтр ищет точное совпадение. Атакующий
шлёт в теле JSON не строки, а объекты:

```json
{"username": {"$ne": null}, "password": {"$ne": null}}
```

Проверено на разборе входа: `json.loads` превращает поле `password` в объект
`{'$ne': None}`, тогда как честный вход даёт строку. Фильтр становится «имя не
равно null и пароль не равен null» — истинным для всех, и база возвращает
первого пользователя. Вход пройден без знания пароля.

Тот же приём работает через строку запроса, где тип теряется: `username=wiener`
заменяют на `username[$ne]=invalid`, и разборщик параметров собирает из этого
вложенный объект с оператором. Другие операторы дают больше: `$regex` достаёт
пароль по символу проверками «начинается на a», `$gt` сравнивает по порядку.
Разбор этих приёмов — за пределами L2; здесь важно, что вход — объект вместо
строки. Разбор снова сходится на правиле темы: дефект не в операторе `$ne`, а в
отсутствующей проверке, что присланное — строка. Что в этом разборе сломается,
если завтра базу сменят с MongoDB на другую документную, а обработчик останется
прежним?

## 5. Как выглядит в коде

Ревьюер ищет место, где значение из тела запроса уходит в фильтр без проверки
типа. Отметьте до разбора, в какой строке присланное получает права команды, и
объясните почему.

```python
# УЯЗВИМО — демонстрация, не для продакшена
def login(body):
    user = db.users.find_one({
        "username": body["username"],   # (1)
        "password": body["password"],   # (2)
    })
    return user
```

1. Значение берётся из разобранного JSON как есть. Если клиент прислал объект,
   в фильтр попадёт объект.
2. То же с паролем. `{"$ne": null}` здесь становится оператором фильтра, а не
   строкой пароля.

Признак дефекта — поле фильтра, равное значению из тела запроса, без приведения
к строке и без проверки, что это не объект. Оператор `$where` с присланным
кодом — отдельный, более явный признак.

## 6. Как чинится

Два приёма, оба про то, чтобы данные не стали оператором.

**Привести к ожидаемому типу.** Поле, которое обязано быть строкой, приводится к
строке до запроса. Объект `{"$ne": null}`, приведённый к строке, перестаёт быть
оператором.

```python
# Исправлено.
def login(body):
    username = str(body["username"])   # (1)
    password = str(body["password"])
    user = db.users.find_one({"username": username, "password": password})
    return user
```

1. Приведение к строке снимает операторную инъекцию: в фильтр уходит строка, а
   не объект. Проверять стоит и явно — отвергать значение, если оно не строка,
   чтобы `str({...})` не превратилось в мусорную строку молча.

**Список разрешённых ключей.** Там, где фильтр строится из нескольких полей,
принимаются только известные ключи, а ключи, начинающиеся с `$`, отвергаются.
Cheat sheet называет свои меры: запрет клиентских операторов (`$where`,
`$regex`, `$expr`), запрет символа `$` в ключах и запросы через объекты
драйвера, а не сборку строки. А там, где серверный JavaScript приложению не
нужен, он советует отключить его настройкой самой базы: тогда синтаксическая
форма через `$where` закрыта целиком. Приведение к типу закрывает частый
случай — поле, обязанное быть строкой; запрет операторов и ключей с `$` —
общий.

**Границы применимости.** Приведение к типу закрывает поля с фиксированным
типом. Там, где поле по замыслу принимает структуру (сложный фильтр отчёта),
приведением не обойтись. Нужен разбор присланного в известную форму и сборка
запроса из проверенных частей, как список разрешённого в `parameterized-queries`.
Драйвер MongoDB параметризует значения сам, но только если ему передают
значение, а не объект с оператором.

## 9. Ловушка

Форму входа перевели с SQL на MongoDB, склейки строк в коде больше нет —
инъекция закрыта? Уверенность родилась из смены базы: документная база не собирает
запрос из строки, значит инъекции в ней нет — склеивать нечего.

**Инъекция сменила форму: команда здесь не строка, а структура, и данные
дотягиваются до оператора.** Отсутствие склейки строк убрало синтаксическую
инъекцию, но открыло операторную. Присланный объект вместо строки — тот же
переход «данные стали кодом», только код записан не текстом, а полем `$ne`.

Контрпример. Форма входа перешла с SQL на MongoDB, и разработчик уверен, что
инъекция осталась в прошлом: кавычки в имени больше ничего не ломают. Запрос
`{"username":{"$ne":null},"password":{"$ne":null}}` в теле проходит вход без
пароля. Ни одной кавычки, ни одной склейки — и полный обход аутентификации.

## 10. Чеклист ревью

1. Verify that поля запроса с фиксированным типом приводятся к этому типу до
   запроса, а не берутся из тела как есть (ASVS v5.0-1.2.4).
2. Verify that значение поля отвергается, если это объект там, где ожидается
   строка или число.
3. Verify that ключи фильтра сверяются со списком разрешённых, а ключи с `$` в
   начале отклоняются.
4. Verify that оператор `$where` и серверный JavaScript отключены, если функция
   их не требует.
5. Verify that разбор параметров строки запроса не собирает вложенные объекты
   из записи вида `field[$ne]=...`.

Возьмите обработчик входа на документной базе — свой или `login` из блока 5. Не
атакуя чужую систему, ответьте письменно: какой тип у поля `password` при
честном входе и какой — при запросе `{"$ne": null}`? Что делает с этим объектом
приведение к строке и почему после него оператор перестаёт работать? Какой
второй приём нужен, если поле по замыслу принимает структуру?

**Критерий выполнения** наблюдаемый: три письменных ответа. Для первого названы
оба типа (строка и объект), для второго — что оператор становится частью
строки-значения, для третьего — список разрешённых ключей и запрет ключей
с `$`.

## 12. Проверь себя

1. Чем операторная инъекция отличается от синтаксической и почему она чаще?
2. Как объект `{"$ne": null}` в поле пароля обходит вход?
3. Почему отсутствие склейки строк не означает отсутствия инъекции в MongoDB?
4. Как приведение к типу и список ключей закрывают операторную инъекцию?
5. Возврат к теме `sqli-basics`: что общего у SQL- и NoSQL-инъекции в рамке
   источник — путь — сток — отсутствующий контроль?

<details markdown="1">
<summary>Ответы</summary>

1. Синтаксическая ломает разбор запроса, как в SQL, и требует, чтобы база
   исполняла выражение. Операторная шлёт объект с оператором вместо значения и
   кавычек не требует — потому и встречается чаще.
2. Поле `password` становится объектом `{"$ne": null}`, и условие «пароль равен
   присланному» превращается в «пароль не равен null» — истинное для всех.
   База возвращает первого пользователя.
3. Команда в MongoDB — структура, а не строка. Данные дотягиваются не до кавычки,
   а до оператора: присланный объект становится частью фильтра.
4. Приведение к строке превращает объект в значение, и оператор перестаёт
   работать. Список разрешённых ключей и запрет ключей с `$` не пускают оператор
   в фильтр там, где принимается структура.
5. Источник — значение из запроса, путь — построение фильтра, сток — вызов к
   базе, отсутствующий контроль — разделение данных и команды. Меняется лишь
   форма команды: строка в SQL, структура в MongoDB.

</details>
