# Password spraying и credential stuffing

Уровень **L2** · время 45 мин (теория 27 / задача 12 / самопроверка 6,
оценка)

Что прочитать сначала: `brute-force-defense`, `password-storage`.

Три атаки на один и тот же вход, смоделированные на стенде, оставляют в
логе разные следы:

```text
атака                      | макс/уч | паролей | макс/пар | успех
брутфорс одной учётки      |     500 |     500 |        1 |  0.0%
распыление пароля          |       1 |       1 |     1000 |  0.2%
подстановка учётных данных |       1 |     400 |        1 |  1.2%
```

Читайте строку распыления: один пароль против тысячи учёток, по одной
попытке на каждую. Счётчик неудач по учётной записи до порога не дошёл
ни разу. Это не сбой защиты, а другая цель атаки: не подобрать пароль к
конкретной учётке, а войти в любую поддавшуюся.

Cheat Sheet OWASP разводит три атаки на живой вход. Брутфорс — много
паролей к одной учётке. Распыление пароля (password spraying) — один
частый пароль против многих учёток. Подстановка учётных данных
(credential stuffing) — пары из чужой утечки, каждая пробуется один раз,
в расчёте на повторно используемые пароли. Защита, поставленная под одну
из них, двух других может не видеть вовсе.

Дальше разберём, по каким величинам лога атаки различают и почему у
подстановки прямого признака нет, а есть доля успеха выше фоновой. И как
собирается защита слоями там, где счётчик молчит: второй фактор, список
утёкших паролей, метрики объёма по входу.

## 0. Коротко

Cheat Sheet OWASP разводит три атаки на живой вход. Брутфорс — много паролей
к одной учётке. Password spraying (распыление пароля) — один частый пароль
против многих учёток, по одной попытке на каждую. Credential stuffing
(подстановка учётных данных) — пары «логин и пароль» из чужой утечки, каждая
пробуется один раз, в расчёте на повторно используемые пароли. След в логе у
трёх атак разный. Защита, поставленная под одну, двух других не видит:
счётчик по учётке молчит на распылении, счётчик по адресу — на распределённой
подстановке.

**Зачем это в работе AppSec-инженера.** «Есть защита от брутфорса» не значит
«закрыты распыление и подстановка»: у них другой профиль. Ревьюер смотрит, по
какому ключу считает защита, и сверяет с тем, как выглядит каждая из трёх
атак. Сильнейший общий слой — второй фактор, а не счётчик, и это тоже надо
уметь обосновать числом.

## 1. Цели

После этого раздела вы сможете:

3. Назвать, почему счётчик по учётке или адресу не ловит две из трёх.
4. Собрать защиту слоями, начиная со второго фактора и списка утёкших.

## 3. Механика

**Откуда это взялось.** Утечки паролей с чужих сайтов сделали атаку дешёвой:
готовые пары «логин и пароль» продаются миллионами, а люди переиспользуют
пароли. Тогда цель смещается. Незачем перебирать пароль к одной учётке, если
можно пробовать украденные пары против многих и брать те учётки, где пароль
повторён. Счётчик, придуманный против перебора одной учётки, эту атаку не
видит: по каждой учётке — одна попытка.

### Три сигнатуры

Прогон (`.smgr/appsec-stage1-auth/exp/e08-logsignature.py`, Python 3.14.7)
моделирует три атаки против одного приложения и считает по логу величины, по
которым Cheat Sheet предлагает их различать:

```text
атака                      | макс/IP | макс/уч | паролей | макс/пар | успех
брутфорс одной учётки      |       2 |     500 |     500 |       1 |  0.0%
распыление пароля          |       4 |       1 |       1 |    1000 |  0.2%
подстановка учётных данных |       2 |       1 |     400 |       1 |  1.2%
```

Брутфорс бьёт по одной учётке (макс/уч = 500) многими паролями. Распыление —
один пароль (паролей = 1) против тысячи учёток, по одной попытке на каждую
(макс/уч = 1), и один пароль пробуют на всех (макс/пар = 1000). Подстановка —
своя пара на учётку (паролей = 400, макс/пар = 1), по одной попытке. Все три
распределены по адресам, потому что адрес атакующий выбирает сам: колонка
макс/IP у всех низкая, и защита по адресу тут слепа.

Величина «макс/уч» ловит брутфорс, «макс/пар» — распыление, но подстановку не
выдаёт ни та, ни другая: у неё и по учётке, и по паролю по единице. Её признак
косвенный — доля успеха выше фоновой и всплеск на многих учётках сразу.

### Почему счётчик не спасает

Счётчик по учётке (`brute-force-defense`) молчит на распылении и подстановке:
там на учётку одна попытка. Счётчик по адресу молчит на любой из трёх, если
атака распределена по адресам, а у подстановки это норма — инструменты гоняют
запросы через прокси-сети. Cheat Sheet прямо говорит: блокировка по адресу —
не основная защита: её обходят сменой адреса.

## 5. Как выглядит в коде

Здесь дефект не в строке, а в выборе защиты. Признак — счётчик под перебор
одной учётки как единственная мера.

```python
# УЯЗВИМО по замыслу защиты, не по синтаксису.
def login(user, password):
    if fails[user] >= 5:                 # (1)
        return deny("too many attempts")
    if verify(user, password):
        fails[user] = 0
        return grant_session(user)
    fails[user] += 1                     # (2)
    return deny("invalid")
```

1. Единственная защита — счётчик по учётке. Против распыления и подстановки он
   молчит: по каждой учётке одна попытка.
2. Ни проверки пароля по списку утёкших, ни второго фактора, ни метрик по
   объёму. Атака, размазанная по учёткам, проходит целиком.

Признаки такие. Счётчик по учётке или адресу как единственная мера. Пароли не
сверяются со списком скомпрометированных. Многофакторной аутентификации
(multi-factor authentication, MFA) нет даже для администраторов.
Нет метрик объёма по входу, по которым видно распределённую атаку. Блокировка
по адресу без учёта прокси-сетей.

## 6. Как чинится

Cheat Sheet ставит меры слоями, и первый слой — второй фактор.

- **Второй фактор.** По данным, которые приводит Cheat Sheet, MFA остановил бы
  подавляющее большинство захватов учётных записей. Где сплошной MFA невозможен,
  его требуют для администраторов и как «step-up» на подозрительный вход
  (новое устройство, адрес, страна) — ASVS v5.0-6.3.3.
- **Список утёкших паролей.** Проверка нового и текущего пароля по базе
  скомпрометированных (ASVS v5.0-6.2.12) убирает те пары, на которых
  подстановка и держится.
- **Метрики объёма.** Каждый слой даёт счётчик обнаруженного и отражённого,
  и по ним видно распределённую атаку, невидимую одному счётчику.
- **Ограничение и CAPTCHA по риску.** Не один предсказуемый порог, а
  градуированный ответ с учётом всплесков, происхождения адреса (хостинг против
  жилого) и географии.

```python
# Направление фикса — слои, а не одна строка.
def login(user, password, ctx):
    require_rate_and_captcha_by_risk(ctx)       # (1)
    if not verify(user, password):
        record_metric("auth.fail", ctx); return deny("invalid")
    if breached(password):                      # (2)
        return force_reset(user)
    if risky(ctx):                              # (3)
        return step_up_mfa(user)
    return grant_session(user)
```

1. Ограничение и CAPTCHA включаются по оценке риска запроса, а не жёстким
   порогом по адресу.
2. Пароль из утечки — на принудительный сброс, даже если он верный.
3. Подозрительный контекст — на второй фактор.

## 9. Ловушка

Частое мнение: блокировка после нескольких неудач закрывает перебор.

**Она закрывает перебор одной учётки, а не подстановку и распыление.** У этих
двух по каждой учётке одна попытка, и счётчик по учётке до порога не доходит.
Распределённые по адресам, они проходят и мимо счётчика по адресу.

Контрпример из прогона. Приложение с блокировкой по учётке после пяти неудач
пропустило распыление: один пароль против тысячи учёток дал два входа и ноль
блокировок. По каждой учётке была ровно одна попытка — порог не сработал ни
разу.

## 10. Чеклист ревью

1. Verify that защита рассчитана не только на перебор одной учётки, но и на
   распыление и подстановку (ASVS v5.0-6.3.1).
2. Verify that пароли проверяются по списку скомпрометированных при регистрации
   и смене (ASVS v5.0-6.2.12).
3. Verify that второй фактор доступен и обязателен хотя бы для
   административных учётных записей (ASVS v5.0-6.3.3).
4. Verify that блокировка по адресу не единственная мера и учитывает
   прокси-сети и распределённый трафик.
5. Verify that каждый защитный слой даёт метрику объёма для обнаружения
   распределённой атаки.
6. Verify that подозрительный вход (новое устройство, адрес, страна) поднимает
   требование до второго фактора.

## 11. Задача

По журналу входов приложения (свой или учебный) или по трём смоделированным
атакам посчитайте на атаку четыре величины. Попыток с одного адреса. Попыток
по одной учётке. Число разных паролей. Попыток одним паролем. Сопоставьте с
тремя сигнатурами из темы.

**Наблюдаемый критерий:** таблица трёх атак по четырём величинам и вывод, какую
из трёх поставленная в приложении защита не заметит. Для подстановки — назвать
косвенный признак, раз прямого счётчик не даёт.

## 12. Проверь себя

1. Чем распыление и подстановка отличаются от брутфорса по цели и по числу
   попыток на учётку?
2. Какая величина в логе выдаёт распыление и почему та же величина молчит на
   подстановке?
3. Почему счётчик по учётной записи не ловит две из трёх атак?
4. Почему Cheat Sheet ставит второй фактор первым слоем, а блокировку по
   адресу — не основной мерой?
5. Возврат к теме `brute-force-defense`: чем ключ счётчика, годный против
   брутфорса, бесполезен против распыления?
6. Возврат к теме `password-storage`: почему проверка по списку утёкших
   паролей — защита именно от подстановки, а не от кражи дампа?

<details markdown="1">
<summary>Ответы</summary>

1. Брутфорс подбирает пароль к одной учётке многими попытками. Распыление и
   подстановка бьют по многим учёткам с одной попыткой на каждую: цель — любая
   поддавшаяся учётка, а не конкретная.
2. Распыление выдаёт «макс/пар» — один пароль пробуют на тысяче учёток. На
   подстановке эта величина равна единице: там на каждую учётку своя пара из
   утечки.
3. При распылении и подстановке по каждой учётке ровно одна попытка, и счётчик
   по учётке до порога не доходит.
4. По данным Cheat Sheet MFA остановил бы подавляющее большинство захватов, и
   он не зависит от того, верен ли украденный пароль. Блокировку по адресу
   обходят прокси-сетью, поэтому она — слой, а не основа.
5. Против брутфорса годится счётчик по учётке: там много попыток на одну
   учётку. При распылении на учётку одна попытка, счётчик по учётке молчит —
   нужен признак по паролю или метрика объёма.
6. Подстановка держится на повторно используемых утёкших паролях; проверка по
   списку убирает именно их. От кражи собственного дампа защищает не список, а
   стойкое хранение (тема `password-storage`).

</details>
