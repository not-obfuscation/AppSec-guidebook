# Атаки на заголовок Host

Уровень **L2** · время 40 мин (теория 24 / задача 10 / самопроверка 6,
оценка)

Что прочитать сначала: `app-architecture`, `http-basics`.

Обработчик сброса пароля собирает ссылку для письма. Домен в ней он берёт
из заголовка запроса — вот два прогона учебного стенда:

```text
Host: accounts.example.com  -> https://accounts.example.com/reset?token=…
Host: evil.attacker.test    -> https://evil.attacker.test/reset?token=…
```

Токен в обеих ссылках один: он выписан жертве. Меняется только домен, и
во второй строке он принадлежит атакующему. Жертва получает законное с
вида письмо, переходит по ссылке и отдаёт токен на чужой сайт.

Виноват заголовок `Host`. Он обязателен в HTTP и называет домен, к
которому обращён запрос: по нему сервер за одним адресом различает сайты.
Значение присылает клиент, и приложение попадает в беду, когда читает его
как доверенное. Из `Host` строят абсолютную ссылку, по нему решают
маршрут к внутреннему узлу, его подставляют в запрос к базе. Даже
проверенный `Host` нередко перекрывает соседний заголовок
`X-Forwarded-Host`, который фреймворк читает по умолчанию.

Дальше — как собирается отравление ссылки сброса, куда ещё бьёт
подставленный домен и чем его закрывают: доменом из конфигурации, белым
списком и отключением заголовков-перекрытий.

## 0. Коротко

Заголовок `Host` обязателен в HTTP и называет домен, к которому обращён запрос
(RFC 9110 § 7.2). Один сервер за одним адресом обслуживает много доменов и по
`Host` понимает, чей контент отдавать. Значение приходит от клиента, и подменить
его можно так же, как любой другой заголовок.

Приложение попадает в беду, когда использует `Host` как доверенный домен. Из
него строят абсолютную ссылку, по нему решают, к какому внутреннему узлу идти,
его подставляют в запрос к базе. Самый частый и наглядный случай — ссылка сброса
пароля. Обработчик генерирует токен для жертвы, вкладывает его в ссылку, а домен
ссылки берёт из `Host`. Атакующий шлёт запрос сброса на чужой аккаунт с
подставленным `Host` — и письмо с токеном жертвы ведёт на домен атакующего.

Даже когда сам `Host` проверяют, его нередко удаётся перекрыть другим
заголовком — `X-Forwarded-Host` и его роднёй. Владелец сайта часто не знает, что
эти заголовки поддержаны по умолчанию, и не проверяет их с тем же вниманием.

**Зачем это в работе AppSec-инженера.** Заголовок `Host` приходит от клиента,
и проверять его положено как любой другой недоверенный ввод — только заметен
он меньше параметра или тела формы. Недостаточная проверка ввода идёт под
CWE-20, и издание OWASP 2025 года ставит её в `A05:2025` Injection.
Маршрутный вариант атаки OWASP считает родней серверных запросов по адресу из
данных (CWE-918). На ревью тема даёт один вопрос к любому месту, где домен,
маршрут или адрес берутся из `Host`. Вопрос один: откуда взялось это значение
и что будет, если его подставит атакующий.

3. Назвать заголовки-перекрытия `Host` и почему они включены по умолчанию.
4. Свести защиту к домену из конфигурации или белому списку хостов.

## 3. Механика

**Откуда это взялось.** Готовые приложения не знают своего домена: он задаётся
при установке. Когда домен нужен, например для абсолютной ссылки в письме,
типовой приём — взять его из `Host`. Приём удобен и потому распространён, а его
цена в том, что значение управляемо клиентом. Отсюда правило: `Host` — вход, а
не факт о сервере.

Стенд собирает ссылку сброса пароля из `Host` и показывает, куда уходит токен
жертвы при подстановке чужого домена.

```text
$ python e03-host.py
Заголовок Host запроса управляет ссылкой (УЯЗВИМО):
  Host: accounts.example.com  -> https://accounts.example.com/reset?token=…
  Host: evil.attacker.test    -> https://evil.attacker.test/reset?token=…
  Host: accounts.example.com + X-Forwarded-Host: evil.attacker.test
    -> перекрытый Host 'evil.attacker.test' -> https://evil.attacker.test/…
```

Токен в обеих ссылках один и тот же — он выписан жертве. Меняется только домен,
и во второй строке он принадлежит атакующему. Жертва получает законное с виду
письмо сброса, переходит по ссылке — и отдаёт свой токен на чужой сайт. Третья
строка показывает перекрытие: сам `Host` остался правильным, но
`X-Forwarded-Host` его подменил.

### Не только сброс пароля

Тот же корень бьёт в трёх местах. Абсолютная ссылка в письме уводит токен, как в
стенде. Решение о маршруте по `Host` превращается в запрос к внутреннему узлу. С
подставленным доменом фронтенд направляет запрос туда, куда снаружи хода нет.
Это маршрутный вариант серверного запроса по адресу из данных (тема
`ssrf-basics`). И `Host`, подставленный в тело ответа или в общий кэш, отравляет
ответ для других (тема `cache-poisoning`).

### Заголовки-перекрытия

За обратным прокси приложение видит не исходный `Host`, а то, что подставил
прокси, и настоящий домен клиента приходит в `X-Forwarded-Host`. Фреймворки
читают этот заголовок по умолчанию, чтобы восстановить исходный домен. Там, где
он не нужен, он остаётся включённым и даёт второй путь к той же подмене —
`X-Forwarded-Host`, `X-Host`, `X-Forwarded-Server` и подобные.

## 5. Как выглядит в коде

Ревьюер ищет домен, маршрут или адрес, собранный из `Host` без проверки.

```python
# УЯЗВИМО — демонстрация, не для продакшена.
def send_reset(request, user):
    token = new_token(user)
    host = request.headers["Host"]                 # (1)
    link = f"https://{host}/reset?token={token}"   # (2)
    send_mail(user.email, f"Сброс пароля: {link}")
```

1. Домен взят из заголовка запроса — то есть из ввода клиента.
2. Токен жертвы вложен в ссылку на домен, которым управляет отправитель запроса.

Соседний признак — чтение `X-Forwarded-Host` там, где оно не нужно: заголовок
переопределяет `Host`, и проверка одного `Host` его не ловит.

## 6. Как чинится

- **Домен из конфигурации, а не из запроса.** Абсолютную ссылку строят по
  домену, заданному при развёртывании; `Host` в её сборке не участвует. Это
  закрывает отравление сброса целиком.
- **`Host` сверяется с белым списком.** Где домен всё же берут из запроса, его
  проверяют по списку разрешённых и отклоняют или перенаправляют незнакомый.
- **Относительная ссылка вместо абсолютной.** Часто абсолютный адрес не нужен:
  относительная ссылка не несёт домена, и подставлять нечего.
- **Заголовки-перекрытия отключаются.** `X-Forwarded-Host` и родню выключают
  там, где они не нужны, а где нужны — тоже сверяют с белым списком.
- **Маршрут не зависит от `Host`.** Обратный прокси направляет запрос только на
  список разрешённых узлов, а не по домену из запроса.

Стенд показывает три меры на том же запросе с подставленным доменом.

```text
Тот же запрос с Host: evil.attacker.test через три меры:
  фиксированный домен:  https://accounts.example.com/reset?token=…
  белый список:         400: неизвестный Host 'evil.attacker.test'
  относительная ссылка: /reset?token=…
```

## 9. Ловушка

Ходовое мнение: `Host` подставляет веб-сервер или прокси, приложение получает
уже проверенное значение.

**`Host` доходит до приложения таким, каким его послал клиент, если специально
не настроено иначе.** Веб-сервер по умолчанию передаёт заголовок дальше, а не
подменяет его доверенным. Хуже того: даже правильно зафиксированный `Host`
перекрывается `X-Forwarded-Host`, который фреймворк читает по умолчанию. Пока в
конфигурации явно не задан домен и не сверяется список хостов, значение остаётся
вводом атакующего.

## 10. Чеклист ревью

1. Verify that абсолютные ссылки в письмах и ответах строятся из домена в
   конфигурации, а не из заголовка `Host`.
2. Verify that там, где `Host` всё же читается, он сверяется с белым списком
   разрешённых доменов.
3. Verify that заголовки-перекрытия `X-Forwarded-Host` и родня отключены или
   тоже сверяются с белым списком.
4. Verify that решение о маршруте к внутреннему узлу не зависит от значения
   `Host` из запроса.
5. Verify that ссылка сброса пароля проверена на увод токена подстановкой
   чужого домена в `Host`.
6. Verify that значение `Host` не попадает без проверки в запрос к базе или в
   тело ответа.

## 11. Задача

Возьмите поток сброса пароля в своём или учебном приложении. Отправьте запрос
сброса с подставленным заголовком `Host`, затем с правильным `Host` и
добавленным `X-Forwarded-Host`. Посмотрите на домен в письме.

**Критерий:** записано, какой домен попал в ссылку в каждом из двух опытов и
дошёл ли туда токен жертвы. Названо, чем закрыт увод: доменом из конфигурации,
белым списком или относительной ссылкой.

## 12. Проверь себя

1. Почему заголовок `Host` считается вводом клиента, а не фактом о сервере?
2. Как из `Host` собирают отравление ссылки сброса пароля и куда уходит токен?
3. Что такое `X-Forwarded-Host` и почему проверка одного `Host` его не ловит?
4. Чем домен из конфигурации закрывает отравление сброса надёжнее белого списка?
5. Возврат к теме `app-architecture`: почему за обратным прокси приложение видит
   не исходный `Host`?
6. Возврат к теме `http-basics`: зачем заголовок `Host` вообще обязателен в
   запросе?

<details markdown="1">
<summary>Ответы</summary>

1. Потому что его значение выбирает клиент и подставляет вместе с запросом, как
   любой другой заголовок. Сервер узнаёт из него свой домен, но проверить, что
   значение настоящее, по самому заголовку нельзя.
2. Обработчик сброса берёт домен ссылки из `Host`. Атакующий шлёт запрос сброса
   на аккаунт жертвы с подставленным `Host`; письмо с токеном жертвы ведёт на
   домен атакующего, и переход по ссылке отдаёт токен ему.
3. Заголовок, в котором обратный прокси передаёт исходный домен клиента.
   Фреймворк читает его по умолчанию и позволяет ему перекрыть `Host`, поэтому
   проверка одного `Host` подмену через него пропускает.
4. Домен из конфигурации вообще не зависит от запроса — подставить нечего.
   Белый список зависит от того, что все точки чтения `Host` проверяются, и
   пропущенная точка оставляет дыру.
5. Потому что прокси принимает соединение от клиента и открывает своё к
   приложению; приложение видит `Host`, который подставил прокси, а исходный
   домен приходит отдельным заголовком.
6. Один адрес обслуживает много доменов, и по `Host` сервер понимает, чей
   контент отдавать. Без него виртуальный хостинг не различил бы сайты.

</details>

   роль в определении целевого ресурса и указании на управляемость значения
   клиентом.
   <https://www.rfc-editor.org/rfc/rfc9110.html>

Каркас этапа: `owasp-asvs-5-document` (ASVS v5.0.0), `owasp-wstg-42`,
`owasp-top10-2025`. Наследуются всеми темами и отдельной строкой не
повторяются.

**Скоропортящийся слой.** Перечень заголовков-перекрытия и то, какие из них
фреймворк читает по умолчанию, — свойство конкретных фреймворков и прокси и
меняется с их версиями; корень (значение `Host` управляемо клиентом) стабилен.

**Маркеры уверенности.** Сборка ссылки сброса из `Host`, увод токена на чужой
домен, перекрытие через `X-Forwarded-Host` и три меры — **проверено лично**
2026-08-24 на Python 3.14.7 (стенд `e03-host.py`): токен один и тот же, домен
берётся из `Host`; фиксированный домен и относительная ссылка увод закрывают,
белый список отвергает чужой хост кодом 400. Обязательность `Host` и его роль в
адресации — **по документации** (RFC 9110 § 7.2, открыт лично 2026-08-24).
Отравление сброса, маршрутный запрос и поведение заголовков-перекрытия — **по
документации** (страница PortSwigger, открыта лично 2026-08-24). Поведение живых
фреймворков и прокси при чтении `X-Forwarded-Host` **не воспроизводилось**:
сетевого узла в стенде нет.
