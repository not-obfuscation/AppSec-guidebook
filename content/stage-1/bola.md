# BOLA: авторизация объектов в API

Уровень **L2** · время 33 мин (теория 20 / задача 8 / самопроверка 5,
оценка)

Что прочитать сначала: `idor`, `rest-and-graphql`.

BOLA — это горизонтальная эскалация в API: точка принимает идентификатор
объекта, выполняет над ним действие и не проверяет права на этот объект.
В отчётах по API это находка номер один, и проверяют её по контракту, а не
по интерфейсу.

Пример. API витрины отчётов, клиент — мобильное приложение; удаление своего
отчёта пользователю положено. Вот вызов этой точки с идентификатором чужого
отчёта:

**Запрос**

```http
DELETE /v1/reports/rp-8842 HTTP/1.1
Host: api.example.com
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJhbm5hIn0...
```

**Ответ**

```http
HTTP/1.1 204 No Content
```

Обхода аутентификации нет: токен настоящий, подпись сошлась, `sub` в нём —
`anna`. Повышения прав нет: вызывать эту точку ей и положено. Дефект в том, что
`rp-8842` дошёл до базы как ключ, а вопрос о правах на этот отчёт не задавался
нигде.

API отдаёт объекты, и номер нужного объекта клиент присылает сам. Вызывать
точку удаления отчёта положено каждому: свои отчёты удаляют все. Вопрос не в
том, кому открыта точка, а в том, чей отчёт стоит в её адресе. BOLA — это
когда второй вопрос не задан нигде: ни в обработчике, ни выше по стеку.

Разница с IDOR в том, что видно ревьюеру, — механика у них общая. В
веб-приложении есть экран, и по нему можно сказать, какие объекты пользователю
показывают. В API экрана нет: есть контракт и есть точки, принимающие
идентификаторы, и других подсказок о замысле не остаётся.

К этому удалению тема возвращается четыре раза. «Механика» объясняет, почему
штатный доступ к точке — признак BOLA, а не оправдание. «Как выглядит в коде»
показывает обработчик изнутри, «Как чинится» — чем в нём заменяют выборку по
ключу. «Ловушка» отвечает на догадку, что `rp-8842` в виде UUID закрыл бы дело.

Механика подмены идентификатора разобрана в теме `idor` и здесь не
повторяется: тема отвечает на вопрос, что меняется, когда клиентом
становится не браузер, а другая программа.

## 0. Коротко

То же в терминах, которыми это обсуждают. BOLA (Broken Object Level
Authorization) — тот же дефект, что IDOR, названный так, как его называют в
отчётах по API. Точка API принимает идентификатор объекта, выполняет над
объектом действие и не проверяет, вправе ли вошедший это действие над этим
объектом выполнить. OWASP ставит риск первым номером своего списка для API.
Чинится проверкой прав на объект в каждой функции, которая достаёт объект по
идентификатору из запроса.

**Зачем это в работе AppSec-инженера.** Точку вида `DELETE /v1/reports/{id}` вы
объявляли сами и вешали на неё проверку токена. На вопрос, чей отчёт пришёл в
`{id}`, отвечал экран: пользователю показывали только его записи, других
идентификаторов у него не было. У клиента-программы экрана нет, и вопрос о
владельце не задаёт больше никто. В отчёте о тестировании API этот дефект
называется BOLA, в отчёте о веб-приложении — IDOR, и разработчик, читающий оба,
считает их разными задачами.

## 1. Цели

После этого раздела вы сможете:

1. Отличить BOLA от BFLA по тому, что именно подменил атакующий.
2. Найти в контракте API точки, принимающие идентификатор объекта.
3. Назвать, почему сверка идентификатора из токена закрывает малую часть
   случаев.
4. Составить проверку объектной авторизации по контракту, а не по интерфейсу.

## 3. Механика

**Откуда это взялось.** Веб-приложение старого устройства собирало страницу на
сервере: какие объекты показать, решал тот же код, который проверял права.
Когда отрисовка ушла в клиент, сервер перестал знать состояние экрана и стал
принимать решения по одному параметру запроса. Список рисков OWASP для API
называет это причиной прямо: интерфейсы отдают точки, которые обрабатывают
идентификаторы объектов, и это создаёт широкую поверхность атаки. Отсюда и
требование: проверку прав на объект нужно ставить в каждой функции, которая
обращается к источнику данных по идентификатору от пользователя.

### Что именно подменяется

Разбор API1:2023 проводит границу, ради которой тема и существует отдельно. При
BOLA доступ к самой точке **штатный**: пользователю положено вызывать этот
маршрут. Нарушение происходит на уровне объекта — через подмену идентификатора.
Если же атакующий добрался до функции, к которой доступа иметь не должен, это
уже BFLA, а не BOLA. Удаление из введения — BOLA по этому признаку: точка
`DELETE /v1/reports/{id}` открыта `anna` штатно, и подменила она только номер
отчёта.

Идентификатор бывает каким угодно: последовательным числом, UUID или
произвольной строкой. Тип значения ничего не меняет, потому что находится
идентификатор одинаково — в пути, в строке запроса, в заголовке или в теле.

### Три места, где это видно

Разбор риска даёт три сценария, и все три встречаются в жизни.

Первый: витрина отчётов о выручке магазинов вызывает точку вида
`/shops/{shopName}/revenue_data.json`, а имена магазинов отдаёт соседняя точка.
Скрипт подставляет имена из списка и собирает выручку тысяч магазинов.

Второй: мобильное приложение автопроизводителя шлёт VIN автомобиля, чтобы
завести двигатель или открыть двери. Сервер не проверяет, что VIN принадлежит
вошедшему.

Третий: удаление документа в GraphQL-мутации по идентификатору документа, без
проверки прав на документ. Точка входа тут одна на все объекты, и по адресу
маршрута дефект не виден вовсе.

### Почему сверки с токеном мало

Разбор риска отдельно предупреждает: сравнение идентификатора текущей сессии,
взятого из токена, с идентификатором из запроса закрывает лишь малое
подмножество случаев. Приём работает, пока объект принадлежит одному человеку.
Он ломается на всём остальном: документ в общем пространстве, заказ филиала,
запись арендатора в многопользовательской системе. ASVS выносит последний случай
в отдельное требование v5.0-8.4.1 — операции одного арендатора не должны
затрагивать чужих.

## 5. Как выглядит в коде

Ревьюер API читает не экраны, а контракт. Каждый маршрут с параметром пути или
тела, похожим на идентификатор, — кандидат. Тот самый обработчик, который
принял `rp-8842`, изнутри выглядит так.

```python
# УЯЗВИМО — демонстрация, не для продакшена.
@api.delete("/v1/reports/<report_id>")
@jwt_required
def delete_report(report_id):
    report = Report.query.get(report_id)   # (1)
    report.delete()                        # (2)
    return "", 204
```

1. Объект достаётся по идентификатору из пути. Владелец в запрос не входит.
2. Действие выполняется. Проверки прав на объект нет ни здесь, ни выше по стеку.

Обёртка, которая выглядит защитой: `@jwt_required` и любой её аналог. Она
отвечает на вопрос, кто пришёл, и на вопрос о правах на объект не отвечает.
Вторая обманчивая форма — сравнение `report_id == claims["sub"]`: оно работает
только там, где объект и есть пользователь. В удалении из введения обёртка
отработала штатно: токен `anna` подлинный, а отчёт `rp-8842` чужой.

Ложное срабатывание: точка, которая принимает идентификатор объекта из
**публичного** каталога, где все объекты открыты по замыслу. Признак — тот же
идентификатор в ответе неаутентифицированного запроса.

## 6. Как чинится

Разбор API1:2023 требует механизма авторизации, опирающегося на политики и
иерархию пользователей, и вызова этого механизма в каждой функции, которая
достаёт запись по вводу от клиента.

```python
@api.delete("/v1/reports/<report_id>")
@jwt_required
def delete_report(report_id):
    report = authz.get_or_403(current_user, Report, report_id, "delete")
    report.delete()
    return "", 204
```

Идентификатор перестал быть ключом к таблице и стал аргументом решения:
единственная функция знает пользователя, класс объекта и действие. На запросе
из введения она отвечает отказом: `anna` есть, отчёт `rp-8842` есть, права на
его удаление — нет.

**Границы применимости.** Единая точка решения окупается на десятках маршрутов
и мешает на трёх: там дешевле выборка, ограниченная владельцем. Случайные
идентификаторы вместо последовательных разбор риска рекомендует, но как меру в
глубину — она поднимает цену перебора и не отменяет проверки. Отдельная цена —
ответы: механизм, отвечающий 403 на чужой объект и 404 на несуществующий,
сообщает атакующему, какие объекты существуют.

## 9. Ловушка

Отчёт из введения адресован номером `rp-8842`, и первое, что приходит на такую
находку, — заменить номера на UUID. Отсюда представление: в API с
непредсказуемыми идентификаторами объектная авторизация закрыта, потому что
чужой идентификатор угадать нельзя.

**Идентификатор не угадывают, его получают.** Разбор риска называет типы
значений равноценными: последовательные числа, UUID и произвольные строки
находятся в запросе одинаково. В самом введении номер тоже не угадан: его отдал
список по соседнему адресу.

Контрпример — первый сценарий разбора: имена магазинов непредсказуемы, но
соседняя точка того же API отдаёт их списком. Одна точка выдаёт идентификаторы,
другая по ним отдаёт данные — и перебирать нечего.

## 10. Чеклист ревью

1. Verify that каждая точка API, принимающая идентификатор объекта, проверяет
   права вошедшего на действие над этим объектом (ASVS v5.0-8.2.2).
2. Verify that проверка прав на объект не сводится к сравнению идентификатора
   из токена с идентификатором из запроса.
3. Verify that проверка стоит в функции, достающей объект, а не только в
   обработчике маршрута.
4. Verify that операции одного арендатора не затрагивают объекты других
   арендаторов (ASVS v5.0-8.4.1).
5. Verify that точки, отдающие списки идентификаторов, ограничены теми же
   правами, что и точки, отдающие сами объекты.
6. Verify that ответ на чужой объект не отличает существующий объект от
   несуществующего там, где само существование чувствительно.

## 11. Задача

Возьмите контракт любого API, к которому у вас есть доступ, — OpenAPI, схему
GraphQL или собранный перехватом список маршрутов. Выпишите все точки, где
идентификатор объекта приходит от клиента, и напротив каждой поставьте место в
коде, где проверяются права на этот объект.

Одна подсказка: идентификатор приходит не только в пути; ищите его в строке
запроса, в теле и в заголовках, а в GraphQL — в переменных мутации.

**Критерий выполнения** наблюдаемый: получилась таблица «точка — параметр —
строка кода с проверкой». В ней либо есть строки с пустой третьей клеткой, либо
стоит доказательство, что таких строк нет.

## 12. Проверь себя

1. По какому признаку дефект относят к BOLA, а не к BFLA?
2. Почему тип идентификатора не влияет на наличие дефекта?
3. В каком случае сверка идентификатора из токена с параметром запроса
   достаточна и в каком перестаёт работать?
4. Чем точка, отдающая список идентификаторов, опасна при исправной проверке
   прав на сами объекты?
5. Возврат к теме `rest-and-graphql`: почему в GraphQL адрес маршрута не
   показывает, какой объект запрошен?

<details markdown="1">
<summary>Ответы</summary>

1. Доступ к самой точке штатный, а нарушение происходит подменой идентификатора
   объекта. Если атакующий попал в функцию, к которой доступа не имеет, это
   BFLA.
2. Идентификатор не угадывается, а берётся из ответа другой точки или из
   интерфейса. Непредсказуемость поднимает цену перебора и не заменяет проверку.
3. Достаточна, пока объект принадлежит ровно одному пользователю. Ломается на
   общих объектах, объектах подразделения и записях арендатора.
4. Она позволяет собрать чужие идентификаторы, после чего перебор не нужен:
   запросы к объектам идут по настоящим значениям.
5. Точка входа в GraphQL одна на все операции, а имя объекта и его
   идентификатор лежат в теле запроса, в переменных операции.

</details>
