# Session fixation и инвалидация сессии

Уровень **L2** · время 45 мин (теория 27 / задача 12 / самопроверка 6,
оценка)

Что прочитать сначала: `sessions-vs-tokens`, `cookies`.

Правило «новый идентификатор при смене уровня доверия» инструкционно: его
проверяют одним запросом. Тема разбирает, что ломается без него и чем выход
на сервере отличается от гашения cookie в браузере.

## 0. Коротко

Session fixation — атака, где значение сессии выбирает атакующий, а жертва
входит уже под ним. Приложение, которое не сменило идентификатор при входе,
оставляет жертву и атакующего в одном сеансе: оба знают значение, оба внутри.
Лечится сменой идентификатора при смене уровня доверия — при входе старая
запись гасится, создаётся новая. Инвалидация — вторая половина темы: выход и
таймаут обязаны гасить сессию на сервере, а не только стирать cookie в
браузере, иначе предъявление старого значения «воскрешает» сеанс.

**Зачем это в работе AppSec-инженера.** Оба дефекта проверяются одним
наблюдением: сравнить идентификатор сессии до и после входа, а после выхода —
предъявить старый. Если при входе значение не поменялось или после выхода
старое всё ещё работает — находка. Ни строчки кода читать не нужно.

## 1. Цели

После этого раздела вы сможете:

1. Назвать правило смены идентификатора при смене уровня доверия.
2. Показать на прогоне, чем закрепление сессии впускает атакующего.
3. Отличить серверную инвалидацию сессии от гашения cookie.
4. Собрать вход и выход так, чтобы старый идентификатор переставал работать.

## 3. Механика

**Откуда это взялось.** Сессия связывает запросы одного пользователя, и до
входа она уже есть — анонимная, с каким-то идентификатором. При входе уровень
доверия меняется: тот же сеанс становится сеансом конкретного человека. Если
идентификатор при этом остаётся прежним, значением сеанса владеет и тот, кто
знал его до входа. Отсюда правило: смена уровня доверия обязана менять
идентификатор. Вторая половина — то же правило на выходе: конец сеанса обязан
делать старое значение непригодным.

### Закрепление сессии

WSTG-v42-SESS-03 формулирует признак прямо: если после успешного входа сервер
не выдал новый идентификатор, закрепление сессии возможно. Атака идёт так.
Атакующий получает от приложения значение сессии (или навязывает своё —
например, с родственного узла, разбор в `cookies`). Он подсовывает это значение
браузеру жертвы. Жертва входит. Сервер не меняет идентификатор, и запись,
которую атакующий знает, теперь принадлежит вошедшей жертве.

Прогон (`.smgr/appsec-stage1-auth/exp/e03-session.py`, Python 3.14.7) на двух
приложениях, уязвимом и исправленном:

```text
=== уязвимое приложение ===
1. сервер принял подставленное значение:      ДА
2. после входа идентификатор прежний:         ДА
3. атакующий со своим значением видит:         anna
4. предъявление cookie после выхода даёт:      boris
=== исправленное приложение ===
1. сервер принял подставленное значение:      нет
2. после входа идентификатор прежний:         нет
3. атакующий со своим значением видит:         аноним
4. предъявление cookie после выхода даёт:      аноним
```

Строки 1–3 — закрепление: уязвимое приложение приняло подставленное значение,
не сменило его при входе, и атакующий со своим значением увидел кабинет
вошедшей жертвы. Исправленное на входе выдало новый идентификатор, и старое
значение осталось анонимным. Строка 4 — инвалидация: после выхода уязвимое
приложение по старой cookie всё ещё показывает кабинет, исправленное —
анонима.

### Инвалидация: сервер против cookie

Выход обязан гасить сессию **на сервере**. WSTG-v42-SESS-06 даёт проверку:
восстановить старую cookie после выхода и дойти по ней до защищённой страницы.
Если получается, выход был только в браузере. Cheat Sheet называет то же:
завершать сеанс на бэкенде, а Clear-Site-Data и стирание cookie — меры
вспомогательные, не замена.

## 5. Как выглядит в коде

Ревьюер ищет, меняется ли идентификатор при входе и гасится ли запись при
выходе.

```python
# УЯЗВИМО — демонстрация, не для продакшена.
def login(request):
    sid = request.cookies.get("sid") or new_sid()   # (1)
    SESSIONS[sid]["user"] = authenticate(request)    # (2)
    return set_cookie("sid", sid)

def logout(request):
    return set_cookie("sid", "")                     # (3)
```

1. Идентификатор берётся из присланной cookie. Значение выбрал клиент, и вход
   его не меняет.
2. Вход пишет пользователя в ту же запись — идентификатор остался прежним.
3. Выход стирает cookie в браузере, но запись на сервере жива: предъявление
   старого значения возвращает сеанс.

Признаки такие. Вход, использующий присланный идентификатор. Отсутствие вызова
смены идентификатора (`session.regenerate`, `HttpSession` пересоздаётся) при
входе. Выход, который трогает только cookie. Приём идентификатора из строки
запроса или из адреса страницы. Отсутствие таймаута.

## 6. Как чинится

Правило: вход выдаёт новый идентификатор и гасит старую запись; выход и таймаут
гасят запись на сервере.

```python
# Исправлено.
def login(request):
    user = authenticate(request)
    if not user:
        return error("Неверный логин или пароль")
    old = request.cookies.get("sid")
    SESSIONS.pop(old, None)                          # (1)
    sid = new_sid()                                  # (2)
    SESSIONS[sid] = {"user": user}
    return set_cookie("sid", sid, http_only=True)

def logout(request):
    SESSIONS.pop(request.cookies.get("sid"), None)   # (3)
    return set_cookie("sid", "")
```

1. Старая запись гасится: подставленное значение перестаёт что-либо значить.
2. Новый идентификатор порождается сервером после проверки (ASVS v5.0-7.2.4).
3. Выход удаляет запись на сервере, а не только cookie (ASVS v5.0-7.4.1).

**Смена уровня доверия — не только вход.** Правило распространяется на любой
подъём привилегий: подтверждение второго фактора (`mfa-bypass`), вход в
административную зону, повторную аутентификацию перед чувствительным действием.
Cheat Sheet требует ротации идентификатора при каждом таком переходе.

**Что ставится рядом.** Таймаут бездействия и абсолютный срок сессии
(Cheat Sheet: 2–5 минут для высокорисковых приложений, 15–30 для остальных,
абсолютный 4–8 часов). Атрибуты cookie из темы `cookies`: `HttpOnly`, `Secure`,
префикс `__Host-`. Гашение прочих сессий при смене пароля (`password-reset-flaws`).

## 9. Ловушка

Частое мнение: при выходе cookie стёрлась, значит сессия закрыта.

**Сессия живёт на сервере, а не в cookie.** Стереть cookie в браузере — не то
же, что погасить запись сеанса. Если запись жива, любой, кто сохранил старое
значение, предъявляет его и возвращается в сеанс.

Контрпример из прогона. Уязвимое приложение после `logout` стёрло cookie, но
предъявление сохранённого значения (строка 4) вернуло кабинет `boris`. Запись
на сервере никто не гасил, и выход оказался косметическим.

## 10. Чеклист ревью

1. Verify that вход выдаёт новый идентификатор сессии и гасит прежний
   (ASVS v5.0-7.2.4).
2. Verify that приложение отвергает идентификатор сессии, которого само не
   выдавало.
3. Verify that идентификатор сессии не принимается из строки запроса или адреса страницы.
4. Verify that выход гасит запись сессии на сервере, а не только стирает cookie
   (ASVS v5.0-7.4.1).
5. Verify that предъявление значения после выхода или таймаута не восстанавливает
   сеанс (WSTG-v42-SESS-06).
6. Verify that идентификатор меняется при каждом подъёме уровня доверия, а не
   только при первом входе.
7. Verify that у сессии заданы таймаут бездействия и абсолютный срок.

## 11. Задача

Возьмите приложение, с которым работаете. Запишите идентификатор сессии до
входа и сразу после. Затем войдите, скопируйте cookie, выйдите и предъявите
скопированное значение защищённой странице.

**Наблюдаемый критерий:** два значения идентификатора (до и после входа) и
ответ на предъявление старой cookie после выхода. Вывод: меняется ли
идентификатор при входе и гасится ли сессия на сервере при выходе.

## 12. Проверь себя

1. Почему вход обязан менять идентификатор сессии, а не только записывать в неё
   пользователя?
2. Как атакующий навязывает жертве значение сессии, если приложение принимает
   присланный идентификатор?
3. Чем серверная инвалидация сессии отличается от гашения cookie и как это
   проверить одним запросом?
4. На какие переходы, кроме первого входа, распространяется правило смены
   идентификатора?
5. Возврат к теме `cookies`: как родственный узел ставит жертве значение
   сессии на весь сайт?
6. Возврат к теме `sessions-vs-tokens`: где живёт сеанс у ссылочной сессии и
   почему выход гасит именно запись на сервере?

<details>
<summary>Ответы</summary>

1. Иначе значением сеанса владеет и тот, кто знал идентификатор до входа. Смена
   уровня доверия без смены идентификатора оставляет жертву и атакующего в
   одном сеансе.
2. Приложение отдаёт анонимную сессию, атакующий подсовывает её значение
   браузеру жертвы (ссылкой с параметром, XSS или cookie с родственного узла).
   Жертва входит под этим значением.
3. Серверная инвалидация удаляет запись сеанса; гашение cookie лишь стирает
   значение в браузере. Проверка: сохранить cookie, выйти, предъявить её —
   если сеанс вернулся, инвалидации на сервере нет.
4. На любой подъём привилегий: подтверждение второго фактора, вход в
   административную зону, повторную аутентификацию перед чувствительным
   действием.
5. Родственный узел `blog.bank.example` ставит cookie сессии с атрибутом на
   весь домен `bank.example`; браузер прикладывает её и к приложению.
6. У ссылочной сессии смысл лежит в хранилище сервера, а идентификатор —
   бессмысленная ссылка на запись. Гасят запись: без неё предъявленное
   значение ни на что не указывает.

</details>
