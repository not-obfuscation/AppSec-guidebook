# Небезопасные генераторы случайных чисел

Уровень **L2** · время 35 мин (теория 21 / задача 9 / самопроверка 5,
оценка)

Что прочитать сначала: `sessions-vs-tokens`.

Два способа предсказать «случайный» токен восстановления пароля показывает
стенд `e04-random.py`:

```text
окно перебора: 7201 секунда; попыток до совпадения: 3601
наблюдений: 624 подряд по 32 бита
следующие 5 значений предсказаны: True
```

Первый случай — генератор засеян временем выдачи: секунда известна, и окно
перебирается за доли секунды. Второй тяжелее: зерно неизвестно, но 624 подряд
идущих значения восстанавливают внутреннее состояние генератора целиком.
Наблюдения не требуют привилегий: столько же идентификаторов приложение
выдаёт обычными запросами.

Обычный и стойкий генераторы дают одинаково ровный разброс, а различаются
другим. Обычный — функция от внутреннего состояния, которое меняется по
известному правилу. Криптографически стойкий (CSPRNG) берёт данные у
операционной системы, и восстанавливать по выводу там нечего. Первый годится
для перемешивания списка, второй обязателен для значений, которые нельзя
угадать: токенов, идентификаторов сессии, солей.

Дальше — как посчитать энтропию токена по длине и алфавиту и почему UUID
этому требованию не отвечает. И как на ревью отличить находку от `random` в
перемешивании карточек.

Требования к самому идентификатору сессии разобраны в теме
`sessions-vs-tokens`. Здесь — источник, из которого он берётся, и остальные
значения приложения, которым непредсказуемость нужна не меньше.

## 0. Коротко

В каждом языке есть два генератора случайных чисел, и разница между ними не в
качестве разброса. Обычный генератор — это функция от внутреннего состояния,
которое меняется по известному правилу: наблюдая достаточно значений, состояние
восстанавливают и считают все следующие. Криптографически стойкий генератор
(CSPRNG) берёт данные у операционной системы, и восстановимого по выводу
состояния у него нет.

Обычный годится там, где нужен разброс: порядок карточек на странице,
перемешивание списка, задержка перед повтором. Стойкий обязателен там, где
значение нельзя угадать: идентификатор сессии, токен восстановления пароля,
токен против межсайтовых запросов, соль, одноразовое значение для шифрования,
ключ. ASVS добавляет вторую половину требования — не меньше 128 бит энтропии —
и отдельно оговаривает, что UUID этому условию не отвечают (`v5.0-11.5.1`).

**Зачем это в работе AppSec-инженера.** Дефект попадается в ревью постоянно и
чинится одной строкой, поэтому находка почти всегда доходит до правки. Работы
здесь на два действия: найти вызовы негодной функции и по каждому решить,
попадает ли значение в разряд секретов. Второе действие и есть тема: `random`
в перемешивании карточек — не находка, `random` в токене восстановления —
находка.

## 3. Механика

**Откуда это взялось.** Генератор в стандартной библиотеке писался под задачи
моделирования: от него требовались равномерность, скорость и воспроизводимость
по зерну — последнее прямо нужно, чтобы повторить численный опыт. Все три
свойства работают против секретности. Когда те же функции взяли для
идентификаторов сессии, воспроизводимость превратилась из достоинства в
уязвимость, и языкам пришлось заводить второй генератор. Первый при этом
остался на месте и по-прежнему зовётся коротким привычным именем.

Стенд показывает два способа предсказать вывод обычного генератора.

```text
$ python e04-random.py
(1) Генератор засеян временем выдачи (УЯЗВИМО)
  окно перебора: 7201 секунда; попыток до совпадения: 3601
  найден seed: 1787600000; токен воспроизведён: True
(2) Генератор по умолчанию, seed неизвестен (УЯЗВИМО)
  наблюдений: 624 подряд по 32 бита
  следующие 5 значений предсказаны: True
(3) secrets (ПРАВИЛЬНО)
  совпали: False; бит энтропии на токен: 128
  внутреннего состояния, восстановимого по выводу, у os.urandom нет
```

Первый случай — явное зерно из времени. Атакующий знает секунду, в которую
пришло письмо, перебирает окно вокруг неё и воспроизводит токен: 3601 попытка
до совпадения, доли секунды работы.

Второй случай тяжелее и потому опаснее: зерно неизвестно и берётся у
операционной системы. Это не помогает. Генератор в стандартной библиотеке
Python — линейный регистр с состоянием из 624 слов, и по 624 подряд идущим
значениям состояние восстанавливается целиком. Стенд восстановил его и
предсказал следующие пять значений точно. Наблюдения при этом не требуют
привилегий: сгодятся 624 идентификатора, полученных обычными запросами.

### Сколько бит

Второе требование — количество. Энтропия считается по алфавиту и длине:
шестнадцатеричная строка даёт 4 бита на знак, набор из 62 знаков — около
5,95 бита. Токен из 32 шестнадцатеричных знаков — 128 бит; из 16 — 64 бита, и
этого мало. Руководство по тестированию описывает и обратную работу: собрать
достаточно выданных значений и посмотреть, нет ли в них общих частей,
возрастающих полей или следов времени.

## 5. Как выглядит в коде

Ревьюер ищет имя функции. Список негодных короткий и для каждого языка свой.
В C это `random()` и `rand()`, в Java — `Math.random()` и `java.util.Random`,
в PHP — `mt_rand()` и `uniqid()`. В C# это `Random()`, в Ruby — `rand()`,
в Go — пакет `math/rand`, в Node.js — `Math.random()`, в Python — `random`.

```python
# УЯЗВИМО — демонстрация, не для продакшена.
import random, time
def reset_token() -> str:
    random.seed(int(time.time()))                       # (1)
    return "%032x" % random.getrandbits(128)            # (2)
```

1. Зерно из времени: значение выводится из момента выдачи.
2. Даже без явного зерна генератор остаётся предсказуемым по своему выводу.

```javascript
// УЯЗВИМО — демонстрация, не для продакшена.
const id = Math.random().toString(36).slice(2);   // (3)
const csrf = Date.now() + '-' + userId;           // (4)
```

3. Годная замена — `crypto.randomBytes` или `crypto.getRandomValues`.
4. Собственная сборка из времени и известного значения: угадывается целиком.

Ложное срабатывание того же вида — `random` там, где непредсказуемость не
нужна: порядок баннеров, разброс времени повтора, выбор узла из списка.
Различает их вопрос: что получит атакующий, угадав значение.

## 6. Как чинится

- **Стойкий генератор для всего, что нельзя угадать.** `secrets` в Python,
  `SecureRandom` в Java, `crypto.randomBytes` в Node.js, `random_bytes` в PHP,
  `crypto/rand` в Go (`v5.0-11.5.1`).
- **Не меньше 128 бит.** Считать по алфавиту и длине, а не на глаз: 32
  шестнадцатеричных знака — 128 бит, 16 — вдвое меньше нормы.
- **Зерно не задавать вручную.** Стойкий генератор берёт его сам; ручное
  зерно — способ сделать вывод воспроизводимым, то есть ровно обратное нужному.
- **UUID — не источник непредсказуемости.** Версия 1 несёт время и узел,
  версия 4 даёт 122 случайных бита. Там, где нужен секрет, берут генератор
  напрямую.
- **Хеш поверх предсказуемого не спасает.** Хеш-функция детерминирована: если
  вход угадывается, то и выход угадывается.

## 9. Ловушка

Ходовой довод: UUID придуманы, чтобы не повторяться, длина у них внушительная,
значит и на роль токена они годятся.

**Уникальность и непредсказуемость — разные свойства, и UUID отвечает за
первое.** Стенд печатает версию 1. Последние двенадцать знаков — узел, тот же у всех
значений этой машины; старшая часть выведена из времени с точностью до сотни
наносекунд. Версия 4 честно случайна, но шесть бит из 128
заняты номером версии и вариантом. Случайных остаётся 122 — ниже нормы,
которую ASVS ставит для непредсказуемых значений, и потому UUID в этом
требовании оговорены отдельно.

Тот же корень у другого довода: «мы засеваем генератор временем, идентификатором
процесса и счётчиком, угадать такое нельзя». Все три величины наблюдаемы или
перебираются, и их смешение не добавляет энтропии — оно её перекладывает.

## 10. Чеклист ревью

1. Verify that значения, которые нельзя угадать, порождаются криптографически
   стойким генератором (`v5.0-11.5.1`).
2. Verify that длина и алфавит такого значения дают не меньше 128 бит
   энтропии.
3. Verify that зерно генератора не задаётся из времени, идентификатора
   процесса или счётчика.
4. Verify that UUID не используется там, где требуется непредсказуемость.
5. Verify that каждое найденное применение обычного генератора разобрано по
   вопросу «что получит атакующий, угадав значение».
6. Verify that генератор остаётся стойким под нагрузкой и не переходит на
   запасной источник (`v5.0-11.5.2`).

## 11. Задача

Соберите из своего или учебного приложения два-три десятка значений одного
вида: идентификаторов сессии, токенов, кодов приглашения. Выпишите их в
столбик и посмотрите на общие части, возрастающие поля и повторяющиеся хвосты.
Затем найдите в коде место, где они порождаются.

**Критерий:** названа функция-источник и решено, годная она или нет. Посчитана
энтропия значения по алфавиту и длине, и число сопоставлено со 128 битами.
Отдельно записано, нашлись ли в столбике общие части.

## 12. Проверь себя

1. Чем восстановление состояния генератора отличается от перебора зерна и
   какой из двух способов работает без знания времени выдачи?
2. Сколько наблюдений понадобилось стенду, чтобы предсказывать вывод
   генератора Python, и почему их сбор не требует привилегий?
3. Как посчитать энтропию токена и сколько бит даёт строка из 32
   шестнадцатеричных знаков?
4. Почему хеширование предсказуемого значения не делает его непредсказуемым?
5. Чем UUID версии 4 отличается от версии 1 и почему ни один из них не
   заменяет стойкий генератор?
6. Возврат к теме `sessions-vs-tokens`: почему предсказуемый идентификатор
   сессии опаснее предсказуемого кода приглашения?

<details markdown="1">
<summary>Ответы</summary>

1. Перебор зерна требует догадки о том, чем засеяли: обычно это время выдачи,
   и работает он только в этом случае. Восстановление состояния идёт по самому
   выводу генератора и о зерне ничего не предполагает — оно работает и тогда,
   когда зерно взято у операционной системы.
2. 624 подряд идущих значения по 32 бита. Сбор не требует привилегий, потому
   что значения выдаются наружу: столько же идентификаторов или токенов
   получают обычными запросами.
3. Умножением длины на двоичный логарифм размера алфавита. У
   шестнадцатеричного алфавита это 4 бита на знак, значит 32 знака дают 128
   бит.
4. Потому что хеш-функция детерминирована: одному входу отвечает один выход.
   Перебирая те же входы, что и раньше, атакующий получает те же хеши и
   сравнивает их с выданным значением.
5. Версия 1 составлена из времени и узла и потому предсказуема почти целиком.
   Версия 4 случайна, но шесть бит заняты номером версии и вариантом, и
   остаётся 122 бита — ниже нормы. Ни та ни другая не задумывались как
   источник секретов: их задача — уникальность.
6. Потому что идентификатор сессии сам по себе даёт доступ: угадав его,
   атакующий работает от имени пользователя без пароля. Код приглашения обычно
   ведёт к отдельному действию с собственными проверками, и цена угадывания
   ниже.

</details>
