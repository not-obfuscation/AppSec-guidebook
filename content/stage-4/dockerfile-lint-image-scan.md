# hadolint и сканирование образов

Уровень **L2** · время 35 мин (теория 20 / задача 10 / самопроверка 5,
оценка)

Что прочитать сначала: `trivy`, `docker-insecure-practices`.

Прогоним линтер по Dockerfile с четырьмя типовыми ошибками:

```text
$ docker run --rm -i hadolint/hadolint < Dockerfile
-:1 DL3007 warning: Using latest is prone to errors …
-:2 DL3008 warning: Pin versions in apt get install …
-:2 DL3015 info: Avoid additional packages …
-:5 DL3025 warning: Use arguments JSON notation …
```

Текст сообщений сокращён по ширине. Четыре находки за секунду, до всякой
сборки. А после сборки образ того же Dockerfile отдаёт сканеру:
python:3.12-slim на день прогона — 19 находок уровней HIGH и CRITICAL.
Это и есть два инструмента темы: линтер читает рецепт сборки, сканер
читает результат.

Дальше — рецепт: что умеет каждый, как запустить оба и как читать вывод.
Практики, которые линтер находит в Dockerfile, чинятся по теме
`docker-insecure-practices`; там же — то, чего линтер не видит вовсе.

## 0. Коротко

hadolint разбирает Dockerfile в синтаксическое дерево и проверяет его по
списку правил DLxxxx, а тело каждого RUN дополнительно прогоняет через
ShellCheck. Сканер образов (здесь — trivy) идёт с другой стороны: читает
состав собранного образа и сравнивает с базой уязвимостей. Первый ловит
«как собрано», второй — «что внутри». Оба ставятся в конвейер с порогом,
иначе прогон остаётся отчётом, который никто не читает.

**Зачем это в работе AppSec-инженера.** Образ — точка, где проверка ещё
дешёвая: до деплоя, до реестра, до кластера. Линтер и сканер дают два
независимых прочтения одного артефакта, и умение читать их вывод —
рабочий навык ревьюера образов.

## 1. Цели

После этого раздела вы сможете:

1. Прогнать hadolint по Dockerfile и разобрать его вывод.
2. Прогнать сканер по образу и отличить находку от шума.
3. Назвать, что линтер не видит и что сканер не проверяет.
4. Поставить обе проверки в конвейер с порогом.

## 3. Механика

**Откуда это взялось.** Dockerfile — текстовый рецепт, и его
проверяемость была заметна сразу. Правила вроде «не latest» и «не ADD
по сети» пишутся по дереву разбора. Проект hadolint добавил к ним второй
уровень: тело RUN —
это shell, и его разбирает ShellCheck. Сканер образов решает задачу,
которую дерево не видит: что фактически попало внутрь. Его устройство —
база уязвимостей и сопоставление пакетов — разобрано в теме `trivy` и
здесь не повторяется; новое место этой темы — сам образ как объект
проверки.

## 4. Что умеет и чего не умеет

hadolint умеет: найти по дереву и по телу RUN ошибки формы — неявный
тег, незафиксированные версии пакетов, CMD не в JSON-форме. Он не видит:
флаги запуска (privileged, сокет, cap-add — это тема
`docker-insecure-practices`), содержимое образа, намерение строки.

Сканер умеет: перечислить пакеты образа и сопоставить им известные
уязвимости с уровнем и ссылкой. Он не проверяет: ваш код, конфигурацию
запуска, секреты в истории (это тема `docker-secret-leaks`), уязвимости,
которых ещё нет в базе.

## 5. Как запустить

Оба прогона ниже выполнены на образах проектов, без установки на хост.
Линтер читает Dockerfile со стандартного ввода:

```bash
docker run --rm -i hadolint/hadolint < Dockerfile
```

Сканер читает образ из локального демона через его сокет:

```bash
docker run --rm -v /var/run/docker.sock:/var/run/docker.sock \
  aquasec/trivy image --severity HIGH,CRITICAL python:3.12-slim
```

Сокет демона здесь отдан чтоб сканер увидел локальные образы — это ровно
та находка из темы `docker-insecure-practices`, и допустима она только
на своём стенде. Порог в конвейере задаётся явно: линтер роняет сборку
по уровню warning, сканер — по уровню уязвимости и наличию фикса.

## 6. Как читать вывод

Вывод линтера — строки вида «строка, правило, уровень, текст». Читается
по коду правила. DL3007 — тег latest: при следующем обновлении базы
сборка изменится молча. DL3008 — версии пакетов не зафиксированы.
DL3025 — CMD в shell-форме: процесс не получит сигналов. Уровень info — не помехи,
а заметки; фильтруются по уровню при шуме.

Вывод сканера — таблица «пакет, CVE, уровень, состояние фикса»:

```text
Total: 19 (HIGH: 16, CRITICAL: 3)
│ gzip │ CVE-2026-41992 │ HIGH │ affected │ 1.13-1 │ …
```

Строки таблицы сокращены по ширине. Читается по колонке состояния:
affected без версии фикса — ждать или менять базу; fix_deferred —
фикс объявлен, ждёт выпуска; есть версия фикса — обновлять. Ложное
срабатывание у сканера: пакет уязвим, но путь его вызова в образе не
задействован — это знание о приложении, а не о таблице. Пропуск:
уязвимость, которой нет в базе на день прогона, — база обновляется
при каждом запуске, и вчерашний «чисто» не доказательство.

## 7. Границы метода

Обе проверки — про образ, а не про запуск: манифест развёртывания они не
читают. Сканер отвечает на состав на день базы; линтер — на форму текста.
Ни один не отвечает на вопрос «а нужен ли этот пакет вообще» — это
вопрос состава, и его решает multi-stage из темы
`docker-multistage-builds`. Образ из чужого реестра обе проверки
прогоняют, но доверия ему это не добавляет: прогон показывает известное,
а не происхождение.

## 8. Ловушка

Распространённый вывод: зелёный прогон сканера означает безопасный
образ.

**Сканер отвечает «известных уязвимостей не найдено», не больше.**
Механизм из блока «Механика»: сопоставление с базой не видит ни вашего
кода, ни конфигурации, ни уязвимостей вне базы.

Контрпример: образ с собственным бинарником, собранным из кода с
уязвимостью, — сканер молчит, потому что пакета в базе нет. И обратно:
19 находок у slim-образа — это повестка на обновление базы, а не
вердикт «образ нельзя использовать».

## 9. Чеклист ревью

1. Verify that каждый Dockerfile проходит hadolint, и замечания выше
   уровня info разобраны.
2. Verify that каждый образ в поставке проходит сканер с порогом по
   уровню и наличию фикса.
3. Verify that теги базовых образов пиннуты по версии (DL3006/DL3007).
4. Verify that сканирование повторяется по расписанию, а не только при
   сборке: база растёт ежедневно.
5. Verify that подавленные находки линтера и сканера несут обоснование
   и срок пересмотра.
6. Verify that флаги запуска проверяются отдельно — линтером они не
   читаются (тема `docker-insecure-practices`).

## 10. Задача

Возьмите Dockerfile и образ своего проекта (или учебный Dockerfile из
введения) и прогоните оба инструмента. Запишите: сколько находок у
линтера и по каким правилам, сколько у сканера и сколько из них с
доступным фиксом.

Одна подсказка: сканеру нужен локальный образ или имя в реестре; линтеру
достаточно текста Dockerfile на стандартном вводе.

**Критерий выполнения** наблюдаемый: два вывода собраны, и для каждой
находки сканера записано решение: обновить, подавить с обоснованием или
принять.

## 11. Проверь себя

1. Что ловит hadolint сверх разбора Dockerfile?
2. Почему флаги запуска не видны линтеру и где они проверяются?
3. Чем находка affected отличается от находки с версией фикса по вашему
   решению?
4. Почему вчерашний чистый прогон сканера не доказательство сегодня?
5. Возврат к теме `trivy`: что сканирует trivy помимо образа и где это
   разобрано?
6. Возврат к теме `docker-insecure-practices`: какие две находки этой
   пары не видны ни линтеру, ни сканеру?

<details markdown="1">
<summary>Ответы</summary>

1. Тело каждого RUN прогоняется через ShellCheck: ошибки shell внутри
   Dockerfile ловятся отдельно.
2. Линтер читает текст Dockerfile, а флаги живут в команде запуска или
   compose-файле. Проверяются глазами по чеклисту или политиками
   кластера.
3. Affected без фикса — ждать, менять базу или подавлять с обоснованием;
   с версией фикса — обновлять пакет или базовый образ.
4. База уязвимостей пополняется ежедневно; прогон отвечает на день базы,
   а не на свойство образа.
5. Зависимости и файловую систему репозитория — это разобрано в теме
   этапа 2; здесь объект проверки — сам образ.
6. Примонтированный docker.sock и privileged: оба — свойства запуска,
   а не текста Dockerfile и не состава образа.

</details>
