# Vault: интеграция с приложением и с CI

Уровень **L2** · время 35 мин (теория 20 / задача 10 / самопроверка 5,
оценка)

Что прочитать сначала: `vault`, `vault-lease-rotation`, `ci-secrets`.

Агент запущен с конфигурацией на восемнадцать строк. Через пять секунд
рядом лежит файл, которого приложение ждало:

```text
$ cat /tmp/agent/db.env
v-approle-reportin-Q6gFi1Sxg2TQBE9f3nsJ-1788269734:PByHNkZ2p-…
```

Приложение не знает слова «Vault»: оно читает файл. Агент вошёл по
approle, получил токен с политикой, вычитал учётку из движка и записал
шаблоном в файл — и будет продлевать аренду, пока работает. Это и есть
интеграция без переписывания. По какому порядку агент превращает шаблон
в файл с секретом — и какие две ловушки пойманы на этом стенде?

## 0. Коротко

Vault Agent — соседний процесс, который берёт на себя хранилище целиком.
Он входит по методу платформы (approle, роль Kubernetes, личность CI),
держит токен, читает секреты и пишет их шаблонами в файлы. Продление
аренды — тоже его работа. Приложение читает файл. В CI то же делает
обмен токена форжа на короткоживущий доступ. Доставка в job написана в
теме `ci-secrets`; здесь остаётся сторона хранилища — как Vault принимает
доверие и что выдаёт взамен.

**Зачем это в работе AppSec-инженера.** Интеграция «не трогая
приложение» — рабочий ответ на вопрос «у нас двести сервисов, мы не
перепишем их». Ревью такой интеграции читает две вещи: чем вошёл агент
и что в его политике.

## 1. Цели

После этого раздела вы сможете:

1. Подключить приложение к Vault агентом, не меняя его код.
2. Написать auto-auth по методу платформы и шаблон секрета в файл.
3. Назвать две ловушки первой интеграции: политика роли и secret_id.
4. Отличить сторону хранилища от стороны конвейера.

## 3. Механика

**Откуда это взялось.** Выдача по политике — тема `vault`, аренда и её
продление — тема `vault-lease-rotation`; там механика разобрана, здесь
она не повторяется. Вопрос этой темы уже: как приложение, написанное до
хранилища, получает выданное. Ответ — процессом-посредником, который
говорит с хранилищем за него.

Агент устроен из трёх частей конфигурации. auto-auth: как войти — метод
и его параметры. `sink`: куда положить полученный токен. template: что
читать и куда записать. Продление и перевход встроены: токен умирает —
агент входит заново, аренда подходит к сроку — агент продлевает или
берёт новую учётку и перезаписывает файл.

## 4. Что умеет и чего не умеет

Умеет: войти по методу платформы без секрета в коде приложения, держать
файл с секретом свежим, продлевать аренды, умереть и перезапуститься.
Не умеет: написать за вас политику (её пишете вы — и это ловушка ниже)
и заставить приложение перечитать файл. Также не умеет защитить
записанный файл сильнее, чем позволяют его права на хосте, — тема
`linux-file-permissions`. Политика, приложение и файл остаются вашими.

## 5. Как запустить

Порядок на стенде темы `vault`, четыре шага:

1. Включите метод входа и заведите роль: `auth enable approle`, роль
   `reporter` с политикой на чтение точки выдачи.
2. Заберите пару role_id и secret_id в файлы рядом с конфигурацией
   агента.
3. Напишите agent.hcl: auto_auth approle с путями к обоим файлам, `sink`
   в файл, template с секретом в `db.env`.
4. Запустите агента и прочитайте файл.

Конфигурация целиком из прогона этой темы. Читается она четырьмя
планами: вход, реквизиты входа, место токена и результат. Вход — блок
auto_auth с методом approle; реквизиты — пути к role_id и secret_id,
там же строка про remove; место токена — sink. Результат — блок
template с секретом в db.env:

```text
auto_auth {
  method "approle" {
    config = {
      role_id_file_path = "/tmp/agent/role_id"
      secret_id_file_path = "/tmp/agent/secret_id"
      remove_secret_id_file_after_reading = false
    }
  }
  sink "file" { config = { path = "/tmp/agent/token" } }
}
template {
  destination = "/tmp/agent/db.env"
  contents = <<-EOT
    {{- with secret "database/creds/reporting" -}}
    {{ .Data.username }}:{{ .Data.password }}
    {{- end }}
  EOT
}
```

Блок template — план «результат» — тот самый файл из введения:
источник — динамическая роль
темы `vault`, содержимое — одна строка «учётка:пароль».

Строка про remove из плана «реквизиты» — не украшение: без неё агент
удаляет secret_id после
первого чтения, и перезапуск умирает с «no known secret ID». Поймано на
стенде этой темы.

## 6. Как читать вывод

Успех — это файл: `db.env` появился и содержит свежую учётку вида
v-approle-… из введения. Вторая проверка — журнал агента: ошибки входа
и рендера шаблона идут туда, и «permission denied» там означает не
сломанный агент, а политику роли без нужного пути. Обе ошибки из этого
текста пойманы прогоном: первая на роли с политикой default, вторая на
перезапуске с удалённым secret_id. По какому из двух каналов — файл
или журнал агента — вы увидите, что учётка сменилась?

## 7. Границы метода

Агент переносит секрет в файл на хосте: права на этот файл — модель из
темы `linux-file-permissions`, и агент пишет с 0600, но каталог вокруг —
ваш. Метод approle годится, пока пара role_id и secret_id хранится
аккуратно; в кластере её заменяет роль Kubernetes, а в CI — личность
job из темы `ci-secrets`. Приложение, читающее файл один раз при старте,
не увидит ротацию — агент пишет, приложение не перечитывает.

Здесь же ответ на вопрос доступности из темы `vault`: у агента есть
кеш. Уже выданное переживает недоступность хранилища: файл с секретом
остаётся на месте. Новой выдачи без хранилища нет.

Отдельная граница — учётка из `connection_url` темы `vault`: ей хватает
создавать и удалять учётные записи динамических ролей и отдавать им то,
что написано в creation_statements. Суперпользователь базы для этого не
нужен, а её утечка отдаёт все выдачи разом.

## 8. Ловушка

Агент запущен, токен на месте — можно ли считать интеграцию
законченной? Вход приравнивают к финишу: раз агент вошёл,
интеграция готова.

**Вход и выдача — разные права.** Токен появился (`sink` написан), а шаблон
падает: политика роли не включает путь секрета. По токену агента вход
выглядит успешным; читается это только по отсутствию файла.

Контрпример из прогона: агент вошёл, токен лежит в `sink`, `db.env` не
создан, в журнале «permission denied» на рендере шаблона. Починка —
политике роли добавить путь, а не перезапускать агента.

## 9. Чеклист ревью

1. Проверьте, что приложение не знает реквизитов хранилища: вход по методу
   платформы, а не токеном в конфиге.
2. Проверьте, что политика роли агента разрешает ровно пути его шаблонов.
3. Проверьте, что файл с секретом пишется с 0600 в каталоге 0700.
4. Проверьте, что secret_id не удаляется после первого чтения либо
   заведён порядок его перевыпуска.
5. Проверьте, что приложение перечитывает файл либо перезапускается по
   ротации.
6. Проверьте, что токен агента ограничен по времени и по политике роли.

## 10. Задача

На стенде темы `vault` поднимите агента по рецепту из блока «Как
запустить» и добейтесь файла db.env со свежей учёткой. Затем сломайте
политику роли (замените на default) и прочитайте журнал агента.

Одна подсказка: агент держит выданный токен; смена политики у роли на
него задним числом не действует — входите заново. Стык с темой `vault`:
там менялось содержимое политики, и оно действует на выданный токен
сразу — токен хранит имя политики, а не её текст.

**Критерий выполнения** наблюдаемый: файл со свежей учёткой записан,
после смены политики в журнале отказ с именем пути, после возврата
политики и перевхода файл снова пишется.

## 11. Проверь себя

1. Агент запущен с таким auto_auth. Предскажите, что случится при
   первом старте и при перезапуске, и проверьте на стенде темы `vault`.

   ```text
   auto_auth {
     method "approle" {
       config = {
         role_id_file_path = "/tmp/agent/role_id"
         secret_id_file_path = "/tmp/agent/secret_id"
       }
     }
     sink "file" { config = { path = "/tmp/agent/token" } }
   }
   ```

2. Прочитайте журнал агента: что сломано — вход или политика, и по какому
   признаку это видно?

   ```text
   (error) template: failed to read secret database/creds/reporting:
   Error making API request. Code: 403. * permission denied
   ```

3. Почему «токен появился в sink» не означает «секрет доехал до файла»?
4. Приложение читает db.env один раз при старте. Чего оно не увидит
   дальше и почему?
5. Возврат к теме `vault-lease-rotation`: кто продлевает аренду, когда
   приложение читает файл?
6. Возврат к теме `ci-secrets`: где кончается доставка секрета в job и
   начинается работа агента?

<details markdown="1">
<summary>Ответ 1</summary>

1. Первый старт пройдёт: агент войдёт и положит токен в sink. Перезапуск
   умрёт с «no known secret ID»: без строки
   `remove_secret_id_file_after_reading = false` агент удаляет файл с
   secret_id после первого чтения, и войти заново нечем. Команда для
   прогона — два запуска `vault agent -config=agent.hcl` подряд на стенде
   лабы; вторая попытка падает с этой ошибкой.

</details>

<details markdown="1">
<summary>Ответ 2</summary>

2. Сломана политика роли, а не вход: вход прошёл — токен лежит в sink и
   запросы подписаны, а 403 стоит на чтении конкретного пути
   `database/creds/reporting`. Политике роли не хватает этого пути;
   починка — добавить путь в политику и войти заново, перезапуск агента
   ничего не меняет.

</details>

<details markdown="1">
<summary>Ответ 3</summary>

3. Вход и выдача — разные права: токен доказывает, что метод входа
   принял агента; чтение секрета решает политика роли. Без пути в ней
   шаблон падает с «permission denied», и по токену агента интеграция
   выглядит успешной — читается это только по отсутствию файла.

</details>

<details markdown="1">
<summary>Ответ 4</summary>

4. Ротации: агент продлевает аренду или берёт новую учётку и перезаписывает
   файл, а приложение держит прочитанное при старте значение. Между
   ротацией и перечитыванием оно ходит мёртвой учёткой. Поэтому к файлу
   прилагается ответ на «как приложение узнаёт»: перечитывание по сигналу
   или перезапуск.

</details>

<details markdown="1">
<summary>Ответ 5</summary>

5. Агент: аренду держит тот, кто писал в файл, — он её и продлевает, пока
   работает, а приложение про аренду не знает ничего. Агент остановлен —
   аренда умрёт по сроку, и файл перестанет обновляться.

</details>

<details markdown="1">
<summary>Ответ 6</summary>

6. Доставка кончается там, где секрет стал доступен job — токеном форжа
   или переменной шага. Агент начинается там, где приложение живёт дольше
   одного job и секрет нужен ему постоянно. В CI обмен токена job на
   короткий доступ решает ту же задачу без файла.

</details>
