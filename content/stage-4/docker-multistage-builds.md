# Multi-stage сборка и минимальный базовый образ

Уровень **L2** · время 30 мин (теория 20 / задача 7 / самопроверка 3,
оценка)

Два образа собраны из почти одного Dockerfile, отличие — вторая строка
FROM. Смотрим, что получилось на выходе:

```text
$ docker images
demo-multi     latest   ed5e065a0db8   179MB
demo-single    latest   73688186a80a   284MB
```

Метки и колонки в выводе сокращены по ширине. В обоих образах
одинаковое приложение, но во второй доехало сборочное окружение на 50 МБ,
а в первый — нет. Разница в выводе вдвое больше: собранный локально
слой хранится в двух копиях, пакетом и распаковкой, и учёт размера
видит обе. Это и есть тема: multi-stage сборка как способ решить,
что из окружения сборки окажется в продакшен-образе.

Если вы писали Dockerfile с компилятором или менеджером пакетов внутри,
вопрос уже стоял: всё, что попало в образ при сборке, едет в продакшен.
Впереди — рецепт: как устроена вторая стадия, как собрать и как прочитать
итог. Приём конечный и раскладывается инструкцией; новой модели здесь
нет.

## 0. Коротко

Multi-stage сборка — несколько стадий FROM в одном Dockerfile. Стадия
сборки содержит компиляторы, заголовки и ключи развёртывания; итоговая
стадия получает только артефакт через COPY --from. Читатель образа видит
итог через docker images (размер) и docker history (слои и команды).
Приём про состав, а не про магию: он убирает из поставки то, что там не
должно оказаться, — инструменты сборки и то, что через них утекает.

**Зачем это в работе AppSec-инженера.** Образ, в котором остались
компилятор и сетевые утилиты, — это готовый инструментарий для того, кто
попал внутрь контейнера. Проверка состава образа — штатный вопрос
ревью, и multi-stage — его дешёвый ответ.

## 1. Цели

После этого раздела вы сможете:

1. Отделить сборочное окружение от рантайма второй стадией FROM.
2. Собрать одну стадию через --target и прочитать, что доехало до
   итога.
3. Прочитать состав образа через docker history и docker images.
4. Назвать, чего multi-stage не умеет.

## 3. Механика

**Откуда это взялось.** Образ собирается слоями, и каждая инструкция
оставляет свой слой навсегда: удалённое следующей инструкцией остаётся
в истории. Подробно эта механика разобрана в теме `docker-secret-leaks`;
здесь важно следствие: почистить образ после сборки нельзя, можно только
не положить. Multi-stage отвечает на это сменой окружения: собираем в
одном образе, поставляем из другого, и слои первого в итог не входят.

У стадии может быть имя (`FROM ... AS build`), и из итоговой стадии в неё
забирают файлы: `COPY --from=build`. Базовый образ итоговой стадии —
отдельный вопрос: slim-вариант или вовсе scratch, где кроме артефакта
ничего нет.

## 4. Что умеет и чего не умеет

Умеет: убрать сборочное окружение из итогового образа, держать сборку и
поставку в одном файле, собирать отдельную стадию через --target.
Не умеет: лечить содержимое базового образа (уязвимый slim остаётся
уязвимым — это тема `dockerfile-lint-image-scan`) и прятать то, что
скопировано в итог: COPY --from тащит файл целиком. Также не подменяет
выбор базового образа. И не делает сборку воспроизводимой само по себе:
тег latest в FROM решает это негативно каждый раз заново.

## 5. Как запустить

Рецепт на учебном примере: «сборка» создаёт артефакт и тяжёлое окружение
(50 МБ, изображают toolchain), итог забирает только артефакт.

```dockerfile
# Файл целиком, собирается docker build
FROM python:3.12-slim AS build
WORKDIR /app
RUN dd if=/dev/urandom of=/app/toolchain.bin bs=1M count=50
RUN dd if=/dev/urandom of=/app/artifact.bin bs=1M count=1

FROM python:3.12-slim
WORKDIR /app
COPY --from=build /app/artifact.bin /app/artifact.bin
CMD ["python", "-c", "print('app')"]
```

Сборка и точечная сборка одной стадии:

```bash
docker build -t demo-multi .
docker build --target build -t demo-build-only .
```

Порядок действий для живого проекта: найдите, что нужно итогу. Обычно
это один бинарник или каталог dist. Перенесите его в COPY --from, уберите
из итоговой стадии всё сборочное, соберите и сравните.

## 6. Как читать вывод

Размер — первый признак, но не доказательство: сравнивать надо состав.
Вводный вывод: 179 МБ против 284 МБ при одном приложении. Состав читает
history:

```text
$ docker history demo-multi
IMAGE          CREATED BY                                     SIZE
ed5e065a0db8   CMD ["python" "-c" "print…                     0B
fbc9aa3fb9f8   COPY file:8e2906a9f430cc70…                   1.06MB
50d047d7bcd0   WORKDIR /app                                   8.19kB
```

Колонки урезаны по ширине, вывод — верхние строки. В истории итога есть
только COPY артефакта; слоёв с toolchain.bin нет. Именно это и есть
критерий приёмки: итоговая история не содержит сборочных инструкций.
Обратная проверка — `docker history demo-single`: там обе строки с dd
на месте.

## 7. Границы метода

Приём решает состав поставки и ничего больше. Секрет, попавший в стадию
сборки, в итог не попадёт — но сам факт его присутствия в сборке опасен
по-другому, и это тема `docker-secret-leaks`. Кеш стадий обманывает:
изменённый исходник при неизменном COPY пересоберётся не так, как
ожидалось, — смотрите на итоговую history, а не на кеш. Базовый образ
итоговой стадии выбирается отдельно и чинится отдельно. И на стенде без
buildx синтаксис секретов сборки недоступен — устаревший builder печатает
предупреждение прямо при сборке.

## 8. Ловушка

Распространённый вывод: раз образ меньше, он безопаснее.

**Размер — следствие, а не свойство.** Механизм из блока «Механика»:
безопасность определяется составом — чем в образе можно воспользоваться.
Образ с bash и curl внутри даёт атакующему готовый набор инструментов;
большой образ без них — нет.

Контрпример: образ на 40 МБ меньше, но содержит компилятор и wget —
для удержания позиции внутри контейнера это готовый набор. Multi-stage
работает только когда меняется состав, а не счётчик мегабайт.

## 9. Чеклист ревью

1. Verify that итоговая стадия не содержит сборочных инструментов:
   компиляторов, менеджеров пакетов, сетевых утилит.
2. Verify that в итог копируется только артефакт (COPY --from), а не
   весь каталог сборки.
3. Verify that история итогового образа не содержит сборочных
   инструкций (docker history).
4. Verify that базовый образ итоговой стадии пиннут по версии, а не
   latest.
5. Verify that секреты в сборку приходят через механизм секретов,
   а не через ARG — тема `docker-secret-leaks`.
6. Verify that выбран минимальный рабочий базовый образ, а не «полный
   на всякий случай».

## 10. Задача

Возьмите Dockerfile своего проекта или учебный из блока «Как запустить»
и переведите его на две стадии: сборка отдельно, поставка отдельно.

Одна подсказка: сначала соберите обе версии и положите рядом вывод
docker images и docker history — разница и есть ответ, замер нужен до
переписывания.

**Критерий выполнения** наблюдаемый: в истории итогового образа нет
сборочных инструкций, приложение стартует из итогового образа, а размер
упал не меньше чем на размер сборочного окружения.

## 11. Проверь себя

1. Что попадает в итоговый образ из стадии сборки и как именно?
2. Почему удаление инструментов последней инструкцией не очищает образ?
3. Что покажет docker history итоговой стадии после multi-stage сборки?
4. Чем multi-stage не поможет, даже если применён правильно?

<details markdown="1">
<summary>Ответы</summary>

1. Только то, что явно скопировано через COPY --from. Слои стадии
   сборки в итог не входят.
2. Удаление — это новый слой поверх; сам файл остаётся в предыдущем
   слое навсегда (тема `docker-secret-leaks`).
3. Только инструкции итоговой стадии: FROM базы, COPY артефакта, CMD.
   Сборочных RUN там нет.
4. Содержимым базового образа, секретами в сборке, воспроизводимостью:
   это инструмент состава поставки, а не их источников.

</details>

> нет предпосылок, это её собственный вход в подраздел.

## 12. Источники

1. Multi-stage builds, документация Docker; реестр `docker-multistage`.
   Разделы: вторая стадия FROM, COPY --from, сборка через --target.
   <https://docs.docker.com/build/building/multi-stage/>
2. docker image history, справка CLI Docker; реестр `docker-image-history`.
   Разделы: колонки вывода, ключи --no-trunc и --format.
   <https://docs.docker.com/reference/cli/docker/image/history/>

Каркас этапа: записи семейства man-* и якоря подраздела 4.2
(docker-engine-security, owasp-cs-docker) — наследуются всеми темами
подраздела.

**Скоропортящийся слой.** Синтаксис и умолчания builder меняются:
устаревший builder в Docker 29 печатает предупреждение, синтаксис
секретов требует buildx. Размеры образов — свойство версий базы
и хранилища образов.

**Маркеры уверенности.** **Проверено лично** 2026-09-01 на Arch Linux,
Docker 29.7.2, образ python:3.12-slim: сборка обеих версий (284 МБ против
179 МБ), история итога без сборочных слоёв, запуск итогового образа
(печатает «app»), предупреждение устаревшего builder. Синтаксис
`RUN --mount=type=secret` проверен на buildx 0.30.1 в изолированном
DOCKER_CONFIG — см. тему `docker-secret-leaks`. Поведение --target и
scratch-базы — **по документации** (docker-multistage, открыта лично
2026-09-01).
