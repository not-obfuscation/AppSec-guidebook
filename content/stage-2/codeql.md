# CodeQL: модель данных и базовые запросы

Уровень **L2** · время 45 мин (теория 28 / задача 12 / самопроверка 5,
оценка)

Что прочитать сначала: `sast-principles`, `semgrep-rules`.

Четыре строки — весь отчёт CodeQL по стенду с тремя подставленными
дефектами:

```text
SQL query built from user-controlled sources | /app.py | 21 | 29
Uncontrolled command line                    | /app.py | 39 | 27
Uncontrolled data used in path expression    | /app.py | 46 | 15
SQL query built from user-controlled sources | /app.py | 31 | 29
```

Читайте имена. «Запрос собран из данных, которыми управляет
пользователь» — не описание формы кода, а утверждение о пути. Значение
дошло от ввода до опасного места через любое число функций. Тот же
файл гоняли ещё двумя инструментами; их таблицу разберём ниже. А те же
три дефекта, переписанные без веб-каркаса, дали в CodeQL ноль находок.
Библиотека не знает, что разбор строки запроса приносит внешние данные,
и путь не начинается.

Предмет темы — модель, из которой это следует. CodeQL превращает
исходный код в базу данных: сущности языка и связи между ними, включая
предвычисленный поток значений. Проверка — запрос к этой базе: «выбери
узлы, для которых верно вот это». Знание об источниках и стоках
приходит из библиотеки языка — в этом сила на знакомом каркасе и та
же причина молчания на незнакомом.

Дальше разберём, из чего состоит база и как она строится извлечением,
и как читается запрос из трёх частей. Отдельно — сравнение трёх
инструментов на одном коде и ответ на вопрос, нужен ли CodeQL рядом с
уже стоящим сопоставлением по образцу.

## 0. Коротко

CodeQL превращает исходный код в базу данных и ищет в ней запросами. В базе
лежат не строки, а сущности языка и связи между ними: выражения, вызовы,
типы, наследование, поток значений. Запрос пишется на своём языке и читается
как «выбери такие узлы, для которых верно вот это».

Отличие от сопоставления по образцу не в объёме выразимого, а в том, откуда
берётся знание. Образец описывает форму кода, и всё знание в нём — от автора правила.
Запрос опирается на библиотеку языка, где уже описано, какие вызовы считаются
источниками внешних данных и какие — опасными стоками. Отсюда обе стороны:
готовая модель даёт находки, которых образцом не выразить, и она же молчит
там, где каркас приложения библиотеке незнаком.

**Зачем это в работе AppSec-инженера.** Отчёт CodeQL читать приходится
независимо от того, пишет ли инженер запросы: инструмент ставят в конвейеры
репозиториев, и его находки разбирают вместе с разработкой. Второй повод
практический. Когда в конвейере уже стоит сопоставление по образцу, вопрос
«зачем второй инструмент» задают на первом же обсуждении бюджета. Отвечать на
него надо числами со своего кода.

## 3. Механика

**Откуда это взялось.** Правила анализаторов писались под конкретный вопрос:
одно правило — один класс дефекта. Ломалось это на вопросах, которых автор
правила не предвидел. Ответом стала другая раскладка: извлечь из кода всё, что
о нём известно, в базу, а вопросы задавать потом — запросами, которые пишет
тот, кому вопрос понадобился.

База строится извлечением. Для языков без сборки — Python, JavaScript, Ruby —
достаточно исходников; для компилируемых нужна сборка, потому что извлекатель
слушает компилятор [^1]. Готовая база — это набор таблиц с сущностями языка и
предвычисленными связями между ними.

Запрос состоит из блока метаданных в комментарии, импортов библиотек и
необязательных своих классов и предикатов. Дальше идут три части: `from`
объявляет переменные, `where` задаёт условие, `select` называет вывод [^2].
Готовые запросы про безопасность почти целиком состоят из вызова библиотеки
потока данных: она описывает источники, стоки и барьеры, а запрос спрашивает,
есть ли путь [^3].

## 4. Что умеет и чего не умеет

**Что умеет.** Спрашивать о связях, а не только о форме. Какие классы
наследуют этот интерфейс, какие вызовы достижимы из обработчика, доходит ли
значение отсюда туда через любое число функций. Межпроцедурный и межфайловый
путь для CodeQL — обычная работа, а не платная надстройка. Модель источников
и стоков приходит из библиотеки, поэтому запрос не переписывается под каждый
новый каркас.

**Чего не умеет.** Первое — работать без модели каркаса. Если библиотека не
знает, что этот вызов приносит внешние данные, путь не начнётся, и запрос
промолчит на настоящем дефекте. Второе — обходиться без сборки на
компилируемых языках. Третье — быть дешёвым: база строится минуты и занимает
место, а прогон полного набора запросов дороже сопоставления по образцу на
том же коде.

## 5. Как запустить

Бесплатный CLI ставится распаковкой сборки, куда входят и стандартные наборы
запросов. Прогон — две команды.

```bash
# CodeQL 2.26.3. Шаг 1: извлечь код в базу.
codeql database create db-shopweb --language=python \
       --source-root=exp/shopweb
```

```bash
# Шаг 2: прогнать набор запросов и получить отчёт.
codeql database analyze db-shopweb \
       codeql/python-queries:codeql-suites/python-security-extended.qls \
       --format=csv --output=out/codeql.csv
```

Для компилируемого языка между этими шагами стоит сборка: команда `create`
принимает `--command` и слушает компилятор [^1].

## 6. Как читать вывод

Отчёт в табличном формате — одна строка на находку: имя запроса, файл,
строка, позиция.

```text
SQL query built from user-controlled sources | /app.py | 21 | 29
Uncontrolled command line                    | /app.py | 39 | 27
Uncontrolled data used in path expression    | /app.py | 46 | 15
SQL query built from user-controlled sources | /app.py | 31 | 29
```

Имя запроса называет не форму кода, а утверждение о пути: «запрос собран из
данных, которыми управляет пользователь». Дубли отсутствуют — одно место
даёт одну строку.

Стенд — обработчики веб-каркаса с тремя подставленными дефектами и одним
чистым местом похожей формы. Строки 21, 39 и 46 — настоящие дефекты. Строка
31 — чистый код: имя таблицы сверено с замкнутым множеством перед
подстановкой. Проверка сравнением барьером для модели не стала, и это то же
ложное срабатывание, которое дали два других инструмента.

Тот же файл, три инструмента:

```text
инструмент         записей   мест   настоящих   пропущено
Semgrep p/default       14      7           3           0
bandit                   4      4           2           1
CodeQL                   4      4           3           0
```

Пропуск bandit — путь к файлу из параметра запроса: без потока данных этот
дефект не виден. Четырнадцать записей Semgrep — не четырнадцать мест: одно и
то же место печатается несколькими правилами набора.

Отдельно стоит второй прогон того же кода без веб-каркаса. Те же три дефекта,
переписанные на стандартную библиотеку и разложенные по шести файлам, дали в
CodeQL **ноль находок**. Библиотека не знает, что разбор строки запроса
приносит внешние данные, и путь не начинается. Semgrep на том же коде нашёл
оба дефекта SQL.

Что делать с настоящими находками, разбирают темы `sqli-basics`,
`os-command-injection` и `path-traversal`.

## 7. Границы метода

**Граница первая: модель источников — это чужое знание.** Своя обёртка над
вводом или редкий каркас означают молчание до тех пор, пока модель не описана
своими средствами. Ноль находок на стенде без каркаса — измеренный случай,
а не предположение.

**Граница вторая: цена.** База строится и занимает место, а полный набор
запросов идёт заметно дольше прогона по образцу. На конвейере это выражается в
отдельном шаге со своим кэшем, а не в добавлении одной команды.

**Граница третья: свои запросы — отдельная профессия.** Прочитать запрос
проще, чем написать его: чтение опирается на имя и метаданные, письмо — на
библиотеку языка целиком.

## 8. Ловушка

Распространённое мнение: раз CodeQL сильнее по модели, он заменяет
сопоставление по образцу, и держать два инструмента незачем.

**Сильнее по модели не значит шире по покрытию.** Прогон на стенде без
знакомого каркаса дал ноль находок там, где сопоставление по образцу нашло два
дефекта из трёх. Модель потока покрывает то, что описано в библиотеке, а
образец покрывает то, что описал автор правила час назад под свою обёртку.

Контрпример к обратному выводу: на том же коде с веб-каркасом CodeQL нашёл
дефект, который bandit пропустил полностью, и сделал это без единого дубля.
Инструменты закрывают разные пропуски, и вопрос «какой из двух» подменяет
вопрос «что каждый из них не видит».

## 9. Чеклист ревью

1. Verify that база построена на том же дереве, которое собирается в
   конвейере, а не на срезе без сгенерированного кода.
2. Verify that для компилируемого языка извлечение шло вместе со сборкой.
3. Verify that набор запросов назван в отчёте: наборов несколько, и они
   различаются по составу.
4. Verify that число просмотренных файлов прочитано: молчание на незнакомом
   каркасе выглядит как чистый отчёт.
5. Verify that каркас приложения входит в модель библиотеки, а не заявлен
   поддерживаемым по имени языка.
6. Verify that CodeQL сопоставлен со вторым инструментом на своём коде, а не
   выбран вместо него по описанию.

## 10. Задача

Собрать базу по своему репозиторию и прогнать набор запросов про безопасность.
Сравнить список мест с прогоном инструмента, который уже стоит в конвейере.

Одна подсказка: сравнивать надо места, а не записи, — иначе разница в числе
находок объяснится дублями, а не покрытием.

**Критерий выполнения** наблюдаемый: получены два списка мест и таблица
расхождений, где каждое место, найденное одним инструментом и пропущенное
другим, снабжено причиной.

## 11. Проверь себя

1. Что лежит в базе CodeQL и чем это отличается от дерева разбора?
2. Из каких частей состоит запрос и какая из них называет выводимое?
3. Почему на коде без знакомого веб-каркаса прогон дал ноль находок?
4. Почему в отчёте CodeQL четыре записи на четырёх местах, а у набора правил
   по образцу — четырнадцать записей на семи?
5. Для какого класса языков между извлечением и анализом обязательно стоит
   сборка и почему?
6. Возврат к теме `semgrep-rules`: в чём разница между «источник описан в
   библиотеке» и «источник описан в правиле»?

<details markdown="1">
<summary>Ответы</summary>

1. Сущности языка и связи между ними: выражения, вызовы, типы, наследование,
   поток значений. Дерево разбора описывает одну форму одного файла, база —
   ещё и связи между файлами и предвычисленные отношения.
2. Блок метаданных, импорты, необязательные свои классы и предикаты, затем
   `from`, `where` и `select`. Выводимое называет `select`.
3. Потому что библиотека не знает, что разбор строки запроса стандартной
   библиотекой приносит внешние данные. Источник не размечен, путь не
   начинается, и запрос молчит на настоящем дефекте.
4. Потому что запрос утверждает наличие пути, и один путь даёт одну строку.
   В наборе правил по образцу одно место совпадает с несколькими правилами
   сразу, и каждое печатает свою запись.
5. Для компилируемых: извлекатель слушает компилятор, и без сборки в базу не
   попадёт ни один файл. Для языков без сборки достаточно исходников.
6. Библиотечная модель приходит с инструментом и покрывает известные каркасы,
   не требуя работы от автора запроса. Модель в правиле пишется под свой код
   и покрывает ровно то, что автор описал, включая внутренние обёртки.

</details>
