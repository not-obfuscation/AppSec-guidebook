# Сканирование API по спецификации OpenAPI

Уровень **L2** · время 40 мин (теория 24 / задача 11 / самопроверка 5,
оценка)

Что прочитать сначала: `zap-scanning`, `rest-and-graphql`.

Замер на учебном стенде: полный обход под входом сделал 2516 запросов.
К путям на `/api` не ушёл ни один. Тот же стенд, но вместо обхода
сканеру отдали файл описания. Итог: шесть адресов в списке, 1323
запроса, три находки высокого риска. Это инъекция `CWE-89`, чтение файла
по обойдённому пути `CWE-22` и отражение разметки на странице ошибки.

Паук находит адреса, переходя по ссылкам. В ответах API ссылок нет:
перечень адресов знает клиент, а не документ, поэтому обходу нечего
читать. Прогон формально состоялся, а API в нём не участвовало.

Файл, подставленный на место паука, — спецификация OpenAPI,
машиночитаемое описание API, которое и так пишут для разработчика
клиента. Каждая операция в нём даёт метод, путь и перечень параметров —
то, из чего сканер собирает по одному запросу на операцию. Этого сканеру
достаточно для прогона.

Дальше разберём, что сканер берёт из описания, а что достраивает сам и
почему выдуманное значение параметра не доходит до проверяемого кода.
Две настройки ломают прогон, если о них не знать. Забытая подмена
базового адреса отправляет запросы на рабочую систему из поля
`servers`. Широкая область разворачивает активные правила на весь
хост. И следствие, к которому тема возвращается в конце: охват прогона
равен полноте описания, поэтому список операций сверяют с маршрутами в
коде отдельной проверкой.

## 0. Коротко

Паук находит адреса, переходя по ссылкам. В API ссылок нет: клиент знает адреса
заранее, потому что их знает разработчик клиента. Отсюда — прогон, который
формально прошёл и не проверил ничего.

Замер на стенде: полный обход под входом сделал 2516 запросов и **ни одного**
к путям, начинающимся на `/api`. Импорт спецификации на место паука добавил
шесть адресов. Активное сканирование по ним нашло три дефекта высокого риска:
инъекцию `CWE-89`, чтение файла по обойдённому пути `CWE-22` и отражение
разметки на странице ошибки. Ни одного из них не было ни в одном прогоне по
разметке.

Спецификация здесь работает как карта: каждая операция даёт метод, путь и
перечень параметров, то есть ровно то, что сканеру нужно для подстановки.
Отсюда и главное следствие: **охват прогона равен полноте спецификации.**

**Зачем это в работе AppSec-инженера.** Первый практический вопрос по
безопасности API — «мы просканировали API?». Ответ «да, ZAP
прошёл по сайту» на этот вопрос не отвечает: сканер по сайту не отправил в
API ни одного запроса.

## 1. Цели

После этого раздела вы сможете:

1. Импортировать спецификацию в сканер вместо обхода и получить отчёт по API.
2. Назвать, что берётся из спецификации, а что сканер достраивает сам.
3. Сверить перечень путей спецификации с настоящими путями приложения.

## 3. Механика

**Откуда это взялось.** Пока весь ввод жил в формах, обход по ссылкам работал:
всё, что можно отправить, лежало на странице. С переездом клиента в браузерный
код и в мобильное приложение перечень адресов ушёл из разметки, и паук перестал
их находить. Первым обходом было записать трафик настоящего клиента и
скормить его сканеру. Это работает, но повторить нельзя: запись зависит от того,
куда в тот раз нажали. Тогда взяли то, что и так пишут для клиента, —
машиночитаемое описание API.

Тема даёт рецепт настройки, поэтому из механики оставлен минимум, нужный для
понимания результата. Как устроен REST и чем он отличается от GraphQL,
разобрано в `rest-and-graphql`; устройство самого прогона — в `zap-scanning`.

Что сканер берёт из спецификации: путь операции и метод, перечень параметров с
местом каждого (путь, строка запроса, заголовок, cookie) и схему тела
запроса [^2]. Из этого он собирает по одному запросу на операцию и кладёт их в
список, откуда их берут активные правила. То есть делает ровно то, что делал бы
паук, только по описанию, а не по ссылкам.

Чего в спецификации нет и что сканер достраивает сам: **значения**. Если у
параметра стоит `default`, берётся оно; иначе подставляется что-нибудь по типу.
Запрос с выдуманным значением может не дойти до кода, который вы хотели
проверить: операция вернёт 400, и активное правило будет работать по странице
ошибки.

## 4. Что умеет и чего не умеет

**Что умеет.** Прочитать описание из файла или по адресу, в JSON или в YAML,
версий 1.2, 2.0 и 3.x. Развернуть его в перечень запросов и передать активным
правилам. Подставить свой базовый адрес вместо того, что записан в описании, —
это нужно всегда, потому что в описании стоит адрес рабочей системы.

**Чего не умеет.** Проверить операцию, которой в описании нет. Ручка
`/api/v1/reports` на стенде не связана ни с одной страницей. Ни один прогон по
разметке её не видел: нашлась она только потому, что её вписали в
спецификацию. Обратный случай встречается чаще: ручка есть, а в спецификации её
нет — тогда её не найдёт и этот прогон.

**Чего не умеет ни один режим на API.** Отличить свой объект от чужого. Ручка
`/api/v1/orders/{id}` отдаёт заказ без проверки владельца; в отчёте её нет.
Почему это не лечится настройкой — `dast-limits`.

## 5. Как запустить

ZAP 2.17.0, стенд «Лавка», описание на `/api/openapi.json`. Работа `openapi`
подставляется на место работы `spider`, остальной план не меняется. В плане
четыре работы, и у каждой своя роль: `openapi` собирает адреса из описания,
`passiveScan-wait` ждёт очередь, `activeScan` идёт по собранному, `report`
выгружает итог:

```yaml
env:
  contexts:
    - name: lavka-api
      urls: ["http://127.0.0.1:8081/"]
      includePaths: ["http://127.0.0.1:8081/api.*"]
jobs:
  - type: openapi
    parameters:
      apiUrl: "http://127.0.0.1:8081/api/openapi.json"
      targetUrl: "http://127.0.0.1:8081/"
      context: lavka-api
  - type: passiveScan-wait
  - type: activeScan
    parameters: {context: lavka-api, maxScanDurationInMins: 10}
  - type: report
    parameters:
      template: traditional-json
      reportDir: "./out"
      reportFile: "api"
```

Вместо `apiUrl` можно дать `apiFile` — путь к файлу описания; так делают, когда
описание лежит в репозитории, а не отдаётся приложением.

Две вещи, которые ломают прогон, если о них не знать.

**`targetUrl` обязателен, даже когда кажется лишним.** В описании стоит поле
`servers`, и в рабочем описании там адрес рабочей системы. Без подмены прогон
уйдёт туда, а не на ваш стенд, — и это тот случай, когда ошибка настройки
означает сканирование чужого узла.

**Область контекста надо сузить.** В плане выше `includePaths` ограничивает
прогон путями `/api`. Без этого активные правила уйдут гулять по всему хосту, и
отчёт перестанет быть отчётом по API.

## 6. Как читать вывод

```text
                             обход по ссылкам   импорт описания
запросов к путям /api                       0              1323
адресов добавлено в список                  0                 6
сработало правил                            —                 5
находок высокого риска                      —                 3
```

Три находки высокого риска:

```text
40018  SQL Injection   GET /api/v1/products?filter='            conf=Low
6      Path Traversal  GET /api/v1/reports?path=/etc/passwd     conf=Medium
40026  XSS (DOM)       GET /api/v1/reports?path=<script>…       conf=High
```

Первая — `CWE-89`, склейка значения со строкой запроса; чинится в
`sqli-basics`. Вторая — `CWE-22`, путь к файлу из параметра; чинится в
`path-traversal`. Третья — отражение полезной нагрузки на странице ошибки: та же
ручка, но найдена по другому признаку.

**Чего в отчёте по API нет и почему.** Ни правила про отсутствующий
`Content-Security-Policy`, ни правила про заголовок от вставки в рамку в отчёте
не сработали ни разу, хотя на стенде их нет нигде. Оба правила смотрят только
на ответы с разметкой: у ответа `application/json` нет ни того, ни другого
смысла. Пассивных правил на API вообще срабатывает меньше — в отчёте их два:
про версию сервера и про отсутствующий `X-Content-Type-Options`, который для
JSON как раз имеет смысл.

**Что означает список адресов.** Работа `openapi` напечатала «added 6 URLs».
Операций в описании пять, шестой адрес — сама спецификация. Это и есть весь
охват прогона, и его надо сверять с настоящим перечнем путей приложения.
Расхождение между описанием и кодом — типовая находка, и находят её не
сканером, а сравнением двух списков: операций в описании и маршрутов в коде.
В отчёте по вашему API шесть адресов, а маршрутов в коде девять — что именно
проверил прогон и что он пропустил?

## 7. Границы метода

**Граница первая: описание — это обещание, а не приложение.** Оно пишется
руками или собирается из кода и отстаёт от него. Операция, снятая с публикации
и оставшаяся в коде, в описании не появится; операция, добавленная вчера, —
тоже. Прогон по описанию проверяет описанное.

**Граница вторая: значения.** Сканер подставляет `default` или что-нибудь по
типу. Операция, которая проверяет входные данные и отвечает 400 на выдуманное
значение, будет проверена по своей же странице ошибки. Признак — отчёт, где все
находки указывают на одну и ту же реакцию приложения.

**Граница третья: вход.** У API он обычно не в cookie, а в заголовке с токеном,
и настраивается отдельно от импорта описания; порядок — в
`authenticated-scanning`. Без него прогон по защищённым операциям вернёт
кучу ответов 401 и ни одной находки.

**Цена.** 1323 запроса на шесть адресов — около двухсот на адрес. Это
дороже в пересчёте на адрес, чем прогон по разметке: там 1331 запрос на
одиннадцать адресов. У операции API параметров обычно больше, а страниц, на
которые нечего подставлять, нет вовсе.

## 8. Ловушка

У метода есть репутация исчерпывающего: если у приложения есть описание OpenAPI, значит его API
можно просканировать полностью. Есть ли описание у вашего API и был ли полным
последний прогон по нему — ответьте на оба до разбора.

**Полнота прогона равна полноте описания, а полноту описания никто не мерил.**
На стенде описание было написано вместе с приложением и совпадало с ним; в
жизни оно живёт отдельно. Ручка, которую забыли описать, для прогона не
существует — ровно так же, как ручка без ссылки не существует для паука.
Метод не расширил охват, он перенёс его границу из разметки в файл описания.

Контрпример к обратному выводу — «значит, и описание не поможет»: на стенде оно
дало два настоящих дефекта, которых не нашёл ни один прогон по разметке.
Правильный вывод не «бесполезно», а «список операций — отдельный артефакт, и
его надо проверять отдельно», сравнением с маршрутами в коде.

## 9. Чеклист ревью

1. Verify that в прогоне подменён базовый адрес и запросы ушли на проверяемый
   стенд, а не на адрес из поля `servers`.
2. Verify that область прогона ограничена путями API, а не всем хостом.
3. Verify that число операций в описании названо и сверено с перечнем маршрутов
   в коде.
4. Verify that операции, требующие входа, прогнаны с токеном, а не отвечают 401.
5. Verify that подставленные значения параметров доходят до проверяемого кода, а
   не отбиваются проверкой входных данных.
6. Verify that про операции, которых в описании нет, сказано в отчёте прямо.

## 10. Задача

Взять описание своего API, прогнать по нему сканер и отдельно собрать перечень
маршрутов из кода. Свести два списка в одну таблицу: есть в обоих, есть только
в описании, есть только в коде.

Одна подсказка: третья колонка — самая интересная, и собрать её обычно можно
одной командой поиска по объявлениям маршрутов в исходниках.

**Критерий выполнения** наблюдаемый. У вас есть число операций в описании,
число маршрутов в коде и поимённый список расхождений в обе стороны.

## 11. Проверь себя

1. Почему обход по ссылкам находит в API ноль адресов?
2. Что сканер берёт из описания и чего в описании нет?
3. Зачем при импорте описания подменять базовый адрес и чем грозит забытая
   подмена?
4. Почему в отчёте по API не сработало правило про отсутствующий
   `Content-Security-Policy`?
5. Ручка есть в коде и нет в описании. Найдёт ли её прогон по описанию и
   почему?
6. Возврат к теме `rest-and-graphql`: почему для GraphQL перечень операций из
   OpenAPI не собрать?

<details markdown="1">
<summary>Ответы</summary>

1. В ответах API нет ссылок, по которым можно перейти: перечень адресов знает
   клиент, а не документ.
2. Берёт метод, путь, перечень параметров с их местом и схему тела. Значений в
   описании нет — сканер подставляет `default` или что-нибудь по типу.
3. В поле `servers` записан адрес рабочей системы. Без подмены прогон уйдёт
   туда, то есть станет сканированием чужого узла.
4. Правило смотрит только на ответы с разметкой. У ответа `application/json`
   политики содержимого нет и быть не должно.
5. Не найдёт. Охват прогона равен перечню операций в описании.
6. У GraphQL одна точка входа и запрос описывается схемой самого языка, а не
   перечнем путей и параметров; перечня операций в форме OpenAPI там нет.

</details>

## 12. Источники

1. ZAP, «OpenAPI Support»; реестр `zap-openapi`. Разделы: импорт описания из
   файла и по адресу, подмена базового адреса, работа `openapi` в плане
   автоматизации и её параметры `apiFile`, `apiUrl`, `targetUrl`.
   <https://www.zaproxy.org/docs/desktop/addons/openapi-support/>
2. OpenAPI Initiative, «OpenAPI Specification»; реестр `openapi-spec`. Разделы:
   объект операции, объект параметра и его поле `in` (path, query, header,
   cookie), тело запроса и его схема, объект `servers`.
   <https://spec.openapis.org/oas/latest.html>

Каркас этапа: `cwe-taxonomy`. Наследуется всеми темами и отдельной строкой не
повторяется.

**Скоропортящийся слой.** Имена параметров работы импорта, поддерживаемые
версии описания, состав мест параметра в спецификации. Соотношение «охват
прогона равен полноте описания» от версий не зависит.

**Маркеры уверенности.** Числа сняты **лично** 2026-08-25 на ZAP 2.17.0 по
стенду на `127.0.0.1`: ноль запросов к путям `/api` за полный обход под входом
в 2516 запросов, пять операций в описании и шесть адресов в списке прогона,
1323 запроса прогона по описанию, пять сработавших правил и три находки
высокого риска, отсутствие правил про
политику содержимого и про вставку в рамку на ответах JSON. Состав того, что
сканер берёт из описания, — **по документации** ZAP и по тексту спецификации
OpenAPI, открытым лично 2026-08-25. Поведение на описаниях версии 2.0 и на
GraphQL **не воспроизводилось**.

[^2]: OpenAPI Initiative, «OpenAPI Specification», реестр `openapi-spec`.
