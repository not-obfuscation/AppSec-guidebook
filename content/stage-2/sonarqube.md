# SonarQube: quality gates и что они закрывают

Уровень **L2** · время 45 мин (теория 27 / задача 13 / самопроверка 5,
оценка)

Что прочитать сначала: `sast-principles`.

## 0. Коротко

SonarQube — сервер, который принимает отчёты сканера, хранит их по проектам и
считает по ним метрики. Поверх метрик стоит порог качества: набор условий вида
«метрика, оператор сравнения, пороговое значение». Если сработало хоть одно
условие, вердикт красный [^1].

Порог отвечает на вопрос «пускать ли эту сборку дальше» на языке метрик, а не
находок. Отсюда главное, что нужно знать инженеру: зелёный вердикт означает
выполнение условий, а не отсутствие дефектов. Насколько велика эта разница,
меряется прогоном, и на бесплатной сборке она оказалась максимальной.

**Зачем это в работе AppSec-инженера.** SonarQube стоит почти в каждом
конвейере, и его зелёный вердикт предъявляют как доказательство
безопасности — на ревью архитектуры, в переписке с заказчиком, в отчёте перед
релизом. Возразить на это можно только числами со своего кода. Какие правила в
этой сборке есть, какие условия стоят в пороге и что из классов дефектов
остаётся за его пределами.

## 1. Цели

После этого раздела вы сможете:

1. Поднять бесплатную сборку и получить отчёт по своему проекту.
2. Прочитать порог качества и назвать условие, которое его уронило.
3. Проверить, есть ли в сборке правило, которого от неё ждут.
4. Назвать классы дефектов, которые зелёный вердикт не покрывает.

## 3. Механика

**Откуда это взялось.** Отчёт сканера живёт до следующего прогона, и решение
по нему принимает человек. Ломалось это на регулярности: отчёт читают, пока он
новый. Ответом стал сервер, который хранит историю, и порог, который
превращает набор метрик в один вердикт для конвейера.

Механики тут ровно столько, сколько нужно, чтобы понять вывод. Сканер
разбирает файлы и отправляет отчёт на сервер, сервер считает метрики и
применяет к ним условия порога. Условие задаётся либо на весь код, либо на
новый; встроенный порог называется Sonar way [^1]. Устройство самого анализа —
дерево, правила, поток данных — разобрано в `sast-principles`, а разбор
найденных дефектов — в темах `sqli-basics`, `os-command-injection` и
`path-traversal`.

## 4. Что умеет и чего не умеет

**Что умеет.** Хранить историю по проектам и считать метрики по коду и по
новому коду отдельно. Сводить их в один вердикт для конвейера, держать наборы
правил профилями и отдавать всё это машинным интерфейсом. Бесплатная сборка
умеет свои профили правил и свои пороги.

**Чего не умеет — в бесплатной сборке.** Строка «Injection vulnerabilities
detection» в таблице возможностей у неё пуста, а у платных вариантов
отмечена [^2]. Разбор ветвей — только магистральной; анализа запросов на
слияние нет; блокировать слияние по красному вердикту она тоже не умеет.
Расширенный статический анализ безопасности значится начиная с корпоративного
варианта.

## 5. Как запустить

Сервер поднимается образом, сканер — вторым образом. Всё локально, без
регистрации.

```bash
# SonarQube Community Build 26.8.0. Сервер.
docker run -d --name sq -p 9000:9000 sonarqube:community
```

Дальше нужен проект и ключ доступа; и то и другое заводится машинным
интерфейсом или через веб-интерфейс на порту 9000. Прогон сканера:

```bash
# Сканер отдельным образом; каталог проекта монтируется в /usr/src.
docker run --rm --network host -v "$PWD/src:/usr/src" \
  sonarsource/sonar-scanner-cli \
  -Dsonar.projectKey=demo -Dsonar.host.url=http://localhost:9000 \
  -Dsonar.token=$TOKEN
```

Результат читается не из вывода сканера, а с сервера: вывод говорит только о
том, что отчёт загружен.

## 6. Как читать вывод

Два запроса к машинному интерфейсу дают всё, что нужно для разбора: список
находок и состояние порога.

```text
GET /api/issues/search?componentKeys=<ключ>
GET /api/qualitygates/project_status?projectKey=<ключ>
```

Стенд — четыре обработчика веб-каркаса на Python с тремя подставленными
дефектами: запрос собран подстановкой, внешняя команда запущена через
оболочку, имя файла сложено с корнем каталога. Прогон бесплатной сборки дал
пять находок.

```text
строка 7   python:S4502  SECURITY HIGH   Make sure disabling CSRF is safe
строка 15  python:S6965  MAINTAINABILITY Specify the HTTP methods ...
строка 24  python:S6965  MAINTAINABILITY Specify the HTTP methods ...
строка 34  python:S6965  MAINTAINABILITY Specify the HTTP methods ...
строка 42  python:S6965  MAINTAINABILITY Specify the HTTP methods ...
```

Ни одной находки по трём подставленным дефектам. Точек внимания к
безопасности — ноль. Состояние порога — `OK`.

Проверить, дефект это настройки или свойство сборки, можно тем же интерфейсом:
спросить сервер про конкретное правило.

```text
GET /api/rules/search?rule_key=python:S3649   ->  total 0
GET /api/rules/search?rule_key=python:S2076   ->  total 0
GET /api/rules/search?rule_key=python:S2083   ->  total 0
```

Правил про внедрение SQL, команду операционной системы и путь к файлу в этой
сборке нет вовсе — они не выключены в профиле, их не существует. В профиле
Sonar way при этом активны 389 правил для Python. Совпадает это с таблицей
возможностей, где строка про поиск инъекций у бесплатной сборки пуста [^2].

Что делать с настоящими дефектами, найденными другими инструментами, разбирают
темы `sqli-basics`, `os-command-injection` и `path-traversal`. Классы этих
дефектов — `CWE-89`, `CWE-78` и `CWE-22`.

## 7. Границы метода

**Граница первая: вердикт считается по метрикам.** Порог не знает про
конкретную находку, он знает про число и рейтинг. Условие «нет блокирующих
проблем» выполнено ровно тогда, когда ни одно правило такую проблему не
подняло, — включая случай, когда правила нет.

**Граница вторая: бесплатная сборка не покрывает инъекции.** Измерено
прогоном и подтверждено таблицей возможностей. Закрывается это другим
инструментом рядом — темы `bandit`, `gosec`, `codeql`.

**Цена.** Сервер требует своей машины и обслуживания: база, индекс, обновления.
Прогон сканера на одном файле — около трёх секунд, оценка по одному прогону;
основная цена не в прогоне, а в содержании сервера.

## 8. Ловушка

Распространённое мнение: зелёный порог качества — это подтверждение того, что
проверка безопасности пройдена.

**Зелёный вердикт означает выполнение условий, а не отсутствие дефектов.** На
стенде с тремя подставленными инъекциями бесплатная сборка дала вердикт `OK`.
Причина не в настройке порога и не в профиле: правил, которые ищут эти классы,
в сборке нет. Порог честно посчитал ноль находок по классам, которых он не
искал.

Контрпример к обратному выводу: сам по себе порог не бесполезен. Из пяти
находок стенда одна была настоящей и относилась к безопасности — отключённая
защита от подделки запроса в настройках каркаса. Инструмент видит то, что
описано его правилами, и вопрос не «доверять ли вердикту», а «что именно
входит в набор, по которому он посчитан».

## 9. Чеклист ревью

1. Verify that вариант сборки назван рядом с вердиктом: бесплатная и платные
   различаются составом правил, а не только ценой.
2. Verify that состав правил проверен запросом к серверу по конкретному
   идентификатору, а не по названию языка.
3. Verify that условия порога прочитаны целиком, включая то, на каком коде
   каждое стоит — на всём или на новом.
4. Verify that классы, не покрытые сборкой, закрыты другим инструментом, а не
   объявлены отсутствующими по зелёному вердикту.
5. Verify that число просмотренных файлов в отчёте сканера сопоставлено с
   объёмом проекта.
6. Verify that зелёный вердикт не предъявляется как результат проверки
   безопасности без списка того, что в нём посчитано.

## 10. Задача

Поднять бесплатную сборку локально и прогнать сканер по своему проекту.
Дальше ответить на два вопроса запросами к серверу. Какие условия стоят в
пороге и есть ли в сборке правило на класс дефекта, который вам важен.

Одна подсказка: наличие правила проверяется поиском по идентификатору; пустой
ответ означает, что правила нет в сборке, а не что оно выключено в профиле.

**Критерий выполнения** наблюдаемый: получен список условий порога с их
пороговыми значениями. Рядом — ответ сервера по конкретному идентификатору
правила, из которого видно, есть оно в сборке или нет.

## 11. Проверь себя

1. Из чего состоит условие порога и когда вердикт становится красным?
2. Чем «правило выключено в профиле» отличается от «правила нет в сборке» и
   как это различить?
3. Почему на стенде с тремя инъекциями вердикт оказался зелёным?
4. Что из строк таблицы возможностей отсутствует у бесплатной сборки, кроме
   поиска инъекций?
5. Почему вывод сканера не годится для разбора находок?
6. Возврат к теме `sast-principles`: к какой причине молчания относится
   отсутствие правила в наборе?

<details>
<summary>Ответы</summary>

1. Из метрики, оператора сравнения и порогового значения. Вердикт красный,
   если сработало хотя бы одно условие порога.
2. Выключенное правило есть в сборке и видно в поиске по идентификатору,
   но не активно в профиле. Отсутствующего правила поиск не находит вовсе:
   ответ сервера содержит ноль записей.
3. Потому что правил, ищущих внедрение SQL, команду операционной системы и
   путь к файлу, в бесплатной сборке нет. Порог посчитал ноль находок по этим
   классам и не отличил ноль от «не искали».
4. Разбор ветвей, кроме магистральной; анализ запросов на слияние; блокировка
   слияния по красному вердикту; расширенный статический анализ безопасности.
5. Потому что сканер только отправляет отчёт, а метрики, находки и вердикт
   считает сервер. В выводе сканера есть подтверждение загрузки и ничего о
   результате.
6. К причине «правила нет в наборе». Признак тот же: тот же код на другом
   наборе правил или на другом инструменте даёт находку.

</details>

**Скоропортящийся слой.** Номер версии сборки, состав правил и профилей, имена
метрик и условий встроенного порога, состав таблицы возможностей. Устройство
порога — условия на метрики и один вердикт — держится дольше.

**Маркеры уверенности.** Пять находок на стенде из четырёх обработчиков, из
них ни одной по трём подставленным инъекциям; ноль точек внимания к
безопасности; вердикт `OK`; пустые ответы сервера по трём идентификаторам
правил; 389 активных правил Python в профиле Sonar way — **проверено лично**
2026-08-25 на SonarQube Community Build 26.8.0.126808 и образе сканера
`sonarsource/sonar-scanner-cli`. Время прогона — **оценка по одному прогону**.
Устройство порога и состав возможностей вариантов — **по документации** Sonar,
открытой лично 2026-08-25. Платные варианты **не воспроизводились**: лицензии
нет, и всё сказанное о них взято из таблицы возможностей.
