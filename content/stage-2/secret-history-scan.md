# Секреты в истории коммитов, а не в HEAD

Уровень **L2** · время 35 мин (теория 21 / задача 9 / самопроверка 5,
оценка)

Что прочитать сначала: `secret-scanners`.

В учебном репозитории семь коммитов. В четвёртом ключи «убрали»: файл с
приватным ключом удалён, значения в коде заменены чтением из окружения.
Один и тот же сканер, два прогона по этому репозиторию:

```text
gitleaks dir ./shop      ~1315 байт        2 находки
gitleaks git ./shop      7 коммитов        5 находок
```

Три из пяти находок второго прогона указывают на файлы, которых в
рабочем дереве давно нет. Среди них `config/deploy_key` с приватным
ключом из коммита `706cd2e` и ключ AWS из коммита `3792914`, открытый с
12 января. Удалённый коммитом секрет никуда не делся: git хранит не
текущее состояние, а все состояния. Новый коммит добавляет новый объект,
прежний остаётся на месте. Первый прогон читает файлы на диске, второй —
вывод `git log -p` по всем коммитам, и это физически разные наборы
данных.

Предмет темы — вторая команда и всё, что от неё зависит. Дальше — как
запустить прогон по истории у обоих сканеров и почему поверхностный клон
в конвейере обесценивает проверку. И по какой строке вывода видно, что
история досталась сканеру целиком.

## 0. Коротко

Секрет, убранный из файла отдельным коммитом, остаётся в репозитории навсегда:
git хранит не текущее состояние, а все состояния. Сканер по рабочему дереву его
не увидит, сканер по истории — увидит. Это одна команда разницы и весь смысл
подраздела: без прогона по истории поиск секретов проверяет только то, что и так
видно глазами.

Приём короткий и конечный: заменить `gitleaks dir` на `gitleaks git`, а
`trufflehog filesystem` — на `trufflehog git`. Тонкости не в команде, а в том,
что именно ей досталось на вход. В конвейере это чаще всего не вся история, и
отчёт получается зелёным потому, что смотреть было не на что.

Класс дефекта — захардкоженные учётные данные (`CWE-798`) — разобран в
`secrets-in-code`; что делать с находкой из истории, разбирает `secret-rotation`,
и ответ там не «переписать историю».

**Зачем это в работе AppSec-инженера.** Это самый частый способ ошибиться в
пользу спокойствия: проверка стоит, отчёт зелёный, репозиторий «чистый». Разбирая
чужой конвейер, первым делом смотрят не на сканер, а на то, что ему дали
сканировать.

## 1. Цели

После этого раздела вы сможете:

1. Запустить сканер по всей истории репозитория, а не по рабочему дереву.
2. Назвать числами разницу между двумя прогонами на одном репозитории.
3. Опознать поверхностный клон и другие способы получить зелёный отчёт впустую.

## 3. Механика

**Откуда это взялось.** Требование появилось не из теории, а из практики
хостингов. GitHub сканирует не текущее состояние, а всю историю на всех ветках.
Сверх того — описания и комментарии задач, запросов на слияние, обсуждений,
вики и приватные gist. То есть площадку целиком, а не файлы на последнем
коммите.

В режиме `рецепт` механика — в объёме, нужном, чтобы понять вывод. Git хранит
содержимое в объектах, адресуемых по хешу, а коммит — это ссылка на дерево
объектов плюс ссылка на родителя. Убрать строку из файла и закоммитить — значит
создать **новый** объект с новым содержимым; старый объект никуда не девается,
на него по-прежнему ссылается прежний коммит. Ровно поэтому «удаление» секрета
обычным коммитом ничего не удаляет. И поэтому же команды `dir` и `git` у
сканера читают физически разные наборы данных. Первая берёт файлы на диске,
вторая — вывод `git log -p` по всем коммитам.

## 4. Что умеет и чего не умеет

**Что умеет.** Прогон по истории видит всё, что когда-либо было закоммичено на
достижимых ветках: удалённые файлы, откаченные строки, временные отладочные
правки. Он же приносит метаданные, которых нет у прогона по дереву: автора, дату и
сообщение коммита. С ними приходит ответ на главный вопрос — сколько времени
ключ был доступен.

**Чего не умеет.** Видеть то, что в истории репозитория не лежит: описания
запросов на слияние, комментарии в трекере, журналы сборки, переменные окружения
конвейера. Это отдельные хранилища, и локальный сканер до них не дотягивается —
их закрывает сканирование на стороне платформы.

**Чего не умеет тем более.** Отвечать за чужие копии. Прогон по вашей истории
ничего не говорит про форки и клоны: они отдельные репозитории со своей копией
тех же объектов.

## 5. Как запустить

Одна и та же цель, два объекта:

```bash
# рабочее дерево: только то, что лежит на диске сейчас
gitleaks dir ./shop --report-format json --report-path gl-dir.json
# вся история: все коммиты на всех достижимых ветках
gitleaks git ./shop --report-format json --report-path gl-git.json

# у trufflehog то же различие проходит по подкоманде
trufflehog filesystem ./shop --json --no-update
trufflehog git file://$PWD/shop --json --no-update
```

Сузить историю до диапазона можно через `--log-opts`, и это то, что ставят в
серверную проверку, где интересны только приходящие коммиты:

```bash
gitleaks git . --log-opts="$oldrev..$newrev"
```

Перед прогоном в конвейере убедитесь, что история вообще выкачана. Проверка — одна
команда:

```bash
git rev-list --count HEAD    # сколько коммитов реально доступно
test -f .git/shallow && echo "клон поверхностный"
```

## 6. Как читать вывод

Стенд — репозиторий из семи коммитов. В четвёртом коммите ключи «убрали»: файл с
приватным ключом удалён, значения в коде заменены на чтение из окружения. Два
прогона Gitleaks 8.30.1 по одному и тому же репозиторию:

```text
gitleaks dir ./shop      ~1315 байт        2 находки
gitleaks git ./shop      7 коммитов        5 находок
```

Три находки видны только в истории:

```text
private-key       config/deploy_key   коммит 706cd2e  2026-01-19
aws-access-token  config/deploy.py    коммит 3792914  2026-01-12
generic-api-key   config/deploy.py    коммит 3792914  2026-01-12
```

Читается это так. Слева — правило, дальше файл, которого **в рабочем дереве
больше нет**, дальше коммит и дата. Дата здесь главная: ключ AWS лежит открытым
с 12 января, и это, а не сам факт находки, определяет, что делать дальше
(`secret-rotation`).

Обратите внимание на строку `INF 7 commits scanned` в выводе Gitleaks. Это не
украшение, а единственный способ убедиться, что сканеру досталась история, а не
один коммит.

### Ловушка конвейера: поверхностный клон

Сборочные системы по умолчанию клонируют с `--depth 1` — так быстрее. Тот же
репозиторий, тот же сканер, разница только в глубине клона:

```text
полный клон          7 коммитов   ->  5 находок
клон --depth 1       1 коммит     ->  2 находки
```

Отчёт во втором случае честен: инструмент отсканировал всё, что ему дали. Дали
один коммит. Проверка «по истории» стоит, зелёная, и не проверяет ничего сверх
того, что нашёл бы прогон по рабочему дереву.

### Побочный эффект, на который нельзя опираться

Прогон `trufflehog filesystem` по каталогу репозитория дал на стенде **больше**
находок, чем прогон по истории: 5 против 3. Причина — он прочитал файлы в
`.git/objects` и наткнулся на распакованные объекты старых коммитов.

```text
Stripe  tests/test_signing.py
Stripe  .git/objects/08/29d80ae1655509b0dfc6aa36b7082ac111dd2b
Slack   .git/objects/27/225769e8a053d411d6ea5456c57afd125d4a6a
AWS     .git/objects/1c/8367ec5e8b088feb42f018e90c247738628641
```

Пользоваться этим нельзя. Распакованными объекты остаются недолго: после сборки
мусора git упаковывает их в один сжатый файл, и текстовый поиск по нему уже
ничего не находит. Это не способ просканировать историю, а напоминание, что
`filesystem` по каталогу репозитория читает служебные файлы заодно.

## 7. Границы метода

**Граница первая: достижимость.** `gitleaks git` идёт по `git log`, то есть по
коммитам, достижимым от ссылок. Коммит, на который не указывает ни ветка, ни
тег, в отчёт не попадёт, хотя объект в репозитории лежит. Как такие коммиты
возникают и почему они всё ещё опасны — `secret-rotation`.

**Граница вторая: только этот репозиторий.** Форк, клон коллеги, зеркало и кэш
хостинга — отдельные копии. Зелёный прогон здесь ничего не говорит про них.

**Граница третья: история шире коммитов.** Описания запросов на слияние,
комментарии, вики и журналы сборки в git-историю не входят. Их сканирует
платформа, и это отдельная поверхность.

**Цена.** Прогон по истории дороже прогона по дереву, но не настолько, чтобы
экономить: на стенде 76 мс против 6 мс. Настоящая цена — в размере отчёта.
История хранит все находки за всё время, включая давно отозванные ключи.
Разбирать её приходится один раз целиком, а дальше держать базовый файл прежних
находок (`--baseline-path`), чтобы видеть только новое.

## 8. Ловушка

Распространённое мнение: если сканер по истории зелёный, секретов в репозитории
нет.

**Зелёный отчёт говорит о том, что сканеру дали, а не о репозитории.** Три
разных способа получить его впустую. Поверхностный клон в конвейере: один
коммит вместо семи. Прогон только по текущей ветке при секрете в другой.
Прогон командой `dir` вместо `git` при том, что в конфигурации написано «скан
истории». Во всех трёх случаях инструмент отработал правильно.

Контрпример к обратному выводу — «значит, отчётам верить нельзя»: верить можно
ровно тому, что видно в выводе. Строка «7 commits scanned» проверяема, и
утверждение «история из семи коммитов на ветке `main` просканирована Gitleaks
8.30.1, известных форм не найдено» — честное. «Секретов нет» — нет.

## 9. Чеклист ревью

1. Verify that в конвейере используется команда по истории, а не по каталогу.
2. Verify that клон полный: `git rev-list --count HEAD` больше единицы, файла
   `.git/shallow` нет.
3. Verify that в выводе видно число просканированных коммитов и оно совпадает с
   ожидаемым.
4. Verify that сканируются все ветки, а не только текущая.
5. Verify that дата и автор коммита из находки учтены при оценке, а не только
   сам факт находки.
6. Verify that про площадки вне git-истории — задачи, запросы на слияние, вики —
   сказано отдельно, а не подразумевается покрытыми.
7. Verify that базовый файл прежних находок обновляется осознанно, а не гасит
   новые находки заодно.

## 10. Задача

Взять свой репозиторий и прогнать сканер дважды: по рабочему дереву и по всей
истории. Затем сделать поверхностный клон и прогнать по нему третий раз.

Одна подсказка: если разница между первым и вторым прогоном нулевая, добавьте
выдуманный секрет известной формы, закоммитьте, удалите его следующим коммитом и
повторите — разница появится.

**Критерий выполнения** наблюдаемый: у вас есть три числа находок и три числа
просканированных коммитов, и вы можете объяснить каждую пару. Для одной находки,
видной только в истории, вы называете дату и автора коммита.

## 11. Проверь себя

1. Почему коммит, удаляющий секрет из файла, не удаляет секрет из репозитория?
2. Какие две команды у Gitleaks различают рабочее дерево и историю?
3. По какой строке вывода видно, что сканеру досталась история, а не один
   коммит?
4. Чем опасен `--depth 1` в конвейере и как это проверить одной командой?
5. Что даёт находка из истории сверх факта находки?
6. Возврат к теме `secret-scanners`: почему прогон `trufflehog filesystem` по
   каталогу репозитория иногда находит больше, чем прогон по истории, и почему
   на это нельзя опираться?

<details>
<summary>Ответы</summary>

1. Git хранит объекты по содержимому: новый коммит добавляет новый объект, а
   прежний остаётся на месте и достижим через свой коммит.
2. `gitleaks dir` — файлы на диске, `gitleaks git` — все коммиты через
   `git log -p`.
3. По строке о числе просканированных коммитов: `7 commits scanned`.
4. Поверхностный клон приносит один коммит, и прогон «по истории» проверяет
   только его; проверяется через `git rev-list --count HEAD` или наличие файла
   `.git/shallow`.
5. Автора, дату и сообщение коммита, то есть срок, в течение которого ключ был
   доступен, — от него зависит порядок реакции.
6. Он читает служебные файлы в `.git/objects` и натыкается на распакованные
   объекты старых коммитов; после сборки мусора они упаковываются и текстовым
   поиском не находятся.

</details>
