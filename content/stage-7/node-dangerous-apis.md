# Node.js: child_process, path, десериализация

Уровень **L2** · время 30 мин (теория 18 / задача 8 / самопроверка 4,
оценка)

Что прочитать сначала: `os-command-injection`, `insecure-deserialization`.

Сервис проверяет доступность хоста: имя приходит из запроса. Прогоним
один ввод `127.0.0.1; echo PWNED; id -u` через две функции одного
модуля:

```text
exec, хвост вывода: PWNED | 1000
execFile, код ошибки: 2 | stderr: ping: 127.0.0.1; echo PWNED; id -u: ...
```

Первая форма выполнила все три команды: exec передал строку шеллу, и тот
разобрал точку с запятой. Вторая отдала весь ввод программе ping одним
аргументом, и тот не нашёл такого хоста. Обе функции — из
`node:child_process`; разница между ними — в одном шелле. Именно шелл
прочитал точку с запятой как приказ.

Эта тема собирает опасные точки входа Node.js: запуск процессов,
исполнение строки как кода, разбор данных с вызовом функций и работу с
путями. Классы дефектов — внедрение команд (CWE-78) и небезопасная
десериализация (CWE-502), категории `A05:2025` и `A08:2025` издания OWASP
2025 года, — разобраны в темах-предпосылках. Обход каталога (CWE-22)
разобран в теме `path-traversal`; здесь у всех троих — форма в Node.js.

## 0. Коротко

Вызовы exec и execSync зовут шелл и передают ему строку. Формы execFile
и spawn по умолчанию исполняют программу напрямую, и метасимволы в
аргументах остаются текстом. Вызовы eval и new Function исполняют строку
как код в текущем процессе. Пакет node-serialize разбирает функции из
данных: разбор чужой строки в нём исполняет код. Функции path.join и
path.resolve нормализуют `..`, но не удерживают путь в каталоге: границу
проверяют после resolve. Правила: процесс — execFile со списком, данные
— JSON.parse, путь — resolve плюс сверка с корнем. То же в терминах,
которыми это обсуждают.

**Зачем это в работе AppSec-инженера.** Node-сервис полон вызовов
наружу: конвертеры, архиваторы, git. Признаки этой темы ищутся поиском
по именам функций, и находка подтверждается одним прогоном на вводе с
точкой с запятой — дешевле любого спора.

## 1. Цели

После этого раздела вы сможете:

3. Собрать безопасную форму: список аргументов, JSON, проверка границы.

## 3. Механика

**Откуда это взялось.** Node рос из шелл-скриптинга на сервере: вызвать
команду строкой — короткий путь, и exec его сохранил. Документация модуля
формулирует различие прямо: exec запускает шелл и исполняет команду в
нём, а execFile запускает файл напрямую, без шелла по умолчанию. У spawn
шелл — опция, по умолчанию выключенная. Наивная склейка строки ломается
о грамматику шелла: `;`, `&&`, `|` — операторы, а не данные.

Вторая дверь — исполнение строки. eval и конструктор Function
компилируют текст в код и исполняют его с правами процесса. Третья —
сериализация с функциями: пакет node-serialize хранит функции в данных
пометкой `_$$ND_FUNC$$_`, и его unserialize исполняет их немедленно.
Проверено прогоном на версии 0.0.4: строка с такой пометкой при разборе
выполнила команду и создала файл. Подпись значения этот риск не снимает:
она доказывает целостность, а разбор исполнит функции и из честно
подписанной строки. Контраст из стандартной библиотеки:
v8.deserialize умеет значения, а не поведение — функции через него не
передаются.

Четвёртая — пути. path.join склеивает сегменты и нормализует; прогон
показывает, что join(`/srv/files`, `../../etc/hostname`) даёт
`/etc/hostname` — база съехала, и никакой границы не было. Рабочая
форма: resolve до абсолютного пути и сверка результата с разрешённым
корнем, причём сравнивать нужно с сепаратором на конце — иначе
`/srv/files-secret` пройдёт за `/srv/files`.

## 5. Как выглядит в коде

Четыре сигнатуры, все находятся поиском по имени. Прежде чем читать
выноски, отметьте в каждой строке точку, куда доезжает ввод:

```javascript
// УЯЗВИМО — демонстрация, не для продакшена
const { exec } = require("node:child_process");
const serialize = require("node-serialize");

exec(`convert ${src} ${dst}`);              // (1)
const fn = new Function("x", req.body);     // (2)
const obj = serialize.unserialize(cookie);  // (3)
const full = path.join(root, name);         // (4)
```

1. Строка команды со склейкой: шелл разбирает ввод.
2. Тело функции из запроса: код исполняется в процессе сервера.
3. Разбор cookie пакетом с функциями в данных: исполнение при разборе.
4. Путь без сверки с корнем: `..` в имени выводит из каталога.

У четырёх сигнатур один общий вид: строка из ввода доезжает до места,
где перестаёт быть данными. Ответьте, не трогая листинг: останется ли
дефект, если четвёртую строку переписать через `path.resolve` без сверки
с корнем?

Обёртки, которые не спасают: экранирование строки для шелла руками
(ломается о вторую форму записи) и проверка входа по чёрному списку
символов. Ложное срабатывание: exec с константной строкой без ввода —
риск в склейке, а не в имени функции.

## 6. Как чинится

Правило одно: команда и данные разделены, строка не становится кодом.

```javascript
// Исправлено
const { execFile } = require("node:child_process");
const path = require("node:path");

execFile("convert", [src, dst], onDone);

const data = JSON.parse(body);  // только данные, без функций

const full = path.resolve(root, name);
if (!full.startsWith(root + path.sep)) throw new Error("вне корня");
```

execFile принимает программу и аргументы отдельно — ввод остаётся одним
аргументом, как в прогоне из введения. JSON.parse читает данные и не
исполняет ничего. Граница пути проверяется после resolve: нормализация
сворачивает `..`, и сверка идёт уже по итоговому абсолютному пути.
Документация Node.js добавляет слой в глубину: модель разрешений
процесса (`--permission`) ограничивает запуск дочерних процессов и доступ
к файлам даже для доверенного кода.

**Когда канон не подходит.** Настоящий конвейер команд собирается из
цепочки spawn со связанными потоками, а не через шелл-строку. А если
формат сериализации с функциями уже уехал в данные между системами,
миграция на JSON — отдельная задача согласования. Временная мера —
строгая проверка входа и изоляция процесса.

## 9. Ловушка

Ответьте до разбора: пакет из официального реестра с многолетней
историей скачиваний — можно ли отдать ему чужую строку? Встречается
мнение, что пакет из реестра npm с историей скачиваний можно вызывать на
чужих данных как безопасный по умолчанию.

**Реестр отвечает за доставку пакета, а не за безопасность его
интерфейса.** Механизм из раздела о механике: если пакет по построению
исполняет функции из данных, никакая популярность этого не отменяет.
Документация Node.js прямо относит вредоносные и скомпрометированные
зависимости к рискам уровня приложения, а не к доверенным по умолчанию.

Контрпример — прогон из раздела о механике: node-serialize версии 0.0.4
из официального реестра исполнил команду при разборе cookie. Признак был
в формате данных, а не в репутации пакета.

## 10. Чеклист ревью

1. Verify that вызовы процессов идут через execFile или spawn со списком
   аргументов, а не через exec со строкой (CWE-78).
2. Verify that eval и new Function не получают строки с данными запроса,
   конфигурации или хранилища.
3. Verify that разбор внешних данных идёт через JSON.parse, а не через
   пакеты, исполняющие функции из данных (CWE-502).
4. Verify that путь из ввода проходит resolve и сверку с корнем с
   сепаратором на конце.
5. Verify that у процесса, которому не нужны дочерние процессы, это
   ограничено моделью разрешений Node.js.
6. Verify that cookie и подписанные значения не разбираются как код даже
   при доверии к подписи — подпись защищает от подмены, а не формат от
   исполнения.

## 11. Задача

Возьмите фрагмент из раздела о коде с exec и перепишите его на execFile.
Прогоните обе версии на вводе с `;` и на вводе с флагом, начинающимся с
дефиса. Затем соберите проверку пути из раздела о починке и прогоните её
на имени с `..` и на имени соседнего каталога.

Одна подсказка: разницу между формами видно по stderr целевой программы —
без шелла она получает весь ввод одним аргументом и жалуется сама.

**Критерий выполнения** наблюдаемый: exec исполнил цепочку команд, а
execFile передал ввод одним аргументом; проверка пути пропустила файл
внутри корня и отклонила `..` и `/srv/files-secret/x`.

## 12. Проверь себя

1. Чем exec отличается от execFile по отношению к шеллу?
2. Почему node-serialize опасен на чужих данных, а v8.deserialize — нет?
3. Почему сверку пути с корнем делают после resolve, а не до?
4. Что ловит сепаратор на конце корня при startsWith?
5. Возврат к теме `insecure-deserialization`: чем формат с функциями в
   данных принципиально отличается от формата только с данными?

<details markdown="1">
<summary>Ответы</summary>

1. exec запускает шелл и отдаёт ему строку целиком; execFile запускает
   программу напрямую, и аргументы не проходят разбор шелла.
2. Формат node-serialize хранит функции пометкой `_$$ND_FUNC$$_`, и
   разбор их исполняет. v8.deserialize переносит значения и не
   восстанавливает поведение.
3. До resolve в имени живут `..` и относительные формы; границу имеет
   смысл проверять у итогового абсолютного пути.
4. Он отличает `/srv/files` от `/srv/files-secret`: без сепаратора
   префикс-совпадение пропускает соседний каталог.
5. Формат с данными при разборе строит значения; формат с функциями при
   разборе исполняет код. У первого ошибка — чтение, у второго —
   исполнение.

</details>

## 13. Источники

1. Child process, документация Node.js; реестр `node-child-process`.
   Разделы: exec запускает шелл, execFile исполняет файл напрямую,
   spawn и опция shell, advanced serialization для IPC.
   <https://nodejs.org/api/child_process.html>
2. Path, документация Node.js; реестр `node-path`. Разделы: join
   (склейка и нормализация), resolve (построение абсолютного пути),
   isAbsolute (не защита от обхода), POSIX и Windows.
   <https://nodejs.org/api/path.html>
3. Security Best Practices, документация Node.js; реестр
   `node-security-best-practices`. Разделы: Malicious Third-Party
   Modules (любой пакет имеет доступ к сети и файловой системе),
   модель разрешений `--permission`.
   <https://nodejs.org/learn/getting-started/security-best-practices>

Каркас этапа: у этапа 7 общих унаследованных источников нет; каждая тема
опирается на документацию своего языка и на материалы этапа 1 по
классам дефектов.

**Маркеры уверенности.** **Проверено лично** 2026-09-02 на Node.js 26.8.1:
ввод `127.0.0.1; echo PWNED; id -u` исполняется цепочкой через exec и
доезжает одним аргументом через execFile (ping отвечает «Name or service
not known»); node-serialize 0.0.4 исполняет функцию из строки при
unserialize (создан файл); v8.deserialize кругово восстанавливает объект
и отказывает битому потоку; path.join и path.resolve со входом
`../../etc/hostname` дают `/etc/hostname`; startsWith по корню без
сепаратора пропускает соседний каталог. Формулировки про шелл у exec и
устройство модели разрешений — **по документации**, все три страницы
открыты лично 2026-09-02. Сам пакет node-serialize не обновлялся с 2017
года и взят как учебный пример формата с функциями, а не как совет к
применению.
