# pickle, eval, exec, небезопасный YAML

Уровень **L2** · время 40 мин (теория 25 / задача 10 / самопроверка 5,
оценка)

Что прочитать сначала: `insecure-deserialization`.

Воркер очереди принимает снимок состояния — файл, записанный где-то через
pickle.dump. Прежде чем загружать чужой снимок, прогоним его через
дизассемблер формата:

```text
$ python3 -m pickletools snapshot.pkl
    0: \x80 PROTO      5
   11: \x8c SHORT_BINUNICODE 'posix'
   19: \x8c SHORT_BINUNICODE 'system'
   28: \x93 STACK_GLOBAL
   30: \x8c SHORT_BINUNICODE 'echo PWNED-from-pickle; id -u'
   62: \x85 TUPLE1
   64: R    REDUCE
   66: .    STOP
```

В потоке 67 байт, и главное в нём — две инструкции. STACK_GLOBAL
разрешает пару имён в функцию posix.system, а REDUCE её вызывает со
строкой из потока. Загрузи воркер этот файл обычным pickle.load — команда
выполнилась бы на его машине ещё до возврата из функции. Никакого взлома
формата здесь не произошло: pickle исполнил ровно то, что в нём записано.

Так ведут себя все функции, которые читают данные как код или как
объекты с конструкторами: pickle.loads, yaml.load с полным загрузчиком,
eval и exec. Это языковая идиоматика небезопасной десериализации — сам
класс дефекта разобран в теме `insecure-deserialization` и здесь не
повторяется. Дальше разберём устройство потока pickle, семейство
загрузчиков PyYAML и то, чем каждый из этих вызовов заменяется в коде.

## 0. Коротко

То же в терминах, которыми это обсуждают. Поток pickle — программа для
маленькой стековой машины, и его разбор исполняет эту программу:
инструкция REDUCE вызывает любую импортируемую функцию с аргументами из
потока. Вызов yaml.load с полным загрузчиком конструирует произвольные
объекты по тегам документа. Функции eval и exec исполняют строку как код
в текущем окружении. Ни один из этих приёмов не рассчитан на чужой ввод: это
CWE-502 (каталог Common Weakness Enumeration). Издание OWASP 2025 года
относит класс к категории `A08:2025`. Чинится заменой формата: json для
данных, safe_load для YAML, ast.literal_eval для литералов. Там, где
pickle неизбежен между своими компонентами, поток подписывают.

**Зачем это в работе AppSec-инженера.** Эти вызовы живут не в
учебниках, а в эксплуатации. Вызов pickle встречается в кэшах, очередях
задач и сохранённых моделях машинного обучения. Вызов yaml.load живёт в
чтении конфигурации, eval — в настраиваемых правилах. Ревьюеру достаточно
одного поиска по дереву, чтобы получить список мест. Работа дальше —
отличить доверенный поток от чужого и предложить замену, которая не
сломает проект.

4. Подобрать замену: json, safe_load или ast.literal_eval.

## 3. Механика

**Откуда это взялось.** pickle задуман как способ сохранить объект между
запусками своей же программы: поток читает тот, кто писал. Для этого
формату хватило бы дерева значений, но авторы дали ему универсальность.
Поток хранит не только данные, но и рецепт восстановления объекта: какую
функцию вызвать и с чем. Наивное решение «читать поток как данные»
ломается ровно здесь: рецепт и есть точка исполнения. То же с YAML:
формат данных оброс тегами, конструирующими объекты языка, и полный
загрузчик честно их конструирует.

Поток pickle — последовательность инструкций стековой машины. Три из них
важны ревьюеру. STACK_GLOBAL берёт со стека два имени — модуля и функции —
и кладёт на стек разрешённый объект, импортировав модуль. TUPLE собирает
аргументы. REDUCE вызывает объект с этими аргументами. Пример из начала
темы — вся программа целиком: импортировать posix.system, вызвать со
строкой команды.

```python
# Так выглядит класс, чья запись порождает тот поток; УЯЗВИМО,
# демонстрация на своей машине
import os
import pickle


class Evil:
    def __reduce__(self):
        return (os.system, ("echo PWNED-from-pickle; id -u",))


data = pickle.dumps(Evil())
```

Документация модуля начинается с предупреждения, которое стоит знать
почти дословно: pickle небезопасен, чужие данные разбирать им нельзя.
Если поток могли подменить, его советуют подписывать через hmac. Там же
названа и форма осмотра без исполнения: pickletools читает опкоды, не
вызывая их.

У PyYAML история другая, а итог тот же. До версии 6.0 вызов yaml.load
молча работал с полным загрузчиком. Он конструирует любой класс по тегу
`!!python/object` и вызывает любую функцию по тегу
`!!python/object/apply`. С PyYAML 6.0 вызов без загрузчика падает с TypeError — проверено
на версии 6.0.3. Но заперт замок по умолчанию, а не дверь. Вызовы
yaml.unsafe_load и yaml.load с Loader=yaml.Loader возвращают прежнее
поведение. В чужом коде вы встретите именно их — как «починку» после
обновления библиотеки.

Функции eval и exec устроены проще: они компилируют строку как код и
исполняют её в текущем пространстве имён. Границы между «вычислить
выражение» и «сделать что угодно» у этого механизма нет: в строке
доступны встроенные функции, импорт через `__import__` и объектный граф
интерпретатора.

## 5. Как выглядит в коде

Ревьюер ищет четыре сигнатуры, все видны по одной строке.

```python
# УЯЗВИМО — демонстрация, не для продакшена
import pickle
import yaml

snapshot = pickle.loads(request.body)          # (1)
cache = pickle.load(open(user_path, "rb"))     # (2)
config = yaml.load(text, Loader=yaml.Loader)   # (3)
verdict = eval(f"price > {threshold}")         # (4)
```

1. Поток из запроса разбирается как программа: любой, кто пишет в этот
   вход, исполняет код на сервере.
2. Тот же дефект через файл: вопрос не «откуда байты», а «мог ли их
   подменить чужой». Кэш на общем диске и запись в общей базе — такой же
   чужой поток.
3. Явный полный загрузчик. Вариант `yaml.unsafe_load(text)` — то же
   самое честным именем.
4. eval на строке с данными запроса: `threshold` становится кодом.

Обёртка, которая выглядит защитой, — собственный Unpickler с
ограниченным find_class: он разрешает только имена из списка. Это уже не
чтение данных, а политика доверия, и цена ошибки в списке — исполнение.
Такой класс в ревью читается как «команда приняла риск осознанно», а не
как «дефекта нет». Вторая обёртка — пустые `__builtins__` у eval — не
работает вовсе. Прогон показывает: выражение
`().__class__.__base__.__subclasses__()` исполняется и в пустом
окружении. Граф объектов языка никуда не делся.

Ложное срабатывание: `pickle.dumps` без чтения чужих потоков — запись
не опасна. Законен и `yaml.safe_load`: на теге `!!python/object/apply`
он отвечает ConstructorError, а не молчаливым исполнением.

## 6. Как чинится

Правило одно: чужой вход читается форматом данных, а не форматом
объектов.

```python
# Исправлено
import ast
import json

import yaml

payload = json.loads(request.body)
config = yaml.safe_load(text)
threshold = ast.literal_eval(user_literal)  # только литералы Python
```

Формат json хранит числа, строки, списки и словари — и ничего больше:
исполнять в нём нечего. Загрузчик safe_load конструирует только
стандартные теги YAML. Функция ast.literal_eval принимает литералы
Python и отказывает любому выражению. На вызове функции она бросает
ValueError — проверено на Python 3.14.

Если pickle неизбежен — потоки между своими компонентами с общей кодовой
базой — поток подписывается ключом через hmac, как и советует
документация. Вход без верной подписи не разбирается вовсе. Это снимает
вопрос «могли ли поток подменить», а не вопрос «безопасен ли формат».
Формат небезопасен по построению, и ASVS v5.0-1.5.2 требует ровно этого:
не применять десериализацию объектов к недоверенному входу.

**Когда канон не подходит.** Сохранённые модели машинного обучения —
это почти всегда pickle внутри, и переписать формат не выйдет. Там ответ
тот же, что у подписи: модель принимают только из доверенного источника
по защищённому каналу, а из пользовательского ввода — никогда.

## 9. Ловушка

Иногда встречается мнение, что eval станет безопасным, если передать ему
пустой словарь встроенных функций.

**Пространство имён — не граница.** Объекты языка доступны через сами
объекты: у любого значения есть класс, у класса — предки, у предков —
подклассы. Среди подклассов находятся те, что читают файлы и запускают
процессы. Прогон из раздела о коде показывает это на одном выражении:
список подклассов object возвращается и с пустыми `__builtins__`.

Контрпример — каждая вторая публикация об обходе «песочниц» на eval:
ограничение ломается не взломом проверки, а хождением по ссылкам между
объектами, которые проверка вообще не рассматривает.

## 10. Чеклист ревью

1. Verify that вход запроса, файла или кэша не попадает в pickle.load
   или pickle.loads — ни напрямую, ни через промежуточное хранилище
   (CWE-502).
2. Verify that чтение YAML идёт через yaml.safe_load, а не через load
   с явным загрузчиком и не через unsafe_load (ASVS v5.0-1.5.2).
3. Verify that eval и exec не получают строки, собранные из внешних
   данных, включая f-строки с параметрами запроса.
4. Verify that потоки pickle, которые системе принимать необходимо,
   подписаны ключом и подпись проверяется до разбора.
5. Verify that у собственного Unpickler с ограничением имён есть тест на
   чужой поток, а не только на свой.
6. Verify that на битом или чужом входе читатель получает отказ
   (JSONDecodeError, ConstructorError), а не молчаливое исполнение.

## 12. Проверь себя

1. Какие две инструкции потока pickle превращают данные в вызов и что
   делает каждая?
2. Чем отвечает yaml.safe_load на тег `!!python/object/apply` и чем
   это отличается от ответа полного загрузчика?
3. Почему `yaml.load(text)` на PyYAML 6 падает с TypeError и как это
   «чинят» в чужом коде?
4. Чем ast.literal_eval отличается от eval по множеству допустимого
   входа?
5. Возврат к теме `insecure-deserialization`: почему подпись потока
   меняет ответ на вопрос «можно ли разбирать», а не делает формат
   безопасным?

<details markdown="1">
<summary>Ответы</summary>

1. STACK_GLOBAL разрешает пару «модуль, имя» в вызываемый объект,
   импортировав модуль; REDUCE вызывает его с аргументами, собранными
   из потока.
2. Он бросает ConstructorError: стандартные теги не включают конструкцию
   произвольных объектов. Полный загрузчик по этому тегу вызывает
   функцию из документа.
3. С версии 6.0 загрузчик требуется явно. «Починка» обычно сводится к
   `Loader=yaml.Loader` или к unsafe_load — то есть к возврату старого
   опасного поведения.
4. literal_eval принимает только литералы Python — числа, строки,
   коллекции — и отказывает любому выражению с вызовом. eval исполняет
   строку как код целиком.
5. Подпись отвечает на вопрос «кто записал поток»: верная подпись
   значит, что поток писал свой компонент. Сам формат при этом остаётся
   исполняемым — доверие перенесено с формата на ключ.

</details>

   <https://pyyaml.org/wiki/PyYAMLDocumentation>

Каркас этапа: у этапа 7 общих унаследованных источников нет; каждая тема
опирается на документацию своего языка и на материалы этапа 1 по
классам дефектов.

**Скоропортящийся слой.** Умолчания библиотек: поведение yaml.load без
загрузчика уже менялось один раз (PyYAML 6.0) и может меняться снова;
протокол pickle по умолчанию меняется между версиями Python. Механика
REDUCE и тегов стабильна, при ревизии перечитываются умолчания.

**Маркеры уверенности.** **Проверено лично** 2026-09-02 на Python 3.14.7
и PyYAML 6.0.3: поток с `__reduce__` исполняет os.system при loads и
читается pickletools без исполнения; yaml.load без загрузчика падает с
TypeError; yaml.load с UnsafeLoader исполняет `!!python/object/apply`;
safe_load на том же документе бросает ConstructorError; выражение через
`__subclasses__` работает и с пустыми `__builtins__`; ast.literal_eval
принимает словарь и отказывает вызову с ValueError. Формулировки
предупреждений — **по документации**, обе страницы открыты лично
2026-09-02. Обходы ограниченного Unpickler здесь не воспроизводились —
в тексте это помечено как политика доверия, а не как проверенная защита.
