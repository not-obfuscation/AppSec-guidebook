# Spring: конфигурация безопасности и actuator

Уровень **L3** · время 15 мин

Что прочитать сначала: `java-reading-syntax`.

Конфигурация безопасности в Spring-приложении — это Java-код, и читается
он по правилам темы-предпосылки. Вот такой фрагмент из ревью — скажите,
что в нём не так, до чтения выноски:

```java
http.authorizeHttpRequests((authorize) -> authorize
    .requestMatchers("/public/**").permitAll()
    .anyRequest().permitAll()        // (1)
);
```

1. Правила читаются сверху вниз, и побеждает первое совпадение. Запись
   `anyRequest().permitAll()` означает «всё остальное — всем»: всякая
   ручка, добавленная позже и не попавшая в список, открыта. При этом
   код компилируется, тесты проходят, а дыра сидит в порядке строк.

Фрагмент из ревью — частный случай общего свойства цепочки: порядок
строк — это семантика, и одно широкое разрешение выше отменяет все
строгие правила под ним. В приложение добавили ручку `/billing/refund`,
а конфигурацию не трогали — кто может её вызвать?

Дальше — коротко: как читается цепочка, чем хорошо умолчание «запрещено»
и что отдаёт наружу actuator без настройки.

## 0. Коротко

Spring Security применяет
правила authorizeHttpRequests по порядку: первое совпавшее решает, и
`anyRequest()` в конце — это ответ для всех остальных. Безопасная
дисциплина — запрет по умолчанию (`denyAll()` или `authenticated()`), а
открытые адреса — списком выше. Документация прямо называет запрет по
умолчанию здоровой практикой, превращающей правила в список
разрешённого.
Отсутствие правила для новой ручки — это CWE-862, «отсутствующая
авторизация» из каталога Common Weakness Enumeration. Actuator по умолчанию отдаёт
через HTTP (Hypertext Transfer Protocol) только `/actuator/health`,
да и тот без деталей: `show-details`
по умолчанию `never`. Открытие остального — явное: свойство
`management.endpoints.web.exposure.include`. То же в терминах, которыми
это обсуждают.

**Зачем это в работе AppSec-инженера.** Ревью Spring-приложения начинается
с двух мест: цепочки authorizeHttpRequests и свойств actuator. Оба
читаются глазами за минуту, и оба отвечают на вопрос «что открыто без
входа».

## 3. Механика

**Откуда это взялось.** Ранний Spring Security конфигурировался XML-файлами;
правила пересекающихся адресов требовали порядка, и порядок стал
семантикой. Форма последних версий — Java-конфигурация с тем же
правилом: совпадения ищутся
сверху вниз, и первое сработавшее правило решает судьбу запроса.

Из этого следуют два чтения одной цепочки. Первое: `anyRequest()` — это
стоп-слово, всё ниже него мёртво, а всё выше проверено им не будет.
Второе: `permitAll()` у любого правила открывает его адрес без входа.
Типовая дыра ревью — пара «широкий паттерн выше, строгое правило ниже»:
`/admin/**` стоит после `/**` с permitAll и не сработает никогда.

Actuator устроен обратно: закрыто по умолчанию. Без настройки через HTTP
виден только `/actuator/health`, а детали здоровья скрыты (show-details
равен never, «показывать только авторизованным» включается отдельно).
Открывают его свойства include и exclude, и exclude сильнее include.
Запись `include: "*"` открывает все конечные точки, включая env и beans с
настройками приложения; в YAML звёздочка при этом требует кавычек.
Документация советует открывать точечно и прикрывать actuator либо Spring
Security, либо сетевой границей.

Границы: тема обзорная по замороженному оглавлению и написана по
документации. На стенде Spring Boot не собирался. Метод-уровневая
безопасность (`@PreAuthorize`) и реактивный стек читаются по той же
цепочке правил, но здесь не разбираются.

## 13. Источники

1. Spring Security Reference; реестр `spring-security-docs`. Разделы:
   Authorize HTTP Requests — порядок правил, `anyRequest`, `denyAll` как
   список разрешённого, совпадения по Ant-паттернам и по методу.
   <https://docs.spring.io/spring-security/reference/index.html>
2. Actuator Endpoints, документация Spring Boot; реестр
   `spring-boot-actuator`. Разделы: Exposing Endpoints (по умолчанию
   только health, include/exclude, приоритет exclude), show-details
   со значением по умолчанию never.
   <https://docs.spring.io/spring-boot/reference/actuator/endpoints.html>

Каркас этапа: у этапа 7 общих унаследованных источников нет; каждая тема
опирается на документацию своего языка и на материалы этапа 1 по
классам дефектов.

**Скоропортящийся слой.** Имена свойств и умолчания actuator меняются
между мажорными версиями Spring Boot; при ревизии перечитывается страница
документации. Правило «первое совпадение решает» стабильно.

**Маркеры уверенности.** Тема написана **по документации**: справочник
Spring Security (раздел Authorize HTTP Requests) и страница Actuator
Endpoints открыты лично 2026-09-02; умолчание «только health по HTTP»,
`show-details: never` и приоритет exclude сверены по тексту страниц.
