# Инъекции в ORM и raw SQL

Уровень **L2** · время 40 мин (теория 25 / задача 10 / самопроверка 5,
оценка)

Что прочитать сначала: `sqli-basics`, `parameterized-queries`.

Приложение на SQLAlchemy, в настройках включён журнал запросов
(`echo=True`). Один и тот же обработчик ищет пользователя по имени из
запроса. Посмотрим в журнал, что уехало в базу, когда в имени пришла
строка `alice' OR '1'='1`:

```text
== запрос собран f-строкой:
SELECT id FROM users WHERE name = 'alice' OR '1'='1'
[...] ()
строк: [(1,), (2,)]
== запрос с параметром :name:
SELECT id FROM users WHERE name = ?
[...] ("alice' OR '1'='1",)
строк: []
```

Первый запрос вернул обе строки таблицы: ввод стал частью текста
запроса. Второй вернул пустой список: текст запроса уехал с
плейсхолдером, а опасная строка — отдельным аргументом, и база искала её
как имя, которого нет. Никакой фильтрации ввода во втором случае не
потребовалось: границу провёл сам протокол обмена с базой.

Это языковая грань внедрения SQL — сам класс разобран в теме
`sqli-basics`, механика параметров — в `parameterized-queries`. Дальше
разберём, где именно у ORM кончается защита, как читаются raw-слои
Django и SQLAlchemy и почему имя столбца параметром не передаётся.

## 0. Коротко

То же в терминах, которыми это обсуждают. ORM (object-relational mapping,
объектно-реляционное отображение) защищает, пока запрос строится её методами:
значения уезжают параметрами отдельно от текста.
Сырой слой — raw() и extra() в Django, text() в SQLAlchemy, курсор
DB-API — принимает текст запроса целиком. Всякий, кто подставил ввод в
этот текст строковой операцией, собрал инъекцию. Это CWE-89 (каталог
Common Weakness Enumeration), категория `A05:2025` издания OWASP.
Чинится связанными параметрами: `%s` и список в Django, `:имя` и словарь
в SQLAlchemy — без кавычек вокруг плейсхолдера. Имена таблиц, столбцов и
направление сортировки параметром не передаются нигде: их сверяют с
разрешённым списком.

**Зачем это в работе AppSec-инженера.** Спор «у нас ORM, инъекций нет»
заканчивается первым же raw-запросом в дереве: отчёты, сложные фильтры
и миграции почти всегда выходят за пределы модели. Ревьюеру нужен короткий
список мест, где ORM молчит, и рабочий приём проверки: журнал запросов
показывает склейку лучше любого чтения кода.

## 3. Механика

**Откуда это взялось.** ORM появилась, чтобы запрос собирался из кода, а
не из строк: пока фильтр — это вызов метода, значение параметром
уезжает автоматически. Но часть запросов в модель не укладывается, и у
каждой библиотеки есть сырой выход. Наивное решение — «подставить
значение в текст f-строкой» — возвращает дефект, от которого ORM
уходила: граница между кодом запроса и данными стирается.

У Django документация насчитывает три таких выхода: raw() у менеджера
модели, фрагменты RawSQL внутри ORM-выражения и курсор из
django.db.connection для полностью своего SQL. Помимо них есть ещё
extra() — тот же сырой фрагмент внутри обычного queryset. Документация
требует две вещи сразу: параметры только через аргумент params с
плейсхолдерами %s и никогда не собирать запрос строковым форматированием.

Отдельно она запрещает кавычки вокруг
%s: `'... = %s'` — единственная допустимая форма, `'... = '%s''` —
ошибка. Почему это ошибка, видно из прогона на Django 6.1. Драйвер
плейсхолдер внутри кавычек не считает, привязка не находит места, и база
отвечает ProgrammingError о неверном числе привязок. То есть кавычки не
«двойная защита», а сломанный запрос.

У SQLAlchemy сырой слой — конструкция text(). Она принимает параметры в
именованной форме `:name` и словарём при выполнении. В журнале из
введения видно, что происходит дальше. Именованный параметр превратился
в `?`: драйвер sqlite говорит в формате qmark, а значение уехало
отдельным кортежем. Библиотека скрывает разницу шести форматов
параметров DB-API, но не скрывает главного: строка внутри text() должна
быть написана автором, а не собрана из ввода.

Остаётся класс мест, куда параметр подставить нельзя в принципе: имена
таблиц и столбцов, направление сортировки, ключевые слова. Плейсхолдер —
место для значения, а не для идентификатора. Поэтому сортировку,
пришедшую из запроса, не «параметризуют», а сверяют с разрешённым
списком имён и подставляют имя из списка, а не из ввода.

## 5. Как выглядит в коде

Ревьюер ищет строковые операции рядом с сырым слоем.

```python
# УЯЗВИМО — демонстрация, не для продакшена
User.objects.raw(
    "SELECT * FROM users WHERE name = '%s'" % name)      # (1)
User.objects.extra(where=[f"name = '{name}'"])           # (2)
session.execute(text(f"SELECT * FROM users WHERE name = '{name}'"))
                                                       # (3)
cursor.execute("SELECT * FROM users ORDER BY " + sort)   # (4)
```

1. Форматирование `%` вместо аргумента params: ввод стал текстом запроса.
2. extra() со склейкой: тот же дефект внутри обычного queryset.
3. f-строка в text(): частый вид в проектах на SQLAlchemy.
4. Имя столбца сортировки из ввода: параметр здесь невозможен, и склейка
   — единственный способ ошибиться.

Обёртки, которые не спасают: «очистка» ввода от кавычки (ломается о
вторую форму записи) и кавычки вокруг плейсхолдера (ломают привязку,
показано выше). Ложное срабатывание: константный текст запроса без ввода
законен; смотрите, участвует ли в строке внешнее значение.

## 6. Как чинится

Правило одно: значения едут параметрами, идентификаторы — из списка.

```python
# Исправлено
User.objects.raw("SELECT * FROM users WHERE name = %s", [name])
session.execute(
    text("SELECT * FROM users WHERE name = :name"), {"name": name})

ALLOWED_SORT = {"name": "name", "created": "created_at"}
column = ALLOWED_SORT.get(sort, "name")
cursor.execute(f"SELECT * FROM users ORDER BY {column}")
```

Параметр в raw() и в text() — второй аргумент вызова, и плейсхолдер в
тексте стоит без кавычек. Для сортировки вход сверяется с разрешённым
словарём, и в текст попадает значение из словаря. Это требование
ASVS v5.0-1.2.4: динамические запросы строятся параметризацией, а то, что
не параметризуется, — белым списком.

**Когда канон не подходит.** Пакетные вставки и запросы с переменным
числом условий собираются библиотечными средствами: в SQLAlchemy это
выражения вместо text(), в Django — Q-объекты и filter(). Если запрос
можно записать средствами ORM, сырой слой не нужен вовсе (проверка класса
через WSTG-v42-INPV-05 идёт по обработчикам, где сырой слой остался).

## 9. Ловушка

Встречается обоснование: «плейсхолдер взят в кавычки, значит, значение
не вырвется из строки».

**Кавычки вокруг плейсхолдера не защищают, а ломают привязку.** Драйвер
ищет плейсхолдер в тексте запроса, а внутри строкового литерала его нет.
Прогон на Django 6.1 с sqlite показывает ProgrammingError — «неверное
число привязок»: параметр остался не у дел.

Контрпример для обратной стороны: даже там, где такой запрос случайно
сработал (драйвер подставил значение внутрь кавычек), защита держится на
конкретной реализации драйвера. Следующая версия или другая база читают
ту же строку иначе, и граница исчезает молча.

## 10. Чеклист ревью

1. Verify that raw-запросы передают значения через params или словарь
   параметров, а не строковым форматированием (CWE-89).
2. Verify that плейсхолдеры в тексте запроса стоят без кавычек.
3. Verify that имена таблиц, столбцов и направления сортировки приходят
   из разрешённого списка, а не из ввода (ASVS v5.0-1.2.4).
4. Verify that extra() и RawSQL либо отсутствуют, либо не содержат ввода
   вне параметров.
5. Verify that журнал запросов на стенде подтверждает: значения едут
   отдельно от текста (видно по `?` и кортежу аргументов).
6. Verify that обработчики с сырым SQL покрыты проверкой на ввод с
   кавычкой и комментарием (WSTG-v42-INPV-05).

## 11. Задача

Поднимите SQLite в памяти с таблицей из двух строк и два запроса из
введения темы: один через f-строку, один через параметр. Прогоните оба с
вводом `alice' OR '1'='1` и сверьте журнал и число строк.

Одна подсказка: в SQLAlchemy журнал включается аргументом `echo=True` у
create_engine, и он печатает и текст запроса, и кортеж параметров.

**Критерий выполнения** наблюдаемый: в журнале первого запроса ввод
стоит внутри текста, и ответ содержит обе строки. В журнале второго
текст оканчивается плейсхолдером, ввод едет отдельным аргументом, ответ
пуст.

## 12. Проверь себя

1. Почему в журнале параметризованного запроса ввод стоит отдельным
   аргументом, и что это даёт?
2. Что отвечает база на плейсхолдер, взятый в кавычки, и почему?
3. Как передать в запрос имя столбца, пришедшее от пользователя?
4. Назовите raw-слои Django и SQLAlchemy по одному признаку каждого.
5. Возврат к теме `parameterized-queries`: чем связанный параметр
   отличается от экранирования в момент отправки запроса?

<details markdown="1">
<summary>Ответы</summary>

1. Текст запроса и данные едут в базу раздельно, и база читает значение
   только как значение: оно не может изменить текст запроса.
2. Ошибкой о неверном числе привязок: плейсхолдер внутри строкового
   литерала для драйвера не существует, и параметр остаётся не у дел.
3. Никак: плейсхолдер принимает только значения. Вход сверяют с
   разрешённым списком имён и подставляют имя из списка.
4. Django: raw() и extra() у модели, курсор из connection; SQLAlchemy:
   text() и явный SQL в execute. Признак общий: текст запроса целиком в
   аргументе.
5. Экранирование правит текст перед отправкой и зависит от правил
   грамматики. Связанный параметр вообще не попадает в текст: границу
   проводит протокол, а не символы.

</details>
