# Java: небезопасная десериализация и цепочки гаджетов

Уровень **L2** · время 30 мин (теория 18 / задача 8 / самопроверка 4,
оценка)

Что прочитать сначала: `insecure-deserialization`.

Класс с полем и методом readObject; сериализуем объект, разбираем обратно
и параллельно прогоняем разбор с фильтром. Вывод (OpenJDK 17):

```text
поток: 72 байт, начало: ac ed 00 05
readObject исполнился для: demo
фильтр отклонил: filter status: REJECTED
```

Три наблюдения. Первое: поток начинается с байтов `AC ED 00 05` — это
подпись Java-сериализации, по ней вход опознаётся в трафике (в Base64 это
префикс `rO0`). Второе: readObject отработал при разборе — до того, как
объект вернулся вызывающему. Третье: фильтр десериализации отклонил класс
до разбора полей.

Общая механика класса разобрана в теме `insecure-deserialization`; это
CWE-502 (каталог Common Weakness Enumeration), категория `A08:2025`
издания OWASP. Здесь — форма Java: что пишет в поток
ObjectOutputStream, откуда берутся цепочки гаджетов и чем отвечать.

## 0. Коротко

То же в терминах, которыми это обсуждают. ObjectInputStream.readObject()
читает поток, где записаны имена классов, и восстанавливает объекты,
вызывая методы их классов (readObject, readResolve, readExternal). Если
поток чужой, класс и его поведение выбирает автор потока, а набор
доступных классов — весь classpath приложения. Цепочка гаджетов — путь из
вызовов через чужие библиотечные классы к исполнению. Ответ платформы —
ObjectInputFilter (с Java 9): фильтр по классам, глубине графа и размеру
потока, с отказом до десериализации. Канонический ответ архитектуры —
не принимать такой формат от чужих вообще.

**Зачем это в работе AppSec-инженера.** Java-сервисы принимают такие
потоки в очередях сообщений, кэшах, RMI и старых HTTP-эндпоинтах. Ревьюеру
нужны три навыка: опознать вход по маркерам, найти readObject в дереве и
проверить, есть ли фильтр.

## 1. Цели

После этого раздела вы сможете:

1. Опознать Java-сериализацию по маркерам потока и по вызовам в коде.
2. Показать, что readObject исполняется при разборе, до возврата объекта.
3. Назначить фильтр десериализации и назвать его предел.
4. Объяснить, почему состав classpath определяет набор гаджетов.

## 3. Механика

**Откуда это взялось.** Сериализация в Java задумана для своих: объект
уходит в файл или по сети тому же приложению. Для этого потоку мало
данных — он несёт рецепт восстановления: имена классов и их полей. Как и
в pickle из темы `python-pickle-eval`, наивное прочтение «это данные»
ломается о рецепт: восстановление вызывает код класса.

Три детали делают класс тяжелее, чем «небезопасный разбор». Первая:
конструктор при десериализации не вызывается, а вызываются методы
сериализации — readObject и его родня; инварианты, установленные
конструктором, в этом пути не действуют. Вторая: класс для разбора ищется
по имени во всём classpath — значит, набор «полезных» классов определяется
зависимостями приложения, и каждая библиотека расширяет его. Третья:
гаджет — это класс из чужой библиотеки, чей readObject делает что-то с
данными потока; цепочка гаджетов — путь вызовов от точки разбора до
исполнения. Атакующему не нужно писать класс: он собирает путь из того,
что уже лежит в зависимостях.

Маркеры входа для ревью и сети (по памятке OWASP): байты `AC ED 00 05`
в начале потока, префикс `rO0` в Base64, тип содержимого
`application/x-java-serialized-object`. В коде — ObjectInputStream с
readObject и перегруженные readObject, readResolve, readExternal в
классах модели.

## 5. Как выглядит в коде

Главный признак — разбор потока, источник которого не доказан:

```java
// УЯЗВИМО — демонстрация, не для продакшена
byte[] body = request.getInputStream().readAllBytes();
ObjectInputStream ois =
    new ObjectInputStream(new ByteArrayInputStream(body));
Object o = ois.readObject();        // (1)
```

1. Разбор чужого потока: имена классов и вызовы методов выбирает
   отправитель. Проверка типа результата после разбора опоздала:
   исполнение уже случилось внутри readObject.

Второй признак — поля, которые не должны уезжать в поток:

```java
// УЯЗВИМО — демонстрация, не для продакшена
public class Account implements Serializable {
    private String login;
    private String passwordHash;   // (1)
}
```

1. Поле уедет в поток и прочитается обратно из чужого потока. Памятка
   OWASP предписывает таким полям модификатор `transient` — они
   исключаются из сериализации.

Ложное срабатывание: сериализация внутри одной системы с общим
доверенным хранилищем — риск в источнике потока, а не в самом вызове.

## 6. Как чинится

Правило одно: разбор допускает только ожидаемые классы — или формат
меняется на данные без поведения.

```java
// Исправлено: фильтр до разбора
ObjectInputFilter filter =
    ObjectInputFilter.Config.createFilter("com.example.dto.*;!*");
ois.setObjectInputFilter(filter);
```

Строка-паттерн читается как список правил: разрешить пакет, запретить
остальное. Фильтр проверяет и метрики — глубину графа, число ссылок,
размер потока, — что закрывает и атаки на память. Глобально фильтр
ставится свойством `-Djdk.serialFilter` для всей JVM; точечно —
setObjectInputFilter на потоке (проверено прогоном из введения: отказ —
InvalidClassException до чтения полей). Старый приём из памятки OWASP —
наследник ObjectInputStream с переопределённым resolveClass, который
пропускает только ожидаемые классы; фильтр платформы делает то же без
наследования.

**Когда канон не подходит.** Фильтр держит границу по классам, но не
знает семантики: разрешённый класс с опасным полем остаётся опасным.
Архитектурный ответ из памятки — смена формата: JSON вместо
сериализации объектов. Историческая починка, если код чужой и патч ждать
нельзя, — агент JVM, внедряющий ограничение в ObjectInputStream глобально.

## 9. Ловушка

Встречается мнение, что опасен только readObject с явным вызовом exec, а
«наш код таких классов не содержит».

**Гаджеты — это чужие классы из зависимостей, а не ваш код.** Механизм
из раздела о механике: поток называет класс по имени, и разбор ищет его
во всём classpath. Библиотека в зависимостях — уже часть набора.

Контрпример: приложению достаточно одной библиотеки с классом, чей
readObject вызывает методы из полей потока, — и цепочка собирается без
единой строки кода самого приложения. Поэтому ревью зависимостей и ревью
десериализации — одна задача, а не две.

## 10. Чеклист ревью

1. Verify that ObjectInputStream не читает потоки из запросов, очередей
   и кэшей без доказанного источника (CWE-502).
2. Verify that на каждом таком разборе стоит фильтр классов со списком
   разрешённых, а не запрещённых.
3. Verify that у фильтра заданы пределы глубины, числа ссылок и размера
   потока.
4. Verify that поля с секретами в сериализуемых классах помечены
   transient.
5. Verify that вход опознаваем: маркеры `AC ED 00 05`, `rO0` и тип
   содержимого ищутся в прокси и журналах.
6. Verify that состав зависимостей известен, а библиотеки с известными
   гаджетами отслеживаются (`A08:2025`).

## 11. Задача

Напишите класс с полем и методом readObject, который печатает значение.
Сериализуйте объект в массив байт, посмотрите на первые байты потока и
разберите его обратно дважды: без фильтра и с фильтром, отклоняющим ваш
класс.

Одна подсказка: фильтр ставится на поток через setObjectInputFilter, и
ставится один раз — вторая установка на том же потоке бросает
IllegalStateException.

**Критерий выполнения** наблюдаемый: вывод из трёх строк по образцу
введения. Подпись потока `ac ed 00 05`, печать из readObject при разборе
без фильтра и InvalidClassException при разборе с фильтром.

## 12. Проверь себя

1. По каким трём маркерам поток Java-сериализации опознаётся в трафике?
2. Почему проверка типа после readObject не защищает?
3. Что проверяет фильтр десериализации помимо имён классов?
4. Почему набор гаджетов определяется зависимостями, а не кодом
   приложения?
5. Возврат к теме `insecure-deserialization`: что общего у потока pickle
   и потока ObjectInputStream, и в чём разница точек исполнения?

<details markdown="1">
<summary>Ответы</summary>

1. Байты `AC ED 00 05` в начале потока, префикс `rO0` в Base64 и тип
   содержимого `application/x-java-serialized-object`.
2. Потому что исполнение происходит при разборе: к моменту проверки
   методы классов уже отработали.
3. Глубину графа, число ссылок, длины массивов и размер потока в байтах.
4. Поток называет класс по имени, и разбор ищет его во всём classpath:
   каждая зависимость пополняет набор классов, из которых собирается
   цепочка.
5. Общее: поток несёт рецепт восстановления объекта, а не только данные.
   Разница: pickle исполняет инструкции потока напрямую, а Java вызывает
   методы классов, найденных по именам из потока.

</details>

**Маркеры уверенности.** **Проверено лично** 2026-09-02 на OpenJDK
17.0.20.1: поток начинается с `ac ed 00 05`; readObject исполняется при

API**, открытому лично 2026-09-02; страница Serialization Filtering
отдаётся JS-оболочкой, и по ней сверено оглавление. Маркеры потока и
совет про transient — по памятке OWASP, открытой в тот же день.

тема об их существовании говорит по источникам, не по стенду.
