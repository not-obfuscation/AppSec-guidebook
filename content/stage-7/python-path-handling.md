# Работа с путями в Python: join, normpath и обход каталога

Уровень **L3** · время 15 мин

Что прочитать сначала: `path-traversal`.

Сервис отдаёт отчёт по имени файла: к базовому каталогу приклеивают имя
из запроса через os.path.join. Проверим клей двумя вводами:

```text
>>> os.path.join("/var/app/files", "../../secret")
'/var/app/files/../../secret'
>>> os.path.join("/var/app/files", "/etc/hostname")
'/etc/hostname'
```

Первый ввод вернул путь с `..` — выход из каталога. Второй сделал хуже:
абсолютный сегмент молча сбросил базовый каталог целиком. Никакой
«склейки внутрь базы» у join нет и не задумано — это и есть тема.

Сам класс дефекта — обход каталога, CWE-22 (каталог Common Weakness
Enumeration) — разобран в теме `path-traversal`. Здесь — питоновые
функции, на которых он возникает, и проверка, которая держит границу.

## 0. Коротко

То же в терминах, которыми это обсуждают. Функции os.path работают со
строкой, а не с файловой системой. Вызов join с абсолютным сегментом
отбрасывает всё до него. Вызов normpath сворачивает `..` лексически
и ничего не знает о символических ссылках. Функция commonprefix ищет
общий префикс посимвольно и путей не понимает. У pathlib оператор `/` с абсолютной правой частью
ведёт себя так же, как join. Рабочая проверка одна: привести путь через
realpath и сравнить с разрешённым корнем через commonpath, а вход с `..`
и абсолютные пути отклонять до этого.

**Зачем это в работе AppSec-инженера.** Отдача файлов по имени из
запроса — типовой обработчик, и join в нём выглядит как забота о путях.
Ревьюеру важно знать, что join про строки, иначе находка «обход
каталога» будет спориться кодом, который «всё правильно склеивает».

## 3. Механика

**Откуда это взялось.** Библиотека путей в Python исторически строковая:
она решает задачу «собрать корректную строку пути», а не «удержать путь
внутри каталога». Отсюда и поведение: абсолютный сегмент в join по
задумке означает «начни заново», и функция честно это делает.

Документация os.path фиксирует и остальные края. Пример для join:
`os.path.join('/home/foo', '/home/bar')` даёт `/home/bar` — базовая
часть отброшена. Вызов normpath сворачивает `..` текстуально, и
документация предупреждает: такая свёртка может изменить смысл пути,
где есть символические ссылки. Функция commonprefix сравнивает строки
посимвольно.
Прогон подтверждает: для `/var/app/files` и `/var/app/files-secret`
она возвращает `/var/app/files`, хотя общего каталога у этих путей
нет. Правильная пара — commonpath, и она честно отвечает `/var/app`.

```python
# Проверка, которая держит границу
import os

root = "/var/app/files"
if os.path.isabs(name) or ".." in name.split("/"):
    raise ValueError(name)
full = os.path.realpath(os.path.join(root, name))
if os.path.commonpath([root, full]) != root:
    raise ValueError(name)
```

Сначала вход отклоняется по форме — абсолютный путь и элемент `..`, —
потом итог сверяется с корнем после разрешения ссылок. Одной формы мало:
ссылка внутри базового каталога может указывать наружу, и это видно
только после realpath. Одного realpath мало без отбора по форме: вход
`/etc/hostname` переживёт свёртку как есть. Процедура ретеста такой
находки — кодированные формы `..` и абсолютные пути — разобрана в
WSTG-ATHZ-01.

Границы: у Windows свои правила разбора, и путь `c:report.txt` —
относительный к текущему каталогу диска, а не к корню; ревью
кросс-платформенного кода это учитывает. Временное окно между проверкой
и открытием файла строковыми функциями не закрывается вовсе.
