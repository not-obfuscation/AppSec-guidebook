# FastAPI и pydantic: уязвимые паттерны

Уровень **L2** · время 40 мин (теория 25 / задача 10 / самопроверка 5,
оценка)

Что прочитать сначала: `jwt-basics`, `rest-and-graphql`.

Два маршрута одного сервиса на FastAPI возвращают один и тот же объект
пользователя из базы. Разница — в одном аргументе объявления маршрута.
Прогон тестовым клиентом:

```text
GET /leak -> {'username': 'alice', 'hashed_password': '$argon2id$...'}
GET /ok   -> {'username': 'alice'}
```

В первом ответе уехал хеш пароля: маршрут вернул объект целиком, а
объект знал про поле. Во втором тот же объект прошёл через
response_model, и поле отфильтровалось при сериализации. Никакой атаки
на протокол не потребовалось: достаточно обычного запроса.

Эта тема — о том, где контракт FastAPI и pydantic расходится с
безопасностью. Устройство токена JWT (JSON Web Token) разобрано в теме
`jwt-basics`, устройство интерфейсов — в `rest-and-graphql`. Дальше:
ответ без фильтрации, валидаторы как парсер, зависимости безопасности и
вызов jwt.decode.

## 0. Коротко

То же в терминах, которыми это обсуждают. FastAPI строит интерфейс из
аннотаций типов: вход валидируется моделью pydantic, выход фильтруется
response_model, а доступ подключается зависимостью Depends. У каждого из
трёх слоёв есть паттерн отказа. Ответ без response_model отдаёт объект
со всеми полями — CWE-200 (каталог Common Weakness Enumeration).
Валидатор приводит тип, а не защищает: строка «false» станет булевым
False. Зависимость OAuth2PasswordBearer только достаёт токен из
заголовка — она его не проверяет. Проверка подписи живёт в jwt.decode,
и PyJWT требует явный список алгоритмов. Вызов без него падает с
DecodeError: защита от подмены алгоритма встроена (CWE-347, категория
`A04:2025` издания OWASP 2025 года).

**Зачем это в работе AppSec-инженера.** FastAPI-проект читается как
набор объявлений, и ревью сводится к вопросу «что объявлено, а что
умолчано». Умолчание в каждом из трёх слоёв работает против автора:
вернуть объект проще, чем отфильтровать; принять ввод проще, чем
проверить; объявить схему проще, чем зависимость.

## 3. Механика

**Откуда это взялось.** Аннотации типов в Python задумывались для
анализа кода, а FastAPI сделал их контрактом: по моделям строится и
проверка входа, и документация. Наивное прочтение «раз модель проверена,
вход безопасен» ломается о назначение валидатора. Он отвечает на вопрос
«соответствует ли значение типу», а не «имеет ли этот вход право быть
здесь». Между этими вопросами и живут паттерны этой темы.

Первый слой — выход. Маршрут без response_model сериализует то, что
вернул обработчик: объект из базы отдаёт всё, что у него есть. Модель
ответа работает как фильтр на запись наружу, и её отсутствие — умолчание
с обратным знаком: всё, что попало в объект, попадёт клиенту.

Второй слой — вход. Валидаторы pydantic бывают четырёх режимов, и у
каждого своя точка зрения на данные. Документация прямо предупреждает:
валидаторы режима before получают сырой вход, которым «может быть любой
объект». Приведение при этом не проверка. Прогон на pydantic 2.13
показывает: поле `is_admin: bool` принимает строки «false», «no», «0»
и «off» как False, а «1» и «true» — как True. Для флага, пришедшего
из формы, это осмысленно; для границы доверия — нет: «проверка типа»
сказала о значении ровно то, что оно булево.

Третий слой — доступ. Схема вроде OAuth2PasswordBearer объявляет, откуда
взять токен, и встраивает схему в документацию. Проверки подписи в ней
нет: она возвращает строку. Проверяет токен вызов jwt.decode, и у PyJWT
оно устроено защитно. Прогон на PyJWT 2.13 показывает: вызов без
аргумента algorithms падает с DecodeError. Список допустимых алгоритмов
библиотека требует явно. Атака подменой алгоритма из темы
`jwt-basics` здесь упирается в этот список, если он записан константой
вроде `["HS256"]`.

## 5. Как выглядит в коде

Три признака, все видны по объявлению маршрута или модели.

```python
# УЯЗВИМО — демонстрация, не для продакшена
@app.get("/user")
def get_user():                       # (1)
    return UserInDB(username="a", hashed_password="...")

@app.post("/items")
def add_item(item: Item):             # (2)
    ...

payload = jwt.decode(token, KEY)      # (3)
```

1. Нет response_model: ответ — всё, что вернул обработчик, включая поля
   хранилища.
2. Модель входа совпадает с моделью хранения: поля, которые клиент не
   должен задавать (роль, владелец, цена), принимаются из тела запроса.
3. Вызов без списка алгоритмов. На PyJWT 2.13 он падает с DecodeError,
   но в коде с более мягкой библиотекой это классическая подмена
   алгоритма; ревьюеру форма вызова видна до версии.

Обёртки, которые не спасают: `@app.get(..., dependencies=[...])` без
понимания, что схема безопасности там только извлекает токен. И отдельная
форма: зависимость объявлена, но забыта у части маршрутов роутера —
FastAPI не навязывает её по умолчанию.

Ложное срабатывание: pydantic-модель с лишними полями во входе сама по
себе не дефект. По умолчанию лишние поля игнорируются; смотрите, есть ли
у модели поля со служебным смыслом и совпадает ли входная модель с
моделью хранения.

## 6. Как чинится

Правило одно: контракт входа и контракт выхода — разные модели, а доступ
объявлен на каждом маршруте.

```python
# Исправлено
class UserOut(BaseModel):
    username: str

@app.get("/user", response_model=UserOut)
def get_user(user: User = Depends(get_current_user)):
    return user

payload = jwt.decode(token, KEY, algorithms=["HS256"])
```

Модель выхода фильтрует ответ; модель входа не содержит полей, которые
клиент задавать не вправе. Токен проверяется с явным списком
алгоритмов и с проверкой времени жизни. Учебный код документации FastAPI
делает именно так, и этот пример годится как образец. Для флагов и
кодов, где приведение недопустимо, pydantic даёт строгие типы
(StrictBool и родственные) — они отказывают строке «false» там, где
нужен именно булев вход.

**Когда канон не подходит.** Внутренние вызовы между своими сервисами
иногда возвращают полную модель намеренно; тогда граница — это сеть, а
не response_model, и ревью переносится на доступность маршрута извне.
Строгие типы ломают формы, где браузер честно шлёт строки, — там ответ
явный валидатор со своей логикой, а не строгий тип.

## 9. Ловушка

Встречается мнение, что раз вход прошёл валидацию pydantic, он доверен.

**Валидация отвечает про форму, а не про право.** Механизм из раздела о
механике: валидатор проверяет соответствие типу и ограничениям поля.
Вопрос «может ли этот пользователь менять это поле» в типе не выражается
вовсе.

Контрпример — модель входа с полем is_admin: вход
`{"username": "a", "is_admin": true}` пройдёт валидацию безупречно.
Форма верная; право отсутствует. Починка — не валидатор, а раздельные
модели: во входной модели этого поля нет.

## 10. Чеклист ревью

1. Verify that у каждого маршрута, возвращающего объект хранилища, задан
   response_model (CWE-200).
2. Verify that входные модели не содержат служебных полей: роли,
   владельца, цены, признаков состояния.
3. Verify that каждый защищённый маршрут несёт зависимость доступа, а не
   только схему в документации.
4. Verify that jwt.decode вызывается с явным списком алгоритмов и
   проверкой срока (CWE-347).
5. Verify that поля-флаги и коды не полагаются на приведение типов:
   строка «false» не должна становиться решением.
6. Verify that валидаторы режима before обрабатывают сырой вход любого
   типа, а не только ожидаемый.

## 11. Задача

Соберите приложение из двух маршрутов по образцу введения: один возвращает
объект с полем-секретом, второй — тот же объект через response_model.
Прогоните оба тестовым клиентом и запишите ответы.

Одна подсказка: тестовый клиент FastAPI (TestClient) поднимает
приложение в памяти, сервер не нужен.

**Критерий выполнения** наблюдаемый: два ответа одного объекта: в первом
поле-секрет присутствует, во втором — отсутствует, и разница объяснена
одним аргументом маршрута.

## 12. Проверь себя

1. Что делает response_model и почему его отсутствие — находка?
2. Чем валидатор режима before отличается от after по виду входа?
3. Что делает OAuth2PasswordBearer и чего он не делает?
4. Как PyJWT 2.13 отвечает на вызов decode без списка алгоритмов и почему
   это защита?
5. Возврат к теме `jwt-basics`: какую атаку на подпись отсекает явный
   список алгоритмов?

<details markdown="1">
<summary>Ответы</summary>

1. Фильтрует ответ по модели выхода: полей, которых в ней нет, клиент не
   получит. Без неё ответ — всё, что вернул обработчик.
2. Валидатор before получает сырой вход любого типа до проверки типом;
   after — уже приведённое значение.
3. Достаёт токен из заголовка `Authorization` и регистрирует схему в
   документации. Подпись он не проверяет: это делает jwt.decode.
4. Падает с DecodeError: список допустимых алгоритмов обязателен. Подмена
   алгоритма в токене перестаёт работать, потому что алгоритм читается
   из списка, а не из токена.
5. Подмену алгоритма: токен с alg из другого семейства или без подписи
   отвергается, потому что проверка идёт только алгоритмами из списка.

</details>

2. Security, документация FastAPI; реестр `fastapi-security`. Разделы:

   <https://fastapi.tiangolo.com/tutorial/security/>
3. OAuth2 with Password (and hashing), Bearer with JWT tokens,
   документация FastAPI; реестр `fastapi-security-oauth2-jwt`. Разделы:
   полный образец: извлечение токена схемой, проверка jwt.decode со
   списком алгоритмов, модели ответа.
   <https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/>

Каркас этапа: у этапа 7 общих унаследованных источников нет; каждая тема
опирается на документацию своего языка и на материалы этапа 1 по
классам дефектов.

**Скоропортящийся слой.** Поведение приведения типов и умолчания
валидаторов привязаны к мажорной версии pydantic: между первой и второй
они менялись, и при ревизии перечитываются. Устройство слоёв — модель
входа, модель выхода, зависимость — держится дольше.

**Маркеры уверенности.** **Проверено лично** 2026-09-02 на FastAPI
0.141.1, pydantic 2.13.5 и PyJWT 2.13.0 (тестовый клиент, без сервера):
маршрут без response_model отдаёт hashed_password, с response_model —
нет; поле bool принимает «false», «no», «0», «off» как False и «1»,
«true» как True; jwt.decode без algorithms падает с DecodeError, со
списком — проверяет. Умолчание extra=ignore у моделей pydantic — **по
документации**, в прогоне не воспроизводилось. Все три страницы
документации открыты лично 2026-09-02.
