# Django и Flask: настройки, CSRF, шаблоны

Уровень **L2** · время 45 мин (теория 28 / задача 12 / самопроверка 5,
оценка)

Что прочитать сначала: `csrf-mechanics`, `ssti`.

Одна и та же вставка значения в шаблон, четыре разных результата. В первые
три строки подставлено `<script>alert(1)</script>`, в четвёртую — значение
`a onmouseover=alert(1)`. Прогон на Django 6.1 (у Flask и
Jinja картина та же):

```text
{{ x }}               ->  &lt;script&gt;alert(1)&lt;/script&gt;
{{ x|safe }}          ->  <script>alert(1)</script>
mark_safe(x)          ->  <script>alert(1)</script>
<a title={{ x }}>     ->  <a title=a onmouseover=alert(1)>
```

Первая строка — защита по умолчанию: значение стало текстом. Вторая и
третья — та же защита, выключенная автором шаблона двумя способами.
Четвёртая тоньше: экранирование не выключали, но атрибут без кавычек
позволил значению породить второй атрибут. Фреймворк тут ни при чём:
границу нарушила разметка.

Эта тема — о том, что из защиты веба в Python делает фреймворк, а что
остаётся автору. Механика CSRF разобрана в теме `csrf-mechanics`,
внедрение в шаблон — в `ssti`. Дальше: что включает Django по умолчанию,
что во Flask надо доустановить, и как выглядит отключенная защита в
коде ревью.

## 0. Коротко

То же в терминах, которыми это обсуждают. Django включает защиту по
умолчанию: автоэкранирование в шаблонах, CSRF-мидлварь, проверка Host по
ALLOWED_HOSTS. Каждую из них можно выключить точечно — |safe, mark_safe,
`{% autoescape off %}`, `@csrf_exempt`, — и именно эти точки читаются в
ревью. Flask несёт минимальное ядро: экранирование Jinja включено, а
защиты от подделки межсайтового запроса (cross-site request forgery,
CSRF) в ядре нет — её даёт расширение вроде Flask-WTF. У обоих DEBUG
в проде возвращает страницу с деталями ошибки наружу. Классы дефектов —
CWE-352 и CWE-79 (каталог Common Weakness Enumeration); категории
издания OWASP 2025 года — `A01:2025` для CSRF и `A05:2025` для инъекций.

**Зачем это в работе AppSec-инженера.** Ревью веб-сервиса на Python
начинается с вопроса «какой фреймворк и что в нём выключено». Ответ
читается поиском по четырём словам — `csrf_exempt`, `mark_safe`,
`autoescape`, `DEBUG`, — а дальше начинается собственно ревью: законно ли отключение в
этом месте.

## 3. Механика

**Откуда это взялось.** Оба фреймворка отвечают на один вопрос: кто
несёт ответственность за защиту — каркас или автор приложения. Django
выбрал «каркас по умолчанию»: защита включена, и отключение остаётся
видимым в коде. Flask выбрал «минимальное ядро»: формы и их защита вне
скоупа. Документация говорит это прямо: место для проверки токена было
бы валидацией форм, которой в ядре нет. Ни один из выборов не
ошибка; у каждого свой паттерн риска. У Django риск в точечном
отключении, у Flask — в недоустановленном слое.

Про CSRF. Мидлварь Django проверяет секрет в каждом изменяющем
запросе. Прогон на Django 6.1 показывает это числом: POST без токена
получает 403, а тот же POST на view с `@csrf_exempt` — 200. Это требование
ASVS v5.0-3.5.1: изменяющие запросы защищены от подделки (класс покрывает
WSTG-v42-SESS-05). Во Flask такого слоя нет вообще: обработчик,
меняющий состояние по POST, уязвим без внешнего расширения.

Про шаблоны. Экранирование обоих движков (Django templates и Jinja)
контекстно-слепое в двух местах, названных документацией. Первое —
атрибут без кавычек: пример из введения, внедрение обработчика
onmouseover. Второе — адрес со схемой javascript: в href. Для второго случая документация
Flask прямо отправляет к политике содержимого — CSP.

Про DEBUG. Прогон с Django 6.1 и DEBUG=True: ответ 500 содержит текст
исключения с его содержимым — в демонстрации в него попала строка с
«паролем». Значения настроек Django при этом маскирует: SECRET_KEY в
тело не попал. У Werkzeug (под Flask) отладочная страница несёт
трейсбек и текст исключения. При evalex=True добавляется интерактивная
консоль на каждом кадре стека. Проверено на werkzeug из комплекта
Flask 3.1.

## 5. Как выглядит в коде

В Django ревьюер ищет выключатели:

```python
# УЯЗВИМО — демонстрация, не для продакшена
from django.utils.safestring import mark_safe
from django.views.decorators.csrf import csrf_exempt

DEBUG = True                     # (1)
ALLOWED_HOSTS = ["*"]            # (2)

@csrf_exempt                     # (3)
def change_email(request): ...

row = mark_safe(comment.text)    # (4)
```

1. DEBUG в проде: детали ошибок уходят клиенту.
2. Звёздочка в ALLOWED_HOSTS отключает проверку заголовка Host.
3. Отключение CSRF-проверки на изменяющем view.
4. Пометка чужого текста как безопасного; в шаблоне то же делают `|safe`
   и `{% autoescape off %}`.

Во Flask набор другой:

```python
# УЯЗВИМО — демонстрация, не для продакшена
from flask import render_template_string, request
from markupsafe import Markup

app.run(debug=True)                                   # (1)

@app.route("/hello")
def hello():
    name = request.args.get("name", "")
    return render_template_string("Привет, " + name)  # (2)
```

1. Отладчик в проде: страница с трейсбеком, а при включённой консоли —
   исполнение кода в кадре стека.
2. Ввод стал частью шаблона: прогон отвечает «Привет, 49» на ввод
   `{{7*7}}` — это внедрение в шаблон, а не в страницу (разбор в `ssti`).

Отдельная форма в обоих мирах: Markup() и mark_safe() на данных
пользователя. Поиск по именам функций находит такие места за минуту.
Ложное срабатывание: mark_safe на константе, собранной из своего
доверенного HTML, законен — смотрите на происхождение значения.

## 6. Как чинится

Правило одно: защита остаётся включённой; там, где её пришлось снять,
вход санитизируется или ограничивается отдельно.

```python
# Исправлено
ALLOWED_HOSTS = ["app.example.com"]
DEBUG = False

@app.route("/hello")
def hello():
    name = request.args.get("name", "")
    return render_template_string("Привет, {{ name }}", name=name)
```

CSRF во Flask доустанавливается расширением (Flask-WTF) или приёмом
double-submit из темы `csrf-tokens` — механика та же, различается
только упаковка. В Django снятый `@csrf_exempt` заменяется возвратом
мидлвари; для API с токеном в заголовке вместо cookie проверка не нужна
вовсе — это граница применимости, а не отключение.

**Когда канон не подходит.** Атрибут без кавычек и схема javascript: в
href не лечатся экранированием по построению: первая лечится кавычками
в разметке, вторая — политикой содержимого. Документация обоих
фреймворков называет эти два места явно, и ревью шаблонов проверяет их
отдельно от флагов autoescape.

## 9. Ловушка

Встречается мнение, что фреймворк с автоэкранированием закрывает
межсайтовый скриптинг целиком.

**Экранирование закрывает один контекст из нескольких.** Механизм из
раздела о механике: движок экранирует текст внутри разметки, но не знает
о границах атрибута без кавычек и о смысле схемы адреса.

Контрпример — четвёртая строка таблицы из введения: `<a title={{ x }}>`
с включённым экранированием породил атрибут-обработчик, потому что
разметка оставила границу атрибута на усмотрение значения. Значение было
экранировано честно; вопрос был не к нему.

## 10. Чеклист ревью

1. Verify that DEBUG выключен в конфигурации прода, а страница ошибки не
   несёт деталей наружу (проверяется запросом на заведомо битый адрес).
2. Verify that ALLOWED_HOSTS перечисляет хосты, а не звёздочку.
3. Verify that изменяющие view не помечены `@csrf_exempt` без
   записанной
   причины (CWE-352, ASVS v5.0-3.5.1).
4. Verify that у Flask-приложения с cookie-аутентификацией есть слой
   CSRF-защиты из расширения или своей проверки токена
   (WSTG-v42-SESS-05).
5. Verify that mark_safe, Markup, |safe и autoescape off не применяются
   к данным, которые мог прислать пользователь (CWE-79).
6. Verify that render_template_string не получает шаблон со склейкой из
   ввода.
7. Verify that в шаблонах атрибуты с подстановками взяты в кавычки, а
   адреса в href не принимают произвольные схемы (`A05:2025`).

## 11. Задача

Возьмите свой учебный проект на Django или Flask. Найдите в нём
выключатели из раздела о коде поиском по именам. Для одного включённого
и одного выключенного экранирования прогоните значение с разметкой
через шаблон и запишите оба вывода.

Одна подсказка: у Flask тестовый клиент вызывается через
app.test_client() и не требует запуска сервера.

**Критерий выполнения** наблюдаемый: таблица «место — выключатель —
законно ли», и два вывода одного значения: экранированный и нет.

## 12. Проверь себя

1. Что отвечает мидлварь Django на POST без CSRF-токена и что меняет
   `csrf_exempt`?
2. Почему во Flask вопрос «где проверяется CSRF-токен» начинается с
   списка расширений?
3. Какие два места шаблона экранирование не закрывает по построению?
4. Что попадает в ответ при DEBUG=True в Django и во Flask с отладчиком?
5. Возврат к теме `csrf-mechanics`: почему API с токеном в заголовке
   не нуждается в CSRF-проверке?

<details markdown="1">
<summary>Ответы</summary>

1. 403 без токена; декоратор снимает проверку, и тот же POST проходит с
   кодом 200 — подделка становится возможной.
2. Потому что в ядре Flask такой проверки нет: ответ либо «установлено
   расширение», либо «проверка написана самим приложением», либо
   «защиты нет».
3. Атрибут без кавычек — значение порождает второй атрибут — и схема
   javascript: в href.
4. Django: код 500 и текст исключения с содержимым, значения настроек
   маскируются. Flask/Werkzeug: трейсбек и текст исключения, а при
   включённой консоли — интерактивное исполнение в кадре стека.
5. Потому что браузер не прикладывает заголовок сам. Атака опирается
   на автоматическую отправку cookie, а токен в заголовке требует
   значения, которого у чужой страницы нет.

</details>

## 13. Источники

1. Security in Django, документация Django (stable); реестр

   mark_safe, is_safe), CSRF protection и csrf_exempt, Host header
   validation, SSL/HTTPS.
   <https://docs.djangoproject.com/en/stable/topics/security/>
2. Security Considerations, документация Flask 3.1.x; реестр
   `flask-security-considerations`. Разделы: XSS (автоэкранирование
   Jinja, Markup, атрибуты без кавычек, схема javascript: и CSP),
   Cross-Site Request Forgery (почему защиты нет в ядре).
   <https://flask.palletsprojects.com/en/stable/web-security/>

Каркас этапа: у этапа 7 общих унаследованных источников нет; каждая тема
опирается на документацию своего языка и на материалы этапа 1 по
классам дефектов.

**Маркеры уверенности.** **Проверено лично** 2026-09-02: Django 6.1 —
шаблон `{{ x }}` экранирует, `|safe` и mark_safe пропускают разметку,
