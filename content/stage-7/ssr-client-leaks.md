# SSR-специфика: утечки на клиент

Уровень **L2** · время 30 мин (теория 18 / задача 8 / самопроверка 4,
оценка)

Что прочитать сначала: `information-disclosure`.

Страница профиля на Next.js: серверный компонент читает пользователя из
базы и передаёт объект целиком клиентскому компоненту «карточка», который
показывает одно имя. Прогоним рендер и посмотрим в данные, которые
уезжают клиенту, — в полезную нагрузку серверных компонентов React:

```text
0:["$","$3",null,{"user":{"id":1,"name":"alice",
"ssn":"123-45-6789","token":"sk-live-42"}},"$1","$2",1]
```

Карточка показывает имя, а в данных страницы — объект целиком, с токеном.
Заметим, чего здесь нет: в HTML ответа токена тоже нет — классический
рендер в строку пропсы не сериализует (проверено renderToString).
Утечка идёт по второму каналу, который появился вместе с серверными
компонентами: сериализованная нагрузка для согласования деревьев.

Это CWE-200 (каталог Common Weakness Enumeration) в специфике
серверного рендеринга: общий класс — раскрытие внутренних сведений —
разобран в теме `information-disclosure`. Дальше: где граница между
сервером и клиентом в Next.js, что через неё проходит и как её держать.

## 0. Коротко

В Next.js App Router страницы по умолчанию — серверные компоненты: они
читают базу и секреты окружения. Клиентский компонент объявляется
директивой `use client`, и всё, что он импортирует, попадает в
клиентский бандл. Данные между ними переходят сериализацией: пропсы,
которые серверный компонент отдал клиентскому, пишутся в RSC payload и
доступны клиенту целиком. Переменные окружения без префикса NEXT_PUBLIC_
в бандл не попадают — но это защита бандла, а не пропсов. Чинится
сужением передачи до нужных полей, пакетом server-only и пометкой taint
для объектов, которым нельзя на клиент. То же в терминах, которыми это
обсуждают.

**Зачем это в работе AppSec-инженера.** Утечка такого вида не видна ни в
разметке страницы, ни в бандле — она лежит в служебном ответе, который
забирает тот же запрос. Ревьюеру достаточно двух проверок: что уходит
пропсами через границу и что импортируется в модули с `use client`.

## 3. Механика

**Откуда это взялось.** Серверный рендеринг вернулся за данными близкими
к базе и за меньшим бандлом. Цена этой выгоды — новая граница: часть
дерева исполняется на сервере, часть в браузере, и между ними нужен
формат обмена. Наивное прочтение «серверный код не доезжает до клиента»
верно про код и неверно про данные: результат серверной части едет
клиенту по построению.

Документация Next.js фиксирует состав этого обмена: нагрузка серверных
компонентов содержит отрисованный результат, ссылки на файлы клиентских
компонентов и **все пропсы, переданные от серверного клиентскому**.
Пропсы обязаны быть сериализуемыми — то есть это данные, и клиент их
читает. Прогон из введения показывает это дословно: объект user с токеном
лежит в нагрузке открытым текстом.

Вторая дверь — бандл. Директива `use client` объявляет границу модуля:
файл и весь его граф импортов входят в клиентский бандл. Переменные
окружения при этом делятся по префиксу: в бандл включаются только
NEXT_PUBLIC_*, остальные заменяются пустой строкой. Поэтому секрет в
клиентском модуле «не работает». Но это не защита ни от пропсов, ни от
импорта серверного модуля с секретом внутри. Для последнего есть пакет
server-only, который роняет сборку при таком импорте.

Третий механизм — явная пометка. React (пока в экспериментальной ветке)
даёт `taintObjectReference`: объект, помеченный в коде доступа к данным,
нельзя передать клиентскому компоненту — при попытке бросается ошибка с
текстом автора. Прогон на experimental-сборке React подтверждает обе
половины: без пометки токен в нагрузке, с пометкой — ошибка вместо
объекта, и токена в нагрузке нет. Документация честно называет и границу
приёма: копия помеченного объекта пометку не несёт, так что это слой
против ошибки при рефакторинге, а не граница безопасности.

## 5. Как выглядит в коде

Первый признак — объект из базы уходит клиентскому компоненту целиком.
Не читая выноски, найдите строку, где токен пересекает границу:

```jsx
// УЯЗВИМО — демонстрация, не для продакшена
// Серверный компонент (без директивы в начале файла)
export default async function Profile({ userId }) {
  const user = await getUser(userId);     // в объекте и токен
  return <Card user={user} />;            // (1)
}
```

1. Пропс сериализуется в нагрузку целиком: клиент получает все поля,
   включая те, что карточка не показывает.

Пять строк, а граница в них пересечена целиком: всё, что ушло пропом,
клиент получает данными, и неважно, что из этого показывает разметка.
Ответьте, не перечитывая листинг: где окажется токен, если передать его
одним строковым пропсом `token={user.token}`?

Второй признак — граница, поставленная слишком рано. Какой из двух
импортов утащит секрет в бандл — решите до выносок:

```jsx
// УЯЗВИМО — демонстрация, не для продакшена
"use client";

import { reportEvent } from "./analytics";  // (1)
import { formatSecret } from "./server-utils"; // (2)
```

1. Всё дерево импортов этого файла — в клиентском бандле.
2. Серверная утилита с секретом внутри уедет в бандл, если её не защитить
   пакетом server-only.

Ложное срабатывание: серверный компонент, читающий секрет и отдающий
наружу только разметку, законен — секрет остался на сервере. Смотрите на
то, что пересекает границу, а не на то, что существует на сервере.

## 6. Как чинится

Правило одно: через границу проходит минимум — отобранные поля, а не
объект.

```jsx
// Исправлено
export default async function Profile({ userId }) {
  const user = await getUser(userId);
  return <Card name={user.name} avatar={user.avatar} />;
}
```

Дальше — слои. Код доступа к данным помечает объекты через
taintObjectReference, и поздний рефакторинг упадёт с ошибкой вместо
утечки. Серверные модули помечаются пакетом server-only, и импорт их из
клиентского графа ломает сборку. Префикс NEXT_PUBLIC_ читается как
явное согласие: значение публично.

**Когда канон не подходит.** Пометка taint живёт в экспериментальной
ветке React и в проде не применяется как опора — это сигнал на будущее
и защита от ошибки, а не гарантия. Если компоненту нужен объект целиком
(редактор профиля), ответ не в передаче всего, а в разделении: форма
получает редактируемые поля, идентификатор и токен остаются на сервере.

## 9. Ловушка

Сначала решите сами: секрет лежит в переменной окружения без префикса
NEXT_PUBLIC_ — может ли он уехать к клиенту? Встречается мнение, что
переменная без префикса NEXT_PUBLIC_ утечь не может, и секретам в
серверном коде ничего не грозит.

**Префикс защищает бандл, а не данные, переданные через границу.**
Механизм из раздела о механике: пропсы клиентскому компоненту пишутся в
нагрузку независимо от того, откуда взялось значение — из окружения,
из базы или из файла.

Контрпример — прогон из введения: токен не был ни в какой переменной
бандла. Он приехал пропом из базы и оказался в нагрузке страницы. А
нагрузку читает любой, кто читает ответ.

## 10. Чеклист ревью

1. Verify that клиентским компонентам передаются отобранные поля, а не
   объекты хранилища целиком (CWE-200).
2. Verify that каждая директива `use client` стоит на самом глубоком
   возможном компоненте, а не на корне страницы.
3. Verify that модули с секретами и доступом к базе помечены server-only
   или не импортируются из клиентского графа.
4. Verify that переменные с префиксом NEXT_PUBLIC_ содержат только
   публичные значения.
5. Verify that нагрузка страницы (ответ RSC) просмотрена на секреты
   инструментами браузера, а не только разметка.
6. Verify that объекты из слоя данных, которым нельзя на клиент,
   помечены taint там, где ветка React это позволяет.

## 11. Задача

Возьмите своё приложение на Next.js App Router (или учебный стенд).
Найдите все переходы пропсов через границу `use client` и выпишите поля
каждого объекта. Затем откройте страницу в браузере и просмотрите ответы
предзагрузки на предмет полей, которых нет в разметке.

Одна подсказка: нагрузка серверных компонентов видна в инструментах
разработчика как отдельный ответ навигации — ищите строки с полями
объектов.

**Критерий выполнения** наблюдаемый: таблица «компонент — поля пропса —
нужны ли все». Плюс один случай, где в нагрузке есть поле, которого нет
в разметке, — найденный или доказанно отсутствующий.

## 12. Проверь себя

1. Что входит в нагрузку серверных компонентов по документации Next.js?
2. Почему секрет в клиентском модуле «не работает» и почему это не
   защита от передачи пропом?
3. Что делает директива `use client` с графом импортов файла?
4. Что даёт taintObjectReference и в чём его заявленная граница?
5. Возврат к теме `information-disclosure`: почему утечку через нагрузку
   RSC не видно при просмотре разметки страницы?

<details markdown="1">
<summary>Ответы</summary>

1. Отрисованный результат серверных компонентов, ссылки на файлы
   клиентских и все пропсы, переданные от серверного клиентскому.
2. Потому что в бандл включаются только переменные с префиксом
   NEXT_PUBLIC_, остальные заменяются пустой строкой. Но значение,
   переданное пропом, сериализуется в нагрузку в обход этого правила.
3. Файл и всё, что он импортирует, входит в клиентский бандл; директиву
   на каждый компонент ставить не нужно.
4. Ошибку при передаче помеченного объекта клиентскому компоненту.
   Граница: копия объекта пометку не несёт, и это защита от ошибки, а не
   граница безопасности.
5. Разметка показывает отрисованный результат, а нагрузка — отдельный
   служебный ответ для согласования деревьев; его нужно смотреть
   отдельно.

</details>

## 13. Источники

1. Server and Client Components, документация Next.js; реестр
   `nextjs-server-client-components`. Разделы: как работают серверные и
   клиентские компоненты, состав RSC payload (пропсы сериализуются),
   `use client` и граф импортов, префикс NEXT_PUBLIC_, пакет server-only.
   <https://nextjs.org/docs/app/getting-started/server-and-client-components>
2. experimental_taintObjectReference, документация React; реестр
   `react-taint-api`. Разделы: назначение пометки, пример с объектом
   пользователя, оговорки о копиях и о статусе экспериментального API.
   <https://react.dev/reference/react/experimental_taintObjectReference>

Каркас этапа: у этапа 7 общих унаследованных источников нет; каждая тема
опирается на документацию своего языка и на материалы этапа 1 по
классам дефектов.

**Скоропортящийся слой.** API пометки taint экспериментален и живёт вне
стабильной ветки React; имена функций и поведение префикса NEXT_PUBLIC_
менялись раньше и проверяются при ревизии. Само правило «граница — это
сериализация» стареет медленнее.

**Маркеры уверенности.** **Проверено лично** 2026-09-02 на Node.js 26.8.1
и react-server-dom-webpack 0.0.0-experimental-21c89c9f-20260901 (сборка без
бандлера, руками собранная ссылка на клиентский модуль): объект user с
токеном целиком попадает в нагрузку RSC; после taintObjectReference
нагрузка несёт ошибку с текстом пометки, а токена в ней нет; классический
renderToString (react-dom 19.2.8) пропсы в HTML не сериализует. Состав
нагрузки, правило префикса и пакет server-only — **по документации**
Next.js; границы пометки — по документации React. Обе страницы открыты
лично 2026-09-02. Полная сборка Next.js-приложения не выполнялась:
показан механизм на уровне формата, а не фреймворка.
