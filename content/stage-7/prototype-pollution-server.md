# Prototype pollution в серверном коде

Уровень **L2** · время 30 мин (теория 18 / задача 8 / самопроверка 4,
оценка)

Что прочитать сначала: `prototype-pollution`.

Обработчик на Node.js принимает настройки в JSON и рекурсивно сливает их
в объект конфигурации. Прогоним его merge на теле
`{"__proto__": {"x": 42}}`:

```text
$ node pp2.js
hasOwn(config): false | у любого объекта: 42
```

Своего свойства `x` у config не появилось — hasOwn отвечает false. Но
свойство `x` появилось у **любого** объекта этого процесса: merge ушёл
по ключу `__proto__` в прототип и записал туда. Никакой ошибки при этом
не случилось: JSON разобрался, merge отработал, ответ ушёл клиенту.

Сам класс — загрязнение прототипа — разобран в теме `prototype-pollution`
на клиентской стороне. Здесь — серверный Node.js: где берётся чужой
объект, чем серверный гаджет отличается от клиентского и какие защиты
реально работают. Всё ниже проверено на Node.js 26.8.

## 0. Коротко

То же в терминах, которыми это обсуждают. Prototype pollution — это
CWE-1321 (каталог Common Weakness Enumeration). Рекурсивный merge или
Object.assign пишут ключ `__proto__` из чужого объекта не как данные, а
как доступ к прототипу. Свойство после этого наследуют все объекты
процесса. На
сервере последствия тяжелее, чем в браузере: гаджеты ведут в конфигурацию
шаблонов, почтовых отправлений и запуска процессов, вплоть до исполнения
кода. Чинится запретом ключей `__proto__`, `constructor`, `prototype` при
слиянии, объектами без прототипа (Object.create(null)), коллекцией Map
или флагом `--disable-proto=delete` (ASVS v5.0-15.3.6 требует проверки
входа с такими ключами).

**Зачем это в работе AppSec-инженера.** Признак читается по одной строке:
рекурсивный merge или Object.assign рядом с JSON.parse тела запроса.
Серверная находка дороже клиентской тем, что процесс один на всех
пользователей: загрязнение прототипа живёт до перезапуска и действует на
чужие запросы.

## 1. Цели

После этого раздела вы сможете:

1. Показать загрязнение прототипа через рекурсивный merge на прогоне.
2. Отличить унаследованное свойство от собственного через Object.hasOwn.
3. Назвать, из каких частей собирается эксплойт: источник, сток, гаджет.
4. Выбрать защиту: объект без прототипа, Map или флаг Node.js.

## 3. Механика

**Откуда это взялось.** В JavaScript у объектов нет фиксированной схемы,
и слияние настроек пишется руками: обойти ключи источника и присвоить их
приёмнику. Наивная реализация не различает обычный ключ и служебный
`__proto__`: присваивание `target["__proto__"] = ...` читается движком
как обращение к прототипу. Рекурсия делает шаг дальше: увидев объект под
ключом `__proto__`, merge пишет вложенные ключи уже в сам прототип.

Эксплойт собирается из трёх частей (так его раскладывает PortSwigger).
Источник — чужой ввод с контролем ключей: тело JSON, строка запроса,
web-сообщение. Важная деталь, проверенная прогоном: JSON.parse честно
сохраняет ключ `__proto__` как данные — `Object.hasOwn(body, "__proto__")`
возвращает true, тогда как у объектного литерала в коде такого свойства
нет. Сток — место, где свойство влияет на выполнение. Гаджет — свойство,
которое код читает «с потолка»: его нет у объекта, и оно приходит по
прототипу.

Классический серверный гаджет — конфигурация с умолчаниями:

```javascript
// УЯЗВИМО — демонстрация, не для продакшена
const url = config.transport_url || defaults.transport_url;
sendReport(url); // если transport_url пришёл по прототипу — чужой адрес
```

Свойства у config нет, значение подъехало из загрязнённого прототипа, и
отчёт ушёл на чужой сервер. В клиентской ветке темы гаджет вёл к
подмене src скрипта; на сервере тот же приём ведёт к конфигурации
почты, шаблонов и дочерних процессов.

## 5. Как выглядит в коде

Ревьюер ищет две сигнатуры рядом: чужой объект и слияние.

```javascript
// УЯЗВИМО — демонстрация, не для продакшена
function merge(target, source) {
  for (const key in source) {                    // (1)
    if (source[key] && typeof source[key] === "object") {
      target[key] = merge(target[key] || {}, source[key]);
    } else {
      target[key] = source[key];                 // (2)
    }
  }
  return target;
}

const cfg = merge(defaults, JSON.parse(req.body)); // (3)
```

1. Цикл по всем ключам источника, включая `__proto__`, `constructor` и
   `prototype`.
2. Присваивание без проверки ключа: на ключе `__proto__` пишет в
   прототип.
3. Вход прямо из тела запроса: источник и слияние встретились.

Обёртки, которые не спасают: проверка `typeof body === "object"` смотрит
на тип, а не на ключи; регулярное выражение по строке запроса ломается о
вложенность и кодировку. Ложное срабатывание: merge двух доверенных
объектов из конфигурации деплоя — источника нет, дефекта нет.

## 6. Как чинится

Правило одно: чужие ключи не попадают в слияние, а объект без прототипа
нечем загрязнить.

```javascript
// Исправлено
const BLOCKED = new Set(["__proto__", "constructor", "prototype"]);

function merge(target, source) {
  for (const key of Object.keys(source)) {
    if (BLOCKED.has(key)) continue;
    const value = source[key];
    if (value && typeof value === "object") {
      target[key] = merge(target[key] || {}, value);
    } else {
      target[key] = value;
    }
  }
  return target;
}
```

Памятка OWASP добавляет запасные уровни, и все три проверены прогоном.
Объект без прототипа: `Object.create(null)` принимает `__proto__` как
обычный ключ данных, записи в прототип не происходит. Коллекция Map вместо
объекта-словаря: у неё нет прототипа данных вовсе. Флаг запуска Node.js
`--disable-proto=delete` убирает свойство `__proto__` у Object.prototype:
тот же прогон merge под флагом даёт `({}).x === undefined` — загрязнения
нет. Флаг — защита в глубину, а не замена фильтрации: ключ
`constructor.prototype` он не закрывает.

**Когда канон не подходит.** Глубокое слияние нужной формы (только
разрешённые ключи из схемы) закрывается валидацией JSON Schema до merge —
так советует и документация Node.js. Object.freeze(Object.prototype)
ломает библиотеки, которые дописывают прототипы, и применяется редко.

## 9. Ловушка

Встречается мнение, что загрязнение через `__proto__` давно закрыто
самим движком.

**Движок закрыл литерал, а не разбор и не слияние.** Механизм из раздела
о механике: объектный литерал `{__proto__: {...}}` в коде — это смена
прототипа, а JSON.parse того же текста создаёт честный ключ. Проверено
прогоном: hasOwn у объекта из JSON.parse возвращает true. Дефект живёт в
слиянии, а не в движке.

Контрпример — прогон из введения: Node.js 26.8, актуальный движок,
рекурсивный merge на три строки, и свойство появилось у всех объектов
процесса.

## 10. Чеклист ревью

1. Verify that рекурсивные merge и Object.assign не получают объекты из
   запроса без фильтрации ключей (CWE-1321).
2. Verify that ключи `__proto__`, `constructor`, `prototype` отбрасываются
   при слиянии или при валидации входа (ASVS v5.0-15.3.6).
3. Verify that словари с чужими ключами — Map или Object.create(null).
4. Verify that свойства конфигурации читаются через Object.hasOwn там,
   где значение влияет на выполнение.
5. Verify that приёмJSON-тела сопровождается схемой, а не только проверкой
   типа.
6. Verify that процесс запускается с `--disable-proto=delete` как мерой
   в глубину, где это совместимо с зависимостями.

## 11. Задача

Напишите merge из раздела о коде, прогоните его на теле
`{"__proto__": {"x": 42}}` и убедитесь, что `({}).x` равен 42. Затем
примените любую защиту из раздела о починке и повторите прогон.

Одна подсказка: смотреть стоит не на целевой объект, а на свежесозданный
пустой — загрязнение видно именно по нему.

**Критерий выполнения** наблюдаемый: два вывода одного скрипта. До
защиты: `({}).x` даёт 42, а Object.hasOwn у цели — false. После защиты:
`({}).x` даёт undefined.

## 12. Проверь себя

1. Почему JSON.parse сохраняет ключ `__proto__`, а объектный литерал в
   коде — нет?
2. Из каких трёх частей собирается эксплойт prototype pollution?
3. Чем серверный гаджет отличается от клиентского по последствиям?
4. Что делает флаг `--disable-proto=delete` и почему это не замена
   фильтрации ключей?
5. Возврат к теме `prototype-pollution`: чем отличаются источники
   загрязнения в браузере и на сервере?

<details markdown="1">
<summary>Ответы</summary>

1. Литерал обрабатывает `__proto__` на уровне синтаксиса языка как смену
   прототипа. JSON.parse строит объект по правилам формата, и ключ
   становится обычными данными.
2. Источник (ввод с контролем ключей), сток (место, где свойство влияет
   на выполнение), гаджет (свойство, читаемое «с потолка» — по
   прототипу).
3. Процесс сервера один на всех пользователей, и загрязнение живёт до
   перезапуска; гаджеты ведут в конфигурацию почты, шаблонов и запуск
   процессов.
4. Он убирает доступ к прототипу через свойство `__proto__`. Ключ
   `constructor.prototype` продолжает работать, поэтому фильтрация ключей
   нужна всё равно.
5. В браузере источник — строка запроса и web-сообщения страницы; на
   сервере — тело запроса и любой чужой JSON, попадающий в слияние.

</details>
