# Обучающие материалы по безопасности: разбор конструкции

> Исследование от 2026-08-16. Все структурные утверждения проверены открытием реальных страниц и файлов
> (raw-выгрузки ASVS CSV, HackTricks SUMMARY.md, Secure Code Game уровней). Даты проверки — в разделе «Источники».

## Краткая сводка

Сильные обучающие ресурсы по AppSec отличает не объём, а **жёсткая типизация единицы контента**. У PortSwigger единица — «тема + набор лаб, привязанных к абзацам темы»; у OWASP Cheat Sheet — «правило с кодом»; у WSTG — «тест-кейс с устойчивым идентификатором»; у ASVS — «атомарное требование `Verify that ...` с уровнем»; у Secure Code Game — «каталог из пяти файлов: код, эксплойт, подсказка, решение, тесты». Как только единица определена и одинакова по всему корпусу, появляется навигация, чеклист, прогресс и возможность ревизии.

Второе, что отличает сильные ресурсы, — **паритет атаки и защиты внутри одной единицы контента**. WebGoat формулирует это прямо: объяснение → задание → mitigation. DVWA даёт четыре уровня одного и того же кода (low/medium/high/impossible) плюс кнопку View Source. Juice Shop добавил к 20+ челленджам фазы «Find It» и «Fix It». Secure Code Game делает критерием прохождения одновременное позеленение `hack.py` (эксплойт больше не работает) и `tests.py` (функциональность не сломана). Это ровно та петля, которой нет в пентест-ориентированных материалах и которая является ядром AppSec.

Третье — **честная разметка сложности и проверяемость**. PortSwigger размечает лабы тремя уровнями (Apprentice / Practitioner / Expert), формулирует цель как машинно-проверяемое условие («удали пользователя carlos», «прочитай `/home/carlos/secret`») и делает эту же формулировку основой экзамена BSCP. Геймификация (очки, стрики, бейджи) при этом почти не влияет на обучение; работает не она, а детерминированный критерий успеха и решение, доступное после попытки.

Главный антипример — HackTricks: 1008 узлов навигации глубиной до 5, страницы по 500+ строк без датировки, где на 45 заголовков приходится один блок «Mitigations», да и тот про частный парсер. Ресурс полезен как справочник практика, но обучать по нему нельзя: нет порядка, нет уровня, нет критерия «тема закрыта», нет защиты.

Отдельная особенность домена — **скорость гниения**. За 2025 год OWASP Top 10 переехал на редакцию 2025 (SSRF влит в A01, появились A03 Software Supply Chain Failures и A10 Mishandling of Exceptional Conditions), ASVS переехал с 4.0.3 на 5.0.0 с полной переномерацией требований. Любой гайдбук, где идентификаторы вкраплены в прозу без версии, устарел в момент публикации. WSTG решает это прямо: рекомендует ссылаться как `WSTG-v42-INPV-05`, а не на `stable`/`latest`.

## Разбор ресурсов

### PortSwigger Web Security Academy

**Как устроено (проверено).** Верхний уровень — четыре раздела: `Server-side topics` (13 тем), `Client-side topics` (6 тем), `Advanced topics` (10 тем), `Burp Suite Certified Practitioner`. У каждой темы в списке стоит счётчик лаб («SQL injection — 18 Labs», «Cross-site scripting — 30 Labs»). Отдельная сущность — Learning paths: курируемые последовательности тем поверх плоского каталога.

Страница темы (проверено на SSRF и SQL injection) строится так: `What is X?` → `Labs` (ранний блок-врезка со ссылкой «View all X labs») → `What is the impact` → перечисление конкретных техник как отдельных H2 → `How to prevent X` в конце. Внутри прозы лабы вкраплены контекстными врезками — прочитал абзац про конкретную технику, тут же ссылка на лабу именно про неё. Сверху — оглавление с якорями. Важная деталь: блок «How to prevent» есть не у всех тем. У SQL injection он развёрнутый и явно называет безопасный паттерн (параметризованные запросы) **вместе с границами его применимости** («нельзя использовать для имён таблиц, колонок и `ORDER BY`»). У SSRF отдельного «how to prevent» в теле обзорной страницы нет — тема целиком про эксплуатацию. Это неровность, а не задумка.

Страница лабы: заголовок `Lab: <название>`, бейдж уровня, одна-две строки описания сеттинга («This lab has a stock check feature which fetches data from an internal system.»), затем цель формулировкой «To solve the lab, ... and delete the user `carlos`». Ниже — раскрываемое `Solution` из пронумерованных шагов и блок `Community solutions` со ссылками на видеоразборы сообщества (Rana Khalil, z3nsh3ll, Michael Sommer). Статус solved/unsolved привязан к аккаунту.

| Что устроено | Что перенять | Что не повторять |
|---|---|---|
| Тема = проза + счётчик лаб + врезки на лабы по месту | Врезка на практику **в том абзаце**, который она закрепляет, а не единым списком в конце | Обзорную страницу без раздела «как чинить» (SSRF) |
| Три уровня лаб: Apprentice / Practitioner / Expert | Ровно три уровня, объявленных один раз и применяемых ко всему корпусу | Смешивать уровень темы и уровень задания — уровень принадлежит заданию |
| Цель лабы = машинно-проверяемое условие («удали carlos») | Каждое задание завершается однозначным артефактом-доказательством | Цели вида «изучите механизм» — они непроверяемы |
| Solution всегда доступно, спрятано под раскрытием | Решение доступно всегда, но за один клик — а не «купите подписку» | Прятать решение навсегда (убивает самодостаточность) |
| Community solutions — внешние видео | Ссылка на сторонний разбор как приятный бонус | Делать сторонние видео обязательным звеном |
| Learning paths поверх каталога | Два входа: линейный маршрут и справочный каталог одних и тех же страниц | Единственный линейный порядок без каталога |

### OWASP Cheat Sheet Series

**Как устроено (проверено).** 150+ шпаргалок, пять параллельных индексов: алфавитный, по ASVS, по MASVS, по Proactive Controls, по Top 10. Декларация: «concise collection of high value information on specific application security topics». Форма отдельной шпаргалки (XSS Prevention): вводный блок с явным адресатом («This cheat sheet helps developers prevent XSS vulnerabilities»), затем правила, сведённые в таблицы с колонками «тип данных / контекст / пример кода / механизм защиты», парные примеры «плохо → хорошо», секция про фреймворки (React, Angular, Lit, Polymer с конкретикой вроде `dangerouslySetInnerHTML`), в конце — Related Articles.

Слабое место, зафиксированное фактически: у Injection Prevention Cheat Sheet **нет даты последней ревизии на странице**, есть только лицензия и «Made with Material for MkDocs». Код только на Java, ссылок на ASVS/Top 10 внутри текста нет — маппинг вынесен в отдельные индексы и не виден из шпаргалки.

| Что устроено | Что перенять | Что не повторять |
|---|---|---|
| Один документ = одна оборонительная задача, адресат назван в первой строке | Начинать защитный блок с «для кого и от чего» | Разлив на 5 экранов там, где нужна одна таблица |
| Правила в табличной форме контекст→кодировка→пример | Табличная форма для «правил выбора безопасного паттерна» | Один язык примеров на весь документ |
| Множественные индексы к одному корпусу | Несколько срезов навигации по одному набору страниц | Маппинги, невидимые со страницы (только внешним индексом) |
| Раздел «фреймворк-специфика» | Явный подраздел «как это выглядит в вашем фреймворке» | Отсутствие даты ревизии — критично для гниющего домена |

### OWASP Web Security Testing Guide (WSTG)

**Как устроено (проверено).** Стабильная версия — 4.2 (03.12.2020), 5.0 в разработке; проект различает `stable/` и `latest/`. 12 категорий: INFO (Information Gathering), CONF, IDNT, ATHN, ATHZ, SESS, INPV (19 тестов), ERRH, CRYP, BUSL, CLNT, APIT. Идентификатор — `WSTG-<CATEGORY>-<NN>`, категория ровно 4 заглавные буквы, номер с ведущим нулём. Явная рекомендация проекта: **ссылаться версионно** — `WSTG-v42-INFO-02`, а не на `stable`/`latest`, «если версия опущена, ссылка считается указывающей на актуальный контент».

Структура тест-кейса (проверено на WSTG-INPV-05): `ID` → `Summary` → `Test Objectives` → `How to Test` → `Remediation` → `Tools` → `References`. Test Objectives — это одна-две строки глаголами действия: «Identify SQL injection points. Assess the severity of the injection and the level of access that can be achieved through it». `How to Test` — самая длинная секция, с реальными payload'ами, техниками детекта, фингерпринтингом СУБД, пятью техниками эксплуатации и обходами сигнатур.

| Что устроено | Что перенять | Что не повторять |
|---|---|---|
| Устойчивый ID `WSTG-<CAT>-<NN>` как первичный ключ | Ввести собственную схему ID (напр. `AG-INPV-05`) и печатать её в заголовке каждой страницы | Ссылаться на `stable`/`latest` — брать версионные ссылки |
| Фиксированный порядок секций у **всех** тест-кейсов | Один и тот же скелет по всему корпусу, без исключений | Раздувать `How to Test` до состояния, когда Remediation теряется в конце |
| `Test Objectives` как проверяемая формулировка задачи | Блок «цель проверки» в 1–2 глагольных предложения | Цели-описания вместо целей-действий |
| Разделение `Remediation` и `Tools` | Инструменты — отдельный блок, не вперемешку с методикой | Считать WSTG учебником: это **чеклист аудитора**, не учебная последовательность |

### OWASP ASVS

**Как устроено (проверено выгрузкой CSV 5.0.0).** Версия 5.0.0, май 2025 (предыдущие — 4.0 в 2019, 4.0.3 в 2021). Машиночитаемые артефакты: CSV, JSON, flat.JSON, CycloneDX, DOCX, PDF. Колонки CSV: `chapter_id, chapter_name, section_id, section_name, req_id, req_description, L`. **345 требований**, распределение по уровням: L1 — 70, L2 — 183, L3 — 92. 17 глав: V1 Encoding and Sanitization (30), V2 Validation and Business Logic (13), V3 Web Frontend Security (31), V4 API and Web Service (16), V5 File Handling (13), V6 Authentication (47), V7 Session Management (19), V8 Authorization (13), V9 Self-contained Tokens (7), V10 OAuth and OIDC (36), V11 Cryptography (24), V12 Secure Communication (12), V13 Configuration (21), V14 Data Protection (13), V15 Secure Coding and Architecture (21), V16 Security Logging and Error Handling (17), V17 WebRTC (12).

Формат требования: строго «Verify that ...», средняя длина 238 символов (min 44, max 620). Пример: `V1.2.2 — «Verify that when dynamically building URLs, untrusted data is encoded according to its context (e.g., URL encoding or base64url encoding for query or path parameters). Ensure that only safe URL protocols are permitted (e.g., disallow javascript: or data:).»` — уровень 1. Схема нумерации `<chapter>.<section>.<requirement>`, а для внешних ссылок README рекомендует `v<version>-<chapter>.<section>.<requirement>`.

| Что устроено | Что перенять | Что не повторять |
|---|---|---|
| Требование = атомарное проверяемое утверждение «Verify that…» | Формулировать критерии закрытия темы в том же залоге: проверяемое утверждение, а не «понимать X» | Смешивать в одном требовании две проверки |
| Три уровня как **охват**, а не как сложность | Разделять «минимум для всех» / «стандарт» / «повышенный» и помечать этим требования, а не темы | Считать L1/L2/L3 сложностью обучения — это профиль риска приложения |
| Машиночитаемая выгрузка (CSV/JSON) наравне с текстом | Держать чеклисты в структурированном виде, генерируя HTML из него | Ручное дублирование чеклиста в двух местах |
| Версионированные ID `v5.0-1.2.2` | Всегда печатать версию рядом с ID | Ссылаться на «ASVS 4.2.1» без года — переномерация в 5.0 сломала маппинги |

### OWASP Top 10

**Как устроено (проверено).** Актуальная редакция — 2025 (8-я, релиз-кандидат в ноябре 2025, финал в январе 2026). Список: A01 Broken Access Control, A02 Security Misconfiguration, A03 Software Supply Chain Failures, A04 Cryptographic Failures, A05 Injection, A06 Insecure Design, A07 Authentication Failures, A08 Software or Data Integrity Failures, A09 Security Logging & Alerting Failures, A10 Mishandling of Exceptional Conditions. SSRF (A10:2021) влит в A01. Две новые категории — A03 и A10.

Структура страницы риска (проверено на A03:2021 Injection): `Factors` (таблица: CWEs Mapped 33, Max Incidence Rate, Avg Incidence Rate, Avg Weighted Exploit, Avg Weighted Impact, Max Coverage, Avg Coverage; плюс Total Occurrences и Total CVEs) → `Overview` → `Description` → `How to Prevent` (маркированный список с оговорками) → `Example Attack Scenarios` (пронумерованные сценарии с кодом) → `References` → `List of Mapped CWEs`.

| Что устроено | Что перенять | Что не повторять |
|---|---|---|
| Жёсткий шаблон: Описание → Как предотвратить → Сценарии атаки → CWE | Взять эту четвёрку как костяк, добавив «как выглядит в коде» и «как ловится автоматикой» | Строить оглавление гайдбука по номерам A01…A10 — они меняются от редакции к редакции |
| Данные (incidence rate, CVE count) как обоснование приоритета | Показывать читателю, **почему** тема в списке | Выдавать Top 10 за учебную программу — это список рисков, не курс |
| Явный список замапленных CWE | Приводить CWE-идентификаторы как стабильный якорь вместо A0x | — |

### HackTricks (антипример)

**Что именно сломано (проверено выгрузкой `src/SUMMARY.md` и страницы SSRF).**

- **Навигация.** 1008 записей в оглавлении, 17 верхнеуровневых разделов, гистограмма глубины: 289 на уровне 0, 515 на уровне 1, 152 на уровне 2, 38 на уровне 3, 12 на уровне 4, 2 на уровне 5. Плоское дерево на тысячу листьев без маршрута, без уровня сложности, без «начни отсюда». Разделы озаглавлены эмодзи-префиксами, включая раздел `✍️ TODO`, вывешенный в публичном оглавлении.
- **Единица контента не определена.** Страница `pentesting-web/ssrf-server-side-request-forgery/README.md` — 545 строк, ~45 заголовков от `## Basic Information` до `## Tools`, где соседствуют базовое определение, экзотика (`SSRF via TLS AIA CA Issuers (Java mTLS)`, `Filename mini-languages as SSRF/file primitives (CFITSIO EFS)`), дампы команд и списки внешних сервисов. Ни уровня, ни порядка чтения, ни «прочитай сначала это».
- **Паритет отсутствует полностью.** Grep по странице: слова `prevent/defend/mitigate/remediate/fix` встречаются 4 раза, и единственный заголовок `### Mitigations` (строка 466) относится к узкому кейсу парсера CFITSIO. На 45 разделов эксплуатации — ноль разделов «как чинить» по существу темы.
- **Непроверяемость и датировка.** Дат на странице нет; понять, актуален ли обход, невозможно иначе как перепроверив вручную. Отдельно: перевод на 14 языков делается автоматически, то есть языковые версии в принципе не вычитаны.
- **Что улучшилось и стоит отметить честно.** Ссылочный аппарат подтянули: в конце страницы `## References` с пронумерованным списком (16 позиций), а в тексте стоят сноски вида `<sup>[[14]](#references)</sup>`. То есть претензия «без источников» уже устарела — сломана именно **конструкция обучения**, а не цитирование.

| Что устроено | Что перенять | Что не повторять |
|---|---|---|
| Максимальная широта покрытия, быстрый поиск по Ctrl+F | Иметь «справочный» режим чтения для того, кто уже знает, что ищет | Дерево на 1000 узлов без маршрута и уровней |
| Пронумерованные сноски на первоисточники | Сноски с номерами и списком в конце страницы | Страницы на 500+ строк без внутренней иерархии «база → продвинутое → экзотика» |
| — | — | Публиковать `TODO`-разделы в оглавлении |
| — | — | Автоперевод без вычитки (для русскоязычного гайдбука это прямая ловушка) |

### Hacker101, PentesterLab, TryHackMe, HTB Academy

**Hacker101** (HackerOne): четыре входа — Getting Started, Videos, CTF, Resources. Единица — видеоурок, практика вынесена в отдельный CTF, флаги из которого исторически конвертировались в приглашения на приватные программы HackerOne. Конструктивно слабое место: теория и практика живут в **разных** артефактах, связь между конкретным видео и конкретным уровнем CTF неявная.

**PentesterLab**: единица — упражнение с оценкой «Avg. Time» и метрикой «Solved by» (сколько человек решило), сложность Easy/Medium/Hard, разметка Free/PRO, группировка в Tracks с бейджами. Отдельный трек **Code Review** (Python, TypeScript, разбор патчей) — редкий пример, где обучают читать диффы, а не только атаковать.

**TryHackMe / HTB Academy**: модель «room / module → learning path → job-role path». Задание внутри модуля обычно проверяется вводом ответа в поле (флаг или значение), прогресс — стрики, очки, лидерборд, бейджи.

| Что устроено | Что перенять | Что не повторять |
|---|---|---|
| Learning path / job-role path поверх модулей | Один-два явных маршрута «с нуля до AppSec-инженера» поверх каталога | Много параллельных маршрутов — читатель зависнет на выборе |
| Оценка времени на упражнение и доля решивших | Указывать ожидаемое время и субъективную сложность у каждой лабы | Лидерборды и стрики — вне многопользовательской платформы это пустой фантик |
| Флаг как ответ в поле проверки | Флаг-строка, вычислимая читателем и сверяемая с хешем в тексте | Требовать сервер/аккаунт для проверки ответа |
| Отдельный трек code review (PentesterLab) | Обязательный трек «читаем чужой диф и находим баг» | Разводить теорию и практику по разным продуктам (болезнь Hacker101) |

**Что из геймификации реально работает:** (1) детерминированный критерий «решено/не решено»; (2) видимый прогресс по разделу — сколько закрыто из скольких; (3) градация сложности как ожидание, а не как награда. **Что фантик:** очки, стрики, лидерборды, бейджи, «уровни аккаунта». Первые три воспроизводимы на статическом сайте через localStorage; вторые требуют сервера и социума и не переносятся.

### Книжная форма (WAHH и родственники)

«The Web Application Hacker's Handbook» (2-е издание, 2011) остаётся структурным образцом, хотя фактура на треть протухла. Что делает книжная форма и чего не делают сайты:

- **Сквозной нарратив с накоплением.** Глава N опирается на главу N−1; читатель обязан пройти линейно. Сайт этого не гарантирует — отсюда необходимость явных блоков «пререквизиты».
- **Отдельная методологическая глава-чеклист** в конце («A Web Application Hacker's Methodology») — конденсат всей книги в виде последовательности шагов. Это то, что читатель распечатывает и держит рядом.
- **Врезки «Hack Steps» / «Tip» / «Note»** — типизированные блоки, визуально отличимые от прозы: пошаговая процедура, предупреждение, замечание.
- **Постоянная глубина главы.** Каждая глава — примерно один объём, одна структура; читатель после третьей главы знает, чего ждать.

**Переносимо:** методологическая глава-конденсат; типизированные врезки; постоянный размер и структура единицы; явные пререквизиты вместо неявного линейного порядка.
**Не переносимо:** отсутствие обновлений (книга не датируется поглавно); объём без якорей и поиска; примеры под давно ушедшие версии стеков.

### GitHub Security Lab: Secure Code Game и CodeQL zero to hero

Самый ценный найденный артефакт для самодостаточного гайдбука.

**Secure Code Game** (проверено чтением файлов уровня): каждый уровень — каталог из ровно пяти файлов:

- `code.py` — уязвимый код с комментарием-инструкцией в шапке;
- `hack.py` — unit-тесты, воспроизводящие эксплуатацию; **изначально падают**, цель ученика — сделать их зелёными;
- `tests.py` — функциональные unit-тесты; **изначально проходят**, задача — не сломать их починкой;
- `hint.js` — короткая подсказка (в Level-1 это шесть строк JS, демонстрирующих потерю точности `float`);
- `solution.py` — одно рабочее решение с оговоркой «There are several possible solutions».

Критерий прохождения сформулирован буквально: «You successfully completed the level when both `hack.py` and `tests.py` pass». Сезоны: S1 Foundations (Python, C, ~6 ч), S2 Multi-Stack (GitHub Actions, Go, Python, JS + CodeQL, ~6 ч), S3 LLM Security (~1.5 ч), S4 Agentic AI (~2 ч), по пять уровней каждый; сезоны самодостаточны и не требуют прохождения предыдущих. У каждого уровня есть Storyline — короткая легенда на 3–4 предложения. Доставка — GitHub Codespaces (< 3 минут), но структура **полностью работает офлайн**: это просто каталог с юнит-тестами.

**CodeQL zero to hero** — пятичастная серия статей с явно опубликованным оглавлением (1. Fundamentals of static analysis → 2. Getting started with CodeQL → 3. Security research with CodeQL → 4. Gradio framework case study → 5. Debugging queries). В части 1 — три структурированных упражнения на поиск sources/sinks в реальных open-source проектах и на разбор запатченных issue. Метка времени чтения (~20 минут) стоит в шапке.

| Что устроено | Что перенять | Что не повторять |
|---|---|---|
| Пятифайловая единица: code / hack / hint / solution / tests | **Взять один в один** как формат лаб по code review | — |
| Критерий = два зелёных набора тестов одновременно | Единственный найденный способ проверить «починено и не сломано» без сервера | — |
| Один hint, одно решение с оговоркой «решений несколько» | Ровно одна подсказка на уровень, решение с явной оговоркой | Лестница из пяти подсказок — размывает попытку |
| Storyline в 3–4 предложения | Микро-легенда для контекста — дёшево и заметно повышает вовлечённость | Развесистая ролевая обёртка |
| Сезоны независимы друг от друга | Возможность войти в середину корпуса | — |
| Серия статей с опубликованным оглавлением и упражнениями | Многочастные лонгриды с оглавлением всей серии в шапке каждой части | — |

### Документация Semgrep как обучающий материал

Semgrep разделил три артефакта: (1) справочная документация (Pattern Syntax → Rule Syntax → Contributing & Testing → Rule Ideas), (2) **интерактивный туториал** `semgrep.dev/learn` — пошаговый, на примерах, (3) **Editor/Playground** `semgrep.dev/editor` как среда написания и немедленной проверки правила. Прогрессия в доке идёт от мотивирующего примера (правило, ловящее сравнение строк через `is` в Python) к формальному синтаксису.

**Что перенять:** разделение «референс синтаксиса» и «туториал»; правило всегда показывается вместе с кодом, который оно ловит, и кодом, который оно не должно ловить (true positive + true negative в одном примере); тестируемость правила как часть обучения (у Semgrep для этого есть формат тест-файлов с аннотациями `ruleid:` / `ok:`).
**Чего не хватает и что не повторять:** playground требует сети — в самодостаточном гайдбуке эквивалентом должен быть локальный запуск `semgrep --config ./rules ./testcases` с закоммиченными фикстурами.

## Паритет атаки и защиты

**Почему это не опция.** Пентестер закрывает задачу артефактом «вот доказательство эксплуатации». AppSec-инженер закрывает задачу артефактом «вот исправленный код, вот подтверждение, что уязвимость ушла, вот правило, которое не даст ей вернуться». Материал, обучающий только первому, готовит не ту профессию. При этом почти весь бесплатный корпус (HackTricks, большинство CTF-платформ, WSTG в части `How to Test`) смещён в атаку, а почти весь защитный корпус (Cheat Sheets, ASVS) смещён в защиту и не показывает, как выглядит провал. Ценность гайдбука — в сшивке этих двух половин **внутри одной страницы**.

**Кто реализовал паритет и как:**

- **WebGoat** — трёхтактная модель урока, заявленная авторами прямо: «сначала объясняем уязвимость, вместо "just hacking"» → задание → «overview of possible mitigations which will help you during your development work». Плюс WebWolf как отдельное приложение-«сторона атакующего», что явно разводит роли.
- **DVWA** — четыре уровня безопасности (`low` / `medium` / `high` / `impossible`) для одной и той же функциональности плюс кнопка **View Source**. Уровень `impossible` — не задание, а образец: «how to secure code as you build». Читатель диффает `low` против `impossible` и видит правку целиком.
- **Juice Shop** — 20+ челленджей имеют фазы **«Find It»** (найти уязвимую строку в реальном исходнике) и **«Fix It»** (выбрать корректный вариант исправления из нескольких).
- **Secure Code Game** — самая строгая форма: паритет закодирован в критерии прохождения (`hack.py` зелёный + `tests.py` зелёный).
- **PortSwigger** — паритет частичный: блок «How to prevent» есть, но неравномерно (у SQL injection развёрнут, у SSRF на обзорной странице отсутствует), и он никогда не проверяется лабой.
- **WSTG** — формально паритет есть (секция `Remediation` в каждом тест-кейсе), но диспропорция чудовищная: `How to Test` на десятки экранов против абзаца ремедиации.

**Вывод:** канонический скелет раздела про уязвимость должен содержать пять обязательных звеньев, из которых три — защитные. Формулировка — в разделе «Канонический скелет».

Отдельно отмечу **kubernetes-goat**: единственный из списка, где половина сценариев — про защиту и аудит (запусти Falco и увидь свою же атаку в алертах). Это прямой прототип блока «как это ловится автоматикой».

### Что делает лабу воспроизводимой и детерминированной

1. **Фиксированное начальное состояние.** Один и тот же сид БД, одни и те же пользователи, одни и те же секреты при каждом старте. Если состояние накапливается между попытками — лаба сломана. Docker Compose с `docker compose down -v` в инструкции по сбросу решает это.
2. **Пиннинг версий.** Не `image: node:latest`, а тег с digest'ом. Не `pip install flask`, а lock-файл. Иначе через полгода лаба перестаёт воспроизводить уязвимость (или, хуже, начинает воспроизводить другую).
3. **Отсутствие сетевых зависимостей на этапе решения.** Никаких Burp Collaborator, `webhook.site`, публичных DNS-callback сервисов. Для out-of-band сценариев — свой контейнер-listener внутри compose (DNS + HTTP логгер).
4. **Единственный однозначный критерий успеха.** Три работающих формы: (а) флаг-строка, добываемая только через эксплуатацию, сверяемая с опубликованным SHA-256; (б) состояние системы, которое читатель может проверить сам («пользователь `carlos` удалён»); (в) набор тестов, меняющий цвет.
5. **Ограниченная поверхность.** Лаба должна допускать один-два пути решения, не двадцать. Иначе разбор решения не соответствует опыту читателя.
6. **Отдельный шаг «почини»** с собственным критерием — иначе половина навыка не тренируется.
7. **Оценка времени** в шапке лабы. PentesterLab даёт «Avg. Time», GitHub — «~6 hrs» на сезон; читателю нужно понимать, во что он ввязывается.

### Как сделать проверку решения без сервера

- **Хеш флага.** Флаг печатается уязвимым приложением; в тексте гайда — только `sha256`. Читатель сверяет сам. Дёшево, работает на статическом сайте.
- **Юнит-тесты в репозитории лабы** (модель Secure Code Game). Единственный способ проверить *исправление*, а не только эксплуатацию. Работает офлайн, даёт мгновенную обратную связь.
- **Скрипт-верификатор в комплекте лабы:** `./verify.sh` внутри compose-окружения, который сам ходит по эксплойту и печатает `PASS/FAIL`. Не требует внешнего сервиса.
- **Самопроверочный чеклист** в конце раздела (пункты в залоге ASVS «Verify that…») для тем, где лаба невозможна (процессы SSDLC, нормативка).
- **localStorage-трекер прогресса** на клиенте: чекбоксы «решено» по разделам, кнопка экспорта прогресса в JSON. Даёт видимый прогресс без бэкенда и без аккаунтов.

### Требования к упаковке

- Один `docker-compose.yml` на лабу, запуск ровно одной командой, порт задокументирован.
- Все образы с пиннингом и, где возможно, собираемые локально из `Dockerfile` в том же каталоге (страховка от исчезновения образа из реестра).
- Инструкция «Сброс» и «Удаление» в каждой лабе (модель Teardown из kubernetes-goat).
- Явное указание, что стенд слушает `127.0.0.1` и почему это принципиально (см. раздел про право).
- Архив-снапшот всех лаб для офлайн-работы; проверка, что после `docker compose up` при отключённой сети лаба поднимается и решается.
- Смоук-тест лаб в CI: раз в месяц поднять каждую лабу, прогнать `verify.sh`, отчитаться о падениях. Это единственная реальная защита от гниения практической части.

## Этика и правовая рамка публичного материала по наступательной безопасности

### Как это делают авторитетные ресурсы

- **DVWA** формулирует границу через свойство артефакта, а не через мораль: «Damn Vulnerable Web Application is damn vulnerable! **Do not upload it to your hosting provider's public html folder or any Internet facing servers**, as they will be compromised». И отдельно снимает ответственность: «We do not take responsibility for the way in which any one uses this application. We have made the purposes of the application clear and it should not be used maliciously».
- **PortSwigger** не вешает дисклеймер на учебные страницы — вместо этого он **устраняет саму возможность нарушения**: все цели атаки живут внутри их инфраструктуры, лабы одноразовые и изолированные, а legal-рамка вынесена в Terms of Service. Это структурное решение вместо текстового.
- **crAPI** сопровождает сборку явной настройкой `LISTEN_IP` и предупреждением о том, что дефолт — локальный; вывод стенда наружу требует сознательного действия.
- **Общая практика зрелых ресурсов:** payload'ы публикуются полностью (без них материал бесполезен), но **не публикуются**: рабочие эксплойты под конкретные непропатченные продукты с указанием версии и вендора; готовые к запуску сканеры/массовые эксплойты «под ключ»; данные реальных жертв; техники сокрытия следов и обхода средств защиты как самоцель. Граница проходит не по детальности payload'а, а по тому, **на что он наведён**: на учебный стенд или на чужую живую систему.

### Российская правовая рамка в объёме, влияющем на формулировки

- **Ст. 272 УК РФ** — неправомерный доступ к охраняемой законом компьютерной информации, если повлёк уничтожение, блокирование, модификацию либо копирование. Ключевое: состав возникает при доступе **к чужой** информации без разрешения. Работа со своим локальным стендом состава не образует.
- **Ст. 273 УК РФ** — создание, использование и распространение вредоносных компьютерных программ **либо иной компьютерной информации**, заведомо предназначенных для несанкционированного уничтожения, блокирования, модификации, копирования информации или **нейтрализации средств защиты**.
- **Ст. 274 УК РФ** — нарушение правил эксплуатации средств хранения/обработки/передачи информации.
- **Постановление Пленума ВС РФ № 37 от 15.12.2022** — базовый документ по практике применения ст. 272–274 и 274.1. Из значимого для автора обучающего материала: (а) под «иной компьютерной информацией» в ст. 273 понимаются любые сведения, не являющиеся программой в совокупности, но позволяющие обеспечить несанкционированные действия или нейтрализацию средств защиты — **в том числе ключи доступа**; (б) выполнение всех действий для неправомерного доступа при ненаступлении последствий по независящим обстоятельствам квалифицируется как покушение.

**Практические выводы для формулировок гайдбука:**

1. Ключевой признак в ст. 273 — **заведомая предназначенность для несанкционированных действий**. Учебный payload, наведённый на локальный стенд, и рабочий эксплойт под чужую систему различаются именно этим. Поэтому в гайдбуке любой payload обязан быть текстуально привязан к конкретной лабе, а не к «типичному приложению в интернете».
2. Не публиковать **ключи доступа, дампы учётных данных, реальные секреты** — Пленум прямо относит их к «иной компьютерной информации» по ст. 273.
3. Не выкладывать готовые массовые сканеры/эксплойт-паки. Инструменты общего назначения (Burp, sqlmap, Semgrep, nuclei) — легальный отраслевой стандарт, о них писать нормально; собственный «эксплойт под кнопку» под конкретный продукт — нет.
4. Дисклеймер сделать **функциональным, а не ритуальным**: не «автор не несёт ответственности», а «все стенды слушают 127.0.0.1; всё, что описано, применимо только к ним; сканирование и эксплуатация чужих систем без письменного разрешения владельца образует состав ст. 272 УК РФ».
5. Дать отдельную короткую страницу про **легальные площадки применения навыка**: bug bounty с публичным scope и safe harbour, собственные стенды, рабочие задачи по договору. Плюс базовая памятка по ответственному разглашению (не публиковать до фикса, не выходить за scope, не эксфильтровать данные, фиксировать переписку).
6. Дисклеймер разместить в трёх местах: на главной, в шапке раздела с лабами, и одной строкой в каждой лабе рядом с командой запуска. Не полагаться на то, что читатель заходит через главную.

## Проверка навыка

**Знание vs навык.** Проверка знания: «объясни, чем отличается stored XSS от reflected». Проверка навыка: «вот исходник, найди в нём XSS, почини, докажи, что почини́л, напиши правило, которое поймает регресс». Первое проверяется вопросом, второе — только артефактом. Все сильные программы проверяют артефактом.

**Как это устроено в образцах формата экзамена:**

- **BSCP (PortSwigger).** 4 часа, **два** приложения, у каждого — три обязательные стадии: (1) получить доступ к любому пользовательскому аккаунту; (2) от него добраться до админ-интерфейса, эскалацией привилегий или компрометацией администратора; (3) через админку прочитать `/home/carlos/secret` и сдать через «submit solution». Конструкция важна: экзамен проверяет не знание конкретной уязвимости, а способность **пройти цепочку в незнакомом приложении**. Отсюда же «Mystery lab challenge» — лабы без указания темы, специально готовящие к ситуации «неизвестно, что искать».
- **OSWE (OffSec WEB-300).** 48 часов проктореда в изолированном VPN: найти уязвимости в исходниках, написать **собственный эксплойт**, получить proof-файлы и сдать **отчёт**. Отсутствие корректной документации по объекту обнуляет баллы за него. То есть отчёт — часть экзамена, а не приложение к нему.

**Что из этого переносимо в гайдбук:**

1. **Критерий закрытия темы формулировать в залоге ASVS**: не «понимать SSRF», а «Verify that: обнаружил SSRF в лабе N без подсказки; нашёл уязвимую строку в исходнике; заменил на безопасный паттерн; `hack` и `tests` зелёные; написал Semgrep-правило, ловящее исходный паттерн и не ловящее исправленный».
2. **Капстоун на каждый этап**: незнакомое приложение, тема не названа, цепочка из нескольких шагов, критерий — конкретный артефакт. Прямая калька с формата BSCP.
3. **Отчёт как обязательный артефакт.** Калька с OSWE: у AppSec-инженера отчёт/тикет — основной продукт. Дать шаблон находки (title, severity + обоснование, PoC, затронутые компоненты, рекомендация, ссылка на CWE/ASVS) и требовать заполнять его по каждой лабе. Это же тренирует триаж — сильную сторону автора.
4. **CTF — вспомогательный, не основной инструмент.** Jeopardy-CTF натаскивает на трюки и на нестандартный вход, но искажает картину: в CTF всегда есть решение, всегда есть флаг, никогда не нужно чинить. Полезен как разминка на «нестандартность», вреден как основная модель проверки. Attack-Defense CTF ближе к AppSec (нужно и чинить, и держать сервис живым), но неподъёмен для одиночного читателя.
5. **Разделять self-check и капстоун.** Self-check в конце каждой темы (5–7 проверяемых утверждений, ~5 минут). Капстоун — в конце этапа (несколько часов).

## Устаревание материалов по безопасности

**Почему гниёт быстрее.** Три независимых источника распада: (1) меняется атака — обходы фильтров, техники, поведение браузеров; (2) меняется защита — дефолты фреймворков закрывают классы уязвимостей (autoescaping в шаблонизаторах, SameSite=Lax по умолчанию), и вчерашняя «уязвимость по умолчанию» становится «уязвимостью при явном отключении защиты»; (3) меняются классификаторы и инструменты — версии, флаги CLI, номера категорий.

**Наблюдаемые примеры за последний год:**
- OWASP Top 10 переехал на редакцию 2025: SSRF, бывший A10:2021, **влит в A01:2025 Broken Access Control**; появились A03 Software Supply Chain Failures и A10 Mishandling of Exceptional Conditions; Security Misconfiguration поднялся с #5 на #2. Любой текст, писавший «SSRF — это A10 OWASP Top 10», теперь неверен.
- ASVS перешёл с 4.0.3 (2021) на 5.0.0 (май 2025) с новой структурой глав (17 глав, 345 требований) — старые идентификаторы вида `V5.3.3` не переносятся механически.
- WSTG стабилен на 4.2 с декабря 2020, версия 5.0 в разработке — то есть у стабильной ветки уже больше пяти лет.

**Как справляются:**
- **WSTG** — версионирование в самом идентификаторе (`WSTG-v42-INPV-05`) плюс прямая инструкция «ссылаться версионно, не на `stable`/`latest`». Лучшая найденная практика.
- **ASVS** — семантическая версия в ссылке (`v5.0-1.2.2`), машиночитаемые выгрузки (CSV/JSON/CycloneDX), позволяющие автоматически диффать редакции.
- **OWASP Top 10** — годовой суффикс в каждом идентификаторе (`A03:2021`), редакция как отдельный сайт-срез, старые редакции остаются доступны.
- **PortSwigger** — не даты, а ведение раздела «новые лабы»/«новое в Академии» и постоянный ремонт лаб (лаба, переставшая решаться, чинится, потому что от неё зависит платный экзамен). Практика: **экономическая связка контента с экзаменом заставляет поддерживать актуальность**.
- **Cheat Sheet Series** — контрпример: даты последней ревизии на странице нет, есть только git-история репозитория. Читатель не может оценить свежесть, не выходя на GitHub. Не повторять.
- **HackTricks** — датировка отсутствует полностью, актуальность непроверяема.

**Практика для гайдбука:** дата последней ревизии и версия — в шапке каждой страницы, а не в подвале сайта; отдельно фиксировать версии стека, на котором проверялись примеры («проверено на Python 3.12 / Django 5.1 / Semgrep 1.9x»); маркировать «долгоживущее» (принцип) и «скоропортящееся» (флаги CLI, конкретные обходы) разными визуальными классами; вести CHANGELOG сайта; раз в квартал — прогон смоук-тестов лаб и сверка идентификаторов внешних стандартов.

## Дополнительные наблюдения

- **Русскоязычная терминология — отдельная инженерная задача.** Прямой перевод («подделка запросов на стороне сервера») никем не используется. Практика, которая работает: русский текст, английский термин в скобках при первом упоминании, дальше — английский термин латиницей. Обязателен единый глоссарий по всему корпусу, иначе один и тот же sink будет то «приёмником», то «стоком», то «синком». Автоперевод HackTricks на 14 языков — наглядное предупреждение о том, во что превращается непроверенный перевод в этом домене.
- **Диаграммы окупаются, скриншоты — нет.** PortSwigger использует SVG-схемы потока запроса (долгоживущие). Скриншоты интерфейсов инструментов протухают за один мажорный релиз и требуют пересъёмки. Правило: схема — да, скриншот — только там, где без него не объяснить (UI Burp), и в отдельном каталоге для быстрой пересъёмки.
- **Копируемые артефакты важнее прозы.** То, что читатель реально уносит: docker-compose файл, Semgrep-правило, шаблон отчёта о находке, чеклист ревью PR, конфиг CI-пайплайна. Каждая тема должна оставлять после себя хотя бы один такой артефакт.
- **Ссылки наружу и самодостаточность.** Самодостаточность не означает «никаких ссылок». Она означает: **навык приобретается без выхода**, ссылка идёт только на первоисточник (RFC, CVE, оригинальное исследование, документация инструмента) и всегда как сноска, а не как замена объяснению. Формат HackTricks с пронумерованными сносками `[1]…[16]` и списком в конце страницы — правильная механика при неправильном содержании.
- **Дублирование ролей: разработчик / ревьюер / автоматизатор.** Одна и та же уязвимость выглядит по-разному для того, кто её пишет, кто её ищет в чужом PR и кто настраивает сканер. Сильные материалы явно называют роль, для которой пишут (Cheat Sheets — «helps developers», WSTG — тестировщик, ASVS — верификатор). Гайдбук должен либо явно объявлять роль в каждом блоке, либо покрывать все три — но осознанно.

## Канонический скелет раздела про уязвимость

Один и тот же порядок блоков для **всех** ~250 тем. Пять содержательных блоков, из которых три — защитные.

```
─────────────────────────────────────────────────────────────
ШАПКА
  ID темы (напр. AG-INPV-05) · Уровень (База / Практик / Эксперт)
  Обновлено: 2026-08-16 · Проверено на: Python 3.12, Django 5.1, Semgrep 1.9x
  Пререквизиты: AG-HTTP-03, AG-INPV-01
  Время: ~90 мин (теория 30 / лаба 45 / self-check 15)
  Маппинг: CWE-89 · ASVS v5.0-1.2.x · WSTG-v42-INPV-05 · OWASP Top 10 A05:2025
─────────────────────────────────────────────────────────────

0. TL;DR — 3–5 строк. Что это, почему опасно, чем чинится. Читается за 20 секунд.

1. МЕХАНИКА
   Откуда берётся уязвимость: доверенная граница, источник данных, sink.
   Схема потока (SVG). Минимально достаточная теория, без истории вопроса.

2. КАК ЭКСПЛУАТИРУЕТСЯ
   Конкретный payload на конкретном стенде. Пошагово, с ожидаемым выводом.
   → врезка: [ЛАБА N] со ссылкой прямо здесь, а не в конце страницы.

3. КАК ВЫГЛЯДИТ В ИСХОДНОМ КОДЕ            ◄── ключевой блок, которого нет у пентест-ресурсов
   Уязвимый фрагмент на 2–4 языках плана (Python, Java/Go, JS/TS, PHP).
   Что именно ищет глазами ревьюер: сигнатуры функций, имена sink'ов,
   типичные обёртки, которые НЕ спасают. Ложные срабатывания глазами.

4. КАК ЧИНИТСЯ (безопасный паттерн)
   Правильный код рядом с уязвимым (диф, не пересказ).
   Границы применимости паттерна — обязательно.
   («параметризация не покрывает имена таблиц и ORDER BY»)
   Что делать, когда каноничный паттерн неприменим: запасной вариант + его цена.

5. КАК ПРОВЕРИТЬ, ЧТО ПОЧИНЕНО             ◄── второй ключевой блок
   Ретест: тот же payload → ожидаемый безопасный результат.
   Юнит-тест на регресс (модель hack/tests: эксплойт падает, функционал живёт).
   Негативные кейсы: что должно продолжать работать после фикса.

6. КАК ЭТО ЛОВИТСЯ АВТОМАТИКОЙ              ◄── третий ключевой блок
   SAST: готовое Semgrep/CodeQL-правило, ловящее блок 3 и не ловящее блок 4.
   DAST/SCA/секрет-сканеры — где применимо.
   Честно: что автоматика поймает, что пропустит, какой шум даст.
   Куда это ставится в пайплайне и на каком пороге ломает сборку.

7. ЧЕКЛИСТ РЕВЬЮ (5–8 пунктов в залоге «Verify that…»)
   То, что реально уносят в работу и вставляют в шаблон PR-ревью.

8. ЛАБА
   Легенда 3–4 предложения · Цель одной проверяемой фразой ·
   Запуск одной командой · Ровно одна подсказка ·
   Отдельная задача «почини» с собственным критерием · Решение под раскрытием ·
   Сброс стенда.

9. SELF-CHECK — 5–7 проверяемых утверждений. Тема закрыта, когда все верны.

10. ЧАСТЫЕ ЗАБЛУЖДЕНИЯ — 3–5 пунктов «так делать нельзя, хотя все делают».

11. ИСТОЧНИКИ — пронумерованные сноски на первоисточники.
```

**Назначение блоков.** 0 — вход для сканирующего чтения и для возврата. 1 — модель, без которой блок 3 не читается. 2 — мотивация и опыт «оно правда работает». **3–5–6 — то, ради чего гайдбук существует**: они превращают пентест-знание в AppSec-навык. 7 — переносимый артефакт. 8 — единственное место, где навык реально формируется. 9 — критерий закрытия. 10 — защита от типичного ошибочного обобщения. 11 — верифицируемость.

**Правила применения скелета.** Блоки 0–7 и 9 обязательны везде. Блок 8 обязателен там, где лаба физически возможна; для процессных и нормативных тем вместо неё — разбор реального кейса плюс расширенный self-check. Блок 6 для тем, где автоматики не существует (бизнес-логика, IDOR в общем виде), обязан содержать честное «автоматика здесь не работает, и вот почему» — это само по себе ценное знание.

## Прикладные решения для гайдбука

1. **Единый скелет страницы для всех ~250 тем**, без исключений. Отклонение допускается только удалением блока с явной пометкой, никогда — перестановкой.
2. **Три уровня сложности, объявленные один раз**: База / Практик / Эксперт (калька с Apprentice/Practitioner/Expert). Уровень принадлежит **заданию**, не теме.
3. **Собственная схема ID** вида `AG-<CAT>-<NN>`, категория 3–4 заглавные буквы, номер с ведущим нулём. ID печатается в шапке страницы и в URL. Схема заимствуется у WSTG.
4. **Внешние идентификаторы всегда с версией**: `ASVS v5.0-1.2.2`, `WSTG-v42-INPV-05`, `A05:2025`. Никогда — «по OWASP Top 10» без года.
5. **Не строить оглавление по номерам OWASP Top 10.** Строить по механике уязвимостей, а Top 10 держать отдельным маппинг-индексом (как это делает Cheat Sheet Series с пятью индексами).
6. **Обязательный блок «как выглядит в исходном коде»** на 2–4 языках плана. Это главный дифференциатор от русскоязычных пентест-материалов.
7. **Обязательный блок «как проверить, что починено»** с юнит-тестом на регресс.
8. **Обязательный блок «как ловится автоматикой»** с готовым Semgrep/CodeQL-правилом, ловящим уязвимый паттерн и не ловящим исправленный.
9. **Формат лаб по code review — прямая калька Secure Code Game**: каталог `code / hack / hint / solution / tests`. Критерий прохождения: `hack` и `tests` зелёные одновременно.
10. **Формат лаб по эксплуатации** — стенд в Docker Compose + `verify.sh`, печатающий `PASS/FAIL`, плюс флаг с опубликованным SHA-256 для самопроверки.
11. **Цель лабы — одной машинно-проверяемой фразой** («удали пользователя `carlos`», «прочитай `/flag`»). Никаких «изучите механизм».
12. **Ровно одна подсказка на лабу** и ровно одно решение с оговоркой «решений несколько». Не строить лестницу подсказок.
13. **Решение всегда доступно**, под раскрытием, без регистрации и оплаты. Самодостаточность несовместима с гейтингом.
14. **Все лабы слушают `127.0.0.1`**, все образы пиннятся по тегу и digest'у, все зависимости — через lock-файлы. У каждой лабы — секции «Запуск», «Сброс», «Удаление».
15. **Никаких внешних сервисов в решении лабы.** Для out-of-band сценариев — собственный listener-контейнер (DNS + HTTP-логгер) внутри compose.
16. **Проверка офлайн-работоспособности** — обязательный приёмочный тест каждой лабы: поднять при отключённой сети и решить.
17. **Ежемесячный CI-прогон всех лаб** (поднять, прогнать `verify.sh`, снести). Практическая часть гниёт быстрее текстовой.
18. **Дата ревизии и версии стека — в шапке каждой страницы**, не в подвале сайта. Прямая правка ошибки Cheat Sheet Series.
19. **Визуально разделять «принципы» и «скоропортящееся»** (флаги CLI, конкретные обходы, версии) — разными классами блоков, чтобы при ревизии сразу видеть, что перечитывать.
20. **Функциональный дисклеймер**, не ритуальный: стенды на localhost, применимость только к ним, прямая ссылка на ст. 272 УК РФ. Размещается на главной, в шапке раздела лаб и строкой в каждой лабе.
21. **Не публиковать** ключи доступа, дампы учётных данных, реальные секреты, готовые массовые сканеры и эксплойты под конкретные непропатченные продукты — п. про «иную компьютерную информацию» ст. 273 (Пленум ВС РФ № 37).
22. **Отдельная страница «где законно применять навык»**: bug bounty с публичным scope и safe harbour, свои стенды, работа по договору; плюс памятка по ответственному разглашению.
23. **Шаблон отчёта о находке** (title / severity с обоснованием / PoC / затронутые компоненты / рекомендация / CWE + ASVS) и требование заполнять его по каждой лабе — калька с OSWE, где отчёт есть часть экзамена.
24. **Капстоун на каждый из 9 этапов**: незнакомое приложение, тема не названа, цепочка шагов, конкретный артефакт на выходе. Калька с трёхстадийной конструкции BSCP.
25. **Self-check в конце каждой темы** — 5–7 утверждений в залоге ASVS «Verify that…». Это и есть определение «тема закрыта».
26. **Два входа в один корпус**: линейный маршрут (9 этапов) и справочный каталог с фильтрами по категории/уровню/языку. Модель PortSwigger (learning paths поверх all-topics).
27. **Прогресс на клиенте**: чекбоксы «решено» в localStorage, счётчик «закрыто N из M» на каждом разделе, экспорт прогресса в JSON. Из геймификации брать только это; очки, стрики и лидерборды не воспроизводимы и не нужны.
28. **Врезка на лабу — в том абзаце**, который она закрепляет, а не единым списком в конце страницы.
29. **Единый глоссарий терминов** с фиксированным русским написанием и английским оригиналом; при первом упоминании в теме — «SSRF (Server-Side Request Forgery)», далее латиницей.
30. **Каждая тема оставляет минимум один копируемый артефакт** — правило, compose-файл, чеклист, шаблон, конфиг пайплайна.
31. **Схемы вместо скриншотов** везде, где возможно; скриншоты держать в отдельном каталоге с пометкой версии инструмента.
32. **Оценка времени в шапке темы** с разбивкой теория / лаба / self-check.
33. **Пререквизиты как явный список ID** в шапке — компенсация того, что сайт не гарантирует линейного чтения (проблема, которую книга решает нарративом).
34. **Методологическая страница-конденсат** на каждый этап: сквозной чеклист «как я захожу в незнакомое приложение / незнакомый репозиторий» — калька с методологической главы WAHH.

## Открытые вопросы и развилки

**1. Лабы: свои стенды или обёртка вокруг готовых (Juice Shop, WebGoat, DVWA)?**
*Рекомендация:* гибрид с перевесом в свои. Собственные микро-стенды (один контейнер, одна уязвимость, `verify.sh`) для 60–70% тем — они детерминированы, минимальны и полностью под контролем. Готовые полигоны — для капстоунов и для тем, где своё воспроизведение неоправданно дорого (Juice Shop как капстоун по вебу, crAPI по API, kubernetes-goat по инфраструктуре). Готовые стенды пиннить по версии и описывать как внешнюю зависимость с датой проверки.

**2. Проверка решения: хеш флага, `verify.sh` или юнит-тесты?**
*Рекомендация:* по типу лабы. Code review → юнит-тесты (модель Secure Code Game), это единственный способ проверить *исправление*. Эксплуатация → флаг + SHA-256 в тексте, плюс `verify.sh` как опция. Конфигурационные темы (CI, инфра) → `verify.sh`, проверяющий состояние. Не делать один универсальный механизм — он будет плох везде.

**3. Языки для блока «как выглядит в коде»: сколько и какие?**
*Рекомендация:* два обязательных (Python как родной для автора и JS/TS как неизбежный в вебе) и один-два опциональных под темой (Java/Go для бэкенда, PHP там, где это исторически значимо). Больше четырёх — не выдержать при ревизиях. Опциональные языки держать в раскрывающихся блоках, чтобы отсутствие не бросалось в глаза.

**4. Публиковать ли рабочие эксплойты для актуальных CVE как иллюстрации?**
*Рекомендация:* нет. Разбирать **запатченные** CVE по опубликованным патчам (модель CodeQL zero to hero, часть 4: кейс-стади фреймворка), где эксплойт уже публичен и фикс выпущен. Это даёт весь обучающий эффект без правового и этического риска.

**5. Глубина нормативного блока РФ (152-ФЗ, приказы ФСТЭК, ГОСТ по РБПО).**
*Рекомендация:* не пересказывать документы. Дать переводную таблицу «требование норматива → что это значит для процесса разработки → какой артефакт закрывает». Нормативка — самый быстро гниющий и самый скучный раздел; ценность в маппинге на инженерные действия, а не в цитировании.

**6. Прогресс и локальное состояние: localStorage или ничего?**
*Рекомендация:* localStorage + экспорт/импорт JSON. Даёт видимый прогресс без бэкенда, аккаунтов и приватностных вопросов. Явно предупредить, что прогресс привязан к браузеру.

**7. Английские термины в русском тексте: транслитерировать или оставлять латиницей?**
*Рекомендация:* латиницей, кроме устоявшегося («уязвимость», «эксплуатация», «полезная нагрузка» — только если по всему корпусу единообразно). Транслитерации вида «санитайзинг» допустимы, если внесены в глоссарий и используются везде одинаково.

**8. Ревизионный цикл при одном авторе.**
*Рекомендация:* три контура разной стоимости. Автоматический ежемесячный: CI-прогон лаб + линк-чекер. Полуавтоматический ежеквартальный: сверка версий инструментов и идентификаторов стандартов по машиночитаемым выгрузкам (ASVS CSV/JSON диффится скриптом). Ручной годовой: перечитывание «скоропортящихся» блоков. Пометка «требует проверки» на странице, не ревизованной дольше 12 месяцев, — честнее, чем молчание.

**9. Стоит ли делать капстоуны привязанными к готовому полигону или своим?**
*Рекомендация:* к готовым (Juice Shop / crAPI / kubernetes-goat). Капстоун ценен именно незнакомостью и объёмом, которые дорого воспроизводить самому; плюс это точка выхода читателя в живую экосистему.

**10. Разделять ли треки «разработчик» и «инженер AppSec»?**
*Рекомендация:* не разделять корпус, но помечать блоки ролью. Один и тот же блок 4 («как чинится») — основной для разработчика и вторичный для аудитора; блок 2 — наоборот. Ролевые метки дешевле, чем два параллельных корпуса, и позволяют позже собрать альтернативный маршрут из тех же страниц.
