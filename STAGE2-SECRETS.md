# Подраздел 2.3 Поиск секретов: четыре темы на скелете инструмента

Отчёт миссии `appsec-stage2-secrets`. Что написано, чем это проверено, что
показали прогоны, что найдено попутно и что осталось долгом.

Это третья волна скелета «тема-инструмент». Четыре темы подраздела 2.3 —
следующие четыре живые страницы после девяти тем SAST и восьми тем SCA.

---

## 1. Итог одной страницей

Четыре темы подраздела 2.3 написаны и лежат в `content/stage-2/`. Оба сканера
запускались локально и бесплатно; все секреты в примерах выдуманы и заведомо
недействительны.

```text
темы          4 из 4: L1 0, L2 4, L3 0 — как и задано оглавлением
корпус        111 тем -> 115 тем; лаб 24 (без изменений)
источников    347 (без изменений: все шесть записей подраздела были заведены)
make check    0 ошибок, 0 предупреждений, 5 снято прежними исключениями
lint-selftest 202 из 202
make links    0 ошибок, 0 предупреждений, 3 снято (с сетью)
make site     121 страница, 17889 внутренних ссылок
инструменты   gitleaks 8.30.1, trufflehog 3.97.1, pre-commit 4.6.2, git 2.55.0
```

Объём каждой темы — в норме своего уровня (L2: 800–1700 слов счётного текста).

| тема | ур. | режим | скелет | слов |
|---|:-:|---|---|---:|
| `secret-scanners` | L2 | рецепт | инструмент | 1532 |
| `secret-history-scan` | L2 | рецепт | инструмент | 1247 |
| `secret-rotation` | L2 | рецепт | инструмент | 1295 |
| `pre-commit-hooks` | L2 | рецепт | инструмент | 1341 |

Ни одна тема этапов 0 и 1 не правилась. В изменениях — только четыре новых файла
тем: `git status` не показывает ничего больше.

## 2. Что запускалось

Оба инструмента бесплатны и поставлены двоичными файлами из релизов проектов.
Ни одной лицензии, ни одного облачного аккаунта, `sudo` не использовался.

| инструмент | версия | как поставлен | объект |
|---|---|---|---|
| gitleaks | 8.30.1 | двоичный файл из релиза проекта | стенд, история, форк, хуки |
| trufflehog | 3.97.1 | двоичный файл из релиза проекта | тот же стенд |
| pre-commit | 4.6.2 | `pip` в окружение миссии | клиентский хук |
| git | 2.55.0 | системный | стенды, правка истории, серверный хук |

Стенды, все собранные для этой миссии:

* `exp/shop` — репозиторий из семи коммитов с выдуманными ключами: ключ доступа
  AWS и его секретная часть, приватный ключ RSA, токен Slack, ключ Stripe в
  тестовой фикстуре, внутренний пароль в `settings.ini`, ключ-пример из
  документации AWS в README. В четвёртом коммите ключи «убраны» — только из
  рабочего дерева.
* `exp/shop-fork` — клон, снятый до всякой уборки.
* `exp/oops` — минимальный репозиторий для отката `git reset --hard`.
* `exp/hooks` — репозиторий с клиентским хуком через pre-commit.
* `exp/server.git` — принимающий репозиторий `git init --bare` с хуком
  `pre-receive`.
* `exp/shallow` — клон `--depth 1` того же форка.

**Про материал примеров.** Все значения сгенерированы для стенда и
недействительны. Настоящие ключи оператора не читались, не искались и не
использовались: ни файлы `~/.supermanager`, ни хранилище agentrouter, ни что-либо
вне каталога гайдбука. Это граница миссии, и она соблюдена.

## 3. Что показали прогоны

### Рабочее дерево против истории

Один репозиторий, два объекта проверки:

```text
gitleaks dir ./shop      ~1315 байт    2 находки
gitleaks git ./shop      7 коммитов    5 находок
```

Три находки видны только в истории: приватный ключ RSA (коммит `706cd2e`), ключ
доступа AWS и его секретная часть (оба в `3792914`, 12 января).

### Поверхностный клон: зелёный отчёт ни о чём

```text
полный клон          7 коммитов  ->  5 находок
клон --depth 1       1 коммит    ->  2 находки
```

Сборочные системы клонируют так по умолчанию. Проверка «по истории» при этом
стоит, зелёная и не проверяет ничего сверх рабочего дерева.

### Два инструмента, два разных списка

```text
                        gitleaks   trufflehog
приватный ключ RSA          да         нет
ключ доступа AWS            да         да
секретная часть AWS         да      (в паре)
токен Slack                 да         да
ключ Stripe в тесте         да         да      ложное срабатывание
пароль в settings.ini       нет        нет     пропуск обоих
ключ-пример в README        нет        нет     законный отказ
итого по истории             5          3
```

gitleaks выдал две независимые находки на пару ключей AWS
(`aws-access-token` и `generic-api-key`); trufflehog — одну, собрав пару в
`RawV2`, и вытащил из идентификатора номер учётной записи, никуда не обращаясь.
Приватного ключа RSA у trufflehog нет: у него нет универсального детектора
«высокая энтропия».

### Коды возврата: замерено, а не пересказано

```text
gitleaks, чисто           0
gitleaks, есть находки    1
gitleaks --exit-code 7    7
trufflehog без --fail     0     <- находки есть, сборка зелёная
trufflehog --fail         183
trufflehog --fail, чисто  0
```

### Ротация против переписывания истории

Сердце подраздела, воспроизведено целиком:

```text
до правки истории                       7 коммитов сканировано   5 находок
после git filter-branch                13 коммитов сканировано   8 находок
  причина: refs/original/refs/heads/main — старая цепочка жива
после снятия refs/original,
  reflog expire --expire=now --all,
  git gc --prune=now                    7 коммитов сканировано   3 находки
  git cat-file -t 3792914…  ->  could not get object info
форк, снятый до уборки                  7 коммитов сканировано   5 находок
  git show 3792914:config/deploy.py  ->  ключ печатается целиком
```

Переписывание истории **увеличило** число находок: инструмент правки оставил
резервную ссылку, и в репозитории стало две истории вместо одной. Уборка
удалась только на четвёртой команде — и ровно ничего не изменила в форке.

Отдельно проверен самый частый способ «убрать» секрет:

```text
git reset --hard HEAD~1
  git log      -> коммита нет
  ls           -> файла нет
  git fsck --lost-found -> dangling commit 9da649d…
  git cat-file -p 9da649d…:secret.py -> TOKEN = "AKIA5TQR7WXZ3KLM6NDF"
```

Объект жив, и `git fsck` находит его сам — знать хеш заранее не нужно.

### Хуки: где проверка живёт

```text
git commit                        -> хук Failed, код 1, коммита нет
git commit --no-verify            -> коммит создан, код 0, следа нет
SKIP=gitleaks git commit          -> хук Skipped, коммит создан, код 0
git push origin main              -> remote rejected (pre-receive hook declined)
git push --no-verify origin main  -> remote rejected — флаг адресован не серверу
git push (без секрета)            -> [new branch] main -> main
```

Клиентский хук обходится двумя документированными способами, и ни один не
оставляет следа в репозитории. Серверная проверка на те же флаги не реагирует:
они до неё не долетают.

## 4. Две причины пропуска, разобранные по исходной конфигурации

Первая версия стенда использовала ключ `AKIAIOSFODNN7EXAMPLE` из документации
AWS — и gitleaks его не нашёл. Причина найдена не догадкой, а чтением встроенной
конфигурации версии 8.30.1, и подтверждена тремя пробами:

```toml
regex = '''\b((?:A3T[A-Z0-9]|AKIA|ASIA|ABIA|ACCA)[A-Z2-7]{16})\b'''
entropy = 3
[[rules.allowlists]]
regexes = ['''.+EXAMPLE$''']
```

```text
AKIAIOSFODNN7EXAMPLE   не найден  — список исключений .+EXAMPLE$
AKIA2E0A8F3B244C9986   не найден  — [A-Z2-7] это base32: цифр 0,1,8,9 не бывает
AKIA5TQR7WXZ3KLM6NDF   найден
```

Второй случай — ошибка автора стенда, а не инструмента: выдуманный ключ был
неправильной формы. Оба вывода вошли в тему как «законный отказ» и как
предупреждение: **выдуманный секрет неправильной формы не найдёт никто, и это
не проверка сканера, а проверка стенда**. Первая версия стенда была
пересобрана, ключ-пример перенесён в README как иллюстрация формы.

## 5. Реестры и словари

**Ничего не добавлялось.** Все шесть источников подраздела были заведены
заранее и подошли без правок: `gitleaks`, `trufflehog`, `gh-secret-scanning`,
`gh-remove-sensitive-data`, `pre-commit`, `gh-push-protection`. Категория
`SECRETS` и теги `secrets`, `tooling` заведены прежними миссиями. Лаб на уровне
L2 скелет не требует, и ни одна из четырёх тем лабу не заводила.

Все шесть источников открыты и прочитаны лично 2026-08-25. Одна запись реестра
подтвердилась ровно в том, о чём предупреждала: в README gitleaks стоит пометка
feature complete — новых возможностей не будет, только исправления
безопасности. Это сказано в теме прямо.

## 6. Решения, принятые этой миссией

Все — в рамках досье, ни одно не требовало оператора.

1. **Все четыре темы — скелет `инструмент`.** Три ложатся на него без натяжки.
   Четвёртая, `secret-rotation`, — тема-процесс, и это первая проверка опасения
   Н-01 отчёта скелета на живом тексте; разбор — в находке Н-03 ниже.
2. **`fixes_in` по факту.** У `secret-scanners`, `secret-history-scan` и
   `pre-commit-hooks` связь ведёт в `secrets-in-code` (класс дефекта) и
   в `secret-rotation` (порядок реакции). У самой `secret-rotation` — только в
   `secrets-in-code`: она и есть тема про починку. Пустых связей нет: `cwe`
   заполнен у всех четырёх.
3. **Границу 2.3.01 / 2.3.03 из оглавления соблюдена дословно.** Блок «Как
   чинится» у `secret-scanners` не пишется; тема кончается там, где сканер что-то
   нашёл, и передаёт дальше явной ссылкой в тексте, а не только полем.
4. **Проверка ключей у поставщика выполнена один раз и описана как решение, а не
   как деталь запуска.** Прогон trufflehog обращается к чужим API; на стенде это
   безопасно (ключи выдуманы, все вернулись `unverified`), но в тему вынесено
   отдельным предупреждением: гнать проверку по чужим репозиториям — значит
   предъявлять чужие ключи их поставщикам.
5. **Серверная проверка показана своим хуком, а не платформой.** Поднимать
   платный тарифный план хостинга миссии нельзя и не нужно: механизм
   `pre-receive` даёт тот же наблюдаемый результат локально. Что именно
   добавляет платформенная защита — охват веб-интерфейса и API, запись обхода в
   журнал аудита — описано по документации и помечено как непроверенное лично.
6. **`asvs` и `wstg` пусты, `owasp` заполнен** — наследуется решение подраздела
   SAST. Значения `A04:2025` и `A07:2025` взяты у темы `secrets-in-code` этапа 1,
   где тот же класс разобран.
7. **Продукты в прозе названы `Gitleaks` и `TruffleHog`** — так они названы в
   реестре источников и в собственных README проектов; нижний регистр оставлен
   команде и коду. Причина не только косметическая — см. Н-01.

## 7. Находки

**Н-01. Разрезатель предложений не видит границы перед словом в нижнем
регистре — и это первый подраздел, где это заметно.** `tools/mdtext.py` режет
текст на предложения только перед прописной буквой или цифрой; так и написано в
его же документирующей строке, и правило `S-SENT-LONG` поэтому живёт на уровне
warning. До сих пор это не мешало: предметы тем назывались Trivy, Syft, CodeQL,
Semgrep. Здесь предмет двух тем пишется в нижнем регистре, и правило склеивало
соседние предложения в одно на 60 слов. Обход найден без правки обвязки:
в прозе продукт называется `Gitleaks` и `TruffleHog` (как в реестре источников и
в README проектов), команда остаётся в нижнем регистре. Заголовок темы взят из
замороженного оглавления и не менялся, поэтому на странице заголовок в нижнем
регистре соседствует с прозой в верхнем. Это осознанный след двух правил, а не
небрежность.

**Н-02. Число находок после переписывания истории выросло, а не упало.**
`git filter-branch` оставляет `refs/original`, и сканер честно находит обе
цепочки: 8 находок против 5 до правки. Это не особенность стенда, а умолчание
инструмента, и оно означает, что репозиторий, где историю «почистили» одной
командой, находится в худшем состоянии, чем до чистки. Документация GitHub
рекомендует `git-filter-repo`, которого в системе нет; перенос вывода на него
помечен в теме как оценочный.

**Н-03. Скелет `инструмент` на теме-процессе натянулся, но со швом.**
`secret-rotation` — порядок действий, а не инструмент. Блоки легли так: «Что
умеет и чего не умеет» пришлось читать расширительно и разложить на две пары
(что умеет ротация / чего не умеет она, что умеет правка истории / чего не умеет
она), «Как запустить» стало нумерованным порядком из шести шагов, «Как читать
вывод» — разбором трёх состояний репозитория после трёх способов уборки.
Читается связно, но блок «Как запустить» на теме, где ничего не запускается,
держится на расширительном чтении. Это подтверждение опасения Н-01 отчёта
скелета в более мягкой форме, чем ожидалось: скелет выдержал, натяжение видно
только автору. Для тем 2.5 (`severity-assessment`, `sla-and-backlog`), где
процесса ещё больше, вопрос остаётся открытым.

**Н-04. Норма объёма L2 для темы-инструмента подтвердилась третий раз.** Все
четыре темы уложились в 1247–1532 слова при вилке 800–1700, и это при том, что
листинги в счётный текст не идут, а темы подраздела живут прогонами. Находка
Н-06 отчёта SCA («достижимо, но тесно») на L2 не воспроизводится: тесно было на
L1. Оснований менять норму нет.

**Н-05. Отпечаток находки gitleaks включает SHA коммита.** Отсюда следствие,
которое в документации прямо не сказано: подавление через `.gitleaksignore` не
переживает переписывание истории — SHA меняется, отпечаток перестаёт совпадать,
подавленная находка возвращается. Проверено косвенно (структура отпечатка
прочитана в выводе, смена SHA при правке истории наблюдалась), прямого прогона
«подавить, переписать, проверить» не делалось; в теме это подано как подсказка к
задаче, а не как утверждение о поведении.

**Н-06. `trufflehog filesystem` по каталогу репозитория читает `.git/objects`.**
На стенде это дало 5 находок против 3 у прогона по истории — три из них по путям
вида `.git/objects/08/29d80a…`. Выглядит как «сканирование истории задаром», но
опираться на это нельзя: распакованными объекты остаются до сборки мусора,
после неё они лежат в упакованном файле и текстовым поиском не находятся. В теме
названо ровно так и с оговоркой.

**Н-07. Долг отчётов этапа 1 открыт и подрос ещё раз.** Покрытие теперь 115 тем
из 188, а `STAGE1-TOC.md` по-прежнему считает «из 196», `STAGE1-ERRORS.md`
по-прежнему обещает этапу 2 «девять подразделов» (категорий пять). Не правил по
той же причине, что две предыдущие миссии: `STAGE1-TOC.md` — замороженное
оглавление, `STAGE1-ERRORS.md` — завершённый отчёт чужой миссии. Долг
наследуется от подразделов SAST (Н-08) и SCA (Н-07) и не закрыт третий раз
подряд. Правка — один абзац в каждом файле; нужно решение оператора о том, кому
её отдать.

## 8. Границы этой миссии

Что **не** делалось:

* Не написано ни одной темы других подразделов этапа 2 (2.4 DAST, 2.5 триаж).
* Не тронуты 111 тем этапов 0 и 1 и подразделов 2.1–2.2: в изменениях только
  четыре новых файла `content/stage-2/**`. Проверено `git status`.
* Не тронуты замороженные оглавления этапов 1 и 2 и учебный план оператора.
  Слаги, уровни, режимы, порядок и предпосылки всех четырёх тем сверены с
  оглавлением дословно; заголовки взяты из него без единого изменения.
* Не правился свод, обвязка и словари: категория `SECRETS` и теги подошли
  готовыми, источники были заведены заранее.
* Не заведено ни одного нового исключения в `exceptions.yaml`; предупреждений
  ноль.
* Не читались и не использовались настоящие секреты оператора — ни как материал,
  ни как пример, ни под маской. Все значения в темах и на стендах выдуманы.
* Ничего не опубликовано наружу: ни `git push` в чужой репозиторий, ни деплоя.
  Единственный `push` в миссии — в локальный `exp/server.git`, каталог внутри
  рабочего дерева. Денег не потрачено, платных лицензий и облачных аккаунтов не
  заводилось, `sudo` не использовался.
* Платформенная защита от отправки на хостинге не включалась и не проверялась:
  она требует тарифного плана. Её поведение описано по документации и помечено.

Файлы миссии лежат в `.smgr/appsec-stage2-secrets/` (каталог в `.gitignore`):
`exp/` — шесть стендов и скрипт их сборки; `out/` — сохранённые прогоны, отчёты
в JSON и выгруженные страницы документации; `tools/` — двоичные файлы обоих
сканеров; `venv/` — окружение с pre-commit.
