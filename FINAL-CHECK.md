# Финальная проверка реестра: попытка написать темы по источникам

Миссия `appsec-final`. Метод взят из досье: реестр проверяется **употреблением**,
а не третьим чтением. По каждой взятой теме открываются **только** привязанные к
ней источники (свои и наследованные от подраздела/этапа), и по ним пишется
черновик четырёх блоков канонического скелета части 4 `PLAYBOOK.md`:

| блок | что должно получиться |
|---|---|
| **механика** | модель, граница доверия, источник и sink |
| **как выглядит в коде** | что ищет глазами ревьюер |
| **как чинится** | канонический паттерн и его границы |
| **как проверить фикс** | ретест и регрессия |

**Правило, отделяющее проверку от самообмана.** В черновик попадает только то,
что есть на открытой странице. Знание, которое есть у модели, но которого нет в
источнике, помечается как `[ПАМЯТЬ МОДЕЛИ]` и считается **дырой**, а не
покрытием: оператор будет писать текст сам и памятью модели не располагает.

Все страницы выборки скачаны заново 2026-08-21 и читались из свежих копий, а не
по полю `notes` реестра и не по `audit.yaml`.

Отчёт устроен так: выборка → черновики по четырём категориям → системные находки →
сводка с процентами → список дыр с указанием, чем закрыть → что исправлено по ходу.
Читать можно с раздела «Сводка», если нужен только результат.

## Часть I. Категория 1 — темы с блоком `partial` в аудите

### Этап 0

#### t-0-0-04 · Сессии: серверные сессии vs stateless-токены
Источники: `owasp-cs-session-management`, `rfc6265bis-cookies`, `rfc7519-jwt`.
Вердикт аудита: `closed`, `how_verified: partial`.

**Механика.** Сессия — последовательность пар «запрос-ответ», связанных с одним
пользователем; HTTP сам по себе состояния не хранит, поэтому состояние вводится
идентификатором сессии, который выдаётся при её создании и предъявляется в
каждом последующем запросе (session-management CS, Introduction). Идентификатор
после аутентификации **эквивалентен самому сильному использованному методу
аутентификации** — паролю, OTP, смарт-карте (там же). Граница доверия: значение
ID приходит от клиента и потому «должно считаться недоверенным, как любой другой
пользовательский ввод» (там же, Manage Session ID as Any Other User Input).
Развилка «серверная сессия против stateless»: в серверной модели вся бизнес-суть
(IP, роль, права, таймауты) лежит на сервере, а ID «обязан быть бессмысленным»,
иначе злоумышленник его декодирует (Session ID Content). В stateless-модели
ровно наоборот — утверждения едут внутри токена: JWT это «строка из трёх частей
через точку, каждая закодирована base64url», и полезная нагрузка — набор claims
(RFC 7519 §3, §4).

**Как выглядит в коде.** Ревьюер смотрит: чем сгенерирован ID — CSPRNG или
`rand()` (требование: CSPRNG, минимум 64 бита энтропии, при hex — не меньше 16
символов, и «если часть ID фиксирована, эффективная энтропия падает»); лежит ли
в значении что-то читаемое (username, роль, ID пользователя — запрещено); каким
механизмом ID ездит (cookie против URL-параметра: «включение ID в URL раскрывает
его в ссылках, логах, истории браузера, закладках, заголовке Referer и поисковых
системах»); кладёт ли фронтенд токен в `localStorage`/`sessionStorage` — прямой
запрет с пометкой WARNING: «одна XSS раскрывает все токены», рекомендуется
`HttpOnly; Secure; SameSite=Strict` или паттерн BFF (HTML5 Web Storage API).
Атрибуты cookie ревьюер сверяет по нормативной части rfc6265bis.

**Как чинится.** Канон из cheat sheet: ID из CSPRNG ≥64 бит энтропии,
бессмысленное значение, обмен только через cookie (`Secure`, `HttpOnly`,
`SameSite=Strict` или `Lax`, «никогда `SameSite=None` без `Secure` и не
полагаться на дефолт браузера»), обновление ID при любой смене уровня привилегий,
idle- и absolute-таймауты **с проверкой на сервере** («если таймаут проверяет
клиент, атакующий подменит счётчик»), явная серверная инвалидация при логауте
(`HttpSession.invalidate()`, `Session.Abandon()`, `session_destroy()`), плюс
клиентская затирка `Set-Cookie: id=; Expires=<прошлое>`. Границы паттерна
названы прямо: `SameSite` — «defense in depth против CSRF, а не замена
CSRF-токена»; idle-таймаут «не ограничивает уже угнанную сессию, потому что
атакующий может её поддерживать активностью».

**Как проверить фикс.** *Готовой процедуры ретеста ни один из трёх источников не
даёт* — это подтверждение вердикта аудита. Но из требований процедура
собирается механически, и это делает автор, а не источник: собрать выборку ID и
проверить длину/энтропию против порога 64 бит; декодировать значение и убедиться,
что PII в нём нет; предъявить ID, выданный до логина, после повышения привилегий
(должен быть отвергнут — требование Renew the Session ID After Any Privilege
Level Change); предъявить ID после логаута и после истечения absolute-таймаута;
проверить, что события создания, обновления и уничтожения сессии попадают в лог
(Logging Sessions Life Cycle перечисляет, что именно логировать). Числовые
ориентиры для теста на месте: idle 2–5 мин для высокорисковых приложений и
15–30 мин для низкорисковых, absolute 4–8 часов для приложения «на рабочий день».

**Вердикт: материала хватило.** Три блока пишутся дословно по страницам,
четвёртый — конструируется из проверяемых требований, что для темы про модель
(этап 0) допустимо. Аудит с `partial` прав по букве, но тема писабельна.

> **Поправка к прежней записи аудита.** Аудит писал, что Session Management
> Cheat Sheet «без stateless-токенов». На странице от 2026-08-21 stateless-часть
> есть, хотя и коротко: раздел HTML5 Web Storage API прямо говорит про JWT и
> refresh-токены и запрещает их клиентское хранение, а раздел Cookies —
> про `SameSite`, префиксы имён и BFF. Это не отменяет того, что развёрнутую
> модель JWT даёт RFC 7519, а не cheat sheet.

#### t-0-0-05 · Same-Origin Policy — что именно ограничивает и что нет
Источники: `mdn-same-origin-policy`, `whatwg-html-origin`.
Вердикт аудита: `closed`, `in_code: partial`, `how_verified: partial`.

**Механика.** Origin — тройка «схема, хост, порт»; два URL одного происхождения,
только если совпадают все три (MDN, Definition of an origin). Ключевое, что
«ограничивает и что нет», на странице дано таблицей из трёх строк:
**cross-origin запись обычно разрешена** (ссылки, редиректы, отправка форм),
**cross-origin встраивание обычно разрешено**, **cross-origin чтение обычно
запрещено — но часто утекает через встраивание**: «можно прочитать размеры
встроенной картинки, действия встроенного скрипта или сам факт доступности
ресурса» (Cross-origin network access). Отдельно названы наследуемые
происхождения: скрипты со страниц с URL `about:blank` или `javascript:`
наследуют origin документа-родителя, а файлы по `file:///` современные браузеры
трактуют как opaque origin, из-за чего соседний файл в той же папке —
уже другое происхождение.

**Как выглядит в коде.** Вопреки вердикту `partial`, конкретика на уровне кода
на странице есть, и её достаточно для «что ищет глазами ревьюер»: вызов
`document.domain = "company.com"` — MDN помечает весь механизм как **deprecated**
и объясняет, почему («подрывает защиту SOP»), а заодно даёт две ловушки, по
которым ревьюер узнаёт неработающий код: любое присваивание `document.domain`,
включая `document.domain = document.domain`, обнуляет порт, поэтому значение надо
ставить с обеих сторон; в sandboxed `<iframe>` присваивание кидает
`SecurityError`, и на `localStorage`, `indexedDB`, `BroadcastChannel`,
`SharedWorker` оно всё равно не действует. Дальше — межстраничные ссылки
`iframe.contentWindow`, `window.parent`, `window.open`, `window.opener` и
`window.postMessage` как единственный законный канал; MDN приводит поимённые
таблицы того, какие свойства `Window` и `Location` доступны cross-origin
(`blur`, `close`, `focus`, `postMessage`, `closed`, `frames`, …).

**Как чинится.** Раздел How to block cross-origin access даёт три рецепта с
границами: против cross-origin **записи** — неугадываемый CSRF-токен, «и надо
дополнительно закрыть cross-origin чтение страниц, которые этот токен содержат»;
против **чтения** — сделать ресурс невстраиваемым, потому что «встраивание всегда
что-то о ресурсе раскрывает»; против **встраивания** — не дать ресурсу выглядеть
как встраиваемый формат, с явным предупреждением, что «браузеры могут не уважать
`Content-Type`: если направить `<script>` на HTML-документ, браузер попробует
разобрать HTML как JavaScript». Для законного открытия доступа — CORS; для
запрета фрейминга назван `X-Frame-Options`.

**Как проверить фикс.** *Процедуры проверки нет ни на одной из двух страниц* —
вердикт аудита подтверждается полностью. Спецификация WHATWG задаёт алгоритмы, а
не тесты; MDN — справочник API. Ретест («открыть консоль на чужом origin и
попробовать прочитать `iframe.contentWindow.document`») — [ПАМЯТЬ МОДЕЛИ],
на страницах его нет. **Это дыра.**

**Вердикт: материала хватило на три блока из четырёх.** Блок «как проверить
фикс» не пишется по привязанным источникам. Чем закрыть — см. раздел «Дыры».

> **Расхождение с аудитом.** `in_code: partial` с мотивировкой «примеров кода
> приложения на странице нет» занижен: `document.domain`, `window.opener`,
> `postMessage` и таблицы доступных cross-origin свойств — ровно тот материал,
> который нужен блоку 5. Ошибка в безопасную сторону, но она показывает, что
> оценки аудита ставились неравномерно.

#### t-0-0-09 · TLS: рукопожатие, цепочка сертификатов, перехват трафика прокси
Источники: `rfc9846-tls13`, `burp-docs-proxy`, `rfc5280-x509`.
Вердикт аудита: `closed`, `in_code: partial`.

**Механика.** RFC 9846 (июль 2026, Standards Track, обсоливает 5077, 5246, 6961,
7627, 8422 и 8446) даёт три задачи рукопожатия — обмен ключами, аутентификация
сервера (клиента — опционально) и выработка общего секрета (§2), порядок
сообщений и Authentication Messages (§4.5, `Certificate`, `CertificateVerify`,
`Finished`), post-handshake-аутентификацию клиента (§4.6.2). Цепочку закрывает
RFC 5280: §6 «Certification Path Validation» с полным алгоритмом — входы (6.1.1),
инициализация (6.1.2), обработка каждого сертификата (6.1.3), подготовка к i+1
(6.1.4), wrap-up (6.1.5), плюс §6.3 «CRL Validation». Перехват: Burp Proxy —
«веб-прокси-сервер между браузером и приложением», позволяющий «перехватывать,
осматривать и изменять трафик в обе стороны, в том числе HTTPS».

**Как выглядит в коде.** Подтверждаю вердикт `partial` и уточняю причину: у темы
нет «кода приложения» не потому, что источники слабы, а потому, что предмет —
протокол. Что реально даёт материал ревьюеру: имена расширений и сообщений из
RFC 9846, по которым читается дамп; из RFC 5280 — `basicConstraints`,
`nameConstraints` и прочие расширения (§4.2.1), то есть то, что ревьюер проверяет
в самом сертификате.

**Как чинится.** Канон — выполнять алгоритм §6 RFC 5280 целиком, а не «проверить,
что сертификат подписан»; поднять версию до TLS 1.3 по RFC 9846.

**Как проверить фикс.** Через Burp: пустить трафик приложения через прокси и
посмотреть, примет ли клиент подставленный сертификат. **Но именно этой
процедуры на привязанной странице нет.** Страница `burp-docs-proxy` — обзорная
на 1 минуту чтения; всё нужное вынесено на подстраницы, которые она только
перечисляет: *Intercepting messages*, *Managing certificates*, *Invisible
proxying*, *Burp Proxy settings*. Установка CA-сертификата Burp в браузер — то,
без чего HTTPS-перехват не работает, — на привязанной странице отсутствует.

**Вердикт: материала хватило на механику и «как чинится»; блоки 5 и 7 —
наполовину.** Дыра не в теме, а в глубине привязки: привязан хаб, а не
содержательная страница.

#### t-0-0-10 · Модель современного приложения: SPA + REST/GraphQL, SSR, reverse proxy, CDN
Источники: `webdev-rendering-on-the-web`, `mdn-proxy-tunneling`, `rfc7239-forwarded`, `rfc9111-http-caching`.
Вердикт аудита: `closed`, `in_code: partial`, `how_verified: partial`.

**Механика.** web.dev даёт словарь и развилку: CSR, SSR, static rendering,
prerendering, hydration и rehydration («выполнение клиентских скриптов, которые
добавляют состояние и интерактивность к серверно отрендеренному HTML; гидратация
предполагает, что DOM не меняется») плюс метрики FCP/TTI/TBT/INP, по которым
подходы сравниваются. Reverse proxy: RFC 7239 объясняет, зачем прокси вообще
появляются («балансировка нагрузки, снятие криптографии»), и что «прокси часто
существуют без ведома конечного пользователя». CDN и кэш: RFC 9111 разделяет
shared cache («хранит ответы для повторного использования более чем одним
пользователем, обычно часть посредника») и private cache, задаёт вычисление
ключа кэша и роль `Vary` (§4.1).

**Как выглядит в коде.** Подтверждаю `partial`: web.dev разбирает подходы
диаграммами и отсылками к фреймворкам, готовых фрагментов кода не даёт. Зато
на уровне заголовков конкретика полная: синтаксис `Forwarded` с параметрами
`for=`, `by=`, `host=`, `proto=` и примерами вида `Forwarded: for="_gazonk"`
(RFC 7239 §4–5), директивы `no-store`, `private` (RFC 9111 §5.2.1.5, 5.2.2.5,
5.2.2.7). Ревьюер ищет: чему приложение верит — `Forwarded`/`X-Forwarded-For`
или реальному адресу соединения; и не уезжает ли персональный ответ в общий кэш.

**Как чинится.** Строго по §8.1 RFC 7239: «заголовок `Forwarded` нельзя считать
корректным, поскольку его может изменить любой узел на пути к серверу, включая
сам клиент». Названный подход — «проверить прокси и внести их в белый список» —
приведён вместе с двумя его слабостями: «цепочка IP-адресов до прокси доверия не
заслуживает» и «если связь между прокси и конечной точкой не защищена, данные
может изменить атакующий с доступом к сети». Это готовая формулировка границ
паттерна. Для кэша — `private`/`no-store` на персональные ответы и корректный
`Vary`; §7.1 RFC 9111 «Cache Poisoning» описывает, чем это грозит.

**Как проверить фикс.** *Процедуры ретеста нет ни в одном из четырёх
источников.* Вердикт аудита подтверждён. «Послать запрос через прокси с
подставленным `X-Forwarded-For` и посмотреть, что попало в лог и в кэш» —
[ПАМЯТЬ МОДЕЛИ]. **Дыра.**

**Вердикт: три блока из четырёх.** Блок 7 не пишется.

#### t-1-1-01 · Модели контроля доступа: RBAC, ABAC, ACL
Источники: `nist-ir-7316`, `nist-sp-800-162-abac` + наследование `ps-access-control`, `owasp-cs-authorization`.
Вердикт аудита: `closed`, `how_verified: partial`.

**Механика.** Пишется целиком по `owasp-cs-authorization`, раздел Prefer
Attribute and Relationship Based Access Control over RBAC: RBAC — «доступ
разрешается или запрещается на основании ролей, назначенных пользователю;
права привязаны не к сущности, а к роли, и сущность наследует права своих
ролей; связь ролей и пользователей обычно многие-ко-многим, роли бывают
иерархическими». ABAC дан цитатой из NIST SP 800-162 стр. 7 — «запросы субъекта
на операции над объектами разрешаются или запрещаются на основании назначенных
атрибутов субъекта, атрибутов объекта, условий среды и набора политик,
выраженных в терминах этих атрибутов»; атрибуты — «пары имя-значение», примеры:
должность, время суток, имя проекта, MAC-адрес, дата создания. Третья модель —
ReBAC, «доступ по отношениям между ресурсами: редактировать пост может только
тот, кто его создал». Рекомендация с обоснованием: «ABAC и ReBAC обычно
предпочтительнее RBAC», выбор «имеет последствия для всего SDLC и должен быть
сделан как можно раньше». `ps-access-control` добавляет ортогональное деление:
вертикальный контроль — «ограничение чувствительной функциональности
определёнными типами пользователей», горизонтальный — «ограничение доступа к
ресурсам конкретными пользователями».

**Как выглядит в коде / как чинится.** Пишется по тому же cheat sheet: разделы
Enforce Least Privileges, Deny by Default, Validate the Permissions on Every
Request, Ensure Lookup IDs are Not Accessible Even When Guessed, Enforce
Authorization Checks on Static Resources, Verify that Authorization Checks are
Performed in the Right Location, Exit Safely when Authorization Checks Fail.
`ps-access-control` даёт пять принципов профилактики, включая «никогда не
полагайтесь на одну лишь неочевидность» и «по возможности используйте один
общеприкладной механизм проверки доступа».

**Как проверить фикс.** Раздел Create Unit and Integration Test Cases for
Authorization Logic даёт не процедуру, а **список вопросов, которые тест должен
задать**: «отказывается ли доступ по умолчанию? безопасно ли приложение
завершает работу при провале проверки, в том числе в нештатных условиях?
действительно ли применяются политики ABAC?» — плюс честную границу: «простые
юнит- и интеграционные тесты никогда не заменят ручное тестирование
квалифицированным взломщиком, они ловят низко висящие фрукты, но не сложные
векторы». Готовых кейсов нет; страница отсылает к WSTG 4.5 — «отличное
руководство по этой теме», — но привязан корень WSTG, где этой главы нет
(находка С-1). Вердикт аудита подтверждён.

**Вердикт: материала хватило на три с половиной блока.** Блок 7 пишется в виде
чек-листа вопросов, но не в виде процедуры.

> **Находка по источникам.** Оба NIST-источника темы — `nist-ir-7316` и
> `nist-sp-800-162-abac` — **не дали ничего**. По привязанным URL лежат не
> документы, а карточки публикаций на csrc.nist.gov: заголовок, авторы, дата,

> `nist-sp-800-162-abac`, — определение ABAC одной фразой, и оно **и так уже

> обе записи в этой теме — балласт. Подробнее — находка С-3 ниже.

#### t-1-1-11 · Принцип deny-by-default, проверка авторизации на сервере
Источники: только наследование — `ps-access-control`, `owasp-cs-authorization`.
Вердикт аудита: `closed`, `how_verified: partial`.

**Механика.** `owasp-cs-authorization`, раздел Deny by Default, даёт саму мысль
дословно: «даже когда ни одно правило явно не совпало, приложение не может
остаться нейтральным — оно обязано принять решение, явно или неявно, разрешить
или запретить», и потому «нельзя целиком полагаться на явно заданные правила,
рассчитывая, что они покроют все возможные запросы». Граница трактовки задана
там же и она нетривиальна: «хотя некоторые фреймворки сами придерживаются
deny-by-default, явную настройку следует предпочитать доверию к умолчаниям
фреймворка или библиотеки — логика и умолчания стороннего кода со временем
меняются, и разработчик может не понимать последствий такого изменения для
своего проекта».

**Как выглядит в коде.** Формулировка для ревьюера берётся дословно: «нужно уметь
явно обосновать, почему конкретное право выдано конкретному пользователю или
группе, а не считать доступ позицией по умолчанию». Дополняют разделы Validate
the Permissions on Every Request и Verify that Authorization Checks are Performed
in the Right Location. Серверную сторону подпирает `ps-access-control`: «по
возможности используйте единый общеприкладной механизм» и «на уровне кода
сделайте обязательным для разработчика объявлять разрешённый доступ к каждому
ресурсу и запрещать по умолчанию».

**Как чинится.** Ровно эти же формулировки — они и есть канонический паттерн.

**Как проверить фикс.** Тот же чек-лист вопросов из Create Unit and Integration
Test Cases. Процедуры нет. Вердикт аудита подтверждён.

**Вердикт: материала хватило.** Тема из тех, где «как чинится» и есть предмет,
поэтому отсутствие процедуры ретеста ощущается слабее, чем в темах про атаки.
Отсутствие собственных источников теме не мешает: наследованные
`owasp-cs-authorization` и `ps-access-control` — содержательные страницы, а не
навигационные.

#### t-1-2-05 · Защита от SSRF: allow-list, запрет редиректов, сетевая сегментация
Источники: только наследование — `ps-ssrf`, `owasp-cs-ssrf`. Аудит: `how_verified: partial`.

**Механика.** `ps-ssrf`: атака заставляет серверное приложение выполнить
HTTP-запрос по подконтрольному адресу; отдельно выделен blind-вариант, где
«ответ на серверный запрос не возвращается во фронтовый ответ». Граница доверия —
URL, приехавший от пользователя, sink — HTTP-клиент бэкенда.

**Как выглядит в коде.** `owasp-cs-ssrf` делит задачу на два случая, и это
главное, что ревьюер должен различать: **случай 1** — приложение обращается
только к известным доверенным адресам (тогда allow-list возможен), **случай 2** —
адрес любой внешний, как у вебхуков, «и allow-list здесь неприменим, потому что
список IP и доменов заранее неизвестен и меняется». В коде ревьюер ищет: приходит
ли в запрос строка/IP/домен/URL, есть ли валидация формата библиотекой, а не
регуляркой («регулярные выражения для сложных форматов трудно поддерживать и они
крайне ошибкоопасны»), и **включено ли следование редиректам** в HTTP-клиенте.

**Как чинится.** Три названных в теме защиты присутствуют дословно.
*Allow-list*: подход allow-list при валидации ввода плюс проверка, что IP
принадлежит одному из адресов доверенных приложений; для формата IP названы
конкретные библиотеки (`InetAddressValidator.isValid` из Apache Commons
Validator для Java) с оговоркой, что их «проверяли на устойчивость к обходам
Hex, Octal, Dword, URL и смешанным кодировкам». *Запрет редиректов*: «отключите
поддержку следования редиректам в веб-клиенте, чтобы предотвратить обход
валидации ввода» — сказано дважды, в случае 1 и в случае 2. *Сегментация*:
раздел Network layer — «цель сетевого уровня в том, чтобы уязвимое приложение не
могло звонить произвольным приложениям: доступны только разрешённые маршруты»,
через firewall и сегментацию сети. Для случая 2 дан полный поток валидации из
семи шагов, включая проверку, что домен публичный (резолвить его внутренним
резолвером и ждать отказа), защиту от DNS pinning через выборку всех A и AAAA
записей, allow-list протоколов HTTP/HTTPS, случайный токен из 20 символов и
приём только POST. Отдельно назван IMDSv2 как «дополнительный defense-in-depth
для AWS», с указанием отключить IMDSv1.

**Как проверить фикс.** Готовой процедуры нет — вердикт аудита подтверждён; но
**обоснование аудита («прогнать обходы из списка ps-ssrf против фикса») здесь
проверку выдерживает**: у `ps-ssrf` действительно есть корпус обходов, годный
как регрессионный набор — альтернативные представления `127.0.0.1`
(`2130706433`, `017700000001`, `127.1`), собственный домен, резолвящийся в
127.0.0.1, URL-кодирование и смена регистра, `@` перед хостом
(`https://expected-host:fakepassword@evil-host`), `#`
(`https://evil-host#expected-host`), поддомен `https://expected-host.evil-host`,
двойное кодирование и связка с open redirect с готовым примером запроса.

**Вердикт: материала хватило на все четыре блока.** Одна из немногих тем, где
блок 7 собирается из источников без обращения к памяти. Наследование сработало
как задумано.

#### t-1-3-05 · Параметризованные запросы, безопасное использование ORM
Источники: `owasp-cs-sqli-prevention` + наследование `owasp-cs-injection`. Аудит: `how_verified: partial`.

**Механика и «как чинится»** пишутся полностью: четыре защиты по порядку —
подготовленные выражения, корректно написанные хранимые процедуры, allow-list
валидация и «КАТЕГОРИЧЕСКИ НЕ РЕКОМЕНДУЕТСЯ: экранирование всего пользовательского
ввода». Ключевая формулировка механики: «параметризованный запрос заставляет
разработчика сначала определить весь SQL-код и лишь потом передать параметры,
поэтому база всегда отличает код от данных, чем бы ни был пользовательский ввод».

**Как выглядит в коде.** Примеров достаточно: безопасный Java
(`connection.prepareStatement(query)` + `pstmt.setString(1, custname)`),
C#/.NET (`OleDbCommand` + `Parameters.Add`), и **пара unsafe/safe для HQL** —
`session.createQuery("from Inventory where productID='"+userSuppliedParameter+"'")`
против `productID=:productid` и `setParameter`. Есть готовый приём ревью
хранимых процедур: «аудиторы должны всегда искать `sp_execute`, `execute` или
`exec` внутри хранимых процедур SQL Server». Есть отдельный случай, который в
коде выглядит иначе, — имена таблиц и колонок и направление сортировки, куда
bind-переменную подставить нельзя: рецепт `switch` по разрешённым значениям с
`InputValidationException` в `default`, и приведение сортировки к boolean
(`sortOrder ? "ASC" : "DESC"`).

**Граница паттерна** названа явно и это ценно: «валидированные данные не
обязательно безопасно вставлять в SQL-запрос сборкой строк»; экранирование
«хрупко, и мы НЕ можем гарантировать, что оно предотвратит все инъекции во всех
ситуациях».

**Чего не хватило — ORM.** Тема названа «безопасное использование ORM», а
про ORM на странице ровно одно предложение — «постройте или перепишите на
параметризованных запросах, хранимых процедурах или каком-нибудь ORM, который
строит запросы за вас» — плюс пример HQL. Ни SQLAlchemy, ни Django ORM, ни
типовой промах «`filter(raw=...)`/`extra()`/`.raw()`» здесь нет. Всё, что я мог
бы сказать про ORM сверх HQL, — [ПАМЯТЬ МОДЕЛИ]. **Полдыры.** (Смягчающее
обстоятельство: `django-raw-sql` и `sqlalchemy-textual-sql` в реестре есть, но
привязаны к теме 7.1.03 другого этапа.)

**Как проверить фикс.** Процедуры нет. И здесь **обоснование аудита не
выдерживает проверки**: аудит написал «проверяется прогоном payload'ов из
`ps-sqli`», но `ps-sqli` к этой теме **не привязан** — он стоит у тем 1.3.01–04,
а подраздел 1.3 наследует только `owasp-cs-injection`. Блок 7 по фактически
привязанным источникам не пишется. **Дыра.**

**Вердикт: два блока целиком, «как выглядит в коде» — без ORM, блок 7 — нет.**

#### t-1-4-04 · Контексты вставки: HTML, атрибут, JavaScript, URL, CSS — и правильное экранирование
Источники: только наследование — `ps-xss`, `owasp-cs-xss-prevention`. Аудит: `how_verified: partial`.

**Механика, «как выглядит в коде» и «как чинится»** — лучший материал из всех
тем выборки. `owasp-cs-xss-prevention` разбирает ровно те пять контекстов,
которые названы в теме, каждый с шаблоном вставки, примером атаки и правилом
кодирования: HTML-контекст (`<div> $varUnsafe </div>`, атака
`<div> <script>alert\`1\`</script> </div>`, таблица сущностей `& < > " '`, безопасный
sink `.textContent`); атрибутный (`<div attr="$varUnsafe">`, атака
`<div attr=”*x” onblur=”alert(1)*”>`, требование обязательных кавычек, безопасные
sink'и `.setAttribute` и `[attribute]` «при условии, что имя атрибута
захардкожено и безобидно, вроде `id` или `class`», и прямое предупреждение, что
атрибуты вроде `onClick` небезопасны никогда); JavaScript-контекст («единственное
безопасное место — внутри quoted data value, все остальные небезопасны»,
кодирование `\xHH`, требование `Content-Type: application/json` для JSON);
CSS-контекст (переменная только в значение свойства, безопасный sink
`style.property = x`); URL-контекст (URL-кодирование).

**Границы паттерна** даны отдельным разделом Common Anti-patterns, и это редкая
находка — источник, который сам объясняет, где канон ломается: опора **только**
на CSP (две проблемы: неявное допущение, что все браузеры клиентов поддерживают
нужные конструкции CSP, и общекорпоративная политика, которая «неизбежно сломает
часть приложений, особенно легаси, и приведёт к waiver'ам, а те — трещины в
броне») и обработка в HTTP-перехватчике (`HandlerInterceptor`, `javax.servlet.Filter`):
«нарушает главный принцип защиты от XSS — кодировать как можно ближе к месту
рендеринга»; «откуда сервлет-фильтру знать, попадёт ли параметр в HTML-контекст
или в JavaScript? Не знать. А HTML- и JavaScript-кодирование невзаимозаменяемы».

**Как проверить фикс.** Здесь я **расхожусь с аудитом в другую сторону**:
аудит написал «процедуры проверки нет», но у `ps-xss` есть раздел How to find
and test for XSS vulnerabilities с настоящей ручной методикой: «подать простой
уникальный алфавитно-цифровой ввод в каждую точку входа, найти каждое место, где
он возвращается в ответах, и проверить каждое место по отдельности — так
определяется контекст, в котором возникает XSS, и подбирается подходящий

**Вердикт: материала хватило на все четыре блока**, блок 7 — на уровне методики,

#### t-1-6-08 · Password spraying, credential stuffing

шаге, обходится прямым обращением к последнему.

**Как чинится / как проверить.** `owasp-cs-authorization`: проверка прав на
каждом запросе; чек-лист вопросов для тестов.

**Вердикт: материала хватило.** Тема без собственного источника закрыта
наследованием полностью — это контрпример к опасению, ради которого категория
и выделялась.

Замечание к аудиту: `how_verified: ok` обоснован так — «лабы академии;
`ps-business-logic` из 1.9 даёт ту же процедуру». `ps-business-logic` к теме не
привязан (находка С-4); лабы на странице действительно упоминаются.

#### t-1-2-02 · Blind SSRF и способы его обнаружения (out-of-band)
**Что есть.** На `ps-ssrf` разделу Blind SSRF отведено **два предложения**:
«возникает, если можно заставить приложение выполнить серверный HTTP-запрос по
переданному URL, но ответ на этот запрос не возвращается во фронтовом ответе» и
«эксплуатируется труднее, но иногда приводит к полному удалённому выполнению
кода на сервере или на других компонентах бэкенда». Дальше — «Read more →
Finding and exploiting blind SSRF vulnerabilities», подстраница в реестр не
заведена.

**Чего нет — ровно то, что вынесено в название темы.** Способов обнаружения
out-of-band на привязанных страницах **нет**: ни внешнего коллаборатора, ни
DNS-запроса как канала подтверждения, ни ожидания HTTP-обращения на
подконтрольный хост. `owasp-cs-ssrf` — про защиту, не про обнаружение. Всё, что
я знаю про Burp Collaborator и OAST, — [ПАМЯТЬ МОДЕЛИ].

**Вердикт: материала не хватило.** Пишется два предложения механики, дальше
ничего. Аудит поставил `closed`, все блоки `ok`. **Расхождение, и одно из самых
наглядных в выборке.**

#### t-1-2-03 · Обход фильтров: альтернативные представления IP, редиректы, DNS rebind
**Что есть.** Раздел Circumventing common SSRF defenses на `ps-ssrf` — сильный
и покрывает две трети темы: обход чёрных списков (`2130706433`,
`017700000001`, `127.1`, свой домен, резолвящийся в 127.0.0.1,
URL-кодирование и смена регистра, редирект на цель со сменой протокола), обход
белых списков через расхождения разбора URL (`@`, `#`, поддомен, одинарное и
двойное кодирование) и отдельный подраздел про обход через open redirect с
готовым примером POST-запроса.

**Чего нет.** **DNS rebinding** — третий пункт в названии темы — на
`ps-ssrf` не разбирается. `owasp-cs-ssrf` упоминает соседний, но другой приём:
«чтобы предотвратить атаку DNS pinning, приложение должно получить все
IP-адреса за доменным именем (записи A и AAAA) и применить к ним ту же
проверку». Это защита от смены резолва, названная другим термином, и механики
rebinding она не объясняет.

**Вердикт: материала хватило на две трети темы.** По названию — недобор.

#### t-1-4-01 · Reflected XSS
**Что есть.** `ps-xss` даёт определение («приложение получает данные в
HTTP-запросе и включает их в непосредственный ответ небезопасным образом») и
**сквозной пример с кодом**: безобидный `.../status?message=All+is+well.` →
`<p>Status: All is well.</p>`, затем тот же параметр с `<script>` и результат в
разметке, и вывод — «скрипт выполнится в браузере пользователя в контексте его
сессии с приложением и сможет выполнить любое действие и получить любые данные,
доступные пользователю». Защиту закрывает `owasp-cs-xss-prevention` (контексты и
кодирование, см. t-1-4-04), проверку — раздел How to find and test.

**Вердикт: материала хватило на все четыре блока.**

#### t-1-4-05 · Обход фильтров и санитайзеров
**Что есть.** Немного и по краям: `ps-xss` упоминает `Bypassing CSP` и
`AngularJS CSP bypass` (в оглавлении, разделами страницы они не раскрыты) и
даёт Dangling markup injection — «техника, позволяющая захватить данные
кросс-доменно там, где полноценный XSS невозможен из-за входных фильтров или
других защит». `owasp-cs-xss-prevention` подходит с другой стороны — Safe Sinks
с поимённым списком (`textContent`, `insertAdjacentText`, `className`,
`setAttribute`, `value`, `createTextNode`, и `elem.innerHTML =
DOMPurify.sanitize(dangerVar)`) и полным перечнем безопасных HTML-атрибутов.

**Чего нет.** Собственно **обходов фильтров и санитайзеров** — mutation XSS,
разночтения парсеров HTML, обход чёрных списков тегов и событий, обход DOMPurify
через mXSS — на привязанных страницах нет. `ps-xss` отсылает к «Cross-site
scripting cheat sheet» (подстраница академии, не заведена).

**Вердикт: материала не хватило.** Пишется «какие sink'и безопасны», но не
«как обходят». Аудит: все блоки `ok`. **Расхождение.**

#### t-1-5-04 · Double-submit cookie, синхронизирующий токен
**Материал отличный, лучший в категории.** `owasp-cs-csrf-prevention` разбирает
оба названных паттерна и, что важнее, ранжирует их: Synchronizer Token Pattern;
Signed Double-Submit Cookie помечен **RECOMMENDED** («самая безопасная
реализация double-submit: токен явно привязан к аутентифицированной сессии
пользователя; простое подписывание без привязки к сессии даёт минимальную защиту
и остаётся уязвимым к внедрению cookie»); Naive Double-Submit Cookie помечен
**DISCOURAGED** с предупреждением-рамкой: «обходится атакующим, способным писать
cookie на целевой домен — через уязвимый соседний поддомен, захват DNS или
внедрение cookie по открытому HTTP в cookie без префикса `__Host-`; для нового
кода используйте подписанный вариант, наивный документирован только для
справки». Есть объяснение, почему проверять cookie против cookie бессмысленно:
«браузеры автоматически отправляют cookie в кросс-сайтовых запросах, атакующий
может это вызвать; безопасность требует явной отправки клиентом — заголовком или
параметром, — доказывающей намерение пользователя». Есть HMAC-вариант с
псевдокодом и требованием сессионно-зависимого значения, и отдельная оговорка
против частой ротации: «обновлять CSRF-токен на каждый запрос — заблуждение,
которое якобы добавляет защиту, а на деле портит удобство».
`ps-csrf` добавляет обзор трёх типовых защит и их слабостей.

**Вердикт: материала хватило на все четыре блока.**

#### t-1-6-02 · Перечисление пользователей (по ответам, по времени)
**Материал есть, и обе половины названия закрыты.** `owasp-cs-authentication`,
раздел Authentication Responses: требование отвечать обобщённой ошибкой
независимо от того, «неверен ли ID пользователя или пароль, не существует ли
аккаунт, заблокирован ли он или отключён», и распространить то же на регистрацию;
цель названа — «не создавать фактор расхождения, позволяющий атакующему провести
перечисление пользователей». Временна́я сторона разобрана отдельно и с
псевдокодом: «сама бизнес-логика может дать расхождение по времени обработки…
задержка в несколько секунд позволяет атакующему провести атаку по времени», и
дальше реализация «быстрого выхода» — `IF USER_EXISTS(username) THEN
password_hash=HASH(password) …` — с разбором, почему при несуществующем
пользователе ответ приходит быстрее.

**Как проверить фикс.** Процедуры нет; но требование «одинаковый ответ и
одинаковое время» проверяемо напрямую.

**Вердикт: материала хватило на все четыре блока.** `ps-authentication`, донор
подраздела, при этом не дал ничего (он хаб — см. выше); тему вытянул один
cheat sheet.

## Ещё две системные находки

### С-3. Семь записей NIST и одна FIPS — карточки публикаций, а не документы

Все ссылки вида `https://csrc.nist.gov/pubs/.../final` и
`https://www.nist.gov/publications/...` ведут не на документ, а на **карточку
публикации**: название, авторы, дата, один абзац аннотации, ключевые слова,
Control Families, история версий и кнопка Download. Сам документ — PDF на
`nvlpubs.nist.gov`.

Затронуты восемь записей реестра: `nist-ir-7316`, `nist-sp-800-162-abac`,
`nist-sp-800-131a-r2`, `nist-sp-800-38a`, `nist-sp-800-61r3`, `nist-sp-800-63b`,
`fips-198-1-hmac`, `nist-sp-500-268`.

В выборку попали шесть из них, и в трёх темах это оказалось решающим:
`t-1-11-02` (единственный источник темы), `t-5-0-12` (единственный источник),
`t-1-11-03` (половина темы). В остальных случаях тему вытянул второй источник —
и характерно, что определение ABAC, за которым в реестр положили NIST SP 800-162,
и так процитировано в Authorization Cheat Sheet со ссылкой на страницу 7.

Аудит эту болезнь **видел один раз**: в примечании к `t-1-11-03` написано «на
странице CSRC только аннотация… содержание проверено в самом PDF», и в
`t-5-0-12` — «при написании открывать PDF». Но в реестр это знание не попало, и
человек, идущий по `sources.yaml`, попадёт на аннотацию.

**Закрыто по ходу проверки:** во все восемь записей дописан прямой адрес PDF с
пометкой, что по основному `url` лежит только карточка. Все восемь PDF скачаны и
прочитаны 2026-08-21 (`pdftotext -layout`), от 137 КБ до 331 КБ текста каждый.

### С-4. Аудит обосновывал вердикты источниками, не привязанными к теме

Проверено скриптом по всем 188 темам: текст `audit.yaml` сопоставлен со списком
источников каждой темы (собственных плюс наследованных). Совпадений — 16.
Большинство приходится на поле `notes` и является **осознанным решением**
(«смежная механика разобрана в теме такой-то, дублировать источник не стал») —
это прямое следование правилу проекта о запрете дублей, и ошибкой не считается.

Но в **оценках блоков** нашлось четыре настоящих случая, где вердикт опирается на
источник, которого у темы нет:

| тема | блок | чем обоснован | привязан ли |
|---|---|---|---|
| `t-1-11-02` Слабые и устаревшие алгоритмы | `how_verified: ok` | «инструменты из `owasp-cs-tls`» | нет, стоит у 1.11.01 |
| `t-1-3-05` Параметризованные запросы, ORM | `how_verified: partial` | «прогон payload'ов из `ps-sqli`» | нет, стоит у 1.3.01–04 |
| `t-1-1-08` Многошаговые процессы | `how_verified: ok` | «`ps-business-logic` из 1.9» | нет, стоит у 1.9.01 |
| `t-4-1-04` Namespaces и cgroups | `how_fixed: ok` | «(`docker-engine-security`)» | нет, источник подраздела 4.2 |

Пятый случай скрипт поймать не мог, потому что источник назван не своим id:
в `t-2-2-07` блок `how_fixed: ok` обоснован фразой «CVSS даёт тяжесть», а обе
записи CVSS (`first-cvss-v31`, `first-cvss-v40`) привязаны к теме 2.5.01.

Отдельно: `t-1-6-06` обоснован «по WSTG 4.6», `t-1-1-01` — «процедура берётся из
WSTG». Главы WSTG к темам не привязаны, привязан корень (С-1).

## Сводка: сколько тем написалось

Планка одна и та же для всех: тема считается **написанной**, если все четыре
блока скелета пишутся по привязанным источникам без обращения к памяти модели.

| исход | тем | доля выборки |
|---|---|---|
| **материала хватило на все четыре блока** | 28 | 42 % |
| **хватило частично** — один-два блока не пишутся или пишутся вполовину | 24 | 36 % |
| **не хватило** — тема по привязанным источникам не пишется | 14 | 21 % |
| не удалось проверить (источник недоступен из этой среды) | 1 | 1 % |

**Тем с дырой — 38 из 67, то есть 57 % выборки.**

По категориям (выборка смещена намеренно, поэтому числа не переносятся на
гайдбук целиком):

| категория | тем | хватило | частично | не хватило | тем с дырой |
|---|---|---|---|---|---|
| 1. блок `partial` в аудите | 43 | 12 | 20 | 10 (+1 непроверенная) | **70 %** |
| 2. только наследование | 8 | 4 | 2 | 2 | 50 % |
| 3. один собственный источник | 8 | 6 | 0 | 2 | 25 % |
| 4. контрольная группа (`ok` всем блокам) | 8 | 6 | 2 | 0 | 25 % |

**Что это значит.**

1. **Смещённая выборка сработала как задумано:** там, где аудит сам признал
   слабость, дыра нашлась у семи тем из десяти. Отчёт «всё хорошо», которого
   опасалось досье, не получился.
2. **Наследование само по себе не порок.** Категория 2 отработала не хуже
   средней по выборке: темы без собственных источников проваливаются не потому,
   что источник наследованный, а потому, что у страницы-донора нужный раздел
   оказался заглушкой «Read more» (t-1-1-03, t-1-2-02, t-1-4-05). Там, где донор
   содержательный, тема пишется целиком (t-1-1-08, t-1-4-01, t-1-5-04, t-1-6-02).
3. **Единственный источник — тоже не порок сам по себе:** категория 3 дала
   лучший результат из всех, шесть полностью написанных тем из восьми.
   Проваливаются в ней те две, где единственный источник оказался не документом
   (`nist-sp-800-131a-r2`) и не текстом (`java-tutorial-language`).
4. **Планка проседает и в контрольной группе.** Две темы из восьми, которым
   аудит поставил `ok` всем четырём блокам, написались лишь частично: `t-2-2-07`
   (из пяти предметов названия закрыты два) и `t-8-0-03` (первый риск закрыт,
   обзор десятки — нет). Это не катастрофа, но это значит, что вердикт `closed`
   в `audit.yaml` — не гарантия.
5. **Главный дефект — один и тот же, и он не про источники, а про глубину
   привязки.** Из 38 тем с дырой в 23 причина ровно эта: привязан хаб,
   оглавление, витрина проекта или карточка публикации, а содержание — на
   странице уровнем ниже, адрес которой обычно виден прямо на привязанной
   странице.

**Расхождения с аудитом — 23 темы из 67 (34 %).** Из них **20 в сторону
завышения** (вердикт `ok` или `partial` там, где по привязанным адресам меньше
материала, чем записано): `t-1-6-06`, `t-1-6-08`, `t-1-9-03`, `t-1-9-05`,
`t-1-11-03`, `t-2-1-05`, `t-2-2-03`, `t-2-2-05`, `t-2-2-08`, `t-2-5-06`,
`t-5-0-05`, `t-5-0-12`, `t-7-1-04`, `t-1-1-03`, `t-1-2-02`, `t-1-4-05`,
`t-1-11-02`, `t-7-4-01`, `t-2-2-07`, `t-8-0-03`. И **3 в сторону занижения**
(аудит был строже, чем позволяют страницы): `t-0-0-05` `in_code`, `t-1-4-04`
`how_verified`, `t-4-1-04` `in_code`.

Три случая завышения — прямые и стоят отдельно: `t-2-2-08`, `t-5-0-05` и
`t-1-11-02` имеют вердикт `ok` там, где на привязанной странице **предмета темы
нет вообще**.

1. **Сначала — глубина привязки, а не новые источники.** Пункт А списка дыр

   `owasp-asvs-5`, `owasp-wstg-42` и `owasp-top10-2025` полезны; как покрытие —

   содержательной (поле в схеме или отдельный список id).
3. **Пункт В списка дыр** — шесть решений, которые за оператора не принимаются:

   разошлось в одном случае из четырёх.
