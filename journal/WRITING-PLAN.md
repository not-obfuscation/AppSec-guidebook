# План написания гайдбука

Составлен диспетчером 2026-08-22 по поручению оператора: «как только закончится
аудит и будут пофикшены все правки, составь план написания гайдбука детальный».

Этот файл — **операционный план производства**, а не пересмотр правил. Правила
лежат в `PLAYBOOK.md` и не обсуждаются: канонический скелет темы (часть 4),
уровни глубины (3.1), критерий назначения уровня (3.2), Definition of done
(11.2), чеклист приёмки страницы (часть 13). План говорит только **в каком
порядке, какими порциями и с какой проверкой** это писать.

## Порядок: три увязки, каждая со своей целью

Порядок не «по важности тем», а по тому, что каждая порция даёт **как измерение**.
Пока нет собственных чисел, любой план производства — план по чужой статистике
(`PLAYBOOK.md`, часть 3.4).

### Увязка 1. Этап 0, первые три темы — калибровка на реальном материале

**Темы:** `t-0-0-01` HTTP (методы, коды, заголовки), `t-0-0-02` структура URL и
кодирование, `t-0-0-03` cookies и их атрибуты.

**Почему эти.** Они первые в порядке чтения, они фундамент для всех девяти
этапов, и у них короткие проверяемые наборы источников (RFC 9110, WHATWG URL,
UTS-39, RFC 6265bis, MDN) — то есть материал заведомо есть, и если тема не
пишется, виноват процесс, а не реестр.

**Что даёт как измерение:**

1. **Фактическое время на тему** по уровням — вместо нормативов чужих людей.
2. **Проверку скелета на настоящем материале:** разваливается ли часть 4, когда
   тема не про уязвимость, а про механику протокола.
3. **Повторный замер достаточности после `appsec-gapfix`** — те же критерии, что
   в `FINAL-CHECK.md`, но на починенном реестре.
4. **Список правок к `PLAYBOOK.md`** — часть 14 держит семь сознательно не
   принятых решений, и три из них закрываются только письмом: сколько языков в
   блоке «как выглядит в коде», стоимость собственного стенда, Mermaid или D2.

**Перед письмом обязательно:** зафиксировать уровни глубины **всех одиннадцати**
тем этапа 0 (`PLAYBOOK.md` 3.3 — оглавление этапа фиксируется до первого
раздела). Это часть увязки 1, а не отдельная работа.

### Увязка 2. Пилот L1 — самый дорогой случай

`PLAYBOOK.md` часть 12 называет пилотом **одну тему уровня L1 из области личного
опыта**, написанную по всем правилам целиком: полный скелет, лаба, правило
Semgrep, блок ловушек, самопроверка, замер времени.

**Почему это идёт второй увязкой, а не первой.** Расхождение с `PLAYBOOK.md`
осознанное, и вот его цена. Плюс порядка: оператор просил начать с того, что идёт
первым, а L1-темы из личного опыта лежат в этапах 1-5, не в начале. Минус: три
темы этапа 0 — не L1, поэтому **стоимость самого тяжёлого случая после увязки 1
останется неизмеренной**, и оценку производства по ней строить нельзя. Отсюда
правило: увязка 2 обязательна до любого планирования сроков, и тему для неё
выбирает оператор — критерий «область личного опыта» может применить только он.

### Увязка 3. Этап 0 целиком, остаток восьми тем

Только после того, как первые две увязки дали числа и правки к своду. Дальше —
ритм по `PLAYBOOK.md` 11.3, с пересчётом остатка часов по фактическому темпу
после каждого этапа (12, фаза 3).

## Порция и приёмка: как устроена одна миссия письма

**Порция — от одной до трёх тем.** Не этап целиком. Причина проверена на этом же
проекте за последние сутки: миссия, которой дали «этап 0 из 11 тем», закрыла его
и объявила себя выполненной по совпадению фразы в прозе; миссии с узкой порцией и
проверяемым выходом закрывались честно.

**Выход одной миссии письма:**

1. Готовые файлы тем по `PLAYBOOK.md` 9.3 (frontmatter со `sources`).
2. Заполненный Definition of done (11.2) по каждой теме — **пунктами, а не
   утверждением «выполнено»**. Пункты `[авто]` (Vale, markdownlint, линк-чекер)
   пока инфраструктуры нет — помечать как непроверенные, а не как выполненные.
3. **Замер: дата, часы, уровень** — в таблицу замеров (11.2 пункт 23).
4. Вердикт по достаточности источников каждой темы, по критериям
   `FINAL-CHECK.md`: хватило / частично / не хватило, и чего именно.
5. Список правок к `PLAYBOOK.md`, если письмо их потребовало.

**Чего в выходе быть не должно:** утверждения без источника, который открыт
лично; числа, версии, флаги, CVE из генерации без ручной проверки (11.2 пункты
10 и 13); советов по безопасности, которые нечем обосновать (14).

## Правило, без которого весь план бессмысленен

**Тема, по которой не набрана компетенция, не пишется, а остаётся заглушкой**
(`PLAYBOOK.md` 3.3). Она не превращается в ссылку наружу и не пишется по чужому
пересказу — свод называет это главным источником репутационного риска.

Для агента это правило читается так: **«знаю из общих знаний, но на открытой
странице этого нет» — это дыра, а не материал.** То же правило было стержнем
`FINAL-CHECK.md`, и именно оно нашло 21 % тем, которые не пишутся. Читатель у
гайдбука один — оператор, — и памяти модели у него нет.
