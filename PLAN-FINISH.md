Финальная стадия = все 188 активных тем написаны, выверены и переведены
в `published` (критерии — SCHEMA.md § 3.3), сайт опубликован, гейты
зелёные. Этап 6 исключён навсегда (SCOPE.md).

## Принципы

1. Порядок железный: этап 4 → 5 → 7 → 8 (по порядку маршрута читателя).
2. Каждый этап проходит один и тот же конвейер: оглавление → письмо
   волнами → приёмка → закрытие с маркером. Никаких новых форм — все
   они уже выстроены на этапах 0–3.
3. Каждый коммит зелёный (`make check`); волна = 4–8 тем одного
   подраздела; схема введения — действующая (пример-артефакт, фраза
   ориентации, без сцен и меток, PLAYBOOK § 4.3 с поправкой 2026-08-31).
4. Письмо и верификация не смешиваются: верификация (перевод в
   `published`) — отдельная волна после закрытия этапа.
5. Токи долгов не копим: всё, что волна задевает, чинится в ней же
   (как skipped_lines в волне введений).

## Фаза 0. Разблокировка (1 миссия)

1. Пакет решений оператора по 20 открытым долгам (список готов в
   `journal/AUDIT-2026.md` и верхнем разделе HANDOFF.md). Критичные для
   производства: **Н-11 и У-2** (критерий назначения уровня L1/L2/L3 —
   без них оглавления этапов 4+ будут условными в третий раз) и
   **19 условно замороженных уровней** этапов 1–3 (разморозить или
   утвердить).
2. Написать отчёт `journal/INTROS-INTROS_S1_02.md` — единственный
   незакрытый хвост остановленной миссии (все замеры в HANDOFF.md).
3. `check_toc.py` перенести из `.smgr/` в `tools/` (долг З-04/З-05) —
   оглавления этапов 4+ будут проверяться им.

Критерий приёма: по каждому из 20 долгов записано решение (даже
«не делаем»), маркер в отчёте. **Без фазы 0 фаза 1 не стартует.**

## Фаза 1. Оглавления этапов 4, 5, 7, 8 (4 миссии)

Для каждого этапа, в порядке 4 → 5 → 7 → 8:

1. Оглавление по образцу `journal/STAGE1-TOC.md`: темы с уровнями
   (по утверждённым Н-11/У-2), режимы, скелеты, предпосылки, оценка
   трудоёмкости, находки с блокерами.
2. Проверка: `check_toc.py` (после его переноса), сверка покрытия
   плана, `make check`.
3. Заморозка решением оператора. Отчёт с маркером
   `ЭТАП N ОГЛАВЛЕНИЕ ЗАМОРОЖЕНО`.

Зависимости: фаза 0 (правила уровней). Этап 7 — особый: языки
для code review могут потребовать третий скелет или расширение
существующего (как этап 2 потребовал «инструмент») — заложить день
на решение.

## Фаза 2. Письмо (4 × N волн)

Для каждого этапа, в порядке фазы 1, по подразделам:

1. Волна письма: 4–8 тем подраздела по шаблонам (`templates/L*.md`,
   `tool-L*.md`), с введением действующей схемы, лабами там, где тема
   их требует (критерий приёмки лабы неизменен: hack/tests на обоих
   файлах; новые лабы — в `labs.yaml` и `make labs`).
2. Приёмка волны: `make check`, `make lint-selftest`, `make site`,
   `make labs`; фактология новых тем сверяется с первоисточниками
   из `sources` темы по ходу письма (урок аудита: «проверено лично»
   пишется только после фактического прогона).
3. Закрытие этапа: отчёт с маркером `ЭТАП N ЗАКРЫТ`, обновление
   HANDOFF.md.

Ориентир по объёму работ: этапы 1–3 писались по 4–12 тем на миссию;
54 темы — это ~7–10 миссий письма. Этап 8 (опциональный) идёт последним
и может быть отложен решением оператора без блокировки финала.

## Фаза 3. Верификация и перевод в published

Критерии перехода — SCHEMA.md § 3.3: фактология выборочно сверена,
лабы пройдены после последней правки, `reviewed` не старше
`review_interval`.

1. Волнами по подразделам (все 188 тем, включая уже написанные):
   фактологический срез — каждая тема проходит сверку ключевых чисел
   и ссылок на стандарты с первоисточниками (методика аудита: ~6 тем/час
   на выборке; полный проход систематизирован по `docs/numbers.md` —
   матрица нормативных чисел обновляется по ходу).
2. `make labs` зелёный по всем лабам этапа.
3. Тема переводится `draft → published` со свежей датой `reviewed`.
4. Метрика: отчёт `published/total` по этапам, цель — 188/188.

## Фаза 4. Финал

1. Полный прогон: `make check`, `make lint-selftest`, `make site`,

2. Обновление документов: STATUS/INFRA приведены к финальному виду,

3. Решение оператора: phone-версия охватывает сейчас только этап 0 —
   расширять или нет.
4. Ретроспектива: что из процесса сработало/нет (кандидаты уже видны:
   «правило проверяет маркер, а не функцию», самоотчёт ≠ приёмка,
   гейт рефакторинга tools = check+site+phone).
5. Финальный маркер: `ГАЙДБУК ЗАВЕРШЁН`.

## Чего план не делает

- Не меняет скоуп (этап 6 не воскресает), уровни глубины не срезает
  ради скорости (SCOPE.md § 5).
- Не трогает ритм корпуса глобально (открытый долг — отдельной
  кампанией, если оператор решит).
- Не обещает дат: детерминирован порядок и критерии приёмки, а не
  календарь.
